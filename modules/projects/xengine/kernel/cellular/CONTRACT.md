# Integer cellular rules, v0.1

- Input and output have exactly `width * height * channels` values and are disjoint. Invalid shape, boundary, alias or tile returns a typed `Failure` before any output write. A valid partial tile leaves all other output values untouched. Storage and publication belong to the caller.
- Rules match in author order. Every condition reads the old field, including same-cell channels. All writes of the first match also read old values, not prior writes. No duplicate channel writes. Empty condition lists match unconditionally; empty writes stop later rules. With no rules, output equals input.
- Inclusive unsigned ranges and integer counts; exact saturating arithmetic. Boundaries are constant (one value for every outside channel), clamp or wrap. Offsets are distinct, but on tiny clamped/wrapped fields several offsets may address the same cell; each offset contributes once. Tile borders are not world borders.
- Default limits: 16 channels, 128 rules, 65,536 descriptor words, 64 Mi values per field. Configurable maximum values/words must not exceed `UINT32_MAX / 4`. Offsets are within ±32, at most 128 per condition. Dimensions plus halo fit signed 32-bit coordinates. These are logical bounds, not a guarantee a device can allocate that much.
- `prepare` is cold and owns a snapshot of rules. Copies own their descriptors; moved-from plans are unprepared. No allocations during `step/step_tile` after caller storage is prepared. Parallel callers require immutable rules/input and disjoint output rectangles; aggregate statistics outside the kernel.
- `words()` exposes a read-only, versioned execution descriptor for optional backends. There is no public unchecked bytecode constructor. Do not persist it as an application authoring format; retain typed/versioned rule definitions instead.

Encoding v1 uses uint32 words: header `[1, channels, rule_count, halo]`, rule-offset table, then variable rule records. A rule starts `[end_offset, condition_count, write_count, writes_offset]`. A condition is `[kind, channel, low, high, min_count, max_count, offset_count]` then offset pairs encoded as `dx+32, dy+32`. A write is `[channel, kind, value]`. Kinds follow the public enums. CPU and GPU execute this one prepared representation; no backend-specific rule authoring/compiler is duplicated.

Encoding v2 (a program whose rules aggregate or whose writes have terms; `Program::encoding()`): the same header with `2` first, the same rule and condition records — condition kinds `2, 3, 4` are a neighbourhood's sum, least and greatest of the values within `[low, high]`, tested against `[min_count, max_count]` — and a write is `[channel, kind, value, term_count]` followed by its terms, each `[source, channel, low, high, multiply, shift, negative, offset_count]` then offset pairs. Sources: `0` the cell's own value, `1` a count, `2` a sum, `3` the least, `4` the greatest. The amount is `plus = value + Σ positive terms`, `minus = Σ negative terms`, a term being `saturating(source × multiply) >> shift`; `set` gives `plus − minus` not below 0, `add_saturating` `old + plus` then `− minus`, `subtract_saturating` `old − plus` then `+ minus`, each step saturating in 32 bits. A sum saturates; of no value the least is `0xffffffff` and the greatest `0`. In v2 the rule-offset table has one entry more, the offset of the stages after the rules: `[transfer_count]`, then each transfer as `[channel, by, by_limit, multiply, shift, offset_count]` and its offset pairs (`by` = `0xffffffff`: none, the conductance is 1). For a cell and each neighbour the flow is `saturating(saturating(|difference| × min(by here, by there, by_limit)) × multiply) >> shift`, gained where the neighbour has more and lost where it has less; the channel's output is the rules' value, less what is lost, plus what is gained (saturating; neither bites while no rule writes the channel, by the bound preparation holds). A cell counts as changed when any channel's output differs from its input. A program that needs none of it is prepared as v1, unchanged.

Numerical level is exact integer equality on verified backends. Ordered updates, stochastic rules, general reaction graphs, conservation/movement, float integration and scientific chemistry are not supported by these operator sets (v2 adds aggregates and linear writes; conserving transfer and movement are the stages after it). Unsupported behavior needs a new declared operator/solver and CTS, not an application-name branch in this kernel.
