# openmui：国际化、自绘窗口与引擎分层

日期：2026-10-28
状态：设计（决策 D-74、D-75、D-76；待决问题 Q-19）

本文回答三个问题：国际化（i18n）怎样做到顶级的 en / zh 支持，而且引擎能独立发布；窗口应该由谁来画；整个框架怎样分层，才能在以后演化出游戏引擎，而 openmui 是其中的 UI 框架。

---

## 1. 国际化

### 1.1 现状

已经有的是文字这一层：

- HarfBuzz 塑形、fribidi 双向文本、自己实现的 UAX #14 断行和 UAX #29 分段（D-47，不依赖 ICU）；
- 字体回退链和随框架发布的默认字体（D-48），中英文、阿拉伯文、emoji 混排的段落在各平台像素一致；
- 输入法的组合文本（preedit）；
- 规范 S-9：ID 不依赖显示文本，换语言以后 agent 脚本和测试照常可用；
- 视图文档里预留了 `{ "tr": "key" }`，构建插件拆分里预留了 `openmui.build.i18n`（D-73）。

缺的是 i18n 本身：消息目录、复数和选择、语言协商和回退、数字 / 日期 / 相对时间 / 列表的格式化、排序、运行时切换语言、伪本地化，以及中文排版的细节。

### 1.2 引擎和数据分开（D-74）

| 层 | 包 | 内容 | 依赖 |
|---|---|---|---|
| 引擎 | `modules/i18n`（`openmui.i18n`） | BCP 47 语言标签、语言协商和回退链、MessageFormat 2（复数、序数、选择、带类型的参数）、由数据驱动的复数规则、数字 / 日期 / 相对时间 / 列表格式化、消息目录、伪本地化 | 只有标准库；**不内置任何语言数据** |
| 语言数据 | `i18n/cldr`（`openmui.i18n.cldr`，按语言分包） | 由 CLDR 生成的数据：复数规则、数字符号和分组、日期模式、星期和月份名、相对时间、列表模式 | 只依赖数据格式 |
| 应用目录 | `<应用>.<语言>.messages.omui.toml` | 应用自己的文案 | 只依赖数据格式 |
| 框架接入 | runtime + `openmui.build.i18n` | `tr()` 跟随语言 signal；构建期提取键、检查缺失和多余、嵌入目录 | 引擎 |

引擎和数据之间只有数据格式（`*.locale.omui.json` 和 `*.messages.omui.toml`，格式写进规范的扩展 `OMUI_EXT_i18n`）。引擎属于 `modules/` 下的独立组件（D-55），不依赖 openmui 的任何其他包，可以单独作为库发布；数据包可以随应用只带需要的语言。

**为什么不用 ICU**：mcpp-index 里没有 ICU 或 CLDR 的包（D-56 先查生态）；更重要的是，ICU 的版本随系统变化，格式化结果会跟着变，这和“同样的输入在每个平台得到同样的字节”（R-2、D-47）冲突，而且 ICU 体积很大。从 CLDR 生成我们自己的数据，结果只取决于数据的版本，数据版本写在包里。

### 1.3 引擎的接口（渐进式披露）

| 层 | 写法 | 用途 |
|---|---|---|
| L0 | `tr("inbox.count", {{"n", 3}})` | 应用代码；语言跟随运行时 |
| L1 | `Formatter{locale}.number(1234.5)`、`.date(t, DateStyle::medium)`、`.relative(-2, Unit::day)`、`.list(names)` | 文案以外的格式化 |
| L2 | `Catalog`、`Bundle`、`negotiate(requested, available)` | 自己管理目录和回退 |
| L3 | `MessageFormat::parse` + 自定义函数、数据包的加载器 | 新的格式化函数、自己的数据来源 |

格式化在热路径上不分配：消息解析一次、按 ID 缓存；格式化写进调用方给的缓冲区。

### 1.4 en / zh 的顶级支持

- **中文排版**：避头尾（句号、逗号、右括号不出现在行首，左括号不在行尾）；中西文之间自动留白（CSS `text-autospace` 的规则）；标点挤压（连续标点、行首行尾的全角标点收半）；简体和繁体分开（`zh-Hans`、`zh-Hant`，并互相回退）。
- **中文格式**：万 / 亿的紧凑数字，`2026年10月28日`、`下午3:05` 的日期时间，农历留作扩展；拼音排序。
- **输入法**：候选窗口跟着光标（`SDL_SetTextInputArea`），组合中的文字画在原位并带下划线。
- **英文**：复数和序数（1st、2nd），连字符断词（Liang 模式，结果确定）。
- **切换语言**：语言是一个 signal；切换只重算受影响的文字，不重新挂载，ID 不变，只重新布局变了的部分。
- **语义树**：每个节点带 `lang`，给无障碍和 agent 用。
- **验证**：en 和 zh 的像素哈希在所有平台固定；CTS 场景在三种语言下得到同一轨迹；伪本地化语言（拉长 40%、加重音符号）用来检查放不下的文字；基准测试保证格式化一条消息每帧不分配。

## 2. 窗口：默认原生，自绘作为完整的深度能力（D-75，2026-10-28 修订）

### 2.1 现状

窗口内容已经全部由框架绘制（CPU 或 GPU），各平台一致；标题栏、边框和窗口按钮是系统的。

### 2.2 决定

**默认使用系统窗口**（原生标题栏和边框），和各平台的习惯一致。**自绘窗口作为一项完整的深度能力**提供，分两层：

| 层 | 包 | 内容 |
|---|---|---|
| 窗口系统（能力） | `openmui.window`（宿主无关的接口，SDL 宿主实现，原生单元补齐 SDL 缺的部分） | 去掉系统外框；命中测试区域（拖动、各边和角的缩放、标题栏按钮，交给系统处理贴靠和全屏）；窗口形状和圆角（透明窗口加输入区域）；阴影；状态（激活、最大化、全屏、最小化、贴靠）和状态变化的事件；输入穿透；与系统的衔接（Windows 的贴靠布局、macOS 的红绿灯位置、Wayland 的 xdg-decoration 协商）；多窗口 |
| 默认窗口组件 | `openmui.ui.window` | 基于上面能力的一套框架默认窗口：标题栏、按钮、布局、交互（双击最大化、拖动、边缘缩放、标题栏右键菜单）、状态外观、打开 / 关闭 / 最小化 / 最大化的动画、主题和风格包；也是语义树里的节点（`window` 角色，`close`、`minimize`、`maximize` 动作） |

**切换要简单**：开发者在 `AppSpec` 里写 `.window = WindowStyle::native()` 或 `WindowStyle::framework({…})`（标题栏高度、按钮位置、圆角、阴影、动画），命令行 `--window native|framework` 可以覆盖；开发者如果提供设置项，用户可以在运行时切换，界面不重启，语义树不变。

**渐进式披露**：L0 什么都不写，就是系统窗口；L1 换成框架窗口，用默认外观；L2 配置标题栏、按钮、形状、动画；L3 直接用 `openmui.window` 的能力自己画整个外框（游戏、媒体播放器、异形窗口）。

### 2.3 窗口也是可动画的对象：关闭时溶解

1. **点击关闭的那一刻，应用在逻辑上就已经关闭**：窗口节点进入 `removing`（S-4，不再接受任何动作），状态保存，焦点交还给下面的窗口。溶解只是呈现。
2. **整个窗口立即变成输入透明**，而不只是溶解掉的像素：用户已经决定关闭，窗口里的任何东西都不该再接收输入；这比逐像素穿透更简单，也更可靠。
3. **动画在渲染线程上按时间求值**（约 200ms），不占用事件循环；“减少动效”时立即关闭；没有合成器时（部分 X11）退化为整窗淡出。
4. 打开、最小化、最大化同样可以定义动画；动画是时间的纯函数，和其他动画一样可以在 headless 下确定地重现。
5. 输入透明由 SDL 宿主的原生单元按平台实现（Q-19 已定，见 issue #2）。

## 3. 引擎分层（D-76）

openmui 的很多子系统本身就是一个引擎需要的东西。`modules/` 下的独立组件已经不依赖 openmui 的其他包（D-55），这里把方向写成分层：

| 层 | 包 | 说明 |
|---|---|---|
| 基础 | memory、geom、anim、unicode、text、**i18n**、raster、render、rhi、task、trace、record | 不知道 UI 的存在 |
| 引擎服务 | 场景（画布的 world::Scene 是起点）、输入、资源、脚本、确定性物理（S4 需要）、音频（缺） | 依赖基础层 |
| 框架 | openmui（UI 框架）；以后的游戏框架 | 依赖下面两层 |

openmui 作为游戏引擎的 UI 模块时：

- **嵌入**：引擎掌握主循环，每帧调用 `omuiFrame`；时钟、渲染设备、输入来源都由引擎注入；
- **共享设备**：和引擎共用一个 rhi 设备，UI 渲染到纹理（`OMUI_EXT_render_to_texture`），引擎决定怎样合成；
- **输入路由**：UI 先处理，没有消耗的事件交给游戏；
- **语义树照常存在**：agent 可以玩游戏、测试可以检查游戏 UI（S4 已经这样做）。

为了防止分层被侵蚀：lint 增加分层规则，依赖只能指向下层，基础层不允许出现 UI 的概念；主循环、时钟、渲染设备、输入都必须可以注入，任何代码都不能假设框架在最上层。

## 4. 实施顺序

1. `modules/i18n` 引擎：语言标签和协商、MessageFormat 2、复数规则、数字和日期格式化、目录、伪本地化；
2. CLDR 生成器（`omui-gen cldr`）和 en、zh-Hans、zh-Hant 数据包；
3. 框架接入：`tr()`、语言 signal、视图文档的 `{ "tr": … }`、`openmui.build.i18n`、三种语言的绑定；
4. 中文排版：避头尾、中西文留白、标点挤压（在 `openmui.text` 的断行和塑形里）；
5. `openmui.window`（自绘窗口的能力）和 `openmui.ui.window`（默认窗口组件），窗口动画；
6. 分层 lint 规则。
