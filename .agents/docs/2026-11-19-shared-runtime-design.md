# 共用运行时：应用是数据，运行时按版本并存（E3a，一页设计）

2026-11-19 起草，**已定**（2026-11-19 review）。任务 E3a（[实施方案](2026-11-18-omui-meng-implementation-plan.md)），挡着 E3b、E4；决策 D-250。背景见[体积与性能方案 §3.5、§5.3](2026-11-18-size-memory-performance-install-lead-design.md)（D-215、D-218、D-221）。

## 1. 要定的

一个 omui 应用怎样不带运行时地分发与启动：运行时是什么包、应用怎么声明它要的版本、启动器怎么找到它、两个应用要不同版本时怎么并存。目标：TS 应用自身 ≤ 100 KB；C++ 应用动态共用时 ≤ 500 KB。

## 2. 事实（2026-11-19）

- TS 应用已经是“数据加播放器”：例子 02 只有 `logic/main.ts` 与一份清单（`[package.metadata.openmui]`：`kind`、`id`、`title`、`size`、`scripts`），由 `omui.entry.player` 读清单并运行。现在缺的只是播放器要在本地编译。
- xlings 按版本并存已经在用：每个包的每个版本各在 `xpkgs/<包>/<版本>/`；本机同一个包装着几十个版本。
- **xlings 的包描述支持带范围的依赖**（已核对本机的索引）：`deps = { "xim:glibc@>=2.38", "xim:libX11@>=1.8" }`。体积方案里“待核对”的这一条成立。精确版本的写法与“范围取哪一个版本”的解析规则还要用一个例子验证（E3b 的第一步）。
- 发布通道的演练已通过：65 个包的 `mcpp publish --dry-run`（RC3.1）。

## 3. 按三级次序（D-185）

**① 原始性创新：应用是一个值，运行时是它的解释器；版本由契约决定，不由二进制决定。**

- TS 应用与运行时之间的边界是规范的脚本接口（`openmui` 的 stubs），它是规范的一部分、只增不改。所以应用声明的不是“某个运行时的构建”，而是**它需要的规范版本与能力**：`openmui = "0.4"`，加它用到的能力（Agent、运行时生成、某个组件包）。
- 运行时的每个版本自描述它实现的规范版本与带的能力（compose 的 `composition.json` 已经写出这次构建装了什么）。启动器做的是一次**匹配**：在已装的运行时里找满足应用声明的最新一个。这比“钉住运行时的版本号”多出两点：运行时可以升级而应用不动；缺的是能力而不是版本时，说得出缺哪一项。
- 应用包因此只有脚本、资源、清单与声明式数据的快照，是纯数据：可以校验、可以签名、可以由 Agent 生成后直接运行，不经过编译器。
- 同一个应用值有三种运行方式，走同一条路径：共用运行时（本文）、`omui package` 打成自带运行时的可分发物、Web 上由页面的引擎运行（D-237）。

**② 前沿加组合：C++ 应用的动态共用。** C++ 模块接口跨共享库只在编译器与运行时完全相同时成立，所以 C++ 应用钉确切的运行时版本，按版本并存正好提供这一点；稳定的边界仍是 C ABI（`openmui.h`）。这一档的收益是体积与共享的代码页，代价是每个运行时版本都要留着。**E4 做，标预览**。

**③ 业界做法（低线）**：.NET 的“依赖框架”与“自带运行时”两种发布；Tauri 与 WebView2 的系统运行时；Flutter 的预编译引擎。按版本并存、缺失时给出安装的出路，是这一级的要求。

## 4. 设计

**包。** xlings 索引里两个包：

| 包 | 内容 | 谁装 |
|---|---|---|
| `omui` | 命令行，自带开发宿主与播放器（E2） | 开发者 |
| `omui-runtime` | 只有播放器与它的共享库、默认字体；四个平台各一份；每个版本带 `composition.json` | 应用的依赖；`omui` 依赖同版本的它 |

**清单。** 应用在已有的 `[package.metadata.openmui]` 里加一节（规范层面的数据，用 `openmui` 的名字）：

```toml
[package.metadata.openmui.runtime]
openmui  = "0.4"                 # 规范的版本：同一主次版本内的任一运行时都可以
needs    = ["agent"]             # 用到的能力；缺省由闭包推导给出（B7b）
runtime  = "=0.1.3"              # 可选：钉确切的运行时（C++ 动态共用的应用必须写）
```

**启动器。** 一个很小的程序（目标 ≤ 200 KB，不链接运行时）：读清单 → 在 xlings 的数据目录里列出已装的 `omui-runtime` 与它们的 `composition.json` → 选出满足声明的最新一个 → 把应用的目录交给它的播放器。找不到时的输出是可执行的出路（D-186）：缺哪个规范版本或哪项能力、装它的那一条命令。数据目录的位置经 `mcpplibs.os` 取，三个桌面平台各自的约定。

**应用作为包。** 应用自己可以是 xlings 的包，`deps` 写 `omui-runtime@>=0.1`（或确切版本）；`xlings install <应用>` 把缺的运行时一起装上；不再被引用的旧版本由 xlings 清理，不另做一套。

**适用范围**（写进文档）：共用运行时要求机器上有 xlings，服务开发者、工具与同一台机器上的多个 omui 应用。面向普通用户的应用、应用商店、Web 用自带运行时。

## 5. 任务与验收

| 任务 | 内容 | 验收（本机） |
|---|---|---|
| E3b | `omui-runtime` 的包描述与本地索引；清单的 `runtime` 一节与它的检查（`omui doctor`）；启动器；匹配的规则与缺失时的出路 | 两个 TS 应用声明两个规范版本，装两个运行时版本后各自启动、同时运行；缺能力时的出路是一条能执行的命令；TS 应用包 ≤ 100 KB |
| E4 | C++ 应用动态链接运行时的共享库，钉确切版本 | 最小 C++ 应用 ≤ 500 KB，或按 §6 降级；两个钉不同版本的 C++ 应用并存运行 |

验证状态：全部用本地的 xlings 索引在本机 Linux x64 上真实验证；macOS 与 Windows 上数据目录的位置与启动靠节点的矩阵，之前标“待确认”。公开的索引不为走通而发（D-216）。

## 6. 风险与降级

| 风险 | 应对 |
|---|---|
| xlings 对范围依赖的解析与设想不同（取最新、取最低、不重装） | E3b 的第一步用一个假的包验证；不符合就在启动器里做匹配（本来就要做），包的依赖只保证“至少有一个可用的” |
| 能力的匹配让清单变复杂 | 缺省由推导给出，人不手写；不写 `needs` 时按 `app` 世界 |
| C++ 动态共用做不到 500 KB 或跨平台不稳 | 降级写法（五项）：目标、实测、试过的、原因、毕业条件；E4 标预览，TS 的共用运行时不受影响 |
| 本会话对 `~/.xlings` 只读 | 验证用独立的 xlings 家目录（本地索引），不动机器上已装的 |

## 7. 已定的（2026-11-19 review：下列各条同意）

1. 应用声明规范版本与能力、由启动器匹配，而不是钉运行时的版本号。
2. 运行时单独成包 `omui-runtime`，`omui` 依赖它；包名就用 `omui-runtime`。
3. C++ 动态共用（E4）标预览、钉确切版本。
