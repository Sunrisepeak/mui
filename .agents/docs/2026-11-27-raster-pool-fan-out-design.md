# 帧的光栅按活分给线程（红 160，一页设计）

状态：已实施（2026-11-27），待 review。决策：无新的，沿用 D-70（帧只在需要时出）、D-184（CPU 是参考）、D-185（三级次序）、D-187（帧的低线）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) §7 的 RM1、UI10；旁及：红 155（同一个列表在 GPU 上）、[UI10 的方案](2026-11-27-window-device-on-demand-design.md) §5 的列表一行。

## 1. 事实

- **量到的**（UI10 方案 §5，2026-11-27 04:28–04:31，负载 0.7–2.6）：本机桌面屏幕 2，列表（10,000 行，1896×1030）由它自己的 Agent 端点每帧滚一格（40 px），`--cpu` 的窗口每帧 CPU 8.0 ms：主线程 1.9 ms，光栅池的 16 条线程各 0.3–0.4 ms，它们每帧的光栅活加起来约 0.5 ms。
- **进程外重量**（这一轮，2026-11-27 06:37–06:40，1 分钟负载 3.2–7.7，另有别的会话在构建）：`omui-devtools bench apps --screen HDMI-0 --scroll-by agent --rounds 3`，程序自己把窗口开在屏幕 2，经它自己的 Agent 端点每 1/120 s 滚一格，指针没有动；线程的 CPU 与切换由进程外读（`process::threads`、`pidstat -w -t`）。`--cpu` 的列表：每秒 120.8 帧，每帧 CPU 8.8–9.5 ms（负载 4.3–4.9 的两轮；第三轮负载 7.7 时 16.5 ms），主线程 2.6–2.8 ms，池的线程合计 6.0–6.4 ms；每秒切换 5,600–5,700 次（每帧约 47 次：主线程 29、池的线程 18）；呈现间隔 p50 8.42、p95 11.30、p99 14.09、最大 17.79 ms；一格到它的帧 p50 3.13 ms。
- **一帧怎么分出去**（改之前）：窗口的 CPU 帧只画损伤跟踪给出的行（UI10 §3.2），滚动时是整窗 1030 行；`mrender::CpuRenderer` 把它们切成每段 64 行，17 段，交给 `omui.core` 的 `Tasks::parallel_for`。它对调用线程以外的每段调一次 taskflow 的 `silent_async`：16 次，每次 `new` 一个任务节点、一份装不进小缓冲的 `std::function`，外加一份 `make_shared` 和一个 `std::promise`；每次都 `notify_one` 叫醒一个工作线程。
- **醒来的线程做什么**（taskflow 4.1.0 的 `executor.hpp`）：工作线程做完手上的任务就去偷：先试 2 × (队列数 + 1) 次（16 个工作线程、5 个共享队列时 44 次），再 `std::this_thread::yield()` 最多 150 次，然后才进两阶段的睡眠。只要还有别的任务没完成（`_num_topologies` 不为 0），这一整轮都要走完；一帧 16 个任务，先做完的线程就在别人做完之前一直偷、一直让。0.3 ms 一条线程、16 条每帧，就是这一轮。
- **一帧的光栅有多少**：这一帧是清背景（1896 × 1030 像素）加 28 行的底色、标题、状态与按钮。整帧在一条线程上画 2.8 ms、CPU 2.9 ms（release，`tests/bench` 的 `core/list-scroll/raster-serial`，§4），估出的活是 4.39 百万单位，约 0.65 ns 一个单位。旧的分法把它切成 17 段交给工作线程：墙钟 0.70 ms，CPU 7.4 ms（`raster-workers-64`）——多出来的 4.5 ms 是醒来找活。UI10 方案里“光栅活加起来约 0.5 ms”是追踪里的估计，低估了。

## 2. 三级次序（D-185）

**① 从本体系出发。** 帧在分出去之前就已知道它要画什么：损伤跟踪给出要画的行，显示表给出每条命令在设备上的范围。所以一帧的活可以在叫醒任何线程之前估出来、按活切开：每一行的活是它的清屏（行宽）加上落在这一行的命令的面积，再加每条命令自己的一份；按前缀和在活刚好过一份的地方下刀，每段的活差不多大。活不到两份的帧就由调用线程自己画，一个线程也不叫醒；够几份就叫醒几个，最多到帧线程组的宽度。这些都是确定的：同一张表、同一组行，切法总是一样；每段都是精确的（`restrict_rows`），切成几段字节都和一条线程画的一样。再加一条：帧的活不该排在后台任务后面，也不该和后台任务共用一批会到处找活的线程，所以帧有自己的一小组线程（`Priority::frame`，接口里早有这个优先级，以前没有用上）。**结论：取这一级。**

**② 前沿与组合。** 查过的做法与取什么：

| 做法 | 现状 | 取什么 |
|---|---|---|
| Skia 的 `SkTaskGroup` 与 `SkExecutor`（`SkThreadPool`） | 一组固定的线程睡在一个信号量上，`add` 一个任务放一个信号；`batch(N)` 就是 N 个任务、最多 N 次唤醒；`wait()` 不阻塞，而是自己去做队列里的活（借用） | 取“醒来的线程做完就睡、调用者自己也做”；不取“一个任务一次唤醒”：唤醒次数应当由活定，而不是由任务数定 |
| Chromium 合成器的瓦片光栅 | 失效区域按瓦片拆成光栅任务，交给一组数量有上限的光栅线程 | 取“线程数有上限”；不取固定大小的瓦片：我们的段按活切，不按面积切 |
| Vello 的 CPU 渲染器（`vello_cpu`，稀疏条带） | 多线程是一个可选特性，`RenderSettings::num_threads` 由调用者给定；建议小的上下文（字形、蒙版、滤镜）用 0 条线程；有项目报告 4 条线程以上收益很小（[vectorcraft#327](https://github.com/storytold/vectorcraft/issues/327)） | 取“小的活不开线程”；线程数由我们按帧的活定，不由调用者猜 |
| tiny-skia | 单线程，没有分带 | 不取 |
| 工作窃取的线程池（taskflow、TBB、Rayon） | 按颗粒（grain）切活，空闲的线程先偷、再让、最后睡；taskflow 4.1 的数见第 1 节 | 取“颗粒要比唤醒贵得多”；不取“醒来先找活”：帧的线程只做这一帧，做完就睡 |
| Slint 的软件渲染器 | 只画脏区（最多 3 个矩形），可以逐行画进行缓冲（`render_by_line`），文档里没有多线程 | 取“只画变了的”（我们的损伤跟踪已经是）；我们比它多的是按活分线程 |

组合：**损伤跟踪的行 + 显示表的命令范围 → 先估活、按前缀和等活切段 + 帧自己的线程组（只叫醒要用的几个、做完就睡、不分配）。**

**③ 业界通行的做法**（固定大小的段或瓦片，交给通用的工作窃取线程池）就是改之前的样子，不取：第 1 节的 16 × 0.3 ms 就是它在这种帧上的代价。

## 3. 设计

### 3.1 估活与切段（`mrender.vector`，`CpuRenderer::share_out`）

- 单位是“写一个像素一次”。一行的活 = 清屏（帧清屏时为行宽）+ 落在这一行的每条命令在设备上的宽度；每条命令再加 `command_work`（256）一份，记在它的第一行。效果层在带外先画好（D-68），在带里只是一张图，按图的范围算。命令的范围用 `device_bounds`（与损伤跟踪同一个），差分数组加前缀和，O(命令数 + 行数)，在调用线程上做。
- 要画的行的总活 `work` 除以 `band_work`（默认 2^20，§4 由实测定）得段数；不到 2 段就一段，由调用者画，线程池不被调用。够了就在 8 行一步里、做完的活刚过第 k 份的地方下刀；一段可以含几段不相连的行，但从不越过这一帧不画的行。
- `CpuOptions::rows_per_task` 大于 0 时照旧按行数切（测试用它强迫切出很多段）。`RenderReport` 多了 `bands` 与 `work`，宿主与基准读得到。
- 每条命令在设备上的范围在估活时量一次，记下它的上下沿；各段剔除落不到自己行里的命令时直接比这两个数，不再各量一遍（一段字形的范围要逐个字形算）。剔除的判断与以前逐段量的完全相同（同一个函数、同一个变换）。
- 字节不变：每段都由 `restrict_rows` 精确画出，切法不影响结果（`damage_test` 的新例：按活切成 8 段以上与一条线程画的字节和对象号相同，整帧与增量都是）。

### 3.2 帧的线程组（`omui.core`，`Tasks` 的 `Priority::frame`）

- `parallel_for(…, Priority::frame)` 不进 taskflow，交给一组帧线程：宽度 `frame_width()` = min(线程数, `frame_width_limit` = 16)，调用者算一个。
- 一次分发叫醒 min(块数 − 1, 宽度 − 1) 个帮手，每次都是同样的前几个；帮手醒来后用一个原子计数领块，领不到就签退、在自己的字上等下一次，不去找别的活。调用者自己也领块，最后等所有被叫醒的帮手签退（它的函数体活到那时）。
- 分发本身不分配：任务描述是线程组自己的，函数体是调用者的；帮手的线程在第一次需要时才起，起了就留着。另一个线程的分发正在进行、或者在分发里面又分发时，由调用者自己做完。
- taskflow 的工作线程也改成第一次有后台活时才起：只有帧的活的程序（CPU 画的窗口）不起它们。
- 可观察：`Tasks::frame_stats()` 给出分发次数、自己做完的次数、叫醒次数、块数、起了几个帮手。

### 3.3 宿主

- 视图的 `raster_parallel()` 用 `Priority::frame`；桌面与无头宿主的 `FrameOptions` 默认按活切（`rows_per_task = 0`）。

## 5. 风险与欠项

| 项 | 现状与应对 |
|---|---|
| 估的活与真的时间不成正比 | 估活只用面积，不分命令的种类：字形、路径、阴影每个像素比清屏贵。它只决定切几段、在哪里切；切法不影响字节。偏差让段不等长，由领块的方式（先做完的帮手接着领）摊开，代价是这一帧晚一点结束，不是多烧 CPU |
| 混合架构的处理器（本机 8 个性能核、16 个能效核） | 帮手落在哪种核上由系统定；没有绑核 |
| 宽度上限 16 | 由本机的 `core/list-scroll/raster` 与 `ui/raster/*` 定（§4）；别的机器没有量过 |
| 帮手醒得慢 | 调用者要等被叫醒的帮手签退；被叫醒的帮手如果来得晚，调用者已经把块做完，等的只是它醒来的时间（不烧 CPU） |
| Web | 单线程，帧的分发都由调用者做完，`frame_stats` 照样计数 |
