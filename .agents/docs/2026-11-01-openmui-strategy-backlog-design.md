## 1. 之前的问题

截至 2026-11-01，评估对象有十个，平均每轮涨 1–5 分，没有一个接近 90：

| 对象 | 起点 | 当前 | 卡分项 |
|---|---|---|---|
| ui-framework | 45 | 63 | platforms_web（headless 里 WebGPU 呈现不了），性能 |
| site | 40 | 62 | 艺术表现 62，性能 64（中文字体 2.7 MB 在首帧之前） |
| style-gallery | 42 | 65 | retro、ink（改过，未复评） |
| markdown-wall / renderer | 36 / — | 65 | — |
| animation / game-engine | — | 62 | — |
| widget-breakout | 45 | 60 | 声音（评分者听不到，暂定分） |
| fighting | — | 57 | — |
| promo-video | 52 | 52 | 字号 52、镜头 55（改造中，未复评） |
| fighting-presentation | — | 25 | 需要美术生产（D-90） |

原因：

1. **铺得太宽**：同时推进十个对象，每轮每个修一两处；整体分取最低维度，修好一项又冒出下一项。
2. **评分不稳、对标过高、工具做不到的维度**：同一对象两次评分差约 5 分；部分对标（Apple 发布片、SF6）意味着工业级产量；声音、连续视频、headless WebGPU，评估工具本身做不到，只能卡在 60 多的暂定分。
3. **每次改动的额外开销高**：构建、看图、重新固定像素、README 媒体、干净 worktree 的 lint、全平台 CI、磁盘。
4. **重心偏到了展示品的外观**，偏离了最初的问题——"真实使用连点击都有问题"。真正有价值的是用出来的框架缺陷。

## 2. 新策略

### 2.1 核心是框架和引擎的能力，官网是它们的验收

- 先定主推的、远超同类的亮点（[定位与官网](2026-11-01-openmui-positioning-site-design.md) §1）；所有工作围绕把这些能力做到、做强。
- **官网是唯一的验收对象**：它是用 openmui 写的程序，跑过 Web 宿主、渲染、无障碍、agent 协议整条链路；它出问题就是框架出问题。
- 官网上的每个展示都是验收用例：交互扫描、像素固定、agent 操作、codex 真实使用都在它上面跑。
- **质量不达标的作品不上官网**，记在本文 §4，达标后再上。

### 2.2 范围完整，按检查点推进

- 讨论定下的内容**全部要做**，不存在"先做几个、其余以后"。
- 检查点只是验证点：每到一个检查点就做一次验证、提交、评估，范围不缩。
- 检查点的划分见各设计文档的"检查点"一节；总的顺序见 §3，按工作流展开的表见[总体方案](2026-11-01-openmui-master-plan-design.md) §6。

### 2.3 评估的改变

| 改变 | 内容 |
|---|---|
| 对象 | 官网（含其上的全部展示）为唯一评估对象；其他对象的评估暂停，结论保留在台账里 |
| 怎么用 | codex 用的就是访客的路径：拿到官网的"复制提示词"，从零连上页面、像访客的 agent 一样操作（[agent 接入](2026-11-01-openmui-agent-connect-rewind-design.md)）；另外照常用 `omui mcp` |
| 交互扫描（新，硬门槛） | 自动工具枚举语义树里每个可操作的节点，逐个真实操作，检查状态确实变化、没有报错、没有死节点、没有被遮挡；进 CI，不靠 codex |
| 评分细则 | 每个维度固定锚点（90 分长什么样）；关键评估跑两次，报告差异 |
| 评分者做不到的维度 | 有替代证据才计分：声音用响度和频谱分析加人试听；动画用导出的连续帧；WebGPU 用有 GPU 的 runner 或明确记为已知限制。补齐之前不作为最低分门槛 |
| 对标 | 官网的设计对标 Linear、Vercel、Raycast、Rive、Framer、Apple 的产品页，和 Flutter、Svelte 的框架官网；性能对标同类框架官网的首屏 |

### 2.4 迭代开销

- 本地只构建、只跑受影响的测试；像素固定和 README 媒体按检查点批量更新。
- 一个 commit 只涉及一个对象；仍在同一个 PR（`openmui-design`）。
