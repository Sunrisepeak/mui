# Live Design 的呈现三层与演出（AG1，一页设计）

状态：草案，待 review（2026-11-26）。决策：D-282、D-283（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 D-262、D-263、D-277、D-279；下游：AG2（工作呈现）、FE4（编排与自动导演）、AG3（页面内的演出）、AG4（导出与动画视频）、AG8（页面内的声音）。

## 1. 事实（2026-11-26）

- 设计历史是数据：`replay@1`（`mlibs.agent`），每步有脚本的文本、说明、作者、秒数、所在的节点。官网的回放是 9 步，每步固定 1.5 秒，共 13.5 秒。
- 实测（有界面的 Chromium，60 Hz）：画面在变的时间约 1.8 秒，**静止 86%**；最后四步每步只改 0.7%–3.2% 的像素，肉眼几乎看不出。没有掉帧（360 帧），所以“慢”不是性能问题，是时间分配与取景的问题。
- 现有的零件：`omui.generate` 的 `Replayer`（在运行的应用里逐步换脚本，变化按编辑的方式呈现）；`hanim.timeline`（轨道、片段、带键的属性、标记，编辑可逆，时间是精确的 flicks）；`meng.video` 的工具（把时间线渲染成影片，片段的来源可以是无头宿主上按时钟画的 omui 视图）；`omui design film` 调它；`eval animate`（Agent 做动画的评测）。
- 缺的：每步放多久、镜头看哪里、怎样过渡，现在没有人决定——都是固定值。

## 2. 三层（D-262 的展开）

| 层 | 是什么 | 归属 | 判据 |
|---|---|---|---|
| **状态** | 设计历史与当前的树。提交一次编辑，同一帧生效 | `mlibs.agent`（历史）、omui（树） | 不依赖下面两层；关掉呈现，结果逐位相同 |
| **工作呈现** | 真实工作时的反馈：改了哪里、谁改的 | omui（`omui.designer`、`omui.generate`） | 给提交增加的延迟为 0 帧 |
| **演出** | 历史之上另做的动画作品：可选、可重新生成、可导出 | 编排归 hanim，取景的事实归 omui，画面归 mrender | 同一份编排在页面内播放与导出成影片，逐帧一致 |

## 3. 三级次序（D-185）

**① 从本体系出发。** 历史是数据，应用是确定的，纯动画是时间的函数。所以演出不是录屏：它是**历史的函数**——由历史算出一份编排，按时间采样出每一帧。同一份编排有两种播放：页面内（每一帧都是真实的界面，人可以暂停、拖动，Agent 可以在任何一帧读树、截图）；导出（无头宿主按帧率采样，得到逐帧确定的影片）。镜头与时长由**量出来的变化**决定（语义的差异与像素的损伤区域），不由人手调。**结论：取这一级。**

**② 前沿与组合。** 查过的做法与取什么：

| 做法 | 取什么 |
|---|---|
| 自动取景的录屏工具（镜头跟随点击与光标自动推近） | 镜头由事件自动决定；我们用变化的区域而不是光标 |
| 把视频写成代码的工具（Remotion、Motion Canvas）、Manim | 时间是函数、逐帧确定；我们已有（hanim） |
| 设计工具的智能过渡（按图层名匹配两帧并插值）、幻灯片的神奇移动、代码差异动画 | 两个状态之间按身份匹配；我们的身份是语义 id（规范 S-8、S-9），不靠名字碰巧相同 |
| 版本历史的可视化 | 不取：它画的是仓库，不是作品本身 |

组合：**按语义 id 匹配的状态过渡 + 由损伤区域推出的镜头 + 确定的采样**。三样都已有底座，缺的是把它们接起来的那份编排。

**③ 业界通行的做法**（录屏后剪辑）不取：不可重新生成，改一步就要重录。

## 4. 设计

### 4.1 编排就是一条 hanim 时间线（D-282）

不新增数据格式。演出的编排是一份 `hanim.timeline`，约定四条轨道：

| 轨道 | 种类 | 片段 | 说明 |
|---|---|---|---|
| `states` | video | 来源 `design:<历史>#<步>`；长度是这一拍的时长 | 相邻两个片段之间是过渡；过渡用哪个配方写在片段的属性 `transition` 上（值是配方的登记名） |
| `camera` | animation | 属性 `x`、`y`、`zoom` 带键 | 取景：把变化的区域放到画面里够大的位置；缓动取导航类的曲线 |
| `captions` | events | 每拍一条说明 | 文字来自历史里那一步的说明 |
| `sound` | audio | 来源是一份 `*.music.xdef.ts`（可选） | 拍点用时间线的标记；页面内默认不取（D-277） |

编辑这份编排用时间线已有的可逆编辑；它可以提交进仓库，也可以每次由自动导演重新生成。

### 4.2 自动导演：事实归 omui，决定归 hanim

- **量（omui）**：把历史在无头宿主上逐步走一遍，每步给出：语义的差异（增、删、改了哪些节点）、像素的损伤矩形、这一步有没有可见的变化。这是 `omui.generate` 的一个函数，输出与领域无关的“拍的事实”：`{步, 变化的矩形与权重, 变化的种类, 画面大小}`。
- **定（hanim）**：`hanim.timeline` 的一个纯函数，由拍的事实得到时间线。同样的输入得到逐位相同的时间线（进契约 CTS）。规则是数据（一份带默认值的参数表），先取这些：

| 决定 | 规则（默认值是假设，由并排实测替换） |
|---|---|
| 一拍多长 | 与变化的量单调相关，夹在上下限之间；**没有可见变化的拍不超过 0.3 秒**，或并进下一拍 |
| 镜头 | 变化的区域小于画面的一定比例时推近，使它占到短边的三分之一以上；连续几拍在同一处就不来回拉 |
| 过渡 | 新增的节点用出现类的配方，文字变了用文字的形变，位置变了用移动；配方都取自已登记的词汇，不新造 |
| 说明 | 每拍至少停留能读完说明的时间（按字数） |

### 4.3 播放与导出是同一条路

- **页面内**：`Replayer` 改为按时间线播放（现在是每步固定秒数）。时间线上任一时刻给出：处在哪一步、过渡的进度、镜头的变换。镜头是根上的一个变换，属于导航类的运动（行内写 `MOTION-OK:`）。播放器的控制（播放、暂停、到某一步、变速）不变，Agent 的 `generate.replay` 不变。
- **导出**：`video render` 渲染同一份时间线（它已经能把视图在无头宿主的时钟上画成帧）。带与不带声音各一份。
- 两条路用同一个求值函数，所以“页面里第 t 秒的画面”与“影片第 t 秒的帧”相同——这是验收。

### 4.4 工作呈现（D-283）

- 提交先生效，呈现后到：编辑在提交的那一帧就改了树与像素；微反馈（改动处的短暂高亮、作者的标识移到那个节点）是叠在上面的动画，由这次提交的差异驱动。
- 不排队：新的提交到来时，上一条反馈直接让位（每个节点至多一条）。连续快改时退化成只移动标识。
- 系统设置了减少动态效果时只留标识。发布构建里这一层整个不在（设计器模式是编译期去掉的，D-149）。
- 量法：`eval hot-reload` 的“编辑到像素”在开与关工作呈现两种情况下各量一遍，差为 0 帧才算过。

### 4.5 实施（FE4，2026-11-27）

- **定（hanim）**：`hanim.timeline:direct`。拍的事实是 `Beat`：这一步显示什么（`design:<分支>#<序号>`）、说明、画面上变化的区域（矩形与权重）、节点按发生了什么计数（增、删、文字、位置、其余）。`direct(beats, 宽, 高, rules)` 给出一条时间线，轨道如 §4.1：`states` 每拍一个片段，**过渡的配方名写在片段的名字上**（片段的属性是带键的数，放不下文字；说明轨的文字同样在名字上）；`camera` 一个片段，`x`、`y`、`zoom` 带键，缓动取 `standard`；`captions` 每组说明一个片段；每拍起点一个标记（`beat <n>`），给配乐对拍。规则是 `Direction`，每项有默认值（§4.2 表里的假设），可由 `direction@1` 的文件给出，问题带位置与最近的正确写法。
- **规则的落实**：有可见变化的拍按变化占画面的比例在 `shortest`–`longest` 之间；没有可见变化的拍是 `still`（0.3 秒），它的说明并进下一个有变化的拍（在结尾时并进前一个），那一组的时长不够读完说明时只加长那个有变化的拍，不加长静止的拍；变化小于画面 `near` 时推近，使它的长边占短边的 `fill`（最多 `deepest` 倍），画面不出界；下一处在 `stay` 之内时镜头不动；移动从拍的起点开始，用 `move` 秒。
- **纯函数**：同样的拍与规则写出的时间线文本逐字节相同，其 FNV-1a 在 GCC 与 wasm32-emscripten 上相同（`direct_test` 钉值）；写出、读回、再写出也相同。
- **量（omui）**：两帧之间变化的区域归 `mrender.raster`（`changed_regions`：16 像素的块，同一行连续的块合成一段，下一行同跨度的段向下合并，每个区域带不同像素的个数）。设计器的 `design.show` 在看不见的副本（twin）里逐步运行影片脚本保留的步、等它静止，拿前后两帧与语义快照：区域换算成窗口的逻辑像素，节点的增删改来自 `semantic::changes_between`（改了 `name`、`value`、`description` 算文字，其余算样式），两边都有、没有别的变化、边界变了的算移动；第一步算整个画面出现。规则取影片脚本旁的 `<分支>.direction.xdef.json`，没有就用默认值；写出 `<分支>.show.timeline.xdef.json`。
- **试过而不取**：用提交时记下的语义变化代替副本里的量——它没有位置，也说不出“没有可见变化”。

## 5. 验收

| 任务 | 验收 |
|---|---|
| AG1 | 本文 review 通过 |
| AG2 | 开与关工作呈现，“编辑到像素”的帧数相同；数进台账 |
| FE4 | 自动导演是纯函数：同一份历史得到逐位相同的时间线（CTS）；规则的参数表是数据 |
| AG3 | 官网的 9 步：没有可见变化的拍不超过 0.3 秒；静止的比例由 86% 降到 30% 以下（假设值）；按时间采样（端点、多个中间态、打断、反向）的检查通过 |
| AG4 | 影片由同一份时间线生成、可重新生成；页面内第 t 秒与影片第 t 秒的帧相同；宣传片改用同一条路后钉值不变；`eval animate` 的任务通过 |

## 6. 不做的

- 不录屏，不存像素形式的中间产物：存的只有历史与时间线。
- 不新增时间线之外的编排格式；不新造过渡的配方（缺的回 hanim 的词汇里补）。
- 自动导演不做“理解内容”的判断（哪一步更重要）：只用量得出的变化。人可以改时间线。
