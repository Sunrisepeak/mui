# 工具链的四层与总入口（RL7，一页设计）

状态：草案，待 review（2026-11-26）。决策：D-287（提议）；名字仍是顶层方案 §11 的第 1 条（倾向命令 `meng`、包 `meng.cli`）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) §4.5、D-278；沿用 D-203–D-207。下游：RL8（T1 的模块库）、RL9（总入口对外）。

## 1. 事实（2026-11-26）

| 层 | 现在有什么 | 在哪里 |
|---|---|---|
| T0 工具内核 | 由操作目录导出命令行、MCP、协议三个入口；主体、会话、端点 | `mlibs.agent`（`:host`）、`mlibs.control`（目录）、`mlibs.control.gen`（`ops-gen`） |
| T1 通用模块库 | 项目模型与体检（`mlibs.project`，341 行）；声明式数据（`mlibs.xdef`）；TS 求值（`mlibs.ts`）。**其余还没有成库** | 见下 |
| T2 每个项目的入口 | `omui`（`omui.cli`，2,338 行）、`hanim`（`hanim.studio`）、`mrender`（`mrender.tool`）、`gongfu-studio`、时间线工具；同日新增 `oweb` | 各项目的 `tools/` 或工具包 |
| T3 总入口 | `xtools`：把各项目的主体放进一个会话；另有检查器与试听 | `modules/projects/xtools` |

- 没有成库、每个入口各写一遍或只有 omui 有的：运行一个外部工具并记录（`run_tool`，各处的写法相近）；从模板新建；`dev`、`run`、`build`、`test`、`package` 这一串步骤的编排；依赖与工具的清点；从候选的产物安装与验证（在仓库维护工具的 `release*.cpp` 里）；打包与交付清单；端点的发现与接入的提示。
- `oweb` 的入口（同日）为了答复请求又写了一遍“数据、失败、参数不成请求”的三个小函数——与 `mrender.tool` 里的逐字相近。这是第三份。
- `xtools` 静态依赖 `gongfu.studio`；gongfu 在 meng 之上。总入口若并进 meng 的工具，这条依赖方向就反了。

## 2. 三级次序（D-185）

**① 从本体系出发。** 工具的能力先是目录（数据），入口由目录导出；所以“每个项目一个命令”与“一个总命令”不是两套代码，而是**同一批主体的两种组合**：T2 把自己的主体放进一个会话，T3 把大家的主体放进一个会话。能复用的不是命令行解析（内核已经做了），而是主体里反复出现的那些做法。**结论：取这一级**——T1 提的是主体的积木，不是又一层命令框架。

**② 前沿与组合。** 对照过的形状：一个命令带子命令（`cargo`、`dotnet`、`flutter`、`go`）；外部子命令按名字发现（`cargo-xxx`、`git-xxx`、`kubectl` 的插件）；语言服务器与 MCP 让同一能力多一个入口。取：**按清单发现**（不按可执行文件的名字碰），因为我们的清单本来就有（贡献清单，D-203）；总入口对不在场的项目给出“怎么装上它”，而不是“未知命令”。

**③ 业界通行的做法**（一个大命令把各项目的命令硬编在一起）正是 `xtools` 现在的形状，不取作终态。

## 3. 设计（D-287）

### 3.1 四层各自的规矩

| 层 | 规矩 |
|---|---|
| T0 | 不认识任何项目。只增不改 |
| T1 | 与项目无关的库，放 mlibs；每个库至少有两个入口在用才成立（否则留在用它的入口里） |
| T2 | 薄程序：自己的操作目录、自己的主体、T1 的库。不依赖别的项目的入口 |
| T3 | 只做组合：不实现任何操作。在引擎层；它之上的类型框架（gongfu）经贡献清单进入，不被它依赖 |

### 3.2 T1 提什么（RL8 的清单）

| 库（暂名） | 提自 | 谁用 |
|---|---|---|
| `mlibs.project`（已有，扩）：模板与新建、依赖与工具的清点、配置的读取 | `omui.cli` 的 `project.cpp` | `omui`、`oweb`、总入口 |
| `mlibs.agent` 的答复小件：数据、失败、不成请求；运行外部工具并记一条 | `omui.cli`、`mrender.tool`、`oweb`（三份相近的） | 每个入口 |
| 生命周期的编排：`dev`、`run`、`build`、`test`、`package` 作为一串可记录的步骤 | `omui.cli` | `omui`、`oweb` |
| 打包与交付清单：文件、字节、压缩后的字节、对预算的结论 | 仓库维护工具的 `check size`、`check site delivery` | `omui build`、`oweb`（ST6） |
| 候选的产出与验证：本地索引、干净目录里的安装与第一个窗口 | 仓库维护工具的 `release*.cpp` | 各项目的候选（RL1、RL2、RL4） |
| 端点的发现与接入提示 | `omui.cli` 的 `agent.cpp`、`page.cpp` | `omui`、`oweb`、总入口 |

每一项提出来之后，原来的入口改用它，命令与输出不变（它们的用例照旧通过）——这是 RL8 的验收。

### 3.3 总入口的二级命令

- 形状：`<总入口> <项目> <操作> …`，二级的名字就是各项目自己的名字（`omui`、`oweb`、`hanim`、`mrender`、`video`、`gongfu`）；总入口自己的只有四个：`find`（按意图检索全部目录）、`subjects`、`mcp`（一个服务列出全部项目的操作）、`inspect`。
- 来源：每个项目的贡献清单说明它的主体在哪个包、叫什么。总入口在构建时把**同层及以下**的清单编进来；在它之上的（gongfu）在运行时按清单发现已安装的入口并转交——不在场时回答怎样装上。
- `<总入口> omui dev` 与 `omui dev` 逐条等价（同一个主体），这是 RL9 的验收；`xtools` 这个名字由 lint 拦住。

### 3.4 名字

`mtools` 不用（已有两个广泛使用的同名者）。在 `meng`（包 `meng.cli`）与 `mtool` 之间，倾向前者，理由与要处理的事见顶层方案 §11 第 1 条；本文的设计不依赖这个选择，RL8 先做，RL9 等名字定下。

## 4. 验收

| 任务 | 验收 |
|---|---|
| RL7 | 本文 review 通过；名字定下 |
| RL8 | 上表每个库有两个以上入口在用；`omui` 的用例不改就通过；`oweb` 与 `mrender` 的入口里没有重复的那三份小函数 |

## 5. 不做的

- 不做新的命令行框架；不做按可执行文件名字发现的插件。
- 不把各项目的操作搬进总入口：目录留在各项目里。
