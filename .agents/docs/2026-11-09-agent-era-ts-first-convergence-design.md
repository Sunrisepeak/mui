# Agent 时代收敛方案：TS/JS 顶级化、全平台自绘、运行时生成与对标特性表

2026-11-09。**设计方案，待维护者 review。** 承接[第二部分方案](2026-11-08-part2-industry-leading-design.md)（§7.3 是当前进度）、[PPet 方案](2026-11-05-pixelpet-generative-capabilities-design.md)和本日两份对比分析（MyGo、GPUI Kit、NSH、Rune、nanoui、Slint、Flutter、Expo、Compose MP、Lynx、Valdi、Next + shadcn、Tauri、Dioxus、SwiftUI）。§1 的决策 D-138–D-145 已在讨论中确认，本文把它们和特性表、优先级、实施步骤合在一起。

## 0. 核心点

1. **TS/JS 是 omui 唯一的上层语言，砍掉 Lua 和 Python。** TS 同时是代码、配置和数据：JSON 是 TS 对象字面量的子集，一个只导出字面量的 TS 模块就是数据，带函数就是代码。所有 TS 先求值，再以 JSON 快照作为规范形式，用于校验、预演、差异比较、版本和事务；TS 源保留下来，用于编辑。
2. **分层**：C++ 负责引擎、组件和性能敏感部分，并给脚本暴露 API；TS 是最薄的一层，只负责组合、状态、事件和胶水，不进入每帧路径，可以热重载；契约、操作目录和主题都用 TS 写（“TS 进、数据出”），构建期用内嵌的 QuickJS 求值，不需要 Node。
3. **运行时生成按 PPet 的范围**，包括 UI、动作和技能、资产、挂载的 UI，全部走同一条管线：TS 或 JSON 草稿 → 类型与契约校验 → 沙箱求值成数据 → 准备 → 真实像素预览 → 提交版本 → 可撤销、可编辑、可复用。下发的 TS 要签名，在 QuickJS 沙箱里运行，有内存、时间和节点数上限。
4. **界面内容在所有平台上自绘**；窗口和系统集成面（窗口边框、菜单栏、托盘、通知、文件对话框）可以选原生或自绘。原生控件会把能力锁在平台的交集里，也会破坏跨平台一致和逐字节确定，所以不采用。自绘需要补齐输入法、无障碍桥、平台行为和平台风格包。
5. **webview 只作为可选的“外部表面”组件**，不提供 Web 前端模式；HTML 子集作为内容输入按需支持。
6. **Agent 观察三种方式并存，不做 computer use**：语义优先，需要看时截任意区域，需要精确数据时读 SVG。用对照实验证明 token 和步数少一个数量级。
7. **自描述取代 skills 和 llms.txt**：运行中的应用和 `omui describe --api` 从契约自动导出 Agent 需要的一切；llms.txt 只是自动导出物；skill 只保留 SOP。
8. **AVX2 走运行时分派**：整数路径逐字节一致，浮点路径不开启收缩。
9. **特性表 §3** 列出 51 项（对手最强的点加上 Agent 时代的核心能力），每一项标明低线、超过、远超三个等级的目标。现在 ★ 15 项、✗ 17 项。
10. **优先级 §4**：P0 打开入口（TS 顶级化、热重载、自描述、观察三模态的证据），P1 运行时生成、性能证据、分发，P2 覆盖面，P3 生态。实施方案在 §5，共 11 条工作流，每条都有检查点和验收标准。

## 1. 已确认的决策

| 编号 | 决策 | 理由 |
|---|---|---|
| **D-138** | **TS/JS 是唯一的上层语言**，砍掉 Lua 和 Python 的应用绑定。TS 即代码也即数据，JSON 是规范形式和传输格式。仓库自己的 Python 工具（lint、lead.py、tasks.py、CI 脚本）不在范围内 | 模型最熟悉 TS；一种语言覆盖数据、配置、代码和运行时生成；维护面减少三分之二 |

## 2. TS 顶级化的设计（D-138、D-139）

### 2.1 现有基础（`omui.lang.js`）

- QuickJS-ng 经 mwrap 引入（`mcpplibs.mwrap.quickjs_ng`），模块 `openmui`。
- 组件构建函数、信号、表达式（**帧内不运行 JS**）、区域、动词、模型、原生模块（`openmui:native/*`）、主题。
- 热重载：`Script::reload` 在 200 ms 内完成，第 n 个 `signal()` 保留原来的值。
- `.d.ts` 从契约生成（`spec/stubs/core.d.ts`）。
- **缺口**：
  - TS 转 JS 依赖外部 esbuild，运行时生成和分发都受影响；
  - 没有沙箱限额，没有签名；
  - 配置还是 TOML；
  - 没有 `describe --api`；
  - CTS 和示例里有三种语言并存。

### 2.2 “TS 即代码也即数据”

| 模块形态 | 例子 | 求值结果 |
|---|---|---|
| 只导出字面量 | `export default { kind: "button", id: "save", text: "Save" }` | 数据（JSON 快照，与写 JSON 等价） |
| 带类型的声明 | `export default defineContract({...}) satisfies Contract` | 数据，加上完整的类型检查 |
| 带函数的组合 | `export const Counter = () => column(...)` | 构建出的视图树（数据）加上事件处理函数（代码） |
| 运行时生成 | AI 写出的 TS 或 JSON | 在沙箱里求值成数据快照，经过预演和提交 |

- **规范形式**：求值后的 JSON 快照。schema 校验、预演、差异、版本、事务、跨语言生成都只认它。JSON 文件可以直接作为输入，也就是和 JSON 配合。
- **源与快照**：源（TS）用于人和 Agent 编辑；快照用于执行和验证。二者带同一个版本号；改了源就要重新求值，快照不能手改。
- **确定的求值**：配置和生成内容求值时，没有 I/O、没有真实时间、没有随机数（需要的话由宿主注入确定的版本，归 `mlibs.math`）、没有网络。同一个源总是得到同一个快照。

### 2.3 TS 转 JS 不依赖外部工具

- **只允许可擦除语法**：类型标注、`interface`、`type`、`satisfies`、`as` 这类去掉就能运行的语法。`enum`、`namespace`、参数属性这类需要转换的语法不允许，`omui check` 会报出位置和改法。
- **C++ 的擦除器**：归 `omui.lang.js`（`src/ts/`），作为运行时和 `omui-gen` 共用的转写器。按词法擦除类型、保留列号（错误位置能对上源码）。
- **类型检查**：开发期和 CI 用 `tsc`（有 TS 7 原生版就用原生版），由 `omui check` 调用，结果统一成 omui 的诊断格式（机器可读，附修复建议）。
- **esbuild**：只在“把多个模块打包进可发布的应用”这一步可选使用；热重载和运行时生成都不依赖它。

### 2.4 用 TS 写契约、操作目录、主题（“TS 进、数据出”）

- `defineContract`、`defineOps`、`defineTheme`、`defineMotion`（动画文档）、`defineView`。
- `omui-gen` 用内嵌的 QuickJS 求值，得到 JSON，再生成 C++ 胶水、`.d.ts`、目录清单和文档。**C++ 用户不需要装 Node。**
- **迁移**：先试点一个组件契约（`button`）和一份操作目录（`studio.ops`），验收标准是生成的产物与现有 TOML 生成的**逐字节一致**；然后一次性迁完，不保留 TOML（按“不留兼容层”的原则）。

### 2.5 TS 应用层“尽量薄”的约束

- 不进入每帧路径（已有：表达式由运行时同步求值）。lint 规则 `script-frame` 检查动画、布局、绘制回调里有没有 JS。
- 计算密集的部分写成 C++ 原生模块，经 `openmui:native/*` 暴露。
- 一个应用的 TS 部分如果超过某个规模（例如 2,000 行），由 `omui check` 提示把哪些部分下沉到契约或原生模块。

### 2.6 热重载与 Agent 版热重载

- **低线**：TS 和视图文档改动后 ≤ 100 ms 生效，状态按稳定的语义 ID 和信号键保留（目前是 ≤ 200 ms）。
- **亮点**：每次重载后，自动回报**语义差异**（新增、移除、改变的节点）、**像素差异**（变化区域加局部截图）和**动画采样差异**（按时间采样的关键帧）。Agent 不用再截图对比，直接拿到“这次改动改变了什么”。
- 经 MCP 的 `ui_reload` 和协议的 `reload` 提供；CLI 是 `omui dev`。

### 2.7 删除 Lua 和 Python（一次删完）

| 范围 | 内容 |
|---|---|
| 包 | `modules/projects/omui/lang/lua`、`lang/python`（含 `embedded`）、`src/entry/python` |
| 规范 | `spec/stubs/core.lua`、`core.pyi`；CTS 中 Lua 和 Python 的执行器（S 级的场景和轨迹保留，只由 JS 执行）；规范文本里关于三语言的描述（在 openmui 仓库提交） |
| 模板 | `templates/app-lua`、`app-py` |
| 示例与作品 | 03-counter、04-rating、05-contrast、promo-video、widget-breakout、player 里的 Lua 和 Python 部分 |
| CI | `python-wheel.sh`、`python-extension-probe.sh`，以及各工作流里的 Lua/Python 步骤和 `--exclude omui.entry.python` |
| 生成器 | `omui-gen native` 只生成 TS 存根 |
| 文档 | README、文档站、官网里的多语言说明 |

lint 规则 `legacy-import` 增加 `omui.lang.lua` 和 `omui.lang.python`，防止被重新引入。

## 5. 实施方案

每条工作流（W）由若干检查点组成。每个检查点承载一项完整能力，有无界面的验证和真实证据，并按 AGENTS.md §6 记入 STATUS。

### P0

**W1 TS/JS 顶级化（C1、C6、C7）**
1. C++ 可擦除语法转写器（`omui.lang.js` 的 `src/ts/`），加 `omui check` 的语法诊断。运行时生成和热重载不再依赖 esbuild。**验收**：仓库里所有 `.ts` 都能转写，结果与 esbuild 去类型后的行为一致；不可擦除语法报出位置和改法。
2. 确定的求值环境（无 I/O、无真实时间、无随机数，宿主注入确定的替代）和 `defineContract`、`defineOps`、`defineTheme`、`defineMotion`、`defineView`；`omui-gen` 内嵌 QuickJS 求值。**验收**：`button` 契约和 `studio.ops` 的试点，生成产物与现有 TOML 逐字节一致。
3. 全量迁移 TOML 到 TS，删除 TOML 读取路径；更新 AGENTS.md 的命名和契约规则。**验收**：全量构建和全部像素基线不变。
4. 删除 Lua 和 Python（§2.7），在 openmui 仓库同步规范、存根和 CTS 执行器。**验收**：CTS S 级全部由 JS 执行，轨迹与之前的钉值一致；lint `legacy-import` 拦截重新引入。
5. 接入 tsc 类型检查，`omui check` 统一诊断格式。

**W2 热重载与 CLI（C2、C5）**
1. 热重载 ≤ 100 ms，按语义 ID 保留状态。**验收**：基准测试 p95 ≤ 100 ms。
2. Agent 版热重载：重载后回报语义差异、像素差异、动画采样差异；协议 `reload`、MCP `ui_reload`、`omui dev`。**验收**：Agent 任务里不截图也能确认改动效果。
3. `omui new`（TS 应用模板，从契约生成类型）。

**W3 自描述 API（A1、D-145）**
1. `omui describe --api`：从契约、组件、令牌、操作目录导出写应用所需的 API（JSON），llms.txt 自动导出；运行中的应用通过协议提供同样的内容。**验收**：导出内容和 `.d.ts` 由同一来源生成，lint 检查二者是否一致。
2. 各产品的 skill 精简为 SOP。

**W4 观察三模态与对照实验（A12、D-142）**
1. MCP `ui_capture` 增加 SVG 格式；skill 写清“先语义、按需截区域、要精确就读 SVG”的次序。
2. 对照实验：同一组任务分三种跑法（omui 混合、纯截图点击、无障碍树加截图），记录成功率、步数、token、越权次数和视觉问题发现率，写入台账，在领先度页展示。**验收**：数据入台账；目标是操作类任务的 token 和步数少一个数量级，视觉类任务的发现率不低于纯截图。
3. “从零写一个应用”任务集（C1 的验收）：同一组应用需求，omui（TS）和 Next + shadcn 各自由新的 Agent 会话完成，比较一次写对率。

## 7. 风险与取舍

| 风险 | 应对 |
|---|---|
| 删除 Lua 和 Python 会失去已有的 CTS 交叉验证（三种语言记录同一条轨迹） | CTS 改由 JS 加 C++ 两条路径交叉验证；轨迹钉值不变 |
| “只允许可擦除语法”可能让一部分 TS 写法不能用 | 只限制编写 omui 内容时的语法；`omui check` 给出改写建议；模型对这一子集同样熟悉 |
| 求值的 TS 配置可能写出不确定的结果 | 求值环境没有 I/O、真实时间和随机数；同一个源两次求值，快照必须逐字节一致（加入 CTS） |
| 运行时下发代码的安全问题 | 签名、沙箱限额、openas 能力表；默认只接受数据形式，只有拿到授权才运行逻辑 |
| 自绘的平台行为做不到位，用户会觉得“不像原生” | D6 逐项对照评审；平台风格包；先覆盖输入法、文本选择和滚动这三项最影响感受的 |
| TS 迁移牵涉面大 | 先试点，逐字节一致后再全量迁移；按包分批，每批都跑完整的像素基线 |

## 8. 自我 review

- **一致性**：D-138 删除 Python 只针对应用绑定，仓库工具仍用 Python，这一点已写明，避免误删 lint 和评测脚本。
- **可验证**：每条 P0 和 P1 工作流都有无界面的验收标准；A12 和 C1 的证据都来自真实 Agent 会话，按应用的实际状态判定，不按 Agent 自述判定。
- **归属**：TS 转写器归 `omui.lang.js`；确定的数学函数归 `mlibs.math`；系统集成归 `mcpplibs.os` 和 omui 宿主；生成管线是公共能力，不属于 PPet。
- **待实测的假设**：
  1. 只允许可擦除语法，对模型一次写对率影响很小；
  2. 语义操作比截图操作少一个数量级的 token；
  3. 自绘的平台行为能做到用户分辨不出。
  这三条分别由 W4 的两组对照实验和 W9 的对照评审验证，不成立就修改方案。
