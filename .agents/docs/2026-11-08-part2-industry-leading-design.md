## 0. 核心点（review 入口）

1. **核心理念：人 → Agent → 系统**（D-136，§1）。
   - 人和 Agent 在三种角色上都是一等执行者：项目开发者、用框架做产品的开发者、产品的终端用户。
   - 主路径是人把意图交给 Agent，再由 Agent 操作系统。人用的界面从“创作工具”转为“审查与驾驭工具”，重点是四件事：**看**（结果、差异、预演）、**指**（指着画面就能定位到节点、参数和代码）、**调**（关键参数直接微调）、**控**（权限、停止、接管、撤销）。
   - 不同场景的侧重不同：批量制作、测试、迁移、试玩以 Agent 为主；对局、交互迭代两者对等；审美判断、外部效果的授权、方向决策以人为主。
2. **原生胜过适配**（§1.4）。别人的 Agent 支持（WebMCP、MCP Apps、A2UI、App Intents、Unity 和 Godot 的 AI 插件）都是界面之外的“第二个接口”。我们有八个原生性质，必须从第一天就进入架构，事后适配补不上：
   - 界面本身就是能力目录；
   - 操作是事务；
   - 确定性；
   - 同源的离屏像素；
   - 执行者是模型的一部分；
   - 授权在核心层；
   - 为 Agent 设计的观察；
   - 为 Agent 设计的工程细节。

   这一点用对照实验证明，例如 xengine 对比 Godot 加 MCP 插件。
3. **三条主线，对应八项卖点 A–H**（§1.5）。原来的“一棵树四种视图”“同源”“可组合”等降为支撑这些卖点的底座。
   - **Agent 能安全地用**：A 先预演、再授权；C 零代码的 Agent 接口。
   - **AI 能可靠地造**：B 用 AI 写 UI 最顺手的框架；F AI 产出的是可编辑的动画程序；H Agent 驱动的设计与动效工作台。
   - **人和 Agent 同在**：D 人机同屏共在；G Agent 在开发、试玩和使用中都是一等执行者；E 生成式 UI 的安全运行时（候选）。
4. **规范的分工**（D-137，§4.8）。
   - **openas** 承载所有 Agent 交互：执行者与委派、操作目录、授权、回执、事务（预演、撤销、分支）、实时会话、存在与意图、接管、请人审查、审计。
   - **openmui** 承载 UI 语义。
   - MCP（`omui mcp` 已有）、WebMCP、A2UI、AG-UI、App Intents、AccessKit 都是**适配层**。

   对外的说法是“它们是传输和入口，我们是它们底下的模型层”，并用一张模型完整度矩阵证明。
5. **“领先”的判定**（D-135，§2）。
   - 每个指标按“我方 ÷ 最强竞品”的比值判定：低于 0.95× 为落后，0.95–1.2× 为持平，≥1.2× 为领先，≥10× 或竞品没有这项能力为远超。
   - 对外称“领先”，要求核心指标里没有落后项，且一半以上领先。
   - 测量时双方在同一个 CI 作业里交替运行，只看比值。
   - 没有设备的项目标为“待真机验证”，不算通过。
6. **评审改为并排对照，不再用 codex 打分**（D-135，§2.4）。
   - 每个维度都和同类项目的同一场景并排比较，判定落后、持平或领先。
   - 评审方是维护者，加上一个不带实现上下文的新 Claude 会话（盲比）；量化指标进台账。
   - M5 的退出条件改为“每个维度对最强同类至少持平”，M7 改为“多数维度领先、没有落后”。
7. **现状**（§3）。
   - 有实测的领先：跨平台逐位确定；hanim 对 GSAP（平均快约 4.8×，p50/p95 快约 2×）。
   - 已有的 Agent 底座：`omui mcp` 已经提供事务、撤销、dry_run、请人确认，以及“只有人能做”的操作。
   - 最大的短板：xrender 的光栅速度（慢 1.6–2.9×）、官网交付（压缩后 3.56 MB，可用 1.84 s）、质感。
8. **分期 LD1–LD5**（§7）：
   - LD1 基线与台账（约 1 周）；
   - LD2 补短板（3–4 周）；
   - LD3 标志性特性（4–6 周）；
   - LD4 应用验证（与 LD3 并行）；
   - LD5 复评与收口（2 周）。

   LD1 和 LD2 的一部分并进 M5 剩余的检查点；M5 的退出条件在 M5 自己的 F 复评时判定，紧接 LD2。LD3 中的游戏部分属于 M6。LD5 是全部项目的复评，在 M6 末尾，为 M7 做准备。
9. **Agent 任务集**（§6.3）：我们自己出题，题型和难度分级参照 WebArena，题目、评判规则和基线配置都公开。每道题跑三种方式：我们的语义接口、截图式 agent、无障碍树式 agent。主要指标：**人需要介入几次、多长时间**，以及**该问人却没问**的次数。

## 1. 核心理念：人 → Agent → 系统（D-136）

[核心设计准则 §9](2026-11-05-local-global-composable-architecture-design.md#9-人与-agent-双第一优先级的设计与验收)已经规定：“人 → Agent → 系统”是正式的使用路径，先定义 Agent 可用的语义，再给人做 GUI。本节在此基础上明确未来的形态，规范版本见准则 §9.7。

### 1.1 两种执行者 × 三种角色

| 角色 | 人 | Agent |
|---|---|---|
| **项目开发者**（开发引擎、框架本身） | 定方向，审查架构和画面，最终拍板 | 实现、测试、迁移、对标、写文档（本项目本身就是这样开发的，这是第一份证据） |
| **用框架做产品的开发者** | 审美判断、关键微调、验收 | 搭界面、写动画、做关卡、批量产出素材、回归、试玩与平衡 |
| **产品的终端用户** | 委托、确认外部效果、少量直接操作 | 替人完成日常操作；在游戏里作为玩家或陪练 |

六种组合都要成立，每一种都至少有一个真实任务作证据（§6.3）。

### 1.2 主路径与人的位置

未来大部分真实操作是“人 → Agent → 系统”，人只做核心的调整、评估和反馈。因此：

- **系统的主接口是 Agent 接口**（ops 与语义契约）。GUI 仍然要有高质量的直接操作（准则 §9.1），但设计重心转向审查与驾驭。
- **人的界面以四件事为中心**：
  - **看**：结果、前后差异、过程帧、预演画面（A）。
  - **指**：在画面上指出问题，系统把“这一点”换算成“这个节点、这个参数、这行代码”，变成结构化的反馈交给 Agent。
  - **调**：Agent 留下的关键参数可以直接拖动微调，Agent 能读到人调过什么。
  - **控**：授权、预算、停止、接管、逐步撤销、审计（AGENTS §2.5）。
- **反馈回路是核心体验**：人指出问题 → Agent 精确修改 → 人看到差异。这个回路越短、越准越好。
- **Agent 要在该问的时候问人**：不确定、涉及外部效果、属于审美判断时，主动请人审查，并附上预演画面和几个选项，而不是做完再说。

### 1.3 场景侧重

| 侧重 | 场景 |
|---|---|
| **Agent 优先** | 批量制作（组件变体、素材、配方）；测试、回归、对标；迁移和重构；大规模试玩与数值平衡；日常的应用操作 |
| **对等** | 游戏对局；交互设计的往复迭代；协同编辑 |
| **人优先** | 审美与品牌判断；最终的关键微调；有外部效果的授权（发布、支付、发送）；方向性决策 |

### 1.4 原生胜过适配

**别人的结构性限制**（按 2026 年的公开情况）：

| 方案 | 做法 | 改不掉的限制 |
|---|---|---|
| WebMCP | 页面用 JS 手写工具函数，注册给 Agent | 工具和界面状态是两套东西，会漂移；人看不到 Agent 在做什么；没有预演和撤销的模型 |
| MCP Apps、Apps SDK | 服务端返回一个 HTML 界面，放在 iframe 里 | 界面对 Agent 是不透明的，Agent 读不到里面的语义 |
| A2UI、AG-UI | Agent 输出声明式的界面描述，或者在 Agent 与前端之间传事件 | 以 Agent 到界面的方向为主；没有授权、撤销、执行者和确定的像素 |
| App Intents、AppFunctions | 在系统层手写可调用的动作 | 和 UI 分离；覆盖面取决于开发者写了多少 |
| Unity、Godot、Roblox 的 AI 插件和 MCP 插件 | 把编辑器函数暴露给 Agent | 编辑器状态以 GUI 为中心；操作不是事务；模拟不确定；只能靠截图验证 |

共同的根源：**界面、能力、授权、时间，这四样东西在它们那里是分开的**，Agent 支持只能在外面加一层适配。

**我们的八个原生性质**（每个项目都要满足，准则 §9.7 是规范版本）：

1. **单一来源**：界面就是能力目录。每个可交互节点（游戏里是每个实体或编辑操作）同时声明它的状态、操作、效果类别、可否撤销和成本。
2. **事务化**：每个操作都可以预演、分支、提交和撤销，因为状态和时间是显式的。
3. **确定性**：所以能快进、重放、分叉出一个“未来”并把它画出来。
4. **同源的离屏像素**：Agent 看到的就是人看到的，每个像素都能追溯来源。
5. **执行者是模型的一部分**：每一步都记录谁做的、受谁委派、在哪个授权下；Agent 的存在和意图可以显示给人看。
6. **授权在核心层**：每个操作都由 `openas::decide` 判定，策略由人设定，不靠外层弹窗。
7. **为 Agent 设计的观察**：观察分精度档，内容紧凑，可以订阅，按 token 成本设计。
8. **为 Agent 设计的工程细节**：ID 稳定；操作幂等；诊断是结构化的、带位置；每个工具都有 CLI；反馈回路足够快（headless 下远快于实时）。

**证明方式**：同一组任务分别在“原生”和“适配”的方案上完成，比较成功率、人介入的次数，以及结果能不能被验证。三组对照：

| 我方 | 对照方 |
|---|---|
| xengine | Godot 4 加 MCP 插件 |
| omui | 加了 WebMCP 的 React 页面 |
| omui 作为 A2UI 的渲染端 | A2UI 的参考渲染器 |

### 1.5 三条主线与八项卖点

| 主线 | 卖点 | 归属 | 一句话 |
|---|---|---|---|
| **Agent 能安全地用** | **A 先预演，再授权** | omui，openas 事务 | Agent 的操作先在分支里执行并画出来，人看到“之前／之后”的真实画面和语义差异，同意才提交 |
| | **C 零代码的 Agent 接口** | 规范，omui | 任何 omui 应用自动成为 MCP 服务端和 WebMCP 提供方，覆盖全部操作，不需要手写工具 |
| **AI 能可靠地造** | **B 用 AI 写 UI 最顺手的框架** | omui，xrender | 编程 Agent 不开浏览器就能拿到确定的像素和语义，问“这个像素是哪行代码画的”，写、看、改形成闭环 |
| | **F AI 产出可编辑的动画** | hanim | AI 产出的是程序，不是视频：能精确修改、结果确定、体积小、可交互，能嵌进 UI、视频和游戏 |
| | **H Agent 驱动的设计与动效工作台** | omui，hanim | 设计稿就是产品：Agent 在分支里给出多个真实渲染的方案，人并排挑选、指出问题、微调，结果直接进入组件库和配方库 |
| **人和 Agent 同在** | **D 人机同屏共在** | omui，hanim，openas 的存在扩展 | Agent 在界面上有“身体”（Mui、`agent_presence`），能看到它在哪、想做什么、在等什么；人随时可以接管；同时操作时有明确的冲突规则 |
| | **G Agent 是一等执行者** | xengine（引擎、工具、游戏），以及各项目 | 开发引擎、用引擎做游戏、试玩与平衡、游玩，Agent 都可以做，有的场景 Agent 优先；人做审查、反馈和控制 |
| | **E 生成式 UI 的安全运行时**（候选） | 规范，omui | Agent 生成的界面以 omui 树渲染：不执行任意代码，自动带动效和无障碍，生成的结果自己能验证。先做一个桥接镜头验证需求 |

原来的特性降为底座：一棵语义树四种视图、通用动效（打断连续）、CPU 与 GPU 同源、Web 优先、可组合、全游戏可回滚。它们仍有各自的指标和 CTS（§4），但对外不作为主卖点。

### 1.6 新的衡量指标

除了速度、体积、画质这些传统指标，每个卖点都要报告“人 → Agent”这条路径本身的效率：

| 指标 | 含义 |
|---|---|
| 人介入的次数和时长 | 完成一个任务，人需要看、指、调、控多少次，花多少时间 |
| 反馈轮数 | 人提出一条反馈，到结果被接受，经过了几轮 |
| Agent 自主完成率 | 不需要人介入就正确完成的任务比例 |
| 被撤销率 | Agent 的操作中，被人撤销的比例 |
| 越权次数 | 必须为 0 |
| 该问未问 | 应该请人审查却没有问的次数，必须为 0。和“人介入次数”互相牵制，防止为了降低介入次数而不问人 |

## 2. “领先”的定义与证据（D-135）

### 2.1 三级目标

名字不用 L-1、L-2、L-3，以免和公开 API 的 L0–L4 分级混淆。

| 级别 | 含义 | 证据 |
|---|---|---|
| **达标（par）** | 能力完整，没有明显缺陷；功能覆盖与主流竞品相当 | CTS、功能清单对照 |
| **领先（lead）** | 核心指标里没有落后项，至少一半领先；并排对照评审中每个维度至少持平 | 台账、bench 通道、对照评审记录 |
| **远超（far）** | 只针对标志性特性：竞品做不到，或差一个数量级（≥10×，或任务成功率高 30 个百分点以上） | 招牌镜头、能力对照矩阵、真实任务 |

### 2.2 判定与测量规则

- **比值与判定**：

  | 判定 | 比值 r = 我方 ÷ 最强竞品（越大越好） |
  |---|---|
  | `behind` 落后 | r < 0.95 |
  | `par` 持平 | 0.95 ≤ r < 1.2 |
  | `ahead` 领先 | 1.2 ≤ r < 10 |
  | `far_ahead` 远超 | r ≥ 10，或竞品没有这项能力 |
  | `pending_hardware` 待真机验证 | 本机和 CI 都没有所需的设备（例如真机 GPU、移动设备）；不算通过，单独列出，有设备后补测 |

  耗时、体积这类越小越好的指标取倒数后再比。画质、正确性这类有上限的指标，按“相对参考的误差”比较。
- **同机同负载**：双方在同一个 CI 作业里交替运行，每边至少 15 次，取比值的中位数和 95% 区间；区间跨过阈值的，判定取较差的一档。竞品用它推荐的发布配置，版本固定；负载两边都由同一份种子数据生成；每条记录写明机器、版本和提交号。
- **不挑指标**：指标清单在 LD1 先评审、再测量；落后的照实写进台账，不删。
- **质量与速度一起计**：不能拿画质或确定性换速度。
- **“逐位”的范围**：CPU 路径和模拟层的“逐位”结论，要在 Linux x64、Linux arm、macOS、Windows、Web 五个平台的 CI 上都成立。GPU 路径只承诺同一台设备上与 CPU 参考的差 ≤ 1/255。
- **对外称“领先”**：核心指标没有 `behind`，至少一半 `ahead`，`pending_hardware` 不计入领先。

### 2.3 领先度台账

新文件 `.agents/docs/evaluation/lead.ledger.omui.jsonl`，一行一条记录，分三类：

```json
{"kind":"metric","date":"…","project":"xrender","metric":"raster.fill_large.ms","better":"lower","ours":{"median":3.1,"ci":[3.0,3.2]},"best":{"name":"skia-m131","median":3.4},"ratio":0.94,"verdict":"behind","machine":"ci-linux-x64","commit":"…","found_by":null}
{"kind":"capability","date":"…","project":"omui","feature":"A.preview_before_grant","test":"…","competitors":[{"name":"webmcp","support":"none"},{"name":"playwright-mcp","support":"none"}],"verdict":"far_ahead","commit":"…"}
{"kind":"task","date":"…","project":"omui","set":"ui","runs":[{"via":"semantic","success":0.93,"human_touches":1.2,"asked_when_needed":1.0},{"via":"a11y-tree","success":0.81}],"verdict":"ahead","commit":"…"}
```

- 生成：`tests/bench/competitors/run.sh --ledger`，CI 的 bench 通道每周跑一次，PR 快车道不跑。
- 呈现：官网文档区的“领先度”页直接读台账，显示每项的最新判定，包括落后项和待真机验证项。
- lint `lead`：某个标志性特性没有招牌镜头测试和 `capability` 条目时报警；对外文案写“领先”而台账不支持时也报警。

### 2.4 评审：并排对照，不用 codex 打分

- **方法**：每个评审维度（架构、API、组件、文字、动效、质感、性能、无障碍、Agent，以及各作品自己的维度）都选定同类项目的同一场景，做成并排的对照材料，包括静态图、过程帧条带和交互录像，然后判定落后、持平或领先。例如：
  - 我们的按钮和 Material 3、HIG 的按钮，在同一状态下并排；
  - 我们的切页动效和 SwiftUI、Framer，过程帧并排。
- **评审方**：
  - 维护者：最终判定。
  - 一个**不带实现上下文**的新 Claude 会话：盲比，材料只标 A／B，不说明哪边是我们。
  - 量化台账。
- **记录**：写进 `ledger.eval.omui.jsonl`，`rubric: "compare-v1"`，每个维度一条判定，附对照材料的路径。11-01 之前 codex 的分数只作参考，不再和新判定比较。
- **退出条件**：
  - M5：UI、动画、渲染、官网的每个维度对最强同类至少持平，质感和细节单列。
  - M7：多数维度领先，没有落后。

## 4. 各项目方案

每个项目统一分四部分：**对标**、**指标与目标**、**标志性特性**（标出属于哪条主线）、**实施要点**。

- 表中的“最强竞品”在 LD1 的第一次同机测量后确定。
- 目标以判定档（par、ahead、far_ahead）或绝对预算表示。
- 本机和 CI 都测不了的，标为“待真机验证”。

### 4.1 omui：UI 框架

一句话定义：用一棵语义树同时驱动像素、强动画、无障碍、Agent 和测试的 UI 框架。

**对标**：Flutter 3.x（含 Web 版）、Jetpack Compose（含 Compose for Web）、SwiftUI、React 19 + DOM、Slint、Qt Quick。Agent 方面对 WebMCP、MCP Apps、A2UI、Playwright MCP。

**指标与目标**

| 指标 | 负载 | 目标 |
|---|---|---|
| 冷启动到首帧（桌面） | 同一个设置页（40 个控件） | 对 Slint、Flutter 中最快者 ≥ par |
| Web 首次绘制 | 官网首页；两种网络：桌面（不限速）和移动（Lighthouse mobile：1.6 Mbps、150 ms RTT、4× CPU 节流） | 移动 ≤ 1.0 s（静态 SVG 首屏）；对 Flutter Web 为 ahead；对同类 React SSR 页面 ≥ par |
| Web 可交互 | 同上 | 桌面 ≤ 1.0 s；移动 ≤ 4 s，对 Flutter Web 为 ahead |
| Web 体积 | 首页首包（压缩后，含字体子集） | ≤ 1.2 MB；其余页面按需加载 |
| 帧时间 p99 | 10,000 行虚拟列表滚动；200 个同时运行的动画 | ≤ 4 ms；对 Flutter、Compose 为 ahead |
| 布局 | 5,000 节点的 flex 与 grid 嵌套 | 对 Taffy ≥ par |
| 输入延迟 | 桌面 120 Hz，从按下到像素变化 | ≤ 1 帧（需要高刷屏，待真机验证） |
| 内存 | 10,000 节点的应用 | 对 Flutter ≥ par |
| 无障碍 | NVDA、VoiceOver、Orca，加上 Web 端；用 guidepup 一类的工具驱动标准任务 | 全部通过；TalkBack 等移动端宿主落地后再加（M6） |
| 中文排版 | 标点挤压、避头尾、IME、双向文字 | 规则覆盖对 Flutter、Compose 为 ahead |
| 热重载 | 修改视图文件或脚本（TypeScript、Python、Lua） | ≤ 100 ms，状态保留；C++ 只记录增量重编时间 |
| Agent 接入成本 | 给同一个应用接入 Agent，覆盖全部操作 | 应用侧新增代码为 0 行；WebMCP 版本记录手写的行数和覆盖率（far_ahead） |

**标志性特性**

1. **A 先预演，再授权**（Agent 能安全地用）
   - **能力**：Agent 的操作（或者一个事务）先在应用的分支里执行，headless 画出结果；人看到“之前／之后”的真实画面和语义差异，同意了才提交，拒绝就没有任何副作用。外部效果（发送、支付、发布）在分支里只记录不执行，并明确标出。
   - **在已有能力上增加的**：现在的 `dry_run` 只给出语义结果；A 增加的是分支执行和渲染出来的画面。
   - **对照**：WebMCP、Playwright MCP、App Intents 都没有渲染出来的预演（capability）。
   - **目标**：100% 的可撤销操作都能预演；没有外部效果的操作，预演画面和真正提交后的画面逐位一致；1280×800 下一次预演 ≤ 100 ms。
2. **B 用 AI 写 UI 最顺手的框架**（AI 能可靠地造）
   - **能力**：编程 Agent 不开浏览器就能拿到确定的像素和语义；能问“这个像素是哪个节点、哪行代码画的”；能读带语义的矢量截图。写、看、改形成闭环。
   - **对照**：同一个编程 Agent，用 omui 和用 React（Vite 加 Playwright）、Flutter 完成同一组“做或改一个界面”的任务。
   - **目标**：成功率高 30 个百分点以上；迭代轮数 ≤ 1/2；人介入次数 ahead。
3. **C 零代码的 Agent 接口**（Agent 能安全地用，和规范共有）
   - **能力**：语义树自动投影成 MCP（已有）、WebMCP、App Intents 风格的操作，授权仍由 openas 判定；应用开发者不需要写任何工具代码。
   - **对照**：WebMCP、App Intents 都要手写。
   - **目标**：接入代码 0 行，操作覆盖率 100%（far_ahead）。
4. **D 人机同屏共在**（人和 Agent 同在）
   - **能力**：Agent 有可见的身体和意图；人随时可以接管；两边同时操作时，冲突按 openas 的存在与接管规则处理；Agent 等人回答时，界面明确显示在等什么。
   - **对照**：现有框架没有这一层。
   - **目标**：同一个任务里，人和 Agent 交替操作 10 次以上，状态一致，没有冲突导致的丢失；接管的延迟 ≤ 1 帧。

**底座**（不作为主卖点，指标和 CTS 照常做）：
- 一棵语义树四种视图：同一任务分别由人、读屏、Agent 和测试完成，状态逐项一致。
- 通用动效：37 类组件都不需要任何声明就能过渡；打断时速度阶跃为 0。
- 像素可审查、可回放：CPU 像素五平台逐位一致；归属定义为“覆盖这个像素的最上层节点”，抗锯齿边缘的像素列出全部贡献者；跳转任意一帧 ≤ 33 ms。

**实施要点**
- 按页交付（M5 的 D5）；冷启动剖析；长列表基准 `ui/frame/list-10k`；三个读屏的实机脚本；中文排版规则；热重载计时进 CI。
- A：运行时快照、分支执行，以及分支内的外部效果隔离（openas 事务扩展）。
- B：像素到源码的映射（节点 → 视图文件或代码位置）、编程 Agent 的任务集。
- C：WebMCP 适配器（Web 宿主）。
- D：openas 的存在与接管扩展，以及 `agent_presence` 的冲突规则。

### 4.2 omui 组件库与质感

**对标**：Material 3、Fluent 2、Apple HIG（含 iOS 26 的 Liquid Glass）、shadcn/ui + Radix、Ant Design。

| 指标 | 目标 |
|---|---|
| 覆盖 | 常用组件 ≥ 60 类（现在 37 类） |
| 状态完整度 | 每个组件都有悬停、按下、聚焦、禁用、加载、错误、空、只读状态，逐项测量 |
| 质感 | 每个组件对 Material 3 和 HIG 的同类组件做并排对照（§2.4），每个维度 ≥ par，“细节”单列 |
| 无障碍 | 每个组件都有键盘路径和读屏脚本，通过率 100% |
| 主题 | 令牌覆盖率 100%，组件里没有硬编码的颜色、尺寸、时长（新增 lint） |

**标志性特性**
1. **真正液态的玻璃**：会折射、能融合、跟随运动，所有平台都有，包括 Web。目标：WebGPU/WebGL 上 60 fps（真机 GPU 部分待真机验证）；没有 GPU 时 CPU 路径结果正确，≥ 30 fps。
2. **组件即画布对象**：任何组件都能放在无限画布上，缩小后依然是活的。目标：1,000 个活组件同屏，帧时间 ≤ 8 ms。
3. **风格包对所有组件生效**：一个风格包同时改变质感和动效配方，切换时有过渡。
4. **H 的组件部分**：Agent 按意图批量做出组件变体，每个都带全部状态、动效、无障碍和契约；人在画布上并排挑选、指出问题、微调（§4.3 的 H）。

### 4.3 hanim：动画引擎

一句话定义：可组合、Agent 原生的高级动画引擎，同一套能力支撑 UI 动画、视频和游戏动画。

**对标**：GSAP 3、Motion、Web Animations API；Rive、Lottie；Manim、Motion Canvas；Spine。AI 方面对 AI 视频生成和 LottieFiles 一类的 AI 动效工具。

| 指标 | 负载 | 目标 |
|---|---|---|
| 每帧开销 | `motion/drive-1000` 扩展到 10,000 个值，每 30 帧重定向一次 | 原生和 wasm 都对 GSAP、Motion ahead；最差帧 ahead |
| 形变质量 | 字形 A→B、带孔、多轮廓 | 没有自交；对照评审对 GSAP MorphSVG 和 flubber 为 ahead |
| 文件与播放 | 同一段 10 秒的品牌动画 | 动画文档体积对 Lottie JSON ahead；播放帧时间对 Rive 运行时 ≥ par |
| 确定性 | 任意时刻跳转 | 五平台逐位一致（capability） |
| 物理感 | 弹簧、软体 | 弹簧与解析解的误差 ≤ 1e-9；300 个顶点的软体每步 ≤ 0.2 ms |
| GPU 批量 | 100 万个控制点的形变 | 一帧内完成（待真机验证）；CPU 与 GPU 的差 ≤ 1e-5 |
| Agent 写作 | 100 个任务（自然语言 → 动画文档 → 修改） | 成功率 ≥ 95%；对照用 Lottie JSON 或 AE 脚本的 Agent 基线 |

**标志性特性**
1. **F AI 产出可编辑的动画**（AI 能可靠地造）
   - **能力**：意图 → 程序 → 读回计划（每段的开始和结束）→ 精确修改（“晚 0.3 秒，弹一点”），每一步都可以撤销；不开 GUI 也能审查任意中间帧。产物是很小的程序，可以嵌进 UI、视频和游戏。
   - **对照**：AI 视频生成（得到的是不能改的像素），以及让 Agent 编辑 Lottie JSON 或 AE 脚本。
   - **目标**：成功率比基线高 30 个百分点以上；修改轮数 ≤ 1/3；“晚 0.3 秒”这类指令一次改对的比例 ≥ 95%。
2. **H Agent 驱动的设计与动效工作台**（AI 能可靠地造，和 omui 共有）
   - **能力**：人说出意图；Agent 在多个分支里给出几个真实渲染的方案（过程帧加实时预览）；人在画布上并排比较，在时间线或画面上直接指出问题（“这里太快”会被换算成对应的参数），拖动微调；Agent 收到结构化的反馈后精确修改；确认后进入配方库或组件库。工作台本身也是 omui 应用，Agent 操作它和人操作它走的是同一棵树。
   - **对照**：Figma（含 Figma Make）、Framer、Rive 编辑器、After Effects、Jitter、Google Stitch、v0。
   - **目标**：从意图到能上线的组件或动画，人介入的次数、反馈轮数和总时长都对同类工具 ahead。
3. **一个引擎服务 UI、视频和游戏，逐位确定**：同一个程序可以在 UI 里交互、在视频里逐帧导出、在游戏里按定步长推进，三处结果逐位一致。
4. **跨表示、拓扑对齐的形变**：属性、轮廓、显示列表片段、字形、像素图之间都能形变，可以加约束和噪声；100 对随机字形和图标全部无自交。这一项主要用来做招牌镜头。

**底座**：可组合（叶子、组合和配方是同一种值；类型化通道；准备阶段检查）；presence 和配方 id 登记在 openmui 规范里。

**实施要点**：弹性体后半；GPU 求值；对照基准增加 lottie-web、rive-wasm、Motion；把 `tools/eval/animate.py` 扩展到 100 个任务；工作台在 hanim.studio 和官网设计师画布的基础上做，补上分支方案、画面指认和参数换算。

### 4.4 xrender：渲染引擎

一句话定义：CPU 与 GPU 同源、Web 优先、像素可供 Agent 审查的渲染引擎。

**对标**：Skia（含 Graphite、CanvasKit）、Vello（含 Vello CPU）、Blend2D、ThorVG、resvg、Rive 渲染器。

| 指标 | 负载 | 目标（CPU） | 目标（GPU，待真机验证） |
|---|---|---|---|
| 大面积填充 | 1024²，100 个大路径 | 对 Blend2D、Skia 中最快者 ≥ par（现在落后，慢 1.6–2.9×） | 对 Vello、Graphite ≥ par |
| 渐变 | 线性、径向、锥形 | 同上 | 同上 |
| 描边 | 1,000 条描边，含虚线和端点 | 同上 | 同上 |
| 小图元 | 10,000 个小矩形和圆 | 保持 ahead（现在约 2×） | ahead |
| 文字 | 5,000 个 CJK 字形 | 对 Skia ≥ par | 对 Skia ≥ par |
| 画质 | 五个场景，相对参考的误差 | 平均通道差 ≤ 0.5 | 与 CPU 参考的差 ≤ 1/255（lavapipe 可以先测） |
| Web 开销 | 每帧提交 5,000 次绘制 | 跨 wasm 边界的次数和 JS 侧耗时，对 CanvasKit ahead | — |
| 体积 | wasm 光栅核心 | 对 ThorVG ≥ par | — |

**标志性特性**
1. **B 的底座：为 Agent 审查而生的像素**（AI 能可靠地造）：每个像素都能归属到语义节点（object id buffer），Agent 可以问“这个像素是谁画的”；任意一帧可以导出带语义的 SVG，每个节点是带标记的组，表达不了的效果作为像素岛单独列出。对照：竞品只输出像素（capability）。
2. **CPU 与 GPU 同源**：同一份渲染图走两条路径，CPU 参考五平台逐位，GPU 与它的差 ≤ 1/255。
3. **Web 优先**：每次提交以紧凑字节流跨一次 wasm 边界。

**实施要点**：光栅器改造（稀疏条带、按行的 SIMD 合成、渐变查表，钉住值不动）；GPU 真机对照（有设备之前标为待真机验证）；毕业所需的独立消费者、API v1、CTS；对外名字在 API 冻结时另定。

### 4.5 xengine：Agent 原生游戏引擎

一句话定义：人和 Agent 地位对等地开发与游玩的 Agent 原生游戏引擎系统。

**对标**：Godot 4、Bevy、Unity（含 Unity AI）；物理对 Box2D v3、Rapier；元胞对 Noita 式的落沙模拟；网络对 GGRS。Agent 方面对 Godot 和 Unity 的 MCP 插件。

| 指标 | 目标 |
|---|---|
| 2D 刚体 | Box2D v3 官方基准场景的步进时间对 Box2D v3 ≥ par；五平台确定。Box2D v3 和 Rapier 本身也有跨平台确定性，这一项不算差异点 |
| 软体与约束 | XPBD 1,000 个约束 ≤ 0.5 ms |
| 元胞 | 4096² 的场 60 fps（待真机验证）；CPU 与 GPU 逐位一致（已有） |
| ECS 与世界 | 10 万个实体的迭代对 Bevy ≥ par |
| 工具 | 场景、关卡、素材的编辑到热重载 ≤ 200 ms |
| 原生 vs 适配 | 同一组游戏开发任务，xengine 对 Godot 4 加 MCP 插件：成功率、人介入次数、结果可验证的比例都为 ahead |

**标志性特性**
1. **G Agent 是一等执行者**（人和 Agent 同在）
   - **能力**：三种角色上 Agent 都能完成完整任务——
     - 开发引擎和工具：ops、skill 和 CTS 都齐全；
     - 用引擎做游戏：场景、关卡、素材和数值全部 headless 完成，并用真实离屏像素自审；
     - 试玩与平衡：上千个人类档的 Agent 自动试玩，找卡关、数值失衡和回归，每个问题附一份逐位回放，开发者可以直接跳到出问题的那一帧；
     - 游玩：作为玩家或陪练。

     人做审查、反馈和控制。批量制作、试玩和回归以 Agent 为主。
   - **对照**：Godot、Unity 的 AI 插件只暴露编辑器函数，不能分叉、不能快进、只能靠截图验证。
   - **目标**：Agent 从零做出一个小游戏并通过人的验收，记录人介入的次数；一次试玩能找出预先埋下的卡关和失衡问题 ≥ 90%。
2. **人与 Agent 平等游玩**：同一套感知限制、反应时间和操作频率；每局可以逐位回放，并能查看 Agent 每个时刻看到了什么、为什么那样做。目标：打砖块和格斗都有人类档的 Agent 玩家；10,000 局回放逐位一致。
3. **原生胜过适配**（§1.4）：场景是数据，编辑操作是事务，模拟确定，离屏同源；所以 Agent 不需要插件。用“原生 vs 适配”的对照实验证明。

**底座**：全游戏可回滚、可分支（模拟层强制确定性）。

**实施要点**：动力学 P1（M6）；世界与 ECS 的基准；关卡工具（ops 优先，GUI 以审查为主）；试玩员（批量的人类档 Agent、问题的分类与回放索引）；Godot 加 MCP 插件的对照环境。

### 4.6 gongfu：格斗框架

一句话定义：确定性、可回滚、角色即数据的格斗游戏框架。

**对标**：GGPO/GGRS；SF6 等商业格斗游戏的公开实测，来源记进台账。

| 指标 | 目标 |
|---|---|
| 回滚开销 | 回滚 8 帧并重算 ≤ 1 ms（桌面），≤ 4 ms（Web） |
| 确定性 | 五平台 10 万次回滚逐位一致 |
| 输入延迟 | 本地从按键到画面，对 SF6 的公开实测 ≥ par |
| 数据驱动 | 从修改一个招式的帧数据到可玩 ≤ 1 s |
| 作品质量 | 对 SF6 做并排对照（2D 与 3D 的差别除外），每个维度判定并记录 |

**标志性特性**
1. **确定性回滚内核，可以原样拆出**：定点数实现，已有 10,000 次随机深度回滚的证据。
2. **角色即数据，由 Agent 制作**：角色和规则全部用数据表达，诊断带行列号；Agent 制作和调整角色（帧数据、判定框、平衡），人审查手感和画面（G）。
3. **Agent 陪练**：任何角色、任何难度，都在人类档的约束下扮演，并能读回放解释自己的选择；也可以作为回滚联机的远端对手（M6）。
4. **回放即教程**：任何一局都能逐帧解释（判定框、帧优势、取消），由 Agent 生成解说。

### 4.8 规范：openas 与 openmui（D-137）

**分工**

| 层 | 内容 |
|---|---|
| **openas**（与领域无关，所有 Agent 交互都放这里；UI、游戏、引擎工具、任何应用都用它） | 执行者与委派链；操作目录（类型、效果类别、可撤销性、成本）；授权与策略；信封与回执；**事务**（预演、提交、撤销、分支，外部效果在分支中隔离）；实时会话（档位、预算、停止）；**存在与意图**；**接管与交接**；观察与订阅；审计；**请人审查**（附预演和选项） |
| **openmui**（UI 语义） | 语义树、角色、状态；动效词汇；像素和矢量截图及其来源；把树上的节点绑定到 openas 的操作；存在在 UI 上如何呈现 |
| **适配层**（实现，不是规范） | MCP（`omui mcp`，已有）、WebMCP、A2UI、AG-UI、App Intents 风格、AccessKit；它们都是 openas 和 openmui 的投影或入口，放在 omui 等实现里 |

**标志性**：模型完整度。对外不说“第一份标准”，而是用一张矩阵说明：事务、预演、撤销、执行者与委派、授权、存在与意图、接管、确定性，这几项在 MCP、MCP Apps、WebMCP、A2UI、AG-UI、App Intents 里各支持多少，openas 加 openmui 全部支持。

**目标**
- openas 的事务、存在与意图、接管、请人审查四项扩展：在 `openas-design` 分支起草，经 omui（A、D）和 xengine（G）两个实现验证后进入规范。
- 第二个实现：用 TypeScript 写一个 DOM 版的 openmui 语义适配器，只按规范文本实现，不读 omui 的代码；规范 CTS 通过率 ≥ 90%。这是同一团队、独立代码库，不宣称是第三方实现。
- 适配器：WebMCP（LD3）；A2UI 渲染端的桥接镜头（E，LD3，可选）。

## 8. 归属与架构约束（不变）

- 单一归属：数学和随机在 `mlibs.math`，动画在 hanim，渲染在 xrender，设备抽象在 `mlibs.rhi`，Agent 交互的模型在 openas（运行时用 `mlibs.control` 和 `openas::decide`）；优化做在 owner 里，不在消费者里复制一份。
- 适配层（MCP、WebMCP、A2UI 等）只做投影，不复制业务状态和授权逻辑（准则 §9.1）。
- 依赖只能向下；作品不写引擎代码；不留兼容层。
- 新能力先定契约再实现；每类插件都有 CTS、trace 和日志。
- 性能优化不能破坏确定性：钉住的像素和回放在优化前后逐位不变；需要改变的，必须说明语义上的原因并一次性重新钉住。

## 9. 风险与取舍

| 风险 | 应对 |
|---|---|
| 某些指标很难超过成熟竞品（Skia 的 GPU 路径、Box2D v3 的求解速度） | 规则是“不落后，且多数领先”；落后项如实公开，这个项目就不对外称领先 |
| 共享 CI runner 的噪声 | 只用同一作业内交替测量的比值；区间跨过阈值时取较差的一档 |
| 对照评审的偏差（同一个模型既写代码又评审） | 评审用不带实现上下文的新会话做盲比；维护者最终判定；量化台账兜底 |
| 对照实验不公平 | 任务集和基线公开；Agent 基线同时用截图式和无障碍树式；“原生 vs 适配”的对照方用社区最好的插件和最新版本 |
| 预演（A）对有外部状态的应用不完整 | 分支只覆盖本地状态；外部效果在分支里只记录不执行，并在预演里明确标出；做不到预演的操作要如实声明 |
| 为了降低“人介入次数”而该问不问 | “该问未问”必须为 0，和介入次数一起报告 |
| “未来 90% 经由 Agent”是判断，不是事实 | GUI 的直接操作质量照样验收（准则 §9.1）；用 §1.6 的指标持续检验这个判断 |
| 生成式 UI（E）范围大 | 只做一个桥接镜头验证需求，LD3 可选 |
| 标志性特性拿不到 `far_ahead` | 按顶层方案 §9.5 修改或删去；一个项目少于两项有证据的特性，就退回 xengine 子系统或 mlibs |
| GPU 真机和移动设备缺失 | 先测能测的，其余标为待真机验证（§2.2） |
| 范围膨胀 | 每期退出条件锁定；新想法进待办，不插队 |
| 磁盘和构建资源（每套配置的 target 约 25 GB，mcpp#874） | 只保留一个构建目录；竞品基准的构建产物放在独立目录，定期清理 |

## 10. 维护者结论（2026-11-08 已确认）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 竞品清单 | 认可（§4、§6.1） |

### 11.2 第二版

第二版修正的问题（第三版保留这些修正）：

- **数字**：hanim 对 GSAP 平均快约 4.8 倍；官网交付是压缩后 3.56 MB；配方 37 个。
- **对照对象**：`mlibs.text` 的塑形本身就是 HarfBuzz，改为和 SkParagraph、ICU 比；Box2D v3 和 Rapier 也有跨平台确定性，不算差异点；SF6 的输入延迟需要公开实测作来源。
- **阈值**：三处互相矛盾的“领先”阈值统一为比值判定表。
- **不可行的目标**：移动网络下 1.5 s 可交互；TalkBack；C++ 热重载 ≤ 100 ms；GPU 跨厂商逐位；60 帧 50 ms 重建；像素归属没有定义抗锯齿边缘。
- **Agent 基线**：增加无障碍树式 agent。
- **共享 runner 的噪声**：只看同一作业内的比值。
- **一致性**：标志性特性和一句话定义对齐；分期编号和级别名与旧编号、API 分级冲突，已改名；M5 的范围被悄悄扩大，已恢复。
