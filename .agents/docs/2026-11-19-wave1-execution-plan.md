## 0. 核心点（review 入口）

1. **终点不变**：第一波（基础层与 omui）达到发布标准、随时可以拆（实施方案 §5 的六条，十三条发布门）。对外发布与拆仓是之后的两个独立决定。
2. **现在的位置**：A 组全部完成；B 组过半（组合框架 K0–K6 已做）；G0、G3 两个最小验证完成；C、D、E、F 基本没开始。剩下约 **110 个检查点**（§2）。
3. **关键路径变了**。实施方案写的两条（规范线、体积线）前半已经做完。按依赖算，现在最长的是 **通道线：E1 → E2 → E3a → E3b → E4 → H，约 19 个检查点**；其次是 **Web 线：G1 → G5 → G6 → H，约 18 个**（官网改为单页面、定制用已有的运行时生成之后，G8 与 G9 不再排在 G1 后面，见[官网的设计](2026-11-19-site-live-design-design.md)第三版）。这两条从今天起都没有前置，任何一天都不应该空着（§3）。
4. **真正的约束是总量与三类等待，不是某一条链**：110 个检查点由一个主会话加至多一个子 Agent 做；会让它停下的是（a）外部条件，（b）要 review 的一页设计，（c）没有数就定不了的目标。三类各有处理办法（§4）。
5. **三处次序的调整**：
   - **先量，再裁**：并排基准（C1、N2）提到体积与性能的调优之前。现在的上限（最小应用 ≤ 8 MB 等）是估计；实测 `app` 是 17.3 MB，compose 子方案已写明靠裁剪到不了。先有对手的同机实测，才知道差多少、往哪做。
   - **四页设计一次写完、一起 review**：终端宿主（F1）、共用运行时（E3a）、官网（G4）、闭包推导（B7a）。它们各自挡着后面 8–15 个检查点，分四次等 review 是四次停顿。
   - **验收里的“在 CI 上”改为“本机通过，检查进了 CI 的步骤”**（D-248）：任务完成不等矩阵；矩阵只在节点按需跑一轮。
6. **推进按五轮**，每轮是一批互不阻塞的任务，结束于一个节点（§5）：量出来 → 体积与性能到线（M1）→ 上手与平台（M2）→ 终端与官网（M3）→ 达标（M4）。
7. **十件事已在 2026-11-19 的两轮 review 里定下**（§8）：没条件验证的先尽量真实验证、做不到的理论验证并标注；磁盘够用；体积的门按并排实测；四页设计通过；降级写明五项；子 Agent 最多一个，测试与 CI 一律不等；官网第五版（安装两个标签、PR 1 上出 Pages）；CI 按车道选是一个功能（D-254）；并排对比现在就做，由子 Agent 接。

## 3. 关键路径

### 3.1 按依赖算的链

只列还没做完的任务；括号里是估计。

```
Web 线    G1(5) ─────────────────────────┐
          G8(5，主题与定制、回放) ────────┤
          G9(3，Agent 接入) ──────────────┼─ G5(5) ─ G6(2) ─┐
          G2(2) ──────────────────────────┤
          K7(3，含 B8) ───────────────┘             │
通道线    E1(3) ─ E2(3) ─ E3a(1，review) ─ E3b(3) ─ E4(3)
                  ├─ E5(2)   E1 ─ E6(1)、E7(2)      │
组合线    K7(3) ─ K8(5，先 B7a 的 review) ─ K9(2)   ├─ H1(3) ─ H2(2) ─ H4(1)
终端线    F1(1，review) ─ F2(3) ─ F3(4) ─ F4(2，要 C1)
并排线    C1(3) ─┬─ C2(3) ─┐                        │
                 ├─ C3(2) ─┴─ G7(2)                 │
                 ├─ C8(1)                           │
                 └─ C4(3，要 D0)                    │
实机线    D0(等) ─ D1(2)、D2(1)、D3(1)、D4(1，等时间)
无前置    B1 第二步、B2、B5、B9、C5、C6、C7、N2、N5、D5、D6、D7
```

| 链 | 到 H 之前 | 加 H（6） | 今天能不能开始 |
|---|---|---|---|
| **Web 线**（G1 → G5 → G6；G8、G9、G2 并行汇入 G5） | 12 | **18** | 能：G1、G2、G8、G9 都没有前置 |
| **通道线**（E1 → … → E4） | 13 | **19** | 能：E1 只依赖 A7，已完成 |
| 组合线（K7 → K8 → K9） | 10 | 16 | 能：K7 |
| 终端线（F1 → … → F4） | 10 | 16 | 能：F1 是一页设计 |
| 并排线（C1 → C2、C3 → G7） | 8 | 14 | 能：C1 |

结论：

- **两条线几乎一样长，都不能空着**。官网改为单页面之后 G5 由 8 降到 5；它要的“有限的 Live Design”就是已有的运行时生成（D-144），所以新增的 G8（主题成为可定制的表面、定制是一层数据、运行时生成接到 Web 宿主、原地回放）与 G9（访问者自己的 Agent 接进标签页）用的都是数据，不依赖 G1，可以与它并行。Web 线由 23 降到 18，通道线（19）成了最长的。Web 线上风险最大的是 G9：https 的页面能不能连到本机的端点，要第一步就验证。
- **通道线**的结果还被别的门引用（门 5、8、9，收口清单的 6 格探针）。官网把安装、接入、验证合成了一个动作（一段提示词，[官网的设计](2026-11-19-site-live-design-design.md)第四版 §5），所以通道线经 G9 汇入 G5：E1 → G9 → G5。**同一个场景守三处**——一个只拿到提示词的 Agent 在干净的环境里装上、接入、改页面：它是官网的验收、通道线“干净机器”的检查、发布门里 Agent 的冷启动任务之一，只做一次。
- 其余三条线各有 6 个检查点以上的余量，可以让给前两条。

### 3.2 按总量算

110 个检查点里，最长的链只占 19。就算 Web 线一刻不停，其余约 87 个检查点仍然要有人做。所以排法的目标是两条：**关键路径上永远有人在做；主会话永远不因等待而停**。子 Agent 接一条与主线代码不相交的线（§5 每轮写明）。

## 5. 五轮

每一轮是一批互不阻塞的任务。**主线**是主会话依次做的；**并行**是子 Agent 或后台验证做的，与主线的代码不相交；**出口**是这一轮结束时本机拿得出的证据。检查点的验证只跑它触及的范围，放后台；节点前本机预检，再按需发起一轮矩阵，下一轮的工作不等它（D-248）。
