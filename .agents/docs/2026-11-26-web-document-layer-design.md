# Web 宿主的文档层（UI3，一页设计）

状态：草案，待 review（2026-11-26）。决策：D-286（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 D-258–D-260；上游：FE1、UI1；下游：UI4（深浅色、打印、减少动态效果）、UI5（带样子的投影、加载策略）、ST2。

## 1. 事实（2026-11-26）

- 有界面的 Chromium 156 与 Firefox 159 里，画布接管之后：页内查找找不到，文字选不中，没有可见的 `<a href>`；打印是空白页（顶层方案 §1.4）。
- Web 宿主已经有一份 DOM 镜像（`omui.host.web:mirror`）：语义树的每个节点是画布上方一个绝对定位的元素，按差异增量同步（一帧里改了一个标签就只发一个属性），焦点、朗读区、跳到主要内容的链接都在它上面。
- 它为什么没解决上面三件事：整层是“视觉上隐藏”的；每个节点都是 `div` 加 ARIA 角色，链接不是 `<a href>`；一段文字只有一个盒子，没有逐行的位置；画布里的滚动不是浏览器的滚动，查找没法把匹配处滚进来。
- 构建时的静态投影（`static_html`）与这份镜像是两套代码：投影现在按属性与标记写出完整的元素（UI1），镜像还是 `div`。程序到达时投影被换掉，不是被接手。

## 2. 三级次序（D-185）

**① 从本体系出发。** 一棵语义树、多种渲染，HTML 是其中一种——那么它应当只有一份：构建时写出的投影、程序到达前读者看到的页面、程序到达后的镜像，是**同一份 DOM 的三个时刻**。程序到达时按 id 接手已有的元素，之后按差异更新；元素的标签、属性、行内结构由同一个映射给出。文字的位置、每一行的盒子、滚动的范围，引擎本来就有（布局是它做的），不必猜。**结论：取这一级。**

**② 前沿与组合。** 查过的做法（2026-11-26 检索）与取什么：

| 做法 | 现状 | 取什么 |
|---|---|---|
| 画布上叠一层透明文字（PDF.js 的文字层；typst.ts 的语义层） | 通行多年。PDF.js 的查找用的是它自己的查找条，不是浏览器的；typst.ts 的讨论里把选中不准归因于拿不到排版信息 | 形状：真实的文字放在画布画它的位置。我们有排版信息，所以逐行对齐可以做准 |
| HTML-in-Canvas（把 DOM 元素画进画布，浏览器负责命中与读屏的同步） | Chrome 148 起试用，155 改过接口（`layoutsubtree` 改为 `drawable` 等），试用期延到 160；有二手消息称 157 默认开启，未经一手来源核实。Firefox 与 Safari 没有实现 | 不作为基础：只有一个引擎、接口还在变。预留：文档层是真实的 DOM，将来可以交给它画 |
| 画布应用另挂一棵语义 DOM（只给读屏） | 我们现在的镜像就是这样 | 不够：查找、选中、链接、打印都不靠 ARIA |
| CSS 自定义高亮（不改 DOM 给一段范围上色） | 各引擎已有 | 留给引擎自己的选中与搜索结果在文档层上的显示（需要时） |

组合：**镜像升格为文档层**——真实的元素（来自 UI1 的映射）、透明而可查找可选中的文字（按引擎的行盒放置）、真实的滚动容器（与引擎的滚动双向同步）。

**③ 业界通行的做法**（画布应用不支持查找与选中，或自己做一套查找条）不取。

## 3. 设计（D-286）

### 3.1 一份映射，三个时刻

- `omui.semantic` 的 HTML 映射（角色与属性 → 标签与特性，标记 → 行内元素）是唯一的一份；`static_html` 与镜像都用它。镜像的每个批次带上节点的标签与由属性来的特性（`href`、`id`、`start`、`align`），文字带行内的结构。
- 程序到达时，页面里已有的投影元素按 `data-omui-target` 被接手：同一个元素换上位置与事件，不重建。之后的更新照旧是差异。
- 页面没有投影时（应用页、`eager` 策略），第一批照旧新建全部元素。

### 3.2 文字：透明、在原位、逐行

- 文档层不再隐藏。文字是透明的（画布画看得见的字），但参与查找、选中与复制；选中的底色与查找的高亮由浏览器画，落在画布画字的位置上。
- 位置：每个节点的盒子（已有）；多行的文字再给出每一行的盒子与这一行的字节范围（引擎的行布局，无障碍那边已经在用），页面把每行放进一个不换行的行内块，宽度不合时按比例缩放到行盒的宽度。
- 字体：页面用引擎自己的字体数据登记同名的字体（`FontFace`），两边的字宽先天接近，缩放只是修正。
- 判据是量出来的：查找的高亮矩形与画布上那段文字的矩形，偏差不超过钉住的像素数（先在 Chromium 与 Firefox 上各量一遍再定这个数）。

### 3.3 链接、滚动、指针

- **链接**是真实的 `<a href>`，盖在画布里链接的位置上：悬停看得到地址、能在新标签页打开、能复制地址。点击先交给引擎（应用内的路由、需要回答的外部链接照 S-1、S-2 走）；引擎不处理的才由浏览器走默认。
- **滚动**：语义树里的滚动视图在文档层里是真实的滚动容器（不显示滚动条），内容的大小取引擎给的范围。两边双向同步：引擎滚了，设它的 `scrollTop`；浏览器滚了它（查找跳到匹配处、锚点、读屏），把偏移发给引擎。于是“查找的下一个”能把屏幕外的匹配滚进来，嵌套的滚动也一样。
- **指针**：文档内容的文字（段落、标题、单元格、代码）接受指针，原生的拖选可用；其余元素不接指针，事件照旧落到画布。落在文字上而不是拖选的点击转给画布。可操作的节点（按钮等）照旧由画布处理，镜像上的激活只给辅助技术。

### 3.4 不变的

- 焦点、朗读区、跳到主要内容、粘贴板、隐藏的输入框：不动。
- 文档层不决定任何像素：画布画什么与它无关（接管后的样子不变）。接管前后的样子一致是 UI5 的事。
- 没有脚本时页面就是投影本身（UI1），不依赖本文。

## 4. 实施的三步

| 步 | 内容 | 验收（有界面的 Chromium 与 Firefox，屏幕 2） |
|---|---|---|
| 1 | 镜像用同一份映射：真实的标签与特性、行内结构；不再隐藏，文字透明；接手已有的投影 | 页面里的 `<a href>` 数与树里的链接数相同，位置在画布的链接上；`window.find` 找到正文里的词；全选后复制得到正文 |
| 2 | 逐行的盒子与字体；偏差的测量 | 查找的高亮与画布文字的偏差不超过钉住的值；跨行的选中连续 |
| 3 | 滚动容器的双向同步；指针的分工 | 查找屏幕外的词，页面滚到它并且画布同步；锚点链接滚到标题；拖选一段跨两行的文字，复制的内容与树的文字相同 |

并排（UI3 的验收里加的一条，顶层方案 §16 第 9 项）：同一篇文档在 Flutter Web 与一个 PDF.js 页面上做同样的三件事（浏览器自己的查找、原生选中、`<a href>`），结果并排记入台账。

## 4a. 实施中定下的（第 1 步，2026-11-26）

- **映射的形状**：`omui.semantic` 的 `html_element(node, inside, find, where)` 给出一个节点是哪个元素——标签、特性（标签自己的在前，然后是 ARIA）、自己的文字（`Inline` 的序列：文字、换行、标记生成的元素、由链接或图片放进文字里的子节点）、哪些子节点被文字放置。`static_html` 写出这些片段，输出逐字节不变；文档层把同样的片段作为数据发给页面。
- **页面不解析标记**：批次里文字是片段的数据（字符串，或 `{tag, c}`，或 `{tag, node, c}`），页面用 `createElement` 与 `createTextNode` 构造；应用写的内嵌标记在文档层里是它的文字，不作为标记注入。
- **`HtmlFor::live` 与文档的差别只有三处**：元素接受焦点（`tabindex`）；人操作的（按钮、复选框）保持 ARIA 的 `div` 形式，激活照旧由程序回答；画布画的图片不是 `<img src>`（不让浏览器再取一次），是带 `role="img"` 与名字的元素。
- **文字里的链接**：它的元素在句子里（`inline`），由文字放置、没有自己的盒子；它自己的特性（`href` 等）仍由它自己的条目给。不再被文字放置时，它重新带上标签、文字与盒子。
- **接手**：第一个批次之前，页面把投影里的元素按 `data-omui-target` 登记；标签相同的被直接取用（清掉原来的子节点，换上位置与事件），不同的（例如文档里的 `<button>` 对文档层的 `div`）留在原处。
- **本步里指针仍然穿过文档层**（`pointer-events: none`）：查找、全选与键盘的选中可用，拖选与链接的悬停留给第 3 步。文档层上的点击（辅助技术发出的）一律阻止浏览器的默认动作，由程序回答；“程序不处理的交给浏览器”也在第 3 步。
- 检查：`oweb` 的 `layer_test`——最小核心文档集的每一页，每个节点在投影里与在文档层的第一个批次里是同一个元素，链接的去向与树相同，带标记的文字逐字相同。

## 4b. 实施中定下的（第 2 步，2026-11-27）

- **行的来源是一个新的查询，不借用无障碍的那一个**：`omui.view` 的 `text_lines()`（组件自述，`Runtime::text_lines(node)`）给出每一行在文字里的字节范围与它在窗口里的盒子；文字原语与 Markdown 视图的文字、代码块实现它。`text_layout`（辅助技术要的逐字形位置）只有可编辑的文字有，静态文字不因此多出节点——无障碍树不变。只在段落按上一次绘制的宽度排好时才回答（测量过程里按别的宽度排过就不回答）。
- **切行在 C++ 里做**：映射的每个片段带它在文字里的字节范围，镜像按行的范围切开，批次里是 `lines`：每行一个盒子（相对元素，四分之一像素）与这一行的片段。换行符是行的结束，不成为内容。行的范围不是文字本身的字节（组件画的不是这段文字）或字没有宽度（没有装整形器）时，退回按流排的 `text`／`content`。
- **跨行的链接**：一个元素只能在一处。链接本身在它的第一行；延续到下一行的部分是一个同样特性的 `<a>`（同一个 `href`），用 `data-omui-part` 指明它是哪个节点的一部分。
- **对齐的做法，按词**：先试过按行对齐（每行一个 `span`，调字号与沿行缩放使行宽相等）。实测（有界面的 Chromium 156 与 Firefox 159，以画布的墨迹为真值）：一行 680 px 的标题上，词的位置最多差 8.1 px（没有行盒之前约 160 px）。页面的字体与画布的不同，按行对齐做不到更好，所以按词放：`TextLineBox` 带每个字形在行上的位置，镜像把一行的文字切成词（词带它后面的空白），每个词给出它在行上的左边与宽度；页面上每个词是行内的一个块，宽度取到下一个词的起点——词仍在行的文本流里（选中一行读到的是一行文字，不是一词一行），又各自落在画布画它的位置。一批的词一起量、一起设：先定一行的字号（使各词的自然宽度之和等于画出来的宽度之和，不超过行高），再给每个词补上各自的缩放。一批两次排版。
- 没有空白分词的文字（中文、日文）一行是一个词，退回到按行的精度；按字形再细分留到需要时。
- **选中时仍然看的是画布**：选中的文字保持透明，高亮半透明。

## 4c. 实施中定下的（第 3 步，2026-11-27）

- **滚动视图在页面上也滚**：批次里滚动视图多一项 `scroll: [x, y, max_x, max_y]`。它的元素是不显示滚动条的滚动容器，内容的尽头用一个 1×1 的标记撑到“范围 + 视口”，偏移设成同一个值。它的孩子的盒子是内容里的位置（窗口里的位置加上偏移），所以滚动时只发 `scroll` 一项，孩子不重发；位置与偏移各自取整带来的一个像素的来回不算移动。
- **偏移取这一帧排版用的那个**（`Runtime::scroll_offset`），不取节点声明的目标：滑行的 140 ms 里页面的元素逐帧跟着走，孩子的盒子与它始终一致。
- **回声靠记住自己设的值**：页面记下程序设的偏移；`scroll` 事件里偏移与它相同就不说话，不同（浏览器自己滚的：查找把匹配带进来、地址里的锚点、读屏）才告诉程序——页面事件的第 8 类 `scroll`（x、y、节点）。宿主把视图的 `x`、`y` 直接设到那里（属性，不滑行）；视图自己把它夹在范围内，夹过的值随下一批回到页面。不需要来源标记。
- **地址里的 `#` 不是锚点**：Web 包里地址的片段是应用的路由（程序的参数），改它会重新载入。文档内的链接（`#标题`）由程序自己滚到标题，页面的元素跟着走；§3.3 里“锚点”一项按这个理解。
- **只有滚动视图会滚**：浏览器把匹配带进视野时，凡是裁剪内容的盒子它都会滚（只裁剪不滚动的元素、图层本身），那会让图层与画布错开。图层上的捕获监听把这些放回 0。
- **指针的分工（修订 §3.3）**：
  - 文字不接指针，拖选是引擎自己的（`omui.view` 的“窗口唯一的选区”：跨段拖选、双击选词、Ctrl/⌘+C；各平台一致，在语义树里，Agent 读得到，精确到字形）。原生的选区只来自浏览器自己发起的动作：查找、全选、键盘与读屏。两套选区同时接指针会同时出现两处高亮，所以不这样做。
  - 链接接指针（`a[href]`）：浏览器显示它的地址，带修饰键或用别的键按下时由浏览器处理（新标签页、新窗口、链接的菜单），程序不取这次按下。
  - 图层与画布在同一个位置，所以程序在图层上再登记一遍与画布相同的鼠标、滚轮、触摸回调：指针在链接上的移动、按下、滚轮照旧是画布上那个链接的悬停与按下，坐标不用换算。普通的按下由程序回答（应用内的路由、外部地址照 S-1、S-2），紧随其后的 `click` 不再算一次激活；没有指针按下的 `click`（读屏、键盘）仍是激活；跨行链接后一行的部分算同一个链接。

- **实测**（2026-11-27；xlings 的 Chromium 159、Firefox 159、WebKit 27.2，有界面，屏幕 2；一篇 10 节的 Markdown 放在滚动视图里，`max_y` 1602）：
  - 浏览器把视野外的匹配带进来：元素滚到 1209，视图的 `y` 随即是 1209，画布画的就是那一屏，高亮在画布的词上。Firefox 与 WebKit 的 `window.find` 自己滚；Chromium 的 `window.find` 只选中不滚（它的查找栏才滚），探针用同一套“滚进视野”代替。
  - 页面滚过之后词与画布墨迹的偏差：Chromium 2.0 px、Firefox 2.2 px（静止时 1.8 与 2.1；只量了这两个）。
  - 滚轮在画布上：视图滑行，元素的偏移与视图一致，停下后不再有来回。
  - 按图层里词的位置在画布上拖过两行：Ctrl+C 得到的文字与两词之间的文字相同（三个浏览器）。
  - 链接：指针下是 `<a href>`，引擎里那个链接是悬停态；按住 Ctrl 点击开出一个新标签页（地址是 `href`），本页不动；普通点击不开标签页、不重复激活；文档内的链接点击后视图滚到标题（`y` 1602），元素同步。
  - WebKit 在这块屏上的设备像素比是 1.25（布局 1024×640），结果相同。WebKit 的 Linux 构建此前起不来（缺系统库）；xlings 的包自带依赖，能起。

## 4d. 打印（UI4 的一项，2026-11-27）

- **打印的是文档层，不是画布**：`@media print` 里画布让开，文档层回到页面的流里——元素不再按盒子摆放，逐行的文字合回一段，按纸的宽度重新换行；标题、列表、代码块、表格、链接的下划线由一小段打印样式给出，文字是黑色的真实文字。所以打印出来能分页、能在 PDF 里选中与查找，链接可点。程序接管之前（或从不接管）打印的是静态投影，同样铺开成整篇。
- **实测**：10 节的文档，headless Chromium 159 打成 A4 的 PDF：3 页，`pdftotext` 读出 1202 个词，首尾两节的词都在；此前是一张空白页。Chromium 与 Firefox 的打印布局里画布 `display:none`、段落在流里、代码块保留换行、列表项有项目符号（加上项目符号之后重打：仍是 3 页、1202 个词）。
- **局限**（归文档层这一级解决）：只有画布画得出的东西（图片、图表、自绘的组件）不在打印里；要打印它们得把画布的像素按节点放进文档层，留到有文档需要时做。打印用的是系统字体，不是画布的字体。

## 4e. 深浅色与减少动态效果跟随系统（UI4，2026-11-27）

次序（D-185）：① 把“使用者的设置”当作宿主报给运行时的一件事实，主题按它取——不是 Web 宿主的特例，窗口、终端、无头都走同一处；② 主题仍是数据，“跟随”写成数据里的一层（方案），不写成代码里的开关；③ 低线是各框架的做法（Flutter 的 `ThemeMode.system`、CSS 的 `prefers-color-scheme`）：应用给出深色主题才跟随，默认不替应用换色。

- **运行时**：`Runtime::set_dark_preferred` 是使用者对深色外观的偏好（宿主从系统读到的）；`set_theme_by_preference(f)` 让主题成为它的函数——现在取一次，偏好变了再取；直接 `set_theme` 就不再跟随。无头与测试里它是一个可设的值，结果确定。
- **主题库**：新的一种层“方案”（`scheme: { light, dark }`），按名字指明两个主题，自己不设任何令牌，站在主题的位置上（`theme = ["system", "compact"]`）。默认包里的 `system` 是 `light` 与 `dark` 之间的方案；应用自己的一对照样声明。合成的结果仍以方案的名字命名（`system+compact`），所以重新合成时还是跟随。方案不能嵌套、不能被继承、不能当覆盖层，各有诊断。
- **C++ 应用**：`AppSpec::dark_theme` 给出就跟随；`--dark` 直接用它（没有就用默认的深色）。
- **Web 宿主**：启动时从页面读 `prefers-color-scheme`、`prefers-reduced-motion`、`prefers-reduced-transparency`；页面开着的时候哪一项变了，页面说一声（第 9 类页面事件 `media`），运行时随即改。减少动态效果此前只在启动时读一次。
- **第一帧之前**：Web 包可以给页面一个深色偏好下的底色（`background_dark`），程序画出来之前页面就是深的；静态投影的文字颜色跟着取。
- **按规范没有做的**：`themes()` 的输出被规范的一致性场景钉住（主题与覆盖层两个列表），方案暂不列在里面；规范给它位置之后再加（一次规范的增补）。
- **实测**（2026-11-27；xlings 的 Chromium 159、Firefox 159、WebKit 27.2，有界面，屏幕 2；那篇 10 节的文档，清单里写 `theme = ["system"]`）：偏好深色时，程序画出来之前页面的底色已经是 `rgb(11, 17, 32)`，画布的底色相同；页面开着把偏好改成浅色，画布变成 `rgb(248, 250, 252)`，页面没有重新载入；改回深色又变回去。三个浏览器结果相同。打印仍是白底黑字。
- **还欠的**：桌面宿主把系统的深浅色报给运行时（SDL 的系统主题与它的变更事件；`omui.host.sdl3` 的另一条线合回之后做）；官网自己的深色样子（它的源码是 Live Design 的历史回放出来的，改色要作为一步设计进历史，归站点那条线）。

## 4f. 文字仍是一段文字：查找能跨词、跨行（红 167，2026-11-27）

- **事实**：按 4b 的做法（每行一个自己定位的盒子，每个词一个行内块），浏览器的页内查找只能找到单个词：Chromium 159 里 `window.find("small")` 找得到，`"small site"` 找不到；程序接管之前的那份文档两个都找得到。读者按 Ctrl+F 搜一个词组，接管之后就搜不到了——文档层要解决的正是“页面里的字搜得到”。
- **试过的六种形态**（`target/d0/find-lab`，Chromium 159 与 Firefox 159，逐一问 `window.find`）：Chromium 的查找不跨行内块、块、`<br>`、保留的换行符、自己定位的盒子（`position: absolute`）；跨普通的行内 `span`、相对定位的行内 `span`、带 `margin` 的行内 `span`、自然的折行（没有空格的中文折行也跨）。Firefox 在 4b 的形态下只在一行之内找得到。
- **做法**：一个元素的各行是它的文本流里的行内 `span`，行与行之间除了文字什么也没有；词是行里的行内 `span`。位置分三步给，仍然一批一起量、一起设：
  1. 定一行的字号（各词的自然宽度之和等于画出来的宽度之和，不超过行高），与 4b 相同；
  2. 词不再有宽度与缩放：每个词用右边距补足到下一个词的起点（可以是负的），第一个词用左边距落在它在行上的位置——字形保持原样，词仍是一段文字；
  3. 行是相对定位的：量出文本流把它放在哪，再移到它的行盒（左边对左边，字的中线对行盒的中线）。
- **文字自己的换行**（代码的一行、段落里写下的换行）：批次里这一行带 `br`，页面在它的 `span` 之后放一个换行符。代码按行复制出来仍是一行一行；词组不跨这样的行尾（Chromium；它本来也不是一句话）。
- **代价**：一批三次排版（4b 是两次）。实测没有多出可见的时间（无界面 Chromium 159，1280 px，机器空闲，从访问到程序画出再过 1 秒的长任务之和，五次的中位数，新旧各两组交替）：参考页（131 行、395 个词）旧 119／118 ms、新 114／113 ms；`/start/`（46 行）新旧都在 50–100 ms 之间。长页滚动的那条红灯（164）单独看。
- **实测**（2026-11-27，`docs` 模板带引擎的 8 个路由，三个宽度，顶部与滚下 700 px）：词的位移全部在 UI5 的界内（最大 0.86 px，中位数 0.18–0.41 px）；词组全部找得到——一行上的每行 8／8（中文页 5–6 个），行尾隔开的 1–8 个全中，中文折行处的四个字也找得到；Firefox（Playwright 的构建）在 1280 与 412 px 上同样找得到；页面没有多出滚动范围；选中一段复制出来是一句完整的话。
- **检查**：`check takeover` 在词落位之后向浏览器的查找问文档里的词组——同一段文字里相邻的两个词，在一行上的至多八个、行尾隔开的至多八个；没有空格的文字（中文、日文）取折行处前后各两个字；有一个找不到就失败并写出是哪些（`phrases.lost`）。对 4b 的形态它是红的（`/start/`，1280 px：一行上的 0／8）。
- **打印不变**：打印时行与词回到文本流（位置与边距归零），一段还是一段。

## 4g. 长页滚动的帧（红 164，2026-11-27）

- **事实（改前）**：见下表的“改前”。另：检查还不等视图到底就量的那两轮里，滚轮停下时长页的视图还没到底（主线程一帧几十毫秒，事件还在路上），42、64 个元素的字还按流排着；检查改成先等视图到底之后，改前改后都是 0。程序自己的 span（负载 1.3）：往回滚时每帧 `mirror.sync` 32 ms，其中 `mirror.take` 29 ms；JS 一侧（`mirror` 减去 `mirror.sync`）每帧不到 0.3 ms，强制排版在往回滚时一共 24 ms——时间不在 DOM 上。
- **原因**：语义树里节点的盒子是窗口坐标。视图滚一下，它里面每个节点的盒子都变了，`changes()` 把它们全报成“更新了”；镜像对每个更新的节点从头再做一遍——HTML 的映射、`text_lines()`（每个字形一个位置）、切词、把整段的行与词序列化成 JSON 来跟上次比——比完发现什么也没变，只发视图的偏移。画过的段落越多这份重算越大，往回滚时全页都画过，一帧 29 ms。
- **三级次序（D-185）**：
  - ① 从本体系出发：文档层是那一棵树的投影，一次滚动是树里的一个值（视图的偏移），在页面上也只应是一个值（元素的 `scrollTop`）。镜像把每个节点的位置记成它在所在那些视图滚动的内容里的位置（窗口里的盒子加回这一帧排版用的偏移，`Runtime::scroll_offset`）——这个量滚动时不变；一个节点除了这个位置之外与上次读到时相同（`SemanticNode` 的相等，位置差在 1/64 px 内），就不再读：比较一次，不映射、不切词、不序列化。还没画出来的文字（`text_lines()` 不回答）每次同步再问一次它的行，画出来的那一帧补上行与词。字体的修订号变了，全部重读。盒子相对父元素一律在内容坐标里算，滚动时不再有“位置与偏移各自取整带来的一个像素的来回”，§4c 里那条一像素的容差随之去掉，视图的孩子也不再因滚动而被重新放置。**取这一级。**
  - ② 前沿与组合（看过、为什么不取）：文档层虚拟化，只保留视口附近的元素（PDF.js 的文字层按页渲染）——浏览器的查找就找不到视口外的词组，正与本层的目的相反；把 DOM 的写入挪出滚动帧、空闲时再量（`requestIdleCallback`）——量出来的时间不在 DOM 上，不需要。
  - ③ 不取。

  - **三级次序（D-185）**：① 从本体系出发——一棵语义树多种渲染，不改变浏览器合成器怎样拿一块 WebGL 画布；能动的是怎样把我们的帧交给合成器，`check scroll --ways` 在同一页上量了另外四种：`desynchronized`、OffscreenCanvas 经 ImageBitmap 交给 `bitmaprenderer`、不带 alpha 的上下文、拷到 2D 画布（`drawImage`），三轮里两个间隔以上的帧（239 帧中）：现行 33、79、43；desync 56、33、35；bitmap 100、37、63；opaque 45、50、71；copy2d 48、21、35——没有一种稳定地好过现行，不采用。② 前沿——WebGPU 画布（Dawn、Vulkan，没有 ANGLE 的 GL 上下文切换）：本机的 Chromium 159 默认没有，`--enable-unsafe-webgpu` 加 Vulkan 的开关下试了一轮，负载 13–15（不可比）：长页 p99 18–27 ms，两条参照 9.5 与 9.0–20.6 ms，没有结论。③ 业界做法：就是现行的 WebGL2 画布。
- **剩下的与归谁**：
  - 在这条线上的浏览器路径（WebGL2 画布在 Linux、NVIDIA、ANGLE 上的显示）：Chromium 的，不是我们的；其余一级平台（macOS arm64 的 Metal、Windows 的 D3D11）上同一页的数没有量过，平台表标“未验证”。确定可做、未做：等机器空闲时（负载 < 2）重量 WebGPU 的天花板与 `?webgpu` 的参照，在 `check scroll` 里加一条。
  - 页面每帧主线程约 3–5 ms（负载约 10）里，文档层占 1.9–2.4 ms，其中 `semantic.changes` 0.7–1.1、`mirror.take` 0.5–0.7：一次滚动里全部约 1,100 个节点的窗口坐标都变了，变更表里便有一千来条“位置变了”，镜像再逐条比出“内容里的位置没变”。让变更表只说“视图滚了”：约 1 ms，归 `omui.semantic`／host.web 的镜像，确定可做、未做；再去掉的是调度抖动里主线程占的那一份，量不出独立的收益，不单立。
  - CPU 画布（`?renderer=cpu`）、第一轮清单的第 4 条与第 5 条不变。
- **检查**：`check scroll` 的判据——每个路由移动时显示的帧 p99 ≤ 16.7 ms（浏览器的线，D-187），并写出与显示器间隔（120 Hz：8.3 ms）的距离；视图要到底；到底后没有还按流排的元素。它对长页与短页仍是红的（上面：浏览器线上的 WebGL2 画布本身就在 16.7 ms 的边上，没有放宽判据）；结尾多印的两条参照 p99 是判断该怪页面还是怪浏览器的依据。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 行内的字宽与画布对不齐（字体回退、字距、连字） | 同一份字体数据；逐行缩放；偏差进检查。对不齐超过界限的文字（例如回退到系统字体的文字）只保证“找得到、选得中”，高亮的位置按行盒 |
| 透明文字层接了指针，挡住画布的悬停与点击 | 只有文档内容的文字接指针；非拖选的点击转发；可操作节点不接 |
| 元素多了（每行一个）拖慢同步 | 滚动不重读：节点的位置记在视图滚动的内容里，只有偏移变了的节点不再读（§4g）；行与词在文字画出来时才补上；虚拟化的列表照旧只镜像物化的项 |
| 文档层与引擎的滚动互相触发 | 每次同步带来源标记，自己引起的回声丢弃 |
