# xdef：声明式数据的内部规范（D-209，方案）

日期：2026-11-16　状态：方案。xdef 是内部代号，先作为仓库内的规范，不升为 OpenLifa 标准。关联：D-139（TS 声明、JSON 快照）、D-203–D-208（[收敛方案 §4.5](2026-11-15-convergence-first-release-design.md)）

## 1. 问题

契约、操作目录、主题、音乐、时间线、物质规则这些数据，都用 TS 声明，确定地求值成 JSON 快照（D-139）。这套做法已经是全仓库的事实标准，但有三个问题：

- **只写在 AGENTS 和各读取器里**，没有可检查的条文。每个读取器各自判断文件的格式和版本。
- **名字挂在一个产品上**。2026-11-16 核对：
  - 289 个文件、约 25 个种类都带 `.omui.` 后缀，其中 hanim 24 个、xengine 18 个、xrender 5 个；
  - 139 个 TS 文件导入 `omui/define` 或 `openmui/define`；
  - `mlibs.control` 的操作目录约定由 `omui-gen ops` 生成。

  omui 一旦单独发布，下层项目的数据就带着上层产品的名字，还要靠上层的工具来生成。
- **格式只能从文件名认出来**。文件被改名、经网络传输、内嵌进别的文件后，就认不出了。

## 2. 两层分开：容器与种类

xdef 只规定**容器**，也就是所有声明式数据共同的部分。每个**种类**的内容由它的拥有者规定，例如：

- `contract`、`native`、`view` 由 openmui 规范规定；
- `animation` 由 hanim 规定；
- `matter` 由 xengine 规定；
- `ops` 由 mlibs.control 规定。

xdef 不认识任何种类的字段。

| 容器规定 | 内容 |
|---|---|
| 文件名 | `<名字>.<种类>.xdef.{ts,json,jsonl}` |
| 格式标识 | 快照顶层的 `"$format": "<种类>@<主版本>"`，这是权威；后缀只是提示 |
| 种类登记表 | 每个种类一个拥有者、一个模式、一个主版本；同一个种类名不能有两个拥有者（lint） |
| 别名后缀 | 项目可以登记带自己标识的后缀，映射到同一个格式标识；本仓库只用规范后缀 |
| 版本 | 同一个主版本内只加字段；升主版本时，拥有者提供迁移 |
| TS 子集 | 只允许可擦除的语法；求值确定（不读时钟、随机、文件、网络）；只能导入种类拥有者的 `define` 模块 |
| 快照的规范形式 | 键的顺序、数字的写法、UTF-8、末尾换行都固定，同一份声明逐字节相同 |
| 问题 | 带 JSON 指针，错误码走 `mlibs.error` 的契约 |

**导入**：

- 种类的 `define*` 来自种类的拥有者：规范层的从 `openmui/define` 导入，实现层的从 `omui/define` 导入，hanim 的从 hanim 的模块导入，这样不跨层。
- xdef 不向 TS 暴露自己的导入：格式标识由种类的 `define*` 写入，登记写在拥有者包的清单里。这样代号 xdef 不会进入用户的源文件，以后改名不影响用户。

## 3. 名字

- **后缀与规范同名，都是 `xdef`**。按 D-208 的约定，以 `x` 开头的名字都是内部代号：名字以后可能改，功能不变。
- **后缀和 `$format` 会被持久化**，所以改名要有工具承担：
  - 仓库内，用改名子命令一次改完（RC3.14）；
  - 用户工程里，由迁移命令改写文件名和导入，并更新 `$format`。0.1 起每次改名都随附迁移命令。
- `xdef` 不与已知的扩展名惯例冲突：`.d.ts` 是 TS 的声明文件，`.snap` 是 Jest 的快照。

## 4. 规范与工具：双重保证

- **参考求值器与检查器**放在工具内核（阶段 0，D-205），不放在 omui。它们从 `omui.lang.ts` 的 QuickJS 求值和 `omui-gen` 的生成里抽出来。
- **登记表是数据**：各拥有者在自己的包里登记种类，检查器读取汇总。
- **CTS**：容器规则一套，每个种类各一套由拥有者提供。别人写的读取器也能用它们验证。
- **lint `data-format`**：后缀、登记、唯一拥有者、快照里的格式标识。

## 5. 迁移（RC3.15）

1. 规范文本和登记表；
2. 求值与生成下沉到工具内核；
3. 用改名子命令把 289 个文件和 139 处导入一次改完，不留兼容层；
4. 读取器先校验格式标识；
5. lint 0，全量通过。

0.1 发布时，后缀与格式标识随发布冻结。

## 6. 不做的

- 不做通用的模式语言：模式由种类的拥有者用 TS 类型和检查器给出。
- 不做跨种类的引用解析：引用由种类的拥有者规定。
- 0.1 不升为 OpenLifa 标准；有外部实现者时再提出。
