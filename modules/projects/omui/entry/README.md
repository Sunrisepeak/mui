# omui's programs

The composition roots of omui (component-binding §10.2): programs, not libraries — each depends on the SDK and what
it hosts, and nothing depends on it.

| Package | |
|---|---|
| [player](player) | `omui.entry.player`: runs a TypeScript application from its manifest (`[package.metadata.openmui]`), registers the official components and the script languages, and runs it with omui's options; saved files reload in place. Its entry `player` registers everything official (`register_official()`: the base components, markdown, the `fuzzy` native module); its entry `closure` registers only what the application's build derived from its scripts (`main = { from = "omui.entry.player/closure" }` with `omui.build`'s `closure()`, B7b; the app-ts template's default), and a component it left out, asked for, says how to carry it. Its program of its own, `omui-player` (`--manifest DIR`), is what the omui tool ships (E2) and, without the designer, the shared runtime (E3b: `--runtime` says its version, the specification it implements and its capabilities, runtime@1) |
| [devhost](devhost) | `omui.entry.devhost`: the development host (`omui dev`, D-154): it holds the window, the application is its render target, and the designer is linked (preview: `omui.designer`) |
| [launcher](launcher) | `omui.entry.launcher` (preview): the shared runtime's launcher (E3b, D-250), `omui-launch [--which] [APP] [-- ARGS]`. It reads what the application declares (`[package.metadata.openmui.runtime]`: `openmui = "0.4"`, the capabilities it `needs`, or one `runtime = "=0.1.0"`), finds the runtimes installed side by side (xlings: `data/xpkgs/*-x-omui-runtime/<version>/`, each with its `runtime.json`), and becomes the player of the newest that satisfies it. With none, it says why each installed one does not and the command that installs one, exit 2. It links no runtime, and is built for the fewest bytes (-Oz), held to [size.budget.xdef.json](launcher/size.budget.xdef.json)'s 200 KB by `omui-devtools check size --native -p omui.entry.launcher --budget …`: 419,704 B loaded on 2026-11-27, over it (STATUS red 145). What it reads with: each runtime's `runtime.json` in place by mlibs.json's own scanner (`Scan`: the grammar checked, a few values read where they are, no JSON parser linked; `--which` written with its `quote`), and the application's `mcpp.toml` with toml++ (76,998 B of it). The tree has no reader of TOML but toml++, and an application's package carries no JSON snapshot of its manifest; which of the two the launcher should read the declaration with is open (red 145) |
