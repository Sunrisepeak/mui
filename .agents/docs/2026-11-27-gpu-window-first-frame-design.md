# GPU 窗口的首帧（UI9，一页设计）

状态：已实施（2026-11-27），待 review。决策：D-289（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) §7 的 UI9、§9.1“GPU 窗口的首帧”；沿用 D-70（帧只在需要时出）、D-184（CPU 与 GPU 是同一份契约的两条路径）、RC3.6（设备在自己的线程上建）。上游：RM1；旁及：红 153、红 154、UI10。

## 1. 事实（2026-11-27，RTX 4080，NVIDIA 580.178.04，HDMI-0 2560×1440 120 Hz，能耗偏好 `performance`）

- **GPU 窗口慢在设备上。** `bench apps --screen HDMI-0`，hello：`app` 世界的 GPU 窗口冷启动 549 ms（p90 598）、热启动 408 ms（5 轮，其他会话的构建使 1 分钟负载在 8–28 之间）；RM1 的 10 轮是 410、355 ms；同一个程序加 `--cpu`（不建设备）98、82 ms；Slint 243、251 ms（RM1）。
- **设备挡在首帧前面。** 宿主在构造时就在另一线程上建设备（RC3.6），但窗口要等它建好、认领窗口、在主线程上建渲染器的管线之后才画第一帧。逐段（追踪）：建设备 213–259 ms（设备线程上）；渲染器的 4 条管线 8–10 ms；认领窗口 65–73 ms（SDL 让窗口与窗口管理器同步约 10 ms，其余是驱动建交换链）；随后 `SDL_SetGPUSwapchainParameters` 用 SDL 已有的参数把交换链又建一遍，48 ms。冷启动时 NVIDIA 驱动的库还要从磁盘读。
- **CPU 与 GPU 画同一张表。** mrender 的 CTS 逐场景对照两条路径：矩形差一级以内，圆角边 8 级以内（CPU 把弧压成 1/32 像素内的弦）。文字有一处已知的差别：CPU 的字形掩码放在四分之一像素上（`mrender.text` 的 phases），窗口里的 GPU 帧按轮廓在真实位置覆盖（`glyph_masks_a_live_frame`，D-188 的“不换图”）。
- **窗口可以先给 CPU 再给设备。** SDL 3.4.18：没有 `SDL_WINDOW_VULKAN` 的窗口在认领时被转成 Vulkan 窗口（`SDL_Vulkan_CreateSurface`）；X11、Windows、offscreen 的窗口自带帧缓冲，CPU 的帧不需要 SDL 的渲染器；Wayland、macOS 没有，CPU 的帧要一个渲染器，它与 SDL_GPU 不能共用一个窗口。SDL_GPU 不接受透明窗口；认领时建的交换链就是 SDR、跟随显示刷新。
- **管线缓存。** SDL_GPU 3.4.18 没有管线缓存的接口（`vkCreateGraphicsPipelines` 传的是空缓存）；NVIDIA 驱动自己的磁盘缓存在 `~/.cache/nvidia/GLCache`（本机 40 MB），Mesa 的在 `~/.cache/mesa_shader_cache`。渲染器建时只有 4 条管线，其余用到时才建：有驱动的缓存 8–10 ms，关掉它（`__GL_SHADER_DISK_CACHE=0`，相当于装好后的第一次运行）489 ms——顶层方案里“第一次 1098 ms”的那条线索就是它。

## 2. 三级次序（D-185）

**① 从本体系出发。** CPU 是确定的参考，GPU 是同一份契约的另一条路径（D-184），两者画同一张显示表；屏幕上那一帧是一个值（表的哈希与它的字节）。所以第一帧不必等设备：**由 CPU 画；设备在第一帧之后建，就绪后在静止时接管；CPU 那一帧的字节原样成为设备的帧纹理，表没变就不重画**（D-70）。从表的下一次变化起由 GPU 画。设备与渲染器的管线都在设备自己的线程上建。**结论：取这一级。**

**② 前沿与组合。** 查过的做法与取什么：

| 做法 | 现状 | 取什么 |
|---|---|---|
| 首帧前建好 GPU 上下文（并排的三家） | RM1 记录：Slint、Flutter、NSH 在本机上都由 NVIDIA 驱动画第一帧（各自的进程映射了它），启动 243–549 ms | 不取：设备的建立时间由驱动定，不由我们定 |
| 驱动的磁盘管线缓存（NVIDIA 的 GLCache、Mesa 的着色器缓存） | 两者默认开着，按管线的内容索引 | 取：它们在 SDL_GPU 之下自动生效；我们自己的 `VkPipelineCache` 要 SDL_GPU 给出接口 |
| 预先编译着色器（Impeller 的做法） | 我们的着色器在构建时编成 SPIR-V／MSL／DXIL（`mlibs.shader`），只剩驱动的后端编译 | 已有 |
| 先显示一个启动画面再换成程序的画面 | 系统或框架画一张不同的图 | 不取：那不是程序的第一帧，换图看得见 |

组合：**CPU 出首帧 + 设备与管线在自己的线程上、首帧之后建 + 驱动的磁盘缓存 + 接管时上传 CPU 那一帧、不重画。**

**③ 业界通行的做法**（首帧前建好设备与管线，与其他启动工作并行——就是 RC3.6 之后的现状）不取作终态：它的下限是驱动建设备的时间。

## 3. 设计

### 3.1 谁画、什么时候换

- 条件：渲染器为 `automatic`；窗口自带帧缓冲（X11、Windows、offscreen）；没有效果目录（效果只有 GPU 画）；没有指定 SDL 的渲染器。满足时窗口按 CPU 窗口打开，第一帧由 CPU 画进窗口自己的帧缓冲；这几帧逐行画、不用光栅的线程池（线程池的线程会为 CPU 不再画的帧一直留着；800×600 的第一帧逐行 1.9 ms，线程池连起线程 4.6 ms）。
- 第一帧显示之后才开始建设备（`GpuService::begin`）：驱动的库的读取与加载、设备的建立都不在第一帧的路径上，冷启动时也不和程序自己的读盘抢。设备建好后，同一线程接着建渲染器的管线，然后通知宿主（`GpuDeviceOptions::made`，宿主唤醒睡着的循环）。
- 接管占主线程：SDL 让窗口与窗口管理器同步、驱动建交换链，约 75 ms（RTX 4080，X11）。所以在**静止时**接管（循环睡着、没有输入到来）；一直在动的窗口在设备就绪一秒后接管——一次停顿，换掉之后一直由 CPU 画的帧。设备就绪时恰有输入的，循环之后至多 50 ms 再看一次（只等事件的睡眠不会自己回来接管）。交换链只建一次：参数与 SDL 认领时的相同（SDR、跟随刷新）就不再设（省 48 ms）。
- 接管：设备认领窗口，放掉帧缓冲，渲染器交给宿主，告诉运行时设备与档位（T2 → T4）。设备是软件光栅（`automatic` 下 CPU 更快）、认领失败（透明窗口）或没有设备时放掉它，CPU 接着画（用线程池）。
- 不满足条件的窗口照旧：构造时开始建设备，第一帧等它（GPU 被坚持、带效果、macOS、Wayland）。
- `Desktop::gpu_pending()` 说接管还没发生；`Desktop::gpu()` 说现在谁在画。

### 3.2 画面不变

- 接管时屏幕上那一帧（CPU 的）原样上传成设备的帧纹理，不画、不呈现；抓取读的是它，与屏幕上的逐字节相同。CPU 那一侧（表面、渲染器的缓存）随即放掉。表变了才由 GPU 画。上传分成约 256 KB 的带、一带等一带：整帧一次上传会让设备的暂存缓冲整块被写过、在窗口的一生里都算进私有脏页（800×600 是 1.9 MB，1896×1030 是 7.8 MB）。
- 接管后的第一张 GPU 帧与 CPU 帧的差有钉住的界限：文字 50 级（CPU 的掩码在四分之一像素上，边最多移 √2/8 像素，满对比的边是 45 级；轮廓与掩码的覆盖差 CTS 给 5 级），其余 8 级（CTS 的圆角边）。RTX 4080 上量到文字 43、其余 2。

### 3.3 管线缓存

- NVIDIA 与 Mesa 的磁盘缓存在 SDL_GPU 之下已经生效：渲染器的 4 条管线有缓存 8–10 ms，没有 489 ms。它们在设备线程上建，不在主线程上，也不在第一帧的路径上：缓存是空的第一次运行，第一帧照样是 CPU 的，接管晚到约 0.7 s。
- 我们自己的管线缓存文件要 SDL_GPU 提供 `VkPipelineCache` 一类的接口（或在 `compat.sdl3` 上打补丁）。重启条件：SDL_GPU 出这个接口，或某个平台的驱动没有自己的磁盘缓存而管线时间重新进入可见的路径。

### 3.4 与 UI10、红 154 的关系

- 这套机制把“什么时候建设备”变成了一个策略：现在是第一帧之后。UI10（用不到 GPU 的窗口不建设备）可以把它推到第一次需要 GPU 的时候：NVIDIA 的 Vulkan 驱动只要设备在，就每秒醒约 114 次（红 154 的结论），常驻内存里也有驱动的那一份。

## 4. 验收与结果（2026-11-27 01:28–01:33，10 轮，1 分钟负载 1.5–3.1）

| 项 | 判据 | 结果 |
|---|---|---|
| 首帧 | GPU 窗口到第一个呈现帧（等于定下来的画面）不晚于 CPU 窗口加一帧（8.3 ms），冷、热各自的中位数 | GPU 窗口 86.3 ms（p90 93.4）、45.8 ms（p90 50.6）；`omui-app-cpu` 84.2（86.1）、43.1（50.8）：差 2.1、2.7 ms，达到 |
| 接管 | 接管时不重画；同一张表的 GPU 帧与 CPU 帧的差在 3.2 的界限内 | `omui.host.sdl3.gpu` 的 `host_test`：接管前后呈现数不变、屏幕上逐字节是 CPU 那一帧；文字 43、其余 2，达到 |
| 静止 | 接管后主线程静止时的唤醒与 CPU 窗口同级 | 主线程 10 轮里 9 轮 0 次（一轮每秒 2.8），CPU 窗口 10 轮 0 次；进程的每秒 113.4 次都是驱动的线程 |

## 5. 风险与欠项

| 项 | 现状与应对 |
|---|---|
| 接管的约 75 ms 停顿 | 放在静止时；一直在动的窗口在一秒后停一次（`host_test`：每帧都变的窗口在第一帧后 1.1 s 接管，此前 CPU 画了 66–68 帧）。其中 10 ms 是 SDL 同步窗口的等待（窗口管理器放的位置与 SDL 记的不同），其余是驱动建交换链。要再短只能把交换链放到别的线程上建，而 SDL 的认领要在主线程上处理窗口事件：等 SDL 提供只建交换链的入口 |
| 依赖设备的内容（画在设备上的世界、画布的 `content: auto`） | 接管前是 CPU 的画法，接管后换成设备的；这类应用写 `renderer = "gpu"`，照旧等设备 |
| 常驻内存 | 同一个程序对照（`--gpu` 即 UI9 之前的路径，2 轮）：hello 的私有脏页 19.9 对 20.1 MiB、USS 71.8 对 72.0；行情板 30.9 对 31.3、USS 89.7 对 89.7。整帧一次上传时曾多出 1.3 与 6.3 MiB（暂存缓冲被写满），分带后没有了 |
| Windows 上 GDI 的帧缓冲之后由 D3D12／Vulkan 认领同一个 HWND | 本机没有 Windows：标“未验证”，随下一轮矩阵确认 |
