## 0. 核心点（review 入口）

1. **0.1.0 是整个项目第一次达到发布水平的版本**：基础库、三个引擎、omui、omui 之上的框架（站点框架、游戏层与 gongfu）、工具链、作品，一个版本、四个一级平台一起；**每个项目带着自己的标注**（稳定、预览、实验，D-189、D-199），不因某一层没到标准而整体不成立。终点是“达到发布水平”，对外发布是之后单独的决定。
2. **范围由五个贯穿切片推出**：应用、Agent 与 Live Design、站点与文档（新）、2D 世界、3D 世界；每个切片有一条人能走通、Agent 也能走通的路径（§3）。
3. **站点框架叫 oweb，是基于 omui 的独立项目**（`modules/projects/oweb`，框架层，排在 omui 之后），与游戏层同级：它只用 omui 的公开能力，缺口回主线补。它把“omui 在 Web 上做文档类内容”这件事验证到底，官网（首页加文档）是它的第一个消费者。
4. **实测改了三个判断**（§1）：接入的 Agent 今天已能完整读一页文档，丢失发生在 HTML 投影与画布接管之后——首要缺口是“文档性”；GitHub Pages 只发 gzip，体积要靠结构；官网的回放 86% 的时间是静止的，回放不等于演出。
5. **真实显示器已接通**（D0）：进程外的性能数字今后以真实显卡为准；Linux 上窗口、首帧、无障碍读回、输入法的格子可以从“未验证”转“实机”；Quay 在真实浏览器里的帧时间（RC2.1）不再被挡。
6. **次序仍是功能纵向、收口横向自下而上**（D-202）；新增的工作里，语义与投影、Web 宿主的文档层在站点框架之前。
7. **不做 HTML 模式，不走 webview**：像素全部自绘（D-140 不动）；HTML 是投影，并常驻为文档层。
8. **Live Design 的呈现分三层**（已确认）：状态、工作呈现、演出；真实工作以性能为主，演出是历史之上由 hanim 渲染的动画作品，可选、可导出。
9. **十二个维度逐项有判据、现状与动作**（§5）；没有实测的不算达到，落后的照实标注。
10. **收敛按三条线走**（§9.1）：功能（每层写明停什么、合什么、补什么、标什么）、架构（每种能力一个 owner，桌面与 Web 同一套组合机制）、质量与性能（实机优先，落后项逐个做到或标注）。
11. **创新只算有证据的**（§6.1）：30 项招牌特性里 12 项有招牌场景；0.1.0 把本版的工作直接证明的 3 项升为有证据，新增 3 项，其余写“计划”。
12. **没有“收不了”的出路**（§9.1）：本机已有真实的显卡、显示器、总线与输入法；九个落后或未测的项里四项只差测量，五项差实现，都进 0.1.0；备注只留给真实的外部约束（托管只发 gzip、驱动自身的开销、Safari 只在苹果的系统上）。
13. **约 116–147 个检查点**（§7），五个节点 P0–P4（§9.2）；十一条门，全部机械可查（§8）。它取代“两波”的排法：一个版本、多种标注（§2.3）。
14. **实施按九条工作线、五个阶段走**（§14）：每条线有唯一的归属层，每个阶段以一个纵向的演示收尾；旧方案没做完的每一项都对到了新任务（§14.5）。
18. **工具链分四层**（§4.5）：工具内核、通用的模块库、每个项目自己的入口、总入口。每个项目都有统一的命令入口，能复用的做成工具链一层的模块库；总入口倾向直接叫 `meng`，其余按二级子命令划分（§11）。
15. **关键路径是站点线，约 20 个检查点**（§15）；但执行者只有主会话加一个子 Agent，约束是总量不是依赖。外部的依赖三处：mcpp#975、macOS 与 Windows 的 CI、需要人在场的两项。
16. **自我 review 的发现**（§16）：十四条，六条已改进正文，四条转成任务，留给 review 的四条已在同日定了（§11）。
17. **文档只用一个最小核心文档集**（§4.4）：它是模板自带的样例，也是往返测试、搜索、冷启动评测与并排对照共用的语料；正式的用户文档不在 0.1.0 的任务里，之后专门梳理。

## 2. 0.1.0 是什么

### 2.1 定位

达到可以公开试用的水平：**装上 `omui`，一条命令新建应用或站点，人和 Agent 都能开发、运行、接入；世界（meng）与格斗框架（gongfu）随带，照实标着预览与实验。** 它要回答的是“这套体系整体能不能用、哪些已经站得住”，不是“每一项都到了顶”。

“达到发布水平”的含义：§8 的十一条门在本仓库里逐条通过，候选的产物从本地索引取（与实施方案 §5 第 1 条同一口径）。对外的发布动作——公共索引、镜像、公告、Action 的上架——不在本方案里。

### 2.2 范围（按层与标注）

| 层 | 项目 | 标注 | 0.1.0 里站住的 | 0.1.0 里要做完、按预览或实验标的 |
|---|---|---|---|---|
| 基础库 | mlibs | 稳定为主 | 现有的稳定面 | 代码高亮；字形子集（B9）；系统字体回退（D5） |
| 引擎 | xrender（改名 mrender） | 稳定与预览 | 2D 的 API v1；CPU 参考、WebGPU、WebGL、SVG | 描边做到不落后；对外的名字（§11） |
| 引擎 | hanim | 稳定与预览 | 现有的稳定面 | 演出的编排；Lottie 做到不落后 |
| 引擎 | meng 的内核 | 预览与实验 | 现有的范围；每个包的 README 写明局限 | 粒子、环境场（实验） |
| UI 框架 | omui | 稳定为主 | 组件、主题、语义树与投影、桌面与 Web 宿主、Agent 面、Live Design、`omui` 命令行 | 终端宿主（F2–F4）；共用运行时（E3b、E4）；Web 宿主的文档层 |

### 2.3 版本、平台与原来的排法

- **版本（已确认）**：统一用 0.1.0，清单不改。本文就是 0.1.0 的顶层方案。
- **范围（已确认）**：核心功能都做，不移出；没到标准的照样在 0.1.0 里，标预览或实验（D-199）。标注沿用三级（稳定、预览、实验；D-189，已确认）。
- **平台（已确认）**：四个一级平台（Linux x64、Web、macOS arm64、Windows x64）一起达到；二级平台（Linux arm64、Android）照现在的行。没有实机的格子按 D-201 标未验证并写毕业条件。
- **矩阵（已确认）**：一轮全绿，平台特有的红灯按根因修后只重跑受影响的行。
- **与原来排法的关系**：原来的“两波”合成一个版本、多种标注；第二波的成员照样在 0.1.0 里，只做验证与收口。原来的十三条门并入 §8 的十一条（“连续两轮”改为一轮；“发布物在公共索引”以本地索引代替）。实施方案 A–H 没做完的任务全部带进来（§7 带 † 的）。

## 4. 分层视角

每层写：它在 0.1.0 里要站住什么、现在差什么。任务号见 §7。

### 4.1 基础库（mlibs）

- **站住的**：数学、内存、几何、JSON、xdef、文字、Markdown、图像、国际化、RHI 的接口、Agent 内核、compose、构建插件的公共部分。它们是全项目的单一归属（AGENTS §2 第 3 条）。
- **差的**：
  - 代码高亮没有 owner（文档与 `code_editor` 两个消费者）；构建时切成带类别的片段作为数据，页面不带高亮器（FE2）。
  - Markdown 把 HTML 注释当正文；行内格式没有区间（FE1）。
  - `mcpplibs.os` 的进程接口在 wasm 上没有实现，挡住依赖它的程序在 Web 上链接（FE5，上游）。
  - 字形子集（B9）与系统字体回退（D5）：最小应用的字体从 0.9 MB 降到 0.3 MB 以内，中文在三个桌面平台靠系统回退显示（CF3、CF4）。
  - 收口第 9 项：从本地索引的包构建的探针。

### 4.2 引擎

- **xrender**：CPU 与 GPU 同源、像素可供 Agent 审查。0.1.0 要定的：描边（C5，做到不落后或写明并标注）；SVG 输出的坐标精度与按节点的片段（给带样子的投影用）；对外的名字（API 冻结之前，§11）。真实显示器接通后，它的窗口呈现数字要在真实显卡上重量（RM1）。
- **hanim**：唯一的通用动画归属。0.1.0 新增**演出的编排**：历史之上的一份数据，自动导演按可见变化定节奏（FE4、AG3）。Lottie（C6）做到不落后或写明。

### 6.2 新增的设计按三级次序（D-185）

只写 0.1.0 新增的设计；已有各层的三级次序在各自的文档里。

**① 原始性创新**

- **投影是渲染，常驻为文档层。** 画布界面在 Web 上弱的地方（查找、选中、链接、打印）不靠第二个渲染器补，靠同一棵树的文档投影常驻。试过的另一条路是 HTML 作第二渲染器：外观与动效不再同源，站点不再是 omui 的验证，放弃。
- **人、搜索引擎、Agent 读同一份内容，由往返测试证明。** 每页的 Markdown 是树的投影；搜索索引的单位是树里的小节，人的搜索框与 Agent 的查询共用。
- **Agent 像人一样到达。** 从哪个门进来，第一个回答都是同一份站点自述；接入时人与 Agent 看同一个页面，Agent 的查询结果人看得见。
- **演出是历史的函数。** 同一份设计历史加一份编排，出页面内的演出与导出的视频；自动导演按可见变化定节奏。
- **每一面只为它用到的付字节。** 读者付文档的，交互付引擎的，Agent 接入时才付 Agent 的文字（[首帧数据的设计](2026-11-20-first-frame-data-design.md)的推广）。
- **一个版本，多种标注。** 发布的单位是整个体系，承诺的单位是每一项能力；没到标准的照样发、照实标（D-199 的推广）。

**② 前沿加组合**：按需接管（islands 与 resumability 的思路，落在语义树的节点上）；面向 Agent 的站点索引与每页的 Markdown；WebMCP；构建时高亮；分块的静态搜索索引。

**③ 业界做法（低线）**：文档站的常规功能（侧栏、目录、搜索、多语言、深浅色、代码复制、站点地图）；发布物的校验和与构建溯源；发布说明与 CHANGELOG。

**架构：0.1.0 时的形状。**

- 五层、三级依赖只向下，项目之间无环；oweb 与游戏层是 omui 之上同级的框架，互不依赖。oweb 是独立项目，层是框架层，次序在 omui 之后；演出的音轨由引擎层的工具渲染成文件，oweb 只引用这个文件，不依赖 meng。
- 每种能力一个 owner；本版新增的四样各有归属：文档属性归规范与 `omui.semantic`，文档层归 Web 宿主，高亮归通用库，演出的编排归 hanim。
- 组合只有一套机制：槽、世界、闭包推导，桌面与 Web 相同；站点的模块、应用的能力开关、世界的裁剪都用它。
- 每个项目对外的面是契约加操作目录；命令行、MCP 与协议三个入口由目录导出（D-203）。
- 跨层接口改动数逐节点下降；拆分的演练做到底（三层各自导出、从零构建，CF6），真正拆仓是之后单独的决定。

### 9.3 次序

- 先定事实，再补地基，再立框架，再做作品，最后对账：P0 就是 RM1（真实显卡上的数）与一轮矩阵（RM4 的第一轮），它们决定后面哪些项要修。
- FE1 与 AG1 的设计先写（便宜、不依赖别的）；RM1–RM3、EN1 与 UI 线不相交，可以并行。
- RL1、RL2 不等 P3：四个平台的候选包越早由 CI 产出，平台特有的问题越早暴露。
- 子 Agent 至多两个（2026-11-26 起；此前是一个），各在自己的 worktree 里接与主线不相交的线（先是 L3 的实机线与 L6 的终端线）；简报里写明主会话正在改的共享包。
- 每个节点记九个计数器（D-202）；跨层接口改动数从 P1 起计。
- 估计只用来排次序（已确认）：每个节点按实际的比率重估余下的量，写进节点记录。

还没定的：

1. **总工具入口叫什么。** `mtools` 已有两个用得很广的同名者（GNU 的 mtools，许多发行版里有同名的命令；MongoDB 的 mtools，1,952 星），不用。候选剩 `meng` 与 `mtool`。倾向 **命令直接叫 `meng`，包叫 `meng.cli`**——与 `omui.cli` 给出 `omui` 是同一个样子；其余按二级子命令划分，二级的名字用各项目自己的名字：`meng omui …`、`meng oweb …`、`meng hanim …`、`meng mrender …`、`meng video …`、`meng gongfu …`，加总入口自己的 `meng find`、`meng subjects`、`meng mcp`、`meng inspect`。好处：少一个品牌（xtools 这个项目并进 meng 的工具，不再单立）；meng 对外本来就是“一个整体加同形的工具链层”。要处理的一点：xtools 现在静态依赖 gongfu 的工具，而 gongfu 在 meng 之上——总入口放进 meng 之后不能反过来依赖它，所以引擎之上的类型框架改为经贡献清单进入（D-203 已有这个机制）。`mtool` 的好处只是不占 meng 这个名字；它多一个要记的名字，与哪个项目的关系也不清楚。`meng` 这个命令名本机与 GitHub 的仓库名里没有查到同名的工具（没有查商标与各包管理器）。
2. **预编译的世界个数**：阅读、应用、完整三个，还是按站点推导（要编译）。等 UI6 的数。
3. **预算里的假设值**：文档页可读之前 100 KB；演出里无变化的拍 0.3 秒。由并排的实测替换。
4. **Action 放在本仓库还是单独的仓库。**

已另有去处的：高亮的实现在 FE2 的一页设计里定。

测试用的预构建浏览器进 xlings 的工具索引一事，已由别的协作者在做，不在本文的任务里；做好后 `check browser` 改用它（并入 QA0）。设计文档的整理（哪些标为已被取代）与正式的用户文档一样，留给之后专门的梳理；本文确认时不改别的文档的状态。

## 14. 实施计划

### 14.1 拆分的原则

- **按架构的层定归属，按切片定验收。** 每个任务只属于一层（一个 owner 包或项目）；它的验收是某个切片的路径往前走了一步。
- **下层的契约先于上层的功能。** 规范与语义先于投影，投影先于文档层，文档层先于站点框架，框架先于官网。
- **先量后改。** 性能与体积的任务以 P0 的实测为起点；没有数的不排优化。
- **“设”类任务先有一页设计**，按 D-185 的三级次序写，review 后再实现。
- **每个阶段以一个纵向的演示收尾**：一条真实的路径，人走一遍，Agent 不开界面走一遍。
