# 首帧之前不带的数据（红 148 的第 2、3 项，一页设计）

2026-11-20 起草，**草案，待 review**。任务：红 148（G5 的页面首帧之前 ≤ 1.2 MB），[官网方案 §6.1](2026-11-19-site-live-design-design.md#61-首帧之前的去向红-1482026-11-20-实测ddc0b49e) 的第 2、3 项。

## 1. 事实

- 页面按首屏切成两半之后，首帧之前 1,487,846 B；程序的前一半压缩后 1.14 MB，其中数据段压缩后约 352 KB。
- wasm-split 只移动函数，**数据段全部留在前一半**。代码移得走，数据移不走。
- 数据里首帧用不到、却占大头的两类：
  - Agent 才读的文字（目录说明、引导、TS 声明；D-186 要求它们是目录的数据）：字符串一类 91 KB 的主要部分；
  - 另一个后端的着色器：WebGPU 的 WGSL 与 WebGL 的 ESSL 两套都在（62 KB），一次运行只用一套。
- 页面已有按需取的通道：字体（`want_fonts`、`want_face`）由程序经宿主的钩子请求，页面去取，到了写进文件系统再通知程序。

## 2. 三级（AGENTS §2 第 10 条）

**① 原始性：一棵语义树，数据跟着需要它的那一面走。**
- 首帧只需要像素这一面；Agent 这一面（说明、声明）在 Agent 接入时才需要，而页面上的 Agent 接入本来就是异步的（`omui connect` 配对之后才有第一次 describe）。
- 所以“Agent 的文字”天然是**第二阶段的数据**：在程序里只留它的键与长度，文字作为包里的一个文件，第一次被问到时取。问到时还没到，就照“正在取”回答（describe 带 `pending` 与重试的时间），这是 D-186 的出路，不是失败。
- 后端也是一样：选哪个后端在页面加载时 JS 就知道（`navigator.gpu`），所以首帧只取那一套着色器，另一套永远不取。

**② 前沿加组合：把数据段也切开。**
- 后一半（deferred.wasm）导入前一半的内存；可以把只有后一半的函数读的数据段搬进后一半，作为它实例化时写入的主动段，地址不变。
- 难点在证明：一个前一半的函数读到还没写入的地址就是静默的错。要证明需要重定位信息（谁引用了哪段数据），wasm-split 与我们的工具今天都没有。
- 结论：**先不做**；等 ① 的两项做完再看剩下的数据。证明的工具（数据的引用者）留给 B3。

**③ 业界（低线）**：Web 应用的按需资源（代码分割出的 JSON 块、按需的着色器包）。① 就是它在本体系里的形状，区别在于语义与出路由框架给出。

## 3. 做法

| 步 | 内容 | 验收（本机） |
|---|---|---|
| 1 | 着色器：xrender 的着色器表按后端成为包里的文件（构建时由同一份 slang 生成，内容不变）；Web 宿主在页面知道后端时取那一份，首帧之前到；原生仍嵌入程序 | `xrender.vector` 测试与像素基线逐字节不变；页面首帧之前少约 30 KB；`check site-page path` 23/23 |
| 2 | Agent 的文字：目录说明、引导与 TS 声明由生成器写成一个数据文件（`agent-text@1`），程序里只留键；原生嵌入，Web 按需取；到之前 describe 带 `pending` 与重试的时间 | 契约 CTS 的文字项在两种取法下相同；`check site-page path` 里 Agent 的 describe 与之前逐字相同；首帧之前再少约 60–80 KB |
| 3 | 按需取的通道收成一个：字体、着色器、Agent 的文字都经宿主的“要一个文件”钩子，页面一处实现 | 字体的检查（官网的 fonts）照旧通过 |

## 4. 风险

| 风险 | 应对 |
|---|---|
| Agent 接入后第一次 describe 变慢 | 页面在首帧之后空闲时就取（与后一半的程序一起），多数情况下 Agent 接入前已到；没到时回答 `pending`，不阻塞 |
| 原生与 Web 两条路径的文字不同 | 同一个生成器、同一份数据；CTS 在两种取法下比对 |
| 着色器文件与程序版本不配 | 文件名带内容的散列（与程序、字体相同的做法），页面只取它的程序点名的那份 |
