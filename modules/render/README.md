# openmui.render

The rendering abstraction (module `openmui.render`, D-57): the display list of contract ⑤ (paths, paints, gradients, strokes, clips, transforms, layers with blend modes and effect parameters, glyph runs, images, external textures, node markers), resources by reference (an image store; glyphs from the text engine through `GlyphSource`), and backends. The CPU backend renders through openmui.raster, byte-for-byte the same on every platform, records pixel provenance, and reports what a CPU cannot draw (effects, external textures — spec R-3). Knows nothing of nodes or views.

**Incremental frames** (`:damage`, D-62). A `DamageTracker` compares a display list with the previous one, segment by segment (the node markers; a segment's hash covers its own commands and its children's order, its bounds are in device space) and returns the bands of rows that can differ. The CPU backend draws only those rows over the previous frame (`CpuOptions::rows`), skipping commands that cannot reach them, and the result is the full render byte-for-byte — `tests/damage_test.cpp` holds it to that for every kind of change (colours, moves with shadows, rotations under rounded clips, clips, layer opacity, z-order, nodes appearing and going, strokes), and the headless host's tests for real frames. On the 1000-node dashboard of M1 ⑤ at 1080p a one-label frame goes from 28 ms to under 2 ms (`tests/bench`). With a `Parallel` (`CpuOptions::parallel`, the host's task pool) the bands are cut into tasks drawn at the same time — each by its own pooled canvas, glyph masks resolved first on the calling thread — and the bytes are still the serial render's: every band is exact. `CpuOptions::measure` fills `RenderReport::kinds`: count and time per kind of command (`command_kind_name`), which is where a frame's raster time goes (the `ui/raster/full-1080p` benchmark reports it).


**GPU backend** (`:gpu`, D-33). `GpuRenderer::create(device)` builds its pipeline and textures on an `omui.rhi` device (any backend that takes one of `gpu_shader_formats()`); `render(list, target, resources, options)` draws the list into an `rgba8_unorm` colour target and returns the same `RenderReport`. One Slang shader (`shaders/ui.slang`, compiled at build time by `openmui.slang.rules` into every format the target's backends take) draws every primitive as an instanced quad, and the work is cut into batches only where a texture changes. What the CPU computes exactly is computed the same way: a device-aligned rectangle covers a pixel by area; gradients read the CPU's own 256-entry tables (`raster::Shader::table`) at the same index; paths, strokes, glyph masks, box shadows and non-rectangular clips are coverage from openmui.raster, placed in an atlas; layers are textures composited on pop; images sample like the CPU's nearest and bilinear. A rounded rectangle is covered by the exact area of its circles, and a rotated one by signed distance. `tests/gpu_test.cpp` renders the same scenes on both backends and holds each to a stated tolerance: within blending's rounding everywhere except rounded edges, where the CPU's chords (1/32 pixel) are at most 8 levels from the exact circle. A layer under any other blend mode is composited by a second shader (`shaders/blend.slang`) over a copy of the target beneath it, with the CPU's arithmetic: given the same pixels it gives the same bytes (the `blend arithmetic` scene). Not drawn on the GPU yet, and counted as the CPU counts what it skips: layer effects, external textures. On Metal the shaders' MSL asks for IEEE arithmetic without contraction (`openmui.slang`), as SPIR-V has it.
