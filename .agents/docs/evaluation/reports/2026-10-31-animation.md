**Benchmark summary**

Rive’s strongest advantage is its integrated authoring-to-runtime system: bones, meshes, IK, graph editing and interactive states operate together. openmui has useful native primitives but lacks comparable authoring cohesion. See [Rive’s character animation capabilities](https://rive.app/use-cases/character-animation).

GSAP’s strongest advantage is practical choreography: timeline positioning and seeking, plus dedicated layout and scroll systems. Basic seek support is therefore parity territory, not a distinguishing achievement. See [timeline seeking](https://gsap.com/docs/v3/GSAP/Timeline/seek%28%29/), [Flip](https://gsap.com/docs/v3/Plugins/Flip/) and [ScrollTrigger](https://gsap.com/docs/v3/Plugins/ScrollTrigger/).

Lottie’s strongest advantage is designer interchange and portable playback from After Effects. Feature compatibility varies by renderer, but openmui has not demonstrated an equivalent pipeline. See [Lottie’s official introduction](https://airbnb.tech/opensource/lottie/) and [renderer feature matrix](https://github.com/airbnb/lottie-web/wiki/Features).

openmui’s clearest strength is combining analytic interruption history, numerical goldens and a framework-visible clock. Its largest deficits are visual authoring and reusable character production. For the skeletal reference, Spine’s [weight editing](https://en.esotericsoftware.com/spine-weights) and [physics constraints](https://us.esotericsoftware.com/spine-physics-constraints) illustrate capabilities beyond the inspected grid-bending and lag approach. No overall performance lead over any benchmark is established.

**Specific defects and limitations observed**

- **Misleading allocation test name:** `modules/base/hanim/tests/set_test.cpp:101` says “evaluating does not allocate,” while lines 105–106 explicitly state it is only a timing smoke test. Passing it provides no measured allocation guarantee.
- **Repeated spring setup:** `modules/base/hanim/src/motion.cppm:185` constructs an oscillator for each lane on every `Spring<T>::value` call. Critical damping construction includes a 64-iteration settling search (`motion.cpp:39`). Cache coefficients for repeated sampling.
- **Nested timeline allocations:** `modules/base/hanim/src/timeline.cpp:147` creates a fresh prefix string per visit; long nested target prefixes can allocate repeatedly. The convenience `sample` at line 173 also constructs an output vector.
- **Retarget allocations:** `modules/base/hanim/src/set.cpp:87` appends history segments without a public reservation mechanism. Zero-allocation evaluation does not imply zero-allocation interruption.
- **History branching concern — inferred:** `Set::push_history` uses the old current segment’s start (`set.cpp:84`), rather than the requested retarget time. Backdated retargets need adversarial tests ensuring retained history stays sorted and superseded future segments disappear.
- **Marker mapping limitation:** `modules/base/hanim/src/timeline.cpp:134` explicitly maps nested markers only for the first forward iteration. Reverse, alternate and repeated marker semantics are incomplete.
- **Determinism leak:** `components/canvas/src/camera.cpp:55`, `:71`, `:84` and `:92` use `std::log`, `std::exp` or `std::sqrt`, bypassing the deterministic math used by hanim.
- **Overbroad continuity wording:** `modules/base/hanim/src/motion.cppm:251` describes interruption as never losing speed, but `tween_to` at line 282 initializes a new eased tween without matching incoming velocity. The velocity-continuity guarantee needs qualification.
- **Stale documentation:** `modules/base/hanim/README.md:3` says standard-library-only, despite the `openmui.math` dependency. `src/set.cppm:8` says channels retain only current motion, contradicting its history implementation and later API comments.
- **Character weighting limitation:** `mgame/gongfu/present2d/src/present2d.cpp:900` derives bend weights from distance along a bone; successive bends are applied sequentially. This is substantially less controllable than authored normalized weights.
- **Secondary motion limitation:** `present2d.cpp:742` recomputes a complete earlier pose for each following bone. This scales poorly with many followers and approximates lag rather than providing a general spring-chain model.
- **Image readability:** in `fighting-mo-level3__02-29-palm.png`, the black impact slash obscures the central hand/chest contact. In fighting `anim-0006.png`, the eye panel conceals both fighters’ upper bodies. These choices make pose and contact evaluation difficult.
- **Evidence limitation:** promo `anim-0045.png` demonstrates scene density, and `anim-0068.png` demonstrates a styled interface, but neither proves camera continuity, spring quality or transition timing. No site glyph-switch sequence was supplied.
