# openmui 特色、旗舰作品、可拔插架构与管线编排

> 状态：设计 review。决策 D-63 到 D-67，待决问题 Q-15 到 Q-18（编号接总体架构文档）。
> 前置阅读：[实施计划](2026-10-26-openmui-implementation-plan.md) §6（动画）、§7（渲染）、§13（展示）；[规范](2026-10-26-openmui-spec-design.md) §7（契约⑤）。

本文回答三个问题：

1. openmui 的特色到底是哪几条？每一条拿什么来证明，而且证明它的东西本身就有用？
2. 液态玻璃（iOS 26 的 Liquid Glass）这类效果怎么做？框架要提供什么通用能力？
3. 框架怎样做成"一切都是可替换的组件"，并且把一帧的流水线做成可以编排的管线？

---

## 1. 原则：每个作品都是双视角（D-63）

**一个作品同时是真实可用的东西和框架的展示。** 不做只为演示而存在的 demo。每个旗舰作品都要满足四条：

| 视角 | 要求 |
|---|---|
| **真实价值** | 有人会因为它本身去用：开发工具、组件、内容、宣传片。有维护、有文档、有测试，进入发布 |
| **展示能力** | 它的核心体验就是某一项框架特色；把这项特色拿掉，作品就不成立 |
| **视觉冲击** | 有一个 3 到 10 秒就能看懂、值得转发的画面（"招牌镜头"），录屏可以直接做成短视频或动图 |
| **可验证** | 招牌镜头能在 headless 下确定地重现：同一个种子、同一份输入，得到逐字节相同的帧，所以宣传素材本身也是测试 |

宣传片（S5）是这条原则的样板：它是框架的介绍片，同时片子本身就是用 openmui-video 实时渲染出来的。下面每一项特色都按同样的方式配一个作品。

## 2. 特色清单和旗舰作品

### 2.1 九项特色

| # | 特色 | 一句话 | 现在的代码基础 |
|---|---|---|---|
| F1 | **统一语义层** | 像素、无障碍、agent、测试是同一棵语义树的四种渲染 | 语义树、紧凑树、查询、录制和回放、H0 到 H3 |
| F2 | **Agent 原生** | 应用自带 agent 接口；动作分效果等级，不可逆的动作必须由人确认 | `openmui.tree@0.1`、`needs-answer`、动作日志、`omui agent` |
| F3 | **确定性** | 同样的输入在三个平台上得到逐字节相同的像素；任何一帧都可以直接算出 | CPU 参考光栅器、固定哈希、精确的增量帧（D-62） |
| F4 | **强动画** | 动画是时间的纯函数；所有可视属性都能动；粒度可以到字形和像素 | `openmui-anim`、OKLab、通用属性过渡（D-60） |
| F5 | **性能和可观测性** | 增量帧精确且快；每一帧都可以测量、追踪和检查 | damage 行带、并行行带、trace、帧阶段耗时、bench 预算（D-59、D-62） |
| F6 | **风格化 GPU 渲染** | Slang 效果是一等公民，参数就是可以动画的属性 | 显示列表的图层和效果参数；GPU 路径在 M4 |
| F7 | **无限画布和富文本** | 上千个 Markdown 窗口，平滑缩放，LOD | 文本引擎、虚拟化；画布在 M4 |
| F8 | **契约优先和多语言** | 组件先写契约，C++ / TS / Python / Lua 的绑定由生成器产出 | `omui-gen`、`openmui.rules`、模板 |
| F9 | **可拔插、可编排**（本文新增） | 每个环节都是可以替换的组件；一帧的流水线是可以编排的管线 | `modules/*` 独立组件、`render::Parallel`、`GlyphSource`、`Stages` |

|---|---|---|---|---|

| F9 | **管线工坊**（`tools/pipeline`，§4） | 查看和编辑一个应用的帧管线：每个阶段的插件、耗时、输入输出 | 应用运行时把 CPU 后端换成 GPU 后端、把动画引擎换掉，画面不中断；每个阶段的耗时柱同步跳动 | M4 |

游戏 S4《组件打砖块》保留，它是九项特色的导览，每一关的玩法对应一项特色。

**这些工具都用 openmui 自己写**（D-61）：Inspector、Perf Lab、Motion Studio、管线工坊共用一个外壳，通过 agent 协议连接目标应用，既能单独运行，也能作为叠加层嵌进目标应用里。它们同时是 F6（玻璃工具栏）、F7（画布）、F4（时间轴）的用户，所以每个工具都在展示不止一项特色。

### 2.3 传播物

每个旗舰作品都产出三样东西，由 CI 在 headless 下渲染，作为发布产物：

- **招牌镜头**：10 秒以内，1080p60 的视频和动图，带确定性哈希；
- **一张图**：可以直接放在 README 或社交媒体上；
- **一行命令**：`mcpp run -p <作品>` 或 `omui <工具>`，看到的人可以马上自己跑。

## 3. 液态玻璃：原理和框架能力（D-64）

### 3.1 它是什么

Apple 在 2025 年发布的 Liquid Glass 不是简单的毛玻璃（背景模糊）。它看起来像一块有厚度的透明材料：

| 现象 | 渲染上的做法 |
|---|---|
| **折射（透镜）**：边缘附近，背后的内容被弯折、放大 | 用形状的有符号距离场（SDF）算出每个像素离边缘的距离 d 和法线；按一条高度曲线 h(d)（圆弧或超椭圆的倒角）得到表面的倾斜；按折射率偏移背景的采样坐标 |
| **色散**：边缘出现彩色的镶边 | R、G、B 用略有不同的折射率分别采样 |
| **模糊**：有的变体带磨砂效果 | 背景先做一组逐级模糊（dual Kawase），按参数在不同级别之间插值 |
| **高光和边缘光**：随着光的方向和设备倾斜变化 | 用法线和光的方向算 Fresnel 加镜面高光；内边缘加一圈细亮线和内阴影 |
| **自适应着色**：在亮的背景上偏暗，在暗的背景上偏亮，保证文字可读 | 统计背景的亮度（低分辨率的平均值），据此调整色调、饱和度和前景内容的颜色 |
| **液态融合**：两个玻璃元素靠近时像水滴一样连在一起，分开时拉断 | 一组玻璃形状的 SDF 用平滑最小值（smooth min）合成一个形状，在一次绘制里完成 |
| **弹性**：按下时轻微形变、回弹 | 形状参数和效果参数都是属性，用 spring 做动画（D-60） |

所以：**是的，它是 GPU 上的风格化渲染**，核心是"读取背后的画面再按形状做变换"（backdrop effect）。只靠模糊做不出来。

### 3.2 框架提供的通用能力

液态玻璃本身是一个组件，但它依赖的几项能力是通用的，其他效果也会用到（水波、放大镜、热浪扭曲、聚光灯、霓虹的 bloom）：

| 能力 | 内容 | 落在哪里 |
|---|---|---|
| **背景输入**（`OMUI_EXT_backdrop_effect`） | 效果的 `EffectInput` 多一张纹理：节点下方、范围外扩一圈之后已经画好的内容。渲染器在这个节点之前截断，把背景渲染到纹理里 | 规范契约⑤的扩展；`modules/render` |
| **形状输入** | 效果拿到节点形状的 SDF（圆角矩形、胶囊、超椭圆，或者路径） | 契约⑤；`EffectInput.shape` |
| **效果组** | 一组节点的形状在一次效果里合成（平滑最小值）：`glass_group` 容器 | 显示列表加一条 `PushEffectGroup` |
| **模糊金字塔** | 背景的逐级模糊被同一帧里的多个效果共享 | render 的图层缓存 |
| **效果参数可以做动画** | 参数就是属性：厚度、折射率、模糊、色散、光的方向、着色 | 已经由 D-60 支持 |
| **damage 的依赖** | 背景效果依赖它下面的内容：下面任何地方变了，效果的范围也算变了 | `DamageTracker`：带背景输入的段，和任何 damage 区域相交时，自己也算 damage |
| **CPU 参考实现** | 同一套数学在 CPU 上也要能算，保证金图和跳转一致性 | Slang 的 CPU 目标（Q-15），或者手写的参考实现 |

### 3.3 组件

`effects/liquid-glass`（包 `openmui-effect-liquid-glass`，契约优先）：

```toml
# liquid_glass.contract.omui.toml（节选）
name = "liquid_glass"
role = "group"
children = "any"
[props]
thickness  = { type = "f32", default = 12,   doc = "玻璃的厚度，决定边缘的折射有多强（逻辑像素）" }
ior        = { type = "f32", default = 1.45, doc = "折射率" }
blur       = { type = "f32", default = 0,    doc = "磨砂程度：背景模糊的半径" }
dispersion = { type = "f32", default = 0.3,  doc = "色散：0 关闭" }
tint       = { type = "color", default = "#ffffff1a" }
light      = { type = "vec2", default = [0.4, -0.8], doc = "光的方向，可以绑定到设备倾斜" }
radius     = { type = "f32", default = 24 }
adaptive   = { type = "bool", default = true, doc = "按背景亮度调整着色，保证内容可读" }
```

```cpp
omui::glass_group({.smoothness = 18}, {
    omui::liquid_glass({.id = "play", .radius = 28}, {omui::icon({.name = "play"})}),
    omui::liquid_glass({.id = "seek", .radius = 20, .blur = 4}, {omui::slider({.id = "time"})}),
});
```

- **语义不变**：玻璃只改变外观；它的语义节点就是普通的分组，agent 和无障碍看到的树和没有玻璃时完全一样（S 级用例）。
- **减少透明度**：系统设置要求减少透明效果时，玻璃退化成不透明的面板，这条进测试。
- **指标**：核显上 1080p、10 个玻璃元素、120Hz；每个元素的 GPU 开销进 bench 报告。
- **真实使用者**：Inspector 的浮动工具栏、视频播放器的控件、宣传片的"风格"一章、风格画廊的玻璃风格包。

## 4. 可拔插架构和管线编排

### 4.1 目标（D-65）

**框架的核心只规定骨架：组件模型、几种数据契约、管线。其他所有东西都是可以替换的组件。** 动画引擎、布局引擎、文本引擎、光栅器、GPU 后端、宿主、效果、组件、编解码器、脚本语言、agent 传输都是插件。好处有三条：

1. **通用性**：每个插件只依赖接口，天然可以单独使用（`modules/*` 已经这样做了：anim、layout、text、render 都不知道 UI 的存在）。
2. **可替换**：换一个动画引擎、一个布局算法、一个渲染后端，不需要改其他部分；只要通过这个插件种类的一致性测试（CTS）。
3. **可分析**：每个插件都有自己的 trace 类别和日志类别；管线按阶段计时；性能问题能直接定位到某个阶段的某个插件。

### 4.2 最小核心规范（契约⑦：插件与管线）

规范增加第 7 个契约，只规定最核心的东西：

| 内容 | 规定 |
|---|---|
| **插件的身份** | `name@version`、种类（kind）、实现的接口和版本（`omui.anim.engine@1`）、需要的接口、能力 |
| **插件清单** | `<名字>.plugin.omui.toml`：上面这些信息，加上配置项的 schema；契约优先，绑定由生成器产出（和组件一样） |
| **接口** | 每个种类一份接口说明：方法、数据契约、调用粒度、线程要求；C++ 用 concept 表达（静态绑定，零开销），C ABI 用带版本号的函数表 `OmuiPluginV1`（动态加载和其他语言） |
| **生命周期** | 创建、配置、启动、停止、销毁；错误用 `expected` 返回，不抛异常 |
| **可观测性** | 每个插件声明自己的 trace 类别和日志类别；管线自动为每个阶段加 span |
| **一致性** | 每个种类有自己的 CTS：例如动画引擎必须是时间的纯函数（任意跳转、结果确定），光栅器必须满足 B 级逐字节一致和行带精确 |

**调用粒度规则**：插件之间的调用按阶段或按批进行（每帧、每个子树、每个字形串），**不按节点或像素进行**。所以运行期的动态分派每帧只有几十次，符合"热路径没有虚函数"的规则。热路径内部是插件自己的代码。

### 4.3 插件种类

| 种类 | 接口 | 现在的实现 | 可以替换成 |
|---|---|---|---|
| `component` | 契约（`*.contract.omui.toml`） | ui-base 的 14 个组件 | 第三方组件包 |
| `animation-engine` | `omui.anim.engine`：通道的创建、目标、求值、是否稳定 | `openmui-anim`（解析解） | 物理模拟引擎、关键帧引擎、外部的动画系统 |
| `layout-engine` | `omui.layout.engine`：样式、测量回调、增量布局 | `openmui-layout`（flex、grid、stack） | Yoga 兼容引擎、约束布局 |
| `text-engine` | `omui.text.engine`：排版、`GlyphSource` | `openmui-text`（HarfBuzz） | 系统文字栈（CoreText、DirectWrite） |
| `damage` | `DisplayList` × 2 → 行带或矩形 | `render::DamageTracker` | 按图块的 damage、GPU 用的矩形 damage |
| `raster` / `renderer` | `DisplayList` → `Surface` / 纹理 | `CpuRenderer`（加 `Parallel`） | `rhi` 上的 GPU 渲染器 |
| `rhi-backend` | `omui.rhi` | M4：rhi-sdl | Vulkan、Metal、D3D12、WebGPU、GLES |
| `effect` | Slang 效果 + `EffectInput` | M4 | 液态玻璃、霓虹、CRT…… |
| `host` | 契约④ | headless、SDL3 | OpenSAL、Web、嵌入式 |
| `codec` | 图片和视频的编解码 | libpng | ffmpeg、硬件编码 |
| `transport` | agent 协议的传输 | 本地套接字（`mcpplibs.os`） | MCP、WebSocket |
| `script` | 脚本薄接口 | M3 | TS、Python、Lua |
| `stage` | 管线阶段（§4.4） | 运行时内部的各个阶段 | 任何自定义阶段 |

### 4.4 管线编排（D-66）

一帧是一张由阶段组成的有向无环图。每个阶段是一个 `stage` 插件，声明自己读写的**带类型的资源**：

```
输入 ─▶ 计时器 ─▶ 对账 ─▶ 动画 ─▶ 布局 ─▶ 范围 ─┬─▶ 语义 ─▶ agent / 无障碍
                                              └─▶ 绘制 ─▶ damage ─▶ 光栅化或 GPU ─▶ 呈现
                                                                          └─▶ 录制 / 编码（视频）
资源：Events、NodeTree、Animations、LayoutTree、Bounds、SemanticDelta、DisplayList、Damage、Surface / Texture、Frames
```

用数据文件描述（`<名字>.pipeline.omui.toml`）：

```toml
# desktop.pipeline.omui.toml
name = "desktop"
[[stage]]
name = "animate"
plugin = "openmui-anim"            # 动画引擎是一个插件
[[stage]]
name = "raster"
plugin = "openmui-render.cpu"
after = ["damage"]
config = { parallel = true, rows_per_task = 64 }
[[stage]]
name = "present"
plugin = "openmui-host-sdl3.present"
```

- **校验**：加载时检查每个资源都有生产者、类型匹配、图里没有环；静态管线在编译期用 `consteval` 检查。
- **现有概念统一成管线**：headless 的 H0 到 H3 就是四条长度不同的管线（H0 停在语义，H1 停在范围，H2 到光栅化，H3 再加 agent）；视频渲染是"去掉呈现、加上编码"的管线；CPU 和 GPU 只是光栅化阶段换了一个插件。现在运行时里的 `Stages` 枚举会迁移到这里。
- **并行**：没有依赖关系的阶段（语义和绘制）可以同时执行；阶段内部可以用任务池（光栅化的行带已经这样做了）。
- **可观测性**：调度器为每个阶段自动加 trace span，并记录每个阶段的耗时，`omui agent stats` 和管线工坊直接显示；bench 的预算可以按阶段写。
- **热替换**：阶段之间只通过资源交换数据，所以运行中可以替换一个阶段的插件，下一帧生效（管线工坊的招牌镜头）；替换失败就回退到原来的插件，并记录诊断。

### 4.5 和现有代码的关系

现有代码已经满足这套架构的大部分前提，所以迁移是渐进的，不需要重写：

| 已经满足 | 还需要做 |
|---|---|
| `modules/*` 都是独立组件，只依赖标准库和彼此 | 契约⑦写进规范：插件清单的 schema、接口版本和能力协商 |
| 渲染器通过 `GlyphSource`、`Parallel` 两个接口和外部交换，不依赖 core | 新增 `runtime/pipeline`（`openmui.pipeline`）：资源类型、阶段接口、调度器、校验、自动 trace |

## 4A. 细粒度动画的基础设施（D-60 的落地，D-68）

目标：任何对象默认就能做动画，粒度到字形和像素，**不需要组件配合**，以后加组件、加效果、加 GPU 路径都不用回头改组件。做法是把子对象层和像素层放在显示列表和运行时上，而不是放在各个组件里。

### 4A.1 显示列表记录字形的来历

- `render::Glyph` 除了字形号和位置，还记录它来自源文本的哪个字节（`cluster`），以及它在段落里是第几个字素、第几个词、第几行。由 `typeset::Paragraph` 在排版时填好。
- 有了这些，字形层的“域”（逐字形、逐字素、逐词、逐行）和“文字范围”（字节区间）就可以在任何组件画出的文字上得到，选区、无障碍和逐字动画用的是同一份数据。

### 4A.2 逐字形的样式在命令里

- `DrawGlyphs` 可以带一组逐字形样式：绕字形原点的仿射变换、透明度和着色（覆盖颜色的权重）。不带时和原来完全一样。
- CPU 渲染器、命令哈希和 damage 都认这组样式，GPU 路径以后用实例数据实现同样的语义，所以动画后的文字和静态文字走同一条路。

### 4A.3 运行时的字形动画（子对象层）

- 任何节点都可以有字形动画，包括：
  - 一个域（字形 / 字素 / 词 / 行）和一个可选的字节范围；
  - 起点和终点状态（位移、缩放、旋转、透明度、颜色）；
  - 过渡（tween 或 spring）、错峰间隔和顺序（正序 / 倒序 / 从中间 / 带种子的随机）。
- 组件照常画文字；运行时在这个节点录制完之后，按 `f(t, i)` 改写它的字形命令。
- 它是时间的纯函数：能跳转，受时间控制（暂停、慢放、逐帧）影响，进 `animating` 状态，结束后节点不再每帧重画。

### 4A.4 效果注册表和图层（像素层）

- `render` 里有一个效果注册表（插件点，D-65）。效果是参数的纯函数（进度、种子……），在图层上逐像素计算，有确定的 CPU 参考实现。
- 内置效果：溶解、擦除、径向显现、位移、噪声、色散、模糊、像素化，以及粒子（图层的像素拆成粒子，按 `f(p, i)` 散开或聚合）。
- 任何节点的 `effect` 属性：运行时把它的子树包进带效果的图层；效果参数是普通属性，可以做动画。
- GPU 路径（M4）：同一个注册项对应 Slang 的片元或 compute 着色器；粒子用 compute，一个线程一个粒子；和 CPU 金图对比（容差写明）。

### 4A.5 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| ① | 字形来历 + 逐字形样式（render、text） | 静态文字的金图不变；带样式的字形逐字节确定；哈希和 damage 覆盖 |
| ② | 运行时字形动画 | 任何组件（`text`、按钮标签、Markdown 段落）不改代码就能逐字动画；跳转一致；暂停 / 逐帧有效 |
| ③ | 效果注册表、`effect` 属性、粒子 | 每个内置效果有金图；跳转一致；参数动画；第三方效果可注册 |
| ④ | GPU 路径（M4） | 和 CPU 金图在容差内一致；粒子 compute |

## 5. 决策

- **D-68** 子对象层和像素层是运行时和显示列表的基础设施（见 4A）：字形带来历、命令带逐字形样式、效果有注册表；组件不需要为了动画做任何事。

| 编号 | 决策 |
|---|---|
| D-63 | **每个作品都是双视角**：既是真实可用的工具、组件或内容，又是某一项框架特色的展示；每个作品要有招牌镜头、可以确定地重现，并产出视频、图片和一行命令三样传播物。九项特色和它们的旗舰作品见 §2.2 |
| D-64 | **液态玻璃是一个效果组件**（`effects/liquid-glass`），建立在通用能力之上：背景输入（`OMUI_EXT_backdrop_effect`）、形状 SDF 输入、效果组（平滑合并）、共享的模糊金字塔、damage 依赖；它只改变外观，语义树不变；减少透明度时退化成不透明面板 |
| D-65 | **可拔插架构**：核心只规定组件模型、数据契约和管线（规范增加契约⑦：插件与管线）；动画引擎、布局、文本、damage、光栅化、GPU 后端、宿主、效果、组件、编解码、传输、脚本都是插件；插件之间按阶段或按批调用，不按节点或像素调用；每个插件种类有 CTS、trace 类别和日志类别 |
| D-66 | **管线编排**：一帧是由 `stage` 插件组成的有向无环图，阶段之间交换带类型的资源，用 `<名字>.pipeline.omui.toml` 描述，加载时校验；headless 的 H0 到 H3、视频渲染、CPU 和 GPU 都只是不同的管线；调度器为每个阶段自动计时和追踪；阶段的插件可以在运行中替换 |
| D-67 | **工具共用一个外壳**：Inspector、Perf Lab、Motion Studio、管线工坊、组件工坊用 openmui 写，共用外壳和 agent 连接，可以单独运行，也可以嵌进目标应用作为叠加层；每个工具都有对应的命令行（D-61） |
