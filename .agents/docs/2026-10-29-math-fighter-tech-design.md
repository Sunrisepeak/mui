# 数学库，以及格斗人物的表现技术：打击、姿态、动作、物理、模型与骨骼、动画

日期：2026-10-29。起因：维护者的两条要求——

1. 把项目里分散的数学和数值计算（向量、矩阵、插值、随机数、确定性函数……）抽成 `modules/base/math`，统一支持，需要性能的地方可以用 GPU（compute shader，可选 CUDA）或其他并行计算，便于管理和优化；
2. 格斗游戏的人物打击效果、姿态细节、动作设计、静止画面里的动感、受击姿态、特效、音效、高性能物理、精细的人物模型和骨骼绑定、动画，以及它们的基础设施，都要按高标准设计；从系统架构、性能、表现力、简洁优雅而不丢细节和功能几个角度分析和架构。

这份文档是这两件事的方案，和[严格的验收评分表](2026-10-29-fighting-acceptance-rubric.md)、[素材管线](2026-10-29-fighting-art-pipeline-design.md)一起读。新增决策 D-87、D-88，待决问题 Q-30、Q-31（§9）。

## 1. 现状：数学散落在各处，人物技术长在一个包里

**数学。** 现在至少有六处各写各的：

| 在哪里 | 有什么 | 问题 |
|---|---|---|
| `hanim:math`（`hanim::dm`） | 逐位确定的 exp、log、sin、cos、atan、atan2、cbrt、pow（fdlibm 算法，只用五种正确舍入的运算） | 只有动画在用的那几个；没有 asin、acos、tan、hypot；挂在动画引擎名下，别人要用就得依赖动画 |
| `openmui.geom` | Point、Size、Rect、Affine、Color | 界面的几何和通用的向量、矩阵混在一起；只有 float |
| `gongfu:fixed` | Q16.16 定点数 | 好，但只有格斗框架能用 |
| `gongfu.present2d`、`fx.cpp`、`hanim:path` | Catmull-Rom 各写一份 | 三份实现，三套边界处理 |
| present2d（4 处）、breakout 的 sim、markdown-wall、gongfu.ai、测试 | splitmix64 把整数变成 [0, 1) 的小函数，各抄一份 | 抄了 8 份以上 |
| `render.vector` 的网格接缝、present2d 的两骨 IK 和蒙皮 | 多边形外扩、余弦定律、线性混合蒙皮 | 通用算法长在特定的包里，别人复用不了，也没法统一做 SIMD 或 GPU |

**人物技术。** 骨骼、片段、IK、蒙皮、跟随、特效、切入画面、演出都在 `gongfu.present2d` 一个包里（约 3500 行）。能用，但：

- 骨骼动画是通用能力（界面里的吉祥物、教程动画、mgame 的其他游戏都要），却只能通过格斗框架用；
- `CinematicLook` 里还有按角色写死的字段（时钟、棱镜、碎裂、云、印章），和新做的通用特效（`[fx]`、面板）并存；
- 每帧在 CPU 上逐顶点蒙皮、每个三角形一次填充，两个人物几千个三角形还够，人物再精细就不够了。

## 2. 原则

- **一个概念一个实现，放在它所属的最低层。** 向量、矩阵、插值、随机数在 math；骨架、蒙皮、约束在 rig；格斗专有的（帧数据、受击框烘焙、演出时间线）留在 gongfu。依赖只向下（D-82）。
- **确定性是分级的，而且写在类型和命名空间上。** 进入模拟、回滚、固定像素和固定声音的计算用逐位确定的实现；只影响画面且允许容差的计算可以用快速实现、SIMD 或 GPU。调用的地方一眼能看出是哪一级，不靠注释。
- **画面是状态的纯函数**（D-85）。物理、二级运动、粒子如果只是表现，也要能从状态和帧号重新算出来，或者由已有的 `Effects` 历史推出，回滚之后画面一样。
- **数据驱动，通用原语组合出角色差异。** 角色的不同来自数据（姿态、特效、演出、声音），不是代码里的 `if (角色 == 刻)`。
- **先有 CPU 参考实现，再有加速实现，用参考实现验收加速实现。** 和渲染器的 CPU 参考 / GPU 路径一样（D-81）。
- **性能声明要有基准和预算**（D-59）：`tests/bench` 里的基准、`budgets.bench.omui.json` 里的预算，CI 检查。

## 3. `modules/base/math`：`openmui.math`

独立组件（D-55）：只依赖标准库，可以拆成独立仓库。包 `openmui.math`，命名空间 `omui::math`，`import openmui.math;`。

### 3.1 内容：先小后大，有使用者才加

第一版只收已经有使用者、已经被抄了好几份的东西；其余等真正有使用者时再加（评审意见：分区不能防止它变成杂货铺）。

| 分区 | 第一版 | 以后（有使用者时） |
|---|---|---|
| `:det` | 从 `hanim::dm` 移来：exp、log、sin、cos、atan、atan2、cbrt、pow、sqrt、`turn`（最短转角）、`mix`；**写明每个函数的定义域和误差界**（现在的 sin、cos 对大角度的归约是为动画取舍过的，pow 只对非负底数有定义） | asin、acos、tan、hypot、双曲函数 |
| `:fixed` | 只在 Q-30 定了之后：`Fixed` 的溢出、最小值取负、除零、转换的行为全部写明并测试（现在的 Q16.16 在这些边界上没有检查） | Q32.32（需要可移植的宽整数）、定点三角函数（查表在编译期生成，表本身的哈希固定） |
| `:vec` | `Vec2<T>`、`Affine2<T>`（现在 present2d、fx、render 各自展开写的那些） | Vec3/4、Mat4、Quat（3D 时） |
| `:curve` | Catmull-Rom（统一现在的三份） | 贝塞尔、弧长参数化、拟合 |
| `:random` | 一个按索引取数的 `unit(seed, i)`（统一现在的八份） | 分布、泊松盘 |

**不放进 math 的**：蒙皮属于 `openmui.rig`；粒子积分属于用它的子系统（特效、物理）；多边形外扩和三角化属于几何或离线网格处理；噪声、最小二乘、多种随机数家族等有使用者再说。

**确定性分三级**（评审意见：`double + det` 本身不够）：

| 级别 | 用在哪 | 要求 |
|---|---|---|
| 模拟精确 | gongfu 和 mgame 的模拟、回滚、联机、回放 | 定点数或只用正确舍入运算的 double；编译选项（`-ffp-contract=off`、不用 fast-math、默认舍入模式、不把次正规数清零）由**使用者的翻译单元**也遵守，lint 检查清单；支持的工具链列明 |
| 画面精确 | 固定像素和固定声音的测试、README 媒体 | 整条链都确定：素材解码、采样、混合、光栅、二级运动、特效；GPU 特效要么有确定的 CPU 版本，要么不出现在精确截图里 |
| 画面容差 | GPU 路径、实时预览 | 和 CPU 参考按容差比较 |

`openmui.geom` 的像素语义和默认值保留，别名只在确实等价的类型上做，不承诺“换成别名 API 就不变”。

### 3.2 加速：SIMD、多线程、GPU

批量函数是加速的入口，单个向量运算不做加速（太小，函数调用的开销就比计算大）。

| 后端 | 放在哪 | 用来做什么 | 确定性 |
|---|---|---|---|
| 标量参考 | `openmui.math`（`:batch`） | 一切；测试的基准答案 | 逐位确定 |
| SIMD | `openmui.math`（`:batch` 的 SIMD 分区，按平台由清单选择，`if constexpr` 分派；GCC 16 的 `std::simd` 可用时用它，否则用编译器向量类型） | 蒙皮、粒子、批量变换、音频的块处理 | 只用不改变舍入的运算（不用 FMA、不重排归约）时逐位等于参考实现；会改变结果的（近似倒数、乱序归约）单独命名 `fast_*` |
| 多线程 | `openmui.math.parallel`（依赖 `taskflow`） | 大批量（上万个元素）：特效粒子、网格烘焙、离线渲染 | 按固定的分块切分、固定的顺序合并，结果和单线程一样 |
| GPU compute | `modules/gfx/compute`（`openmui.compute`，gfx 层，基于 `omui.rhi` 的 compute pass 和 Slang） | 只影响画面的大批量：几万个粒子、布料和头发的显示用模拟、网格变形、后处理 | **不逐位确定**；用 CPU 参考实现按容差验收（和渲染器的 GPU 路径同样的规则） |
| CUDA | `modules/gfx/compute/cuda`（可选插件，运行时探测，没有就退回 compute shader 或 CPU） | 单独论证的离线实验（例如自动蒙皮权重）。**不用于 bot 对战**：那会是第二个模拟器，要做等价测试；平衡模拟用 CPU 多线程 | 不确定；只用于离线 |

规则：**模拟（gongfu 的帧、mgame 的模拟）永远走确定的 CPU 路径**；GPU 和 CUDA 只做表现和离线工作。这样回滚、联机、回放、固定像素都不受影响，同时大批量的表现计算可以放到 GPU 上。

一个批量函数的 Slang 版本和 C++ 参考版本是两份要维护的实现，不是“写一次”；它们放在一起，测试逐元素比较（容差写在测试里）。**GPU compute 只在测量证明值得之后才上**：算上上传、同步和回滚后的恢复，CPU 的 SIMD 版本更慢时才换。

### 3.3 迁移

1. 建 `openmui.math`，先放 `det`、`random`、`curve`、`vec`、`geom2`、`numeric`，带测试（数值精度对照高精度参考、逐位固定的哈希）；
2. `hanim::dm`、`geom` 的向量和矩阵、各处的 `unit()` 和 Catmull-Rom 改成用它（固定像素不变，作为迁移正确的证明）；
3. `:batch` 和 SIMD：先做蒙皮和点变换（§5.3 用），基准对比标量；
4. `openmui.compute`：粒子和网格变形的 compute 路径；
5. CUDA 插件：自动蒙皮权重和大规模 bot 对战（按需要）。

lint 增加规则 `math`：math 以外的包不再自己写 splitmix、Catmull-Rom、fdlibm 函数（按函数特征检查）。

## 4. 人物技术的分层

```
openmui.math（基础）          向量、矩阵、曲线、随机、确定性函数、批量计算
openmui.rig（基础，新）        骨架、姿态、蒙皮网格、约束（IK、注视、跟随、弹簧链）、混合、重定向
openmui.compute（gfx，新）     GPU 上的批量计算（粒子、变形）
render.vector / render.mesh    2D 矢量；带骨骼蒙皮的网格绘制（新的渲染特性）
mgame.physics                  确定性物理（自写，S4 已有）；表现用的物理（布料、头发、碎片）
gongfu.present2d               格斗的画面：外观 = rig + 片段 + 打击 + 特效 + 演出；纯函数
gongfu.studio                  绑定、摆姿态、时间线、打击调校（命令行 + openmui 界面）
作品（showcase/fighting）       角色数据、素材
```

`openmui.rig` 从 `gongfu.present2d` 里拆出的是**姿态的求值**，不是 present2d 的对象模型（评审意见）：骨架的拓扑、坐标约定、绑定姿态和逆绑定变换、归一化的权重、片段采样、约束的顺序（握持、`aim`、跟随）、遮罩、叠加层的参考姿态、调用方提供的临时缓冲区（不分配）。rig 输出姿态和形变数据；贴图、材质、绘制顺序归渲染；`limb` / `prop` 这类受击框相关的标记、受击反应的选择、受击框烘焙归 gongfu。绑定文件用通用的名字 `*.rig.omui.toml`。

## 5. 精细的人物模型、骨骼绑定和动画

### 5.1 模型：从“分件贴图”到“可变形的插画”

| 层次 | 内容 | 现在 |
|---|---|---|
| 分件 | 每个部件一张图，绑在一根骨头上 | 有 |
| 网格 | 部件是三角网格，顶点有多根骨头的权重 | 有（规则网格 + 关节处混合） |
| **自动网格和权重** | 按部件轮廓自动三角化（轮廓 + 内部点，`math:geom2`），权重按骨骼距离的热扩散算（离线，可用 CUDA），可以手修 | 新 |
| **形变器** | 自由形变网格（FFD）和挤压拉伸：一个部件或整个人物按关键帧形变（出拳时前臂拉长、落地时压扁） | 新 |
| 替换画 | 关键姿势用专门画的部件（握拳的透视、甩出的袖子、表情） | 有（`drawings`、`swap`；表情六种） |
| **法线和光** | 每个部件一张法线图（生成或从插画推出），场景的光按法线给人物打亮边和阴影；特效（墨、霓虹）发的光照到人物上 | 新；现在是整体的明暗偏移 |
| 深度 | 部件的前后顺序可以按关键帧变（转身、手臂越过身体） | 新；现在是固定的 `depth` |
| 3D（以后） | 同一套 rig 接口，glTF 模型、骨骼蒙皮在 GPU 上，gongfu 的模拟不变 | 以后 |

数据：绑定单独成文件 `*.rig.omui.toml`（骨骼、部件、网格、权重、约束），外观（`*.look.gongfu.toml`）引用它；这样一份绑定可以给多个配色、皮肤用，工具可以只改绑定。

### 5.2 动画：姿态的表现力

- **关键姿势**（有）：世界角度（`aim`）、IK 握持和踩地；**加**：关键帧之间的“打破”（breakdown）姿势、每个关键帧的缓动（有）、形变器的关键帧、深度顺序的关键帧。
- **叠加层**（新）：在当前片段上叠加的片段——受击的抖动、呼吸、视线跟随对手、出招时的重心前移。叠加层按权重混合（`rig` 的混合），所以“任何招式里被打中”都有合适的反应，而不是一律切到受击片段。
- **程序化的二级运动**（有跟随和悬挂）：**加**弹簧链（头发、腰带、袖子）。**重建的约定**（评审意见：随便取一段“预热”窗口重算，和连续模拟不一样）：链的状态定义为有限历史的函数——驱动它的骨骼位置取自 `Effects` 保存的最近 K 个状态（K 不小于链静止下来需要的帧数，所以要把现在的 8 帧扩大并写明），从 K 帧前的静止姿态积分到现在。这样回滚、跳转、换片段、转向、停顿之后，链都是同一个函数的值；代价是 K × 节数，有预算；测试覆盖跳转、换片段、转向、停顿和最大回滚深度。
- **拖影和残像**（部分有）：**加**挥舞的拖影带（取武器骨头在最近几帧的位置——同样从片段重新算——生成贴图条带，就是特效里的笔触），以及关键一帧的“拉伸画”（smear frame）。
- **静止画面里的动感**：每个关键姿势检查几条可以量化的指标，`gongfu.studio` 显示出来、`check` 命令报告：
  - 剪影：纯黑剪影在不同招式之间的差别（面积、外接形状），太像的报出来；
  - 动作线：从脚到头（或到武器）的主曲线的弯曲程度；
  - 负空间：手、武器和身体之间是否留出空隙（剪影里能不能分开）；
  - 重心：重心在支撑脚之间还是之外（决定姿势是稳是冲）。
  这些是诊断，不是验收：不代替评审，但能把“像同一个身体换了胳膊”（codex 对墨的批评）变成能看到的数字。
- **性能**：网格和权重预先建好、不每帧重建（现在的 `picture_part` 每帧重建拓扑、逐个关节混合，要改）；一个人物几十根骨头、几千个顶点；姿态计算（含 IK 和弹簧链的回算）每帧小于 0.1 ms，蒙皮走 `math:batch`（SIMD），GPU 路径在顶点着色器里蒙皮（`render.mesh`），CPU 参考实现给固定像素用。预算写进 `budgets.bench.omui.json`。

### 5.3 绘制：网格成为一种渲染特性

现在的 `DisplayList::draw_mesh` 把每个三角形当成一次贴图填充，CPU 参考实现正确但慢。新增渲染特性 `render/mesh`：

- 一次提交一整个蒙皮网格（顶点、索引、骨骼矩阵、贴图），GPU 上在顶点着色器里蒙皮、一次绘制；
- CPU 参考实现按同样的光栅规则（共享边不留缝）画，固定像素用它；
- 和矢量特性记录进同一张渲染图（D-81），所以人物、特效、界面可以任意交错；
- 支持法线图的光照、按 alpha 着色（黑墨在暗场景上加亮边、霓虹加色）、加色和滤色混合。

## 6. 打击感：一次接触是一组同步的反馈

打击感来自很多通道在同一帧对齐。一次接触由一个**打击档案**描述（有，`[impact.<名字>]`），各通道都由它驱动，数据集中在一处、调校也在一处：

| 通道 | 内容 | 现在 → 要做的 |
|---|---|---|
| 停顿 | 双方冻结（hitstop），被打的一方在冻结时按攻击方向抖动 | 有冻结 → 加方向抖动 |
| 镜头 | 沿攻击方向的震动、推近、轻微的旋转 | 有震动和推近 → 加方向、旋转、按距离衰减 |
| 受击 | 按部位（头、身、下段）、轻重、方向、站立/蹲下/空中选反应，叠加在当前姿态上；重击有“失去平衡”的过程 | 有按部位和轻重选择（`hitstun.head/body/low/heavy`）→ 加方向、叠加层、表情替换 |
| 特效 | 接触点的冲击图（沿攻击方向）、武器的拖影、飞溅、地面的痕迹；暗场景上可读 | 有（`[fx]`）→ 加方向、按 alpha 着色的亮边、地面贴花 |
| 声音 | 三层（起手的瞬态、命中的主体、尾音），按材质（墨、玻璃、霓虹、肉体）和轻重；每个人物自己的语音（出招、受击轻重、倒地、必杀台词） | 有三层合成音效 → 加 CC0 语音包和每人的语音集（素材管线 §2） |
| 画面 | 闪白、反色、色差、径向模糊、颜色分级的瞬间变化 | 有闪白和反色 → 加后处理（渲染图的后处理 pass） |
| 手柄 | 振动的强度和时长 | 有 |
| 界面 | 连段数字的弹出、伤害的数字、血条的延迟扣减 | 部分 → HUD 重做时做 |

调校工具（`gongfu.studio` 的打击调校器）：选一招，循环播放命中的那几帧，可以慢放、逐帧、A/B 对比两套档案，改数据立刻看到和听到（开发模式下热重载外观和档案，回滚设计保证安全）。

**回滚下的声音和振动**（评审意见：纯函数的样本生成撤不回已经放出去的声音）：每个事件有稳定的身份（帧、种类、攻击方、第几下），声音和振动按身份去重；回滚后预测错了的事件淡出取消，确认的不重放；分清模拟的帧、动画时间（停顿时冻结）和声音的时钟。回放测试检查回滚之后没有重复的声音。

**验收**（量化的部分进 CI）：画面、声音、振动的起始延迟和抖动按测量值验收（不是“同一帧”这种说法）；任何一帧的接触点上都有可见的特效（不被身体完全遮住）。不要求每个通道都随轻重单调变大——重击也可以靠一瞬间的安静和克制来表达；可读、节奏和有意的对比比一律更大更重要。

## 7. 物理

格斗游戏的**玩法**不用刚体物理：位置、推挤、受击框都在 gongfu 的定点模拟里，逐位确定，可以回滚。物理用在**表现**上，分两类：

| 类别 | 做法 | 回滚 |
|---|---|---|
| 短链和小系统（头发、腰带、袖子、耳机线） | `rig` 的弹簧链，从最近 N 帧重新积分（§5.2） | 纯函数，天然一致 |
| 碎片和粒子 | 弹道的解析式（现在的飞溅就是），从事件的帧算起 | 纯函数 |
| 倒地 | 手定的倒地动作（关键姿势），不用布娃娃 | 纯函数 |
| 布料、布娃娃 | **推迟**：等短链、碎片、手定倒地都到位并评审过，再看是否需要 | — |

`mgame.physics`（S4 自写、确定性）继续作为通用游戏的物理；性能靠宽相位的空间哈希、固定的求解顺序，SIMD 在测量之后再加。是否引入 Box2D v3 / Jolt 作为可选后端，按需要再定（Q-31）。

## 8. 简洁和优雅：怎么不丢细节又不变复杂

- **少量正交的原语，组合出全部效果**：精灵、笔触、飞溅、面板、叠加片段、形变器、弹簧链。角色的独特性用数据组合这些原语，不加角色专用的代码。现有的 `CinematicLook` 里按角色写死的字段（时钟、棱镜、碎裂、云、印章、字形）改写成通用原语的组合，然后删除（这是一项明确的清理任务）。
- **每个概念一个文件格式**：rig、look、fx 可以拆成各自的文件，但格式规则一样（located diagnostics、写回去读回来一样、`check` 命令）。
- **纯函数到底**：画面、声音、二级运动都是（状态、帧）的函数。这一条让回滚、回放、测试、离线渲染、录视频都免费。
- **一套参考、多种加速**：每个计算先有确定的参考实现，加速实现按它验收。
- **工具是一等公民**：每个环节都有命令行（JSON、退出码，给 agent 和 CI）和 openmui 界面（给人），读同一份数据（D-61）。

## 10. 实施顺序（评审后调整：先把一段完整的对打做到位，再铺基础设施）

1. **墨和霓的一段完整对打**：预备、接触、后坐、恢复、过渡、踩地、深度变化、替换画、形变修正；受击的叠加层要有遮罩和覆盖规则（有的接触要整个换姿态）；评审通过再往下；
2. `gongfu.studio` 的绑定、姿态、时间线、打击调校界面（工具先行，上一条的效率靠它）；
3. 网格预建和 `render.mesh`（CPU 参考 + 顶点着色器蒙皮），保持半透明部件的顺序和矢量、网格的交错；
4. `openmui.math` 第一版（§3.1 的小范围）和迁移（固定像素不变）；lint 规则 `math`；确定性三级的编译选项检查；
5. `openmui.rig` 拆出（§4 的边界）；弹簧链按重建约定；
6. 回滚下的声音和振动事件（§6）；
7. 演出的旧字段改写成通用原语并删除；
8. 按 alpha 着色、加色混合；法线图光照；
9. 测量之后再决定：SIMD 蒙皮、`openmui.compute`；自动网格和权重；布料。

每一步的验收：已有的固定像素和声音不变（或者有意改变并说明）；新增能力有测试、基准和按实测设的预算（写明硬件和百分位）；格斗游戏按评分表重新评审。
