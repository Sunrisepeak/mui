# omui／openmui 项目情况与进度综合评审

2026-11-05。评审基线：`openmui-design` 的 **`e492836dd02e31b4d6937c0e9cb623c01d36eb0f`**；最近实现及运行验证基线：**`79081cc5b4af6216b72c70f1b405f17788cb0619`**。本报告是代码、计划、历史运行证据及选定图像的综合评审，不是新一轮全项目测试或正式竞品评分。

证据分类：**代码核对**＝当前源码/API/依赖；**既有实测**＝原执行记录，本轮校验文件与哈希；**图像查看**＝保留的参考图或已有报告引用的本地图；**评审判断**＝由这些证据推导的风险及建议。配套[证据快照](2026-11-05-project-progress-evidence.report.omui.json)保存核对结果；原始大体积报告、日志和构件多在未跟踪的 `target/`、`/tmp/`，该快照不是全部原始证据的归档替代。

## 1. 总体判断

**项目已经具备较广的框架基础和可运行产品雏形，近期在独立动画消费、确定性、真实像素验证及官网交付上取得可核实进展；距离“通用多引擎体系＋成熟开发工具＋高质量官网”的完整目标，仍有较大实施与验收缺口。当前处于基础设施贯通和产品质量收口阶段。**

最需要解决的是三种进度之间的差距：

1. **设计覆盖面领先于实现。** 多域对象、过程 effect、通用反应、异构执行、相机、音频自动化、九类工具等已有设计，但不能据此报告功能支持。
2. **底层能力领先于产品贯通。** 独立 hanim 已可真实运行，UI 默认动效及官网展示仍主要使用原 UI 路径，尚未形成一条公共库被所有消费者复用的链路。
3. **局部工程验证领先于最终体验验收。** 602 项浏览器检查、可重复像素和微基准是真实成果，但不覆盖全部组件状态、动态美术、真实 LLM 任务、硬件设备和全部制作工作流。

因此不提供缺少权重与验收分母的“项目完成百分比”。当前可以报告具体能力和通过范围；**C2、R0–R6、C3–C6 均不能整体记为完成，每维 ≥90 也没有当前版本的验收证据。** 此判断不是要求等待远端 CI 才能继续工作：本地相关真实检查通过即可推进，跨平台结果异步登记。

## 3. hanim：已经完成了什么，关键断点在哪里

### 3.1 已有成果

- **纯时间基础**：曲线、Tween/Track、解析弹簧、路径、时间线以及已准备轮廓的确定性采样；共享数学归 `openmui.math`。
- **对象与所有权**：owner／slot／generation、稳定部件 ID、拥有数据的快照，避免播放器依赖 UI 临时内存。
- **真实轮廓形变**：`anim::morph_to` 可准备、采样及打断后从当前几何继续；不是仅用透明度交叉模拟形变。
- **组合编排**：`bind / sequence / parallel / stagger` 编译成对象轨道与分段；简单 play 和预备 Program 使用同一个 Engine。
- **控制及发布**：pause、seek、reverse、retarget、cancel、restore、release；retarget当前支持单轨（包括单轨sequence），多轨选择性替换未实现；批次先准备再原子发布，失败不提交部分新姿态。
- **独立消费**：外部 CLI 工程无需 UI／窗口，可输出真实 PNG 区域及来源信息；可选 renderer adapter 使用已有 renderer。

具体入口在 [core](../../modules/base/hanim/core/README.md)、[object](../../modules/gfx/hanim/object/src/object.cppm)、[library](../../modules/gfx/hanim/library/src/library.cppm)、[effect](../../modules/gfx/hanim/effect/README.md)、[program](../../modules/gfx/hanim/program/src/program.cppm)、[engine](../../modules/gfx/hanim/engine/README.md)、[render.vector](../../modules/gfx/hanim/render/vector/README.md)。

### 3.2 尚不能支持的承诺

| 目标 | 当前真实边界 | 必须补的内容 |
|---|---|---|
| 任意对象／属性可动画 | 当前公开 ObjectDescription 的部件载荷为 Transform2D、contours、optional fill | 类型化属性、单位／空间、选择器、版本、写入仲裁及不同域 adapter |
| 任意 A→B 的默认匹配 | 严格部件身份／层级／次序和轮廓兼容约束 | 多种匹配策略、拓扑处理、对应缓存与可解释诊断；不声称所有形状自动成功 |
| 动画×过程效果 | EffectSpec 是有序参数计划，blur/tone 是 helper；尚无通用过程算子 | 匹配成本、顶点路径扰动、属性迁移、响应规则与渲染效果分别定约、共同编排 |
| 多层组合及交叉播放 | Program 的 Binding／Segment 固定严格 morph；同对象重叠拒绝 | 通道混合、组／子树 scope、合成顺序、时间映射、资源读写／生命周期 IR |
| 像素级物质／骨骼／相机 | 已有几何采样后真实光栅化；不能等同每像素状态迁移、rig 或通用相机协议 | 分域插件、不同 carrier 表示；相机 pose／lens／view-output 的独立约束与 adapter |
| 属性＋状态＋触发反应 | 已有设计，尚未通用落地 | 条件／事件／接触／邻域／阈值、状态转移、确定顺序、有界级联、checkpoint/replay |
| GPU 动画 | RHI WebGPU 可以 compute，hanim 当前求值仍为 CPU | 同一计划的 GPU kernel、驻留／同步／回读、数值差异和真实设备计时 |
| UI 是普通 hanim 用户 | `modules/ui/motion/mcpp.toml` 仍依赖 hanim.core，没有接入新 Engine／Program | UI→HObject/属性 adapter、默认配方迁移、显示／命中／焦点／语义同步 |

**首要架构风险是旧 UI 动画与新独立引擎长期平行扩展。** 这会重复匹配、阶段管理、效果与打断逻辑。下一步应先贯通一条公共契约路径，再扩动画条目；同时保留单对象 CPU 轻路径，避免每个简单按钮都支付完整图调度／GPU／模拟的成本。

`import hanim;` 当前只重新导出 core，完整能力需要显式导入高层包。这也是“用户找不到动画库”的产品可发现性问题。应提供清楚的产品入口与依赖档位，不能直接令 base 层伞包反向依赖 gfx 来修补。动画中心 API 是推荐候选；类型、所有权和组合语义验证后再定最终签名。

环境场只是反应输入的一个例子；Noita 类材料／邻域反应是一个验证场景。纯采样仍应保持确定性；有状态演化交给独立模拟插件，明确历史重建和副作用策略。不得将全部物理／化学／元胞实现塞进 hanim.core，也不能用少数几何微基准推断大规模像素反应性能。

| **37 类默认配方映射** | 按组件类型选择 update/state/enter/exit 等策略 | 映射存在不代表每类运动、形状和用途的中间态均已验收 |
| **1 种新公共库动画配方** | `hanim.library` 当前公开的 `anim::morph_to` | 不把 core 的数学/曲线能力或官网条目并入此计数 |

36 个官网样张与 37 类默认映射属于不同清单，不是互相矛盾的统计。依据：[组件目录](../../site/src/gallery.cpp)、[基础设计](../../site/src/basic_motion.cpp)、[创意组合](../../site/src/creative_motion.cpp)、[类型与配方](../../modules/ui/view/src/theme.cpp)、[原语定义](../../modules/ui/view/src/theme.cppm)。

“默认动画都没了”在当前代码层面不能再表述为完全没有：默认配方已经补入。但是**存在配置、运行时触发、用户看得见且符合用途**是三层验收。需对按钮／开关／输入／列表／浮层／布局等代表类别检查触发、中间态、打断、减少动态效果，再扩到完整类型矩阵。

40／20 的最终计数应由同源清单关联公共符号、参数／效果兼容性、独立消费者、官网场景、默认配方及验收记录；只为同一公共能力增加标题或示例颜色变体，不重复计数；只在 site 内实现的条目也不计作公共库交付。颜色插值本身可以是一项有独立契约和消费者验证的公共能力。

## 7. Agent、工具与跨平台的真实位置
