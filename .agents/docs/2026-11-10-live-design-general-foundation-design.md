# Live Design 的通用底座：Agent 原生的生成式 × 实时交互创作框架（D-160）

日期：2026-11-10　状态：方案（底座先行，实现聚焦 UI）　关联：D-149、D-151、D-152、D-155、S-14、[收敛方案](2026-11-09-agent-era-ts-first-convergence-design.md) W14／W16、[核心设计准则 §9](2026-11-05-local-global-composable-architecture-design.md)

## 1. 要求与定位

人的要求（2026-11-10）：Live Design 现在集中在 UI／GUI 应用的实时设计和开发上——运行中的应用同时也是设计器。但底层架构要做得通用，为以后把它发展成通用的、Agent 原生的“生成式 × 实时交互预览”创作框架打好基础。目标领域包括动画创作、美术资源、UI 组件、特效、2D／3D 人物、建模、绘图、工程制图。

底座要支持：

- 多个 Agent 并行创作。
- 画布模式和多个工作区。
- 人通过窗口和可视化实时预览、交互、调整。
- 每个 Agent 有一个“指针标识”，能看出哪个 Agent 在哪里、做什么。
- Agent 可以申请独占工作区、区域或组件，防止被其他 Agent 破坏；这同时表示它正在那里设计。锁的粒度尽量小，并且有可见的标识。

这样也就解决了多个 Agent、Agent 与设计器之间并行时的状态、预览和交互问题。

**实施边界**：本文档记录底座的完整方向。代码只实现当前 UI 框架需要的部分，以及与方向一致、可以顺手完成的部分。其他领域的适配器不进入当前路线，以免路线偏移、无法收敛。

## 2. 原则

1. **内核与领域无关，领域只写适配器。** 内核只认“主体、历史、编辑、参与者、认领、工作区”这几个概念；UI、动画、模型等领域各自说明它们在本领域是什么。
2. **人掌握最终控制（S-14、D-155）。** 人可以越过任何认领、收回任何认领、接手任何 Agent。认领约束的是 Agent 之间，以及 Agent 与人的默认行为。
3. **语义优先、可观察。** 每个参与者、每个认领、每一步编辑都是可查询的事实（经 openas 的执行者、会话和委派），并且画在画面上；Agent 不靠截图猜测别人的状态。
4. **呈现与状态分离（D-149）。** 设计过程的呈现由 hanim 驱动（编辑长出、撤销回放、切换淡化），状态只在历史和主体中。
5. **确定性。** 同一组编辑按同一顺序作用于同一状态，结果逐字节相同；并行只发生在不相交的认领上，合并规则是确定的。

## 3. 分层模型

| 层 | 是什么 | 领域无关的契约 | UI 领域（现在） | 其他领域（以后） |
|---|---|---|---|---|
| L0 主体 | 被设计的东西：一组带地址的源（文本、结构化数据、按内容寻址的资产），以及运行它们得到的作品 | `DesignSources`：此刻的各源文本、把一组文本放进运行中的作品、作品的语义哈希；以后扩展为 `DesignSubject`：资产、求值、语义视图、渲染 | TS 源（player，编辑立即运行）；C++ 项目文件（devhost，写回后构建） | 动画：时间线与配方；美术：图层与矢量；模型：网格与骨骼；工程图：图纸与视图 |
| L1 历史 | 内容寻址的提交、分支、标签、合并、时间线、胶片 | `DesignHistory` 与历史动词（`:history_verbs`），由持有者（应用或宿主）持有 | 已有 | 同一份实现 |
| L2 编辑 | 结构化操作或代码编辑；预演（替身里运行）、提交、撤销、事务 | 编辑 = 对主体的一个变换，带执行者、目标地址、效果（openas） | `design.edit`／`design.ops`、`design.preview`、事务 | 每个领域的结构化操作集合（例如“移动关键帧”“挤出面”） |
| L3 参与者与在场 | 人和 Agent、会话、委派；每个参与者在哪里、做什么、想做什么 | 执行者身份（openas）、意图（`design.begin`、AgentNote）、在场模型（位置、动作、轨迹、所持认领） | `agent_presence`（单个 Agent 的框、轨迹、提问卡片）、接手（S-14） | 同一模型，位置换成本领域的坐标（画布点、骨骼、时间点） |
| L4 认领 | 细粒度独占：谁正在设计哪一块 | 见 §4 | 节点、部件、属性 | 图层、对象、骨骼、网格分区、时间区间、图纸视图 |
| L5 工作区与画布 | 一个工作区是一个主体在一个分支上的一个可见实例（本体或替身）；画布把多个工作区和画板排在一个可缩放平移的平面上 | 工作区的创建、命名、归属、观察和关闭；画布的布局与相机 | 替身（预览、变体板）已有；工作区命名和画布模式以后做 | 同一机制：多个镜头、多个角色、多个视图并排 |
| L6 领域适配器 | 本领域的 L0 实现、语义视图、结构化操作、认领单元的寻址 | 每个适配器一份 CTS（`mlibs.cts`） | UI（`omui.designer`） | 按 xengine、hanim 的需要逐个接入 |

## 4. 认领（Claims）：细粒度独占

**地址。** 认领的对象是一个层级地址：`工作区 / 区域 / 节点 / 部件 / 属性`。在 UI 中，节点就是语义 ID 路径（`main/settings/notifications`），部件和属性写在后面（`main/save#label`、`main/card.padding`）。画布上的区域是矩形。其他领域用本领域的路径（图层路径、骨骼名、时间区间）。

**粒度尽量小。**

- 默认只认领一个节点本身，不含子树。子树认领要显式写出（`subtree: true`）。
- 只改一个属性时，认领那个属性。
- 认领子节点时，祖先上留下“意图”标记：别人可以继续改祖先的其他属性，但不能整棵子树独占它（层级意图锁）。

**模式。**

- 读永远不需要认领。
- 写需要覆盖目标的认领，否则就自动做一次轻量认领，只在这次动作期间持有。
- 两个认领不相交才能同时成立。

**租约。**

- 认领带时长，持有者要续约（心跳）。
- 会话断开、被撤销或租约到期时自动释放。
- 委派出去的子 Agent 只能在委派者的认领范围内再认领（不能扩大权限）。

**冲突。**

- 碰到别人的认领，写操作被拒，答复 `conflict`，附上持有者、它的意图、认领的地址和预计剩余时长（`retry_after`）。
- 申请者可以选择排队等待（`wait`）。

**人。**

- 人的直接操作不受认领阻止：人改了一块被认领的地方，持有它的 Agent 收到通知；这和 S-14 的“人操作过的控件 Agent 要等”同一个方向。
- 人可以收回任何认领，也可以“接手”某个 Agent（暂停它，并收回它的全部认领）。

**可见。**

- 每个认领在画面上画成持有者颜色的框或角标，带名字和意图。
- 语义树中节点带“被谁认领”的状态。
- Agent 用 `design.claims` 查询全部认领。

**记录。** 认领、续约、释放、冲突都进入 journal 的因果链，`ui.explain` 能回答“为什么我的编辑被拒”。

## 5. 指针标识（在场标记）

- 每个参与者有一个稳定的标识：颜色由执行者 ID 的哈希在主题的可读色板中选出，另有名字和图标。人始终是同一种标记。
- 标记显示：当前位置（节点框，或画布上的点）、正在做的动作、意图（`design.begin`／AgentNote）、所持认领、最近几步的轨迹。
- 多个 Agent 同时显示，标签互相避让，不遮挡正在编辑的内容。
- 人按下一个标记：看到它的轨迹和意图，可以暂停、恢复、接手它，或者收回它的认领。
- 现有 `agent_presence` 组件（单个 Agent）扩展为多 Agent：同一个模型（`agent_presence_state`），每个执行者一份。

## 6. 多 Agent 并行

- 每个 Agent 一个会话（openas），读不阻塞，写经过认领。
- 两种协作方式，由人或协调 Agent 选择：
  - **同一分支、不相交认领**：各自的编辑直接进入同一历史，提交按执行者记录。
  - **各自分支**：每个 Agent 在自己的分支和工作区里做，用已有的 `design.history.merge` 合并；冲突时按源点名，不自动解决。
- 预览：每个工作区有自己的替身（离屏、确定），人在画布上同时看到它们；工作区之间的切换和比较复用变体板与时间线。
- 后台任务走 W8 的全双工会话（`TaskBroker`）：生成在线程池上跑，在 UI 线程的帧边界提交，提交时重新判定权限和认领。

## 7. 人的交互

- 人在窗口和画布上实时预览，可以直接拖动、调整。人的调整同样是一次编辑，进入历史。
- 人可以对任何 Agent 的请求作答（openas 的 answer），可以暂停或恢复 Agent。
- 画布模式下，人缩放平移整张画布，按下一个工作区进入它；按下一个 Agent 的标记跟随它。

## 9. 实施路线（只做 UI 需要的和方向一致的）

1. **已完成**：`DesignSources` 与历史动词分离；devhost 持有历史。
2. **认领（完成，标识除外）。** 在运行时实现节点、部件、属性粒度的认领：子树显式、祖先意图、租约与续约、会话结束释放、冲突带持有者与 `retry_after`、人可越过和收回。Agent 的写（动作、动词、设计编辑）检查认领。语义树带“被谁认领”，journal 记录全过程。操作是运行时的，不只属于设计器：`ui.claim`、`ui.release`、`ui.claims`（omui 的操作目录，协议的 `claim`／`release`／`claims`）；Agent 的节点动作在 S-14 检查之后检查认领。部件（`#part`）粒度留到有部件级编辑时再加。验收：omui.agent 的 claims_test（两个 Agent 各持一块；冲突答复带持有者、意图、`retry_after`；祖先节点本身可并存、整棵子树不行；同一节点的两个属性可并存；续约、到期、放手后他人可取；人不受阻；接手收回全部）。
3. **多 Agent 标记（完成，按下标记的操作除外）。** `agent_presence` 按执行者分别画出颜色、名字、动作、意图和所持认领，标签避让；人按下标记可以暂停或接手。
4. **以后（方向一致时再做）**：命名工作区（替身的命名与长期存在）、画布模式（多个工作区排在画布上）、`DesignSubject`（资产、求值、渲染）、第一个非 UI 适配器（hanim 的动画创作，与 hanim studio 合流）。

## 10. 底座验收

两个 Agent 同时设计一个设置页：

- A 认领 `main/settings/notifications`，B 想修改它时被拒，答复里有持有者 A 和 A 的意图。
- B 认领 `main/settings/appearance` 并修改；两者的修改都进入历史，各自记在自己名下。
- 人在窗口里看到两个颜色不同的标记和两个认领框。
- A 断开后，它的认领在租约到期时释放，B 随即可以认领那一块。
- 人接手时收回全部认领，两个 Agent 的写都等待人交还。

每一步都有无 GUI 的验证（协议答复、语义树、journal），标记和认领框有离屏像素。
