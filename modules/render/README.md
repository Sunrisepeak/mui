# openmui-render

The rendering abstraction (module `openmui.render`, D-57): the display list of contract ⑤ (paths, paints, gradients, strokes, clips, transforms, layers with blend modes and effect parameters, glyph runs, images, external textures, node markers), resources by reference (an image store; glyphs from the text engine through `GlyphSource`), and backends. The CPU backend renders through openmui-raster, byte-for-byte the same on every platform, records pixel provenance, and reports what a CPU cannot draw (effects, external textures — spec R-3). Knows nothing of nodes or views.

**Incremental frames** (`:damage`, D-62). A `DamageTracker` compares a display list with the previous one, segment by segment (the node markers; a segment's hash covers its own commands and its children's order, its bounds are in device space) and returns the bands of rows that can differ. The CPU backend draws only those rows over the previous frame (`CpuOptions::rows`), skipping commands that cannot reach them, and the result is the full render byte-for-byte — `tests/damage_test.cpp` holds it to that for every kind of change (colours, moves with shadows, rotations under rounded clips, clips, layer opacity, z-order, nodes appearing and going, strokes), and the headless host's tests for real frames. On the 1000-node dashboard of M1 ⑤ at 1080p a one-label frame goes from 28 ms to under 2 ms (`tests/bench`).
