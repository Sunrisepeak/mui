# 局部能力中心 × 全局契约协作：统一架构准则

2026-11-05。维护者明确的设计原则，纳入[AGENTS.md](../../AGENTS.md)；具体API、模块拆分和后端仍按各设计review与真实验收推进。与[多引擎产品架构](2026-11-04-multi-engine-product-architecture-design.md)、[hanim可组合／反应IR](2026-11-05-hanim-composable-operators-reactions-ir-design.md)配套。

## 1. 核心准则

**局部围绕本域核心能力建模，以通用底层能力、可控数据、可组合算子／管线和自定义扩展覆盖场景；全局通过公开、类型化的契约与适配组合各系统，共享同职责的基础实现，保留领域语义、时间和实时约束，按需承担依赖与成本。**

这是一套交叉视角：单独看每个系统，它应是完整、通用、可独立使用的产品；放到全局，它又是可与其它系统协作的能力模块。场景越复杂，越需要显式契约和良好的组合能力，不把场景分支堆进内核。

“统一”首先统一设计语言、契约表达、组合／扩展模式、能力与错误、生命周期、观测及人／Agent控制方式。各系统的数据表示、算法、状态和调度仍遵守本域要求。

## 2. 每个模块有自己的核心视角

| 系统 | 局部核心视角 | 可组合能力举例 | 对外输出／协作边界 |
|---|---|---|---|
| hanim | 公开适配的属性／对象／相机／运动／参数都可动画 | 对应、插值、路径、变换、修饰、反应与编排 | 已采样属性／姿态／场、执行计划及控制；业务状态和render资源由其所有者维护 |
| audio | 适用的声音、数据与事件均可作为音源、信号或控制／调制源 | 声源、采样、路由／总线、混合、DSP、包络、自动化与音序 | 音频块、设备／离线输出、分析、时钟与控制；不由GUI帧率驱动采样 |
| renderer | 适配的内容和数据可进入视觉表达／合成 | 2D／3D／文字／粒子／场、材料、相机、效果与pass | 图像／视图／读回和资源能力；不接管业务／玩法状态 |
| simulation／reaction | 选定域的属性／状态按规则与输入演化 | 约束、邻域、连续影响、条件／触发、状态迁移与检查点 | 版本化状态、事件／统计及可重建输入；求解模型为可选模块 |
| UI | 应用的交互／状态以同一语义契约呈现给人、无障碍、Agent和测试 | 组件、布局、输入、焦点、动作、motion和style | 业务／交互事实与公开adapter；作为动画／渲染等能力的普通消费者 |
| compute／HPC | 合适的类型化数据可由批量算子计算 | 数值、几何、信号／场算子、CPU／SIMD／GPU执行 | 数据视图、kernel／执行能力及同步；不拥有UI或某个上层引擎的生命周期 |
| AI／Agent（可选） | 合法观察、约束与任务可生成可校验意图 | 规则／策略、模型调用、工具编排、外部Agent委派 | 带revision／期限的Intent；通过同一领域操作提交，不接管引擎状态或绕过授权 |

“万物可动画／可audio”指开放可适配的数据与处理能力。例如相机pose可供动画控制并作为audio listener输入，温度可映射为色彩或音高；数据映射、单位、采样率和权限仍需明确。身份、资源代次和内部不变量不因此变成任意可写的动画属性。

模块可互相提供能力，但C++包依赖仍保持单向。运行时双向信息交换由中立数据契约、adapter、宿主组合及显式时间边连接，不能形成UI↔hanim↔renderer的静态依赖环。

## 3. 从少量能力组合场景，场景保持在上层

统一模式是：**基础数据／数值 → 本域算子与模型 → 组合／可编排计划 → 可复用配方 → 应用／工具。**

- 先识别目标、属性／端口、输入输出、状态和执行频率；
- 可跨系统复用的算法／存储／调度机制给一个明确owner；
- 本域算法和策略通过稳定契约扩展，用户可提供满足能力要求的自定义算子；
- 常见场景包装为配方，配方仍可展开、观察和重组；
- 从简单入口到高级图／数据描述，都进入同一实现与执行计划。

例如“玻璃按钮进入重力区域并触发声音”应由UI部件／状态、动画、反应profile、材料／renderer及audio触发组合；不在hanim写特定按钮行为，也不在audio重新实现一个按钮系统。组合扩大场景覆盖面，数量清单不能代替通用性、质量和性能证据。

图／端口／版本／存储等公共机制可以复用；hanim的动画IR、audio的DSP图、renderer的资源图仍保留各自语义，通过adapter和宿主连接。统一设计模式不要求audio或renderer依赖hanim播放器，也不要求所有领域使用同一种IR。

## 4. 可控属性与统一算子，保留类型与领域

每个公开目标都有schema、选择器、单位、空间、范围、默认值、版本／所有权和可控制性。位置、焦距、路径点、效果幅度、滤波截止频率、总线增益、材料温度等可以使用一致的描述／控制模式；具体插值、约束和有效范围由域定义。

通用算子／函数可用于不同上下文。例如noise可影响路径、力、材质或声音调制，但需要明确输出尺度／频带／单位及域adapter。算法共享不意味着无类型连接；颜色通道、空间坐标、声道和模拟属性的含义分别保留。

自定义是正式扩展能力：算子声明typed端口、读写集、阶段、状态／时间、后端、数值等级、预算与观测。脚本只构造／控制，热路径执行已准备的原生批次或编译后的kernel。缺少某个后端实现时通过能力／降档契约处理，不假装任意回调都可GPU执行。

## 5. 公共基础按职责收敛，不过度统一

| 候选公共能力 | 复用边界 |
|---|---|
| math／数值／插值／随机 | 已有公共实现及其确定性规则；域算法消费，不各写同名函数 |
| buffer／内存／格式与通道布局 | typed view、stride、位宽／格式描述、所有权与生命周期；声道／颜色／场通道的解释由域提供 |
| time／时间映射 | 单位、时间基与转换／同步契约；保留audio sample clock、animation time、simulation tick及render submission边界 |
| signal／采样／重采样 | 确有共享语义时提取通用算法；音频抗混叠、图像过滤、场重建和精度预算分别声明 |
| task／pipeline／compute／RHI | 阶段／批次与资源依赖、设备能力和同步；domain scheduler仍满足本域deadline |
| trace／log／session／CLI／Agent | 共同事件／查询／版本与结果模式；实时线程使用有界轻量通道，不格式化大日志或执行网络请求 |

位宽、采样、通道等是值得评估的公共基础，不因概念同名就提前造一个巨型通用库。优先复用现有模块和mcpp生态；在明确多个消费者／独立用途、共同语义和收益后提取一个实现。可选库／算法／后端按需引入，不把全部audio／GPU／模拟拖入轻量UI或动画。

mcpp是构建工具，借GPU／HPC构建插件交付运行时库和算子；运行时执行、数据驻留和调度由相应独立模块承担。

核心契约与可选实现按包／feature分离，构建闭包和资产决定体积，运行开关决定已编入能力的使用。可选内置AI不改变默认双用户控制；决策来源可为规则、内置Agent或openas外部Agent。风格包通过token／部件选择／公共effect／motion组合，允许局部scope和混合风格，组件不写按风格名分支。具体边界与反例见[feature／AI／style补充](2026-11-05-features-ai-agent-scoped-style-design.md)。

### 5.1 目录、语言模块与独立包分开判断

`mcpp.toml`代表可独立选择、构建、测试和管理的库／产品边界。**一个职责、一个目录或一个`.cppm`不自动等于一个包。** 少量实现、几百行的内部能力，默认先归入现有owner的`src/<职责>/`，用实现单元或C++模块分区组织，测试也归所属包；按职责解耦不要求为每个职责再建清单、版本和依赖边。

新建独立包应能回答“谁会独立使用它、为什么现有包内组织不足”：

- 已有足够内聚的实现和公开契约，确有独立使用的库边界；代码量只是评审信号，不是最低行数或拆包理由。
- 已明确作为独立库／产品建设，即使初期代码少，也写清职责、API、消费者／目标任务和阶段验收；不以“以后可能需要”预建微型包。
- 确实需要隔离可选重依赖、设备后端、平台／工具链、许可证或host-build与target-runtime。小型契约、adapter、共享CTS或兼容入口可以例外，但必须说明实际隔离收益与生命周期。单包feature能清楚实现时，优先比较该方案。

插件是契约和组合机制，不等于“一插件一包”；同一库中的多个算子、动画、效果、provider和内部IR通常先以目录／分区组织。构建选择必须真实排除关闭功能的源码、依赖和资产，不能拿运行时开关冒充裁剪。包内的公共API、依赖方向、测试和Agent语义仍清晰，不因少建清单而把不同引擎混成一个万能库。

新增包的review至少记录：owner与消费者、独立使用／隔离理由、包内目录／feature替代方案、公开入口与依赖闭包、构建和维护成本。重复实现先收敛到唯一owner；只有这个owner确需独立库时再拆包。代码增长、第二个真实消费者或新的隔离需要出现时，可以从`src/xxx`提取；没有这些需要时就保持内部组织。

维护者补充：独立的内部子项目也必须有具体原因，不因仓库尚未拆分就放宽标准。多模块共用需要同时具备内聚、可独立消费的库／引擎意义；同一产品的几个内部模块互相引用，不自动构成多个库。理由写进所属README，说明局部职责与全局消费者、依赖收益；用同包feature能清楚隔离的能力，优先收敛。Hanim本轮将六个细分包合入产品`src/`，保留独立语言模块与feature，`hanim.core`继续承担std＋math基础层共享边界。

既有小包逐项评审，不按行数批量删除。合并时先核对公开import／依赖键、平台条件、host/target、feature、许可证与独立消费者；必要的兼容转发只有一份底层实现，并写明迁移范围。比较构建／增量编译、产物和最小依赖闭包后再验收。目录树中的候选职责不是必须逐项创建`mcpp.toml`的清单；本条修订旧文档的“每个目录都是workspace成员”表述（D-99）。

命名归属遵循[D-100](2026-11-05-product-namespace-migration-design.md)：标准 openmui、UI omui、具名引擎自身名、通用库 mlibs、暂名引擎 xengine。该归属与物理分层分别管理，不改变本节的共享 owner、包粒度、依赖及实时约束；已有 `openmui.*` 实现入口处于兼容迁移期。

## 6. audio体现相同思想，同时有独立实时约束

从audio视角，源、信号、参数、路由与效果都可组合、调制和控制：文件／振荡器／流可作为音源，事件触发voice，运动／状态可以经映射控制音高、增益或空间位置。外部环境可提供混响区域或其它控制输入。

自动化曲线可复用公共时间／数值能力，audio按自己的采样时间／block求值，不依赖每个sample调用一个GUI／hanim对象。区分control-rate、audio-rate、跨线程参数更新及sample-accurate事件；从渲染帧输入参数时声明时间映射、插值／平滑及延迟。

音频callback必须遵守无分配、无阻塞／GUI锁／网络／GPU同步等待等本域实时要求。GUI／CLI／Agent经有界命令通道控制，结构更新在合法边界准备／发布。离线输出和实际设备共用领域算法，设备生命周期与调度仍有自己的契约。

本仓库已有独立[openmui.audio](../../modules/media/audio/README.md)及音源／总线／效果、音乐和离线工具。首条跨域自动化由可选[openmui.timeline.audio](../../modules/media/timeline/audio/README.md)实现：冻结时间线曲线并按sample clock驱动总线增益，同一源供视觉／Agent只读查询；不为audio另造插值器，也不让audio内核依赖hanim。当前换绑要求静默边界，完整通用调制图、跨线程实时发布与有状态DSP重建仍未交付。

## 7. 属性＋状态＋条件／触发的反应是通用模式

环境场只是影响来源之一。通用反应可来自事件、属性变化／阈值、区域进入离开、接触、邻域、材料组合、时间等。反应契约描述输入／读写集、条件与触发方式、状态迁移／输出、时间／顺序和成本。

| 场景例示 | 同一设计模式中的角色 |
|---|---|
| 动画对象经过区域 | 当前姿态＋响应属性＋场／区域条件→路径／属性／状态变化 |
| 相机遭遇事件 | 相机状态＋触发事件→shake／跟随／镜头参数配方 |
| audio包络／门限／区域响应 | 信号或状态＋条件／控制输入→增益、调制、路由或效果变化 |
| Noita类像素反应 | 材料／温度等属性与状态＋邻域／阈值规则→迁移、扩散或反应；只是通用求解能力的一个场景 |

共同的是契约模式，反应算法和执行由对应域承担。纯插值不必变成事件系统；大规模格点也不必逐像素发事件或调用虚函数。需要的条件／状态可编译成批量mask、数值／邻域kernel与有界状态边。

## 8. 全局协作示例与验收

场景可由模拟产生状态／反应，hanim编排对象与相机，renderer呈现，audio消费映射后的状态／事件，UI与工具负责交互和审查。各系统交换带时间／版本的数据，不共享一团可变世界状态。

宿主明确时钟映射、状态／资源所有权、写入仲裁和发布边界。音频事件映射到sample时间；视觉采样不重复推进模拟或重复发声；相机／运动快照可供renderer和audio各自按合法时间消费。纯函数、可重建状态和外部副作用分别处理。

Agent和人通过相同公开操作／数据控制与观察；工具提供完整CLI／API、可选GUI、结构化报告及实际离屏像素。双第一优先级、最小skill／SOP、权限与验收细则见§9；纯库不为Agent控制强制依赖UI或网络。

新增功能的review至少回答：本域核心语义是什么；通用基础／领域插件／上层配方归谁；能否由已有能力组合；是否引入重复实现或依赖环；未使用时付出什么成本；时间／状态／实时语义是否成立；怎样做CTS、性能／资源预算、观测与独立消费者验证。

上述原则指导实现，不替代具体功能验收。当前完整通用IR、反应／调制图、各域adapter及跨引擎工具仍需逐项落地。

## 9. 人与 Agent 双第一优先级的设计与验收

本节是维护者要求的开发规范，适用于独立库、引擎、UI框架、组件、工具、应用／游戏及其开发和使用阶段。**先定义可由Agent原生操作的领域语义，再构造人的GUI／TUI视图；两类用户的体验与可用性同时属于第一优先级。** 这种顺序决定能力如何建模，不降低人的设计优先级。

### 9.1 直接用户与共享契约

“人→Agent→系统”是正式使用路径。Agent侧重批量、组合、精确控制、自动验证与可恢复任务；人侧重意图、审查、决策、少量直接控制及有反馈／情绪价值的交互。GUI也保留高质量的直接操作，不把人强制变成只能聊天的用户。

设计每项公开能力时，先给出稳定ID／revision、输入输出类型、能力发现、查询、操作、事件、错误和生命周期，再决定可视化组织。GUI、TUI、CLI及openas调用同一领域实现，观察同一状态；不得为Agent复制业务状态、授权实现或另设绕过公开契约的控制路径。同等授权下，人的观察／控制能力具有原生Agent等价语义，无需模仿鼠标点击才能访问；交互测试仍可注入真实输入验证人的路径。

openas承载共同的actor、操作效果、授权与报告语义，领域schema／参数由产品维护。通用缺口先形成可复现任务、候选契约、兼容说明和CTS，再按独立标准仓库流程迭代openas；未发布的提案标明状态，不在各引擎复制协议。仅实现CLI或列出verb名称不足以宣称完成原生语义控制。

### 9.2 Headless包含完整任务和真实视觉

任务从发现、创建／加载、修改、执行、查询到验证、保存／导出，都应能在不启动GUI应用、不创建窗口、不依赖显示服务器、无需人工点按的环境完成。长任务提供任务身份、进度／结果及取消语义，不阻塞交互或实时线程。纯库可由薄的CLI／openas宿主承接这一流程，无需每个数学或DSP函数单独启动服务。

视觉输出通过同一renderer及素材／布局／效果链离屏生成，可指定对象或surface、camera、区域、时间／帧、缩放／DPI、色彩空间和工程revision，并返回来源与实际后端。GUI关闭时仍可渲染组件、工具面板或场景；截图请求不能隐式推进模拟或重复外部副作用。语义查询帮助理解结构，真像素帮助判断视觉质量，两者互补。

所选视觉能力必须声明离屏支持及其后端依赖；不要求纯计算安装图形环境。缺少设备或效果实现时，可采用已声明的CPU／离屏后端降档并说明差异，或返回可诊断的unsupported；不得悄悄启动GUI、返回示意图，或把不支持算作验收通过。音频对应真实片段／样本与分析数据，波形图片不能代替声音输出。

### 9.3 最小skill／SOP随能力交付

每个独立产品／模块提供可发现、版本化的最小指南，可由包文档、生成的agent指南或能力描述引用；共用流程可以链接复用，无需每个叶子模块复制长篇说明。至少包括：

1. 能力用途、版本／feature／后端要求、输入资源与前置条件。
2. 所需权限及其可查询范围；无GUI的最短可执行路径和结构化结果。
3. 准备→执行→观察→验证的SOP；长任务的查询、取消及结果获取。
4. 正确性依据：实际状态、产物、像素／音频、trace或预算；不能只检查返回成功。
5. 错误诊断、重试是否安全、部分成功如何处理，以及实际支持的撤销／恢复边界。

指南从真实契约和已验证示例维护，明确已支持与计划中的能力。它既服务外部Agent，也服务内置Agent；不绑定某个模型、供应商或GUI安装步骤。文档不能替代实现，流程中的命令／参数应由独立消费者验证。

### 9.4 多级权限、隐私与委派

开发preset默认预授权可信开发会话对所属应用／引擎实例的全部已声明开发能力，支持创建、调试、测试和profile，常规操作不逐次要求审批。开发者／用户的显式收窄与宿主实际能力仍有效；授权由可信宿主建立，不能由来访请求的`dev=true`自行升级，也不能打包继承本机开发会话。

发布应用的有效范围为**开发者允许范围∩用户配置∩宿主约束∩会话约束**；范围内的具体授权决定复用openas。用户可查询开放范围与限制原因、暂停或撤销；Agent原生入口默认存在不等于任何Agent都可无条件操作。规范中明确的人类专属条件仍须如实表达，不能伪造actor绕过；此类限制不应扩散为普通任务的GUI前置条件。

权限同时约束读取、修改和副作用；语义树、局部截图、日志、trace与导出不得泄露作用域外或被策略屏蔽的信息。配置、必要确认与撤销本身提供无GUI的可信宿主／CLI路径，不把用户决策等同于必须打开窗口。Agent→Agent委派只能在已有授权内进一步收窄，保留身份／委派链、资源范围、期限及结果，撤销与过期传播到后续操作；外部模型／服务只能收到授权范围内的观察数据。

控制面与领域热路径分离。独立库不强制依赖UI、网络、模型服务或内置AI；公开类型／操作由边界adapter映射到openas，实时执行继续遵守本域有界提交、无阻塞与性能约束。可选内置AI的feature关闭时，保留所选产品原有的双用户控制能力。

### 9.5 新增能力的评审与验收门槛

| 评审问题 | 要求的证据 |
|---|---|
| Agent能发现和直接使用吗？ | 实际能力描述、类型化操作、状态／错误／权限查询；GUI与Agent调用同一owner |
| 不启动GUI能完成整个任务吗？ | CLI／openas真实任务，从输入到保存／导出；无窗口／显示服务器前提，失败和取消可观察 |
| 视觉／声音结果可独立审查吗？ | 带版本与时间来源的真实离屏区域／音频产物；语义正确与呈现正确分别验证 |
| 动画的中间过程也通过了吗？ | 按§9.6保存时间采样、关键事件前后帧与回放；检查轨迹、形变、叠加与可读性；实时节奏和交互另验，A／B端点不能代替过程证据 |
| 人的使用体验同样优先吗？ | 可视化审查、反馈、直接控制与可访问性验证；人与Agent对同一状态的操作一致 |
| 最小skill／SOP可执行吗？ | 独立消费者运行已交付能力的流程；文档、契约与版本一致 |
| 权限配置和委派有效吗？ | dev预授权、显式收窄、release交集、撤销／委派及观察数据边界的真实验证 |
| 未使用的模块有额外成本吗？ | 纯库、headless宿主与GUI／内置AI选项的实际依赖闭包、运行资源与热路径预算 |

这些要求纳入相应模块CTS与本地验证，再接入CI；其他平台CI不阻塞已授权的本地推进。这里新增的是规范与验收要求，**不意味着现有全部引擎provider、skill／SOP、离屏后端和权限链已经交付**；实施范围继续逐项在[检查点台账](2026-11-05-system-implementation-checkpoints-design.md)记录。

### 9.6 动画以过程采样和实际播放验收

动画的交付对象包含整个变化过程。A、B端点正确，只能证明静态状态正确；参数插值正确，也不能替代像素、文字和真实交互的验证。Agent须能通过公开时间控制与同源离屏renderer审查过程，不要求打开GUI。

1. **覆盖时间轴**：记录一组有明确时间戳的真实帧，包含端点和多个中间态。采样密度随时长、变化频率和局部速度选择；短促动效、弹簧极值、快速路径及局部异常需要加密，不能固定取三张图就判定全部动画通过。
2. **覆盖事件边界**：根据场景补充delay前后、sequence接续／并行叠加、循环交界、打断／retarget、反向／seek、取消、reduced/off等关键时刻的前／后帧。纯动画可任意求值；有状态模拟须按其检查点／重建契约推进，视觉采样不得重复触发外部副作用。
3. **检查人实际看到和操作的内容**：非预期闪烁／跳变、位置与速度变化、形变和效果叠加、遮挡／裁剪、文本重影／交叉／对比度、可见控件的命中和焦点。区分正常spring回弹、像素网格步进等已声明行为与缺陷，不强制所有动画单调或连续。
4. **保存可审查证据**：工程／配置与资源版本、随机种子（如使用）、起止时间及采样时刻、camera／区域、后端、DPI／尺寸、颜色／alpha与合成背景、实际图像和判定依据。输出关键帧拼图或帧序列，并提供按时间播放的片段；保留异常帧附近的上下文，不能只选最好看的几帧。帧hash用于回归，不代替视觉评估。
5. **分开验证离线过程与实时体验**：确定性seek采样不能证明流畅性。实速播放还需检查帧间隔／丢帧、输入延迟、动画节奏和打断手感；美术与人的观感另留review结论。采样存在盲区，必要时加密或用连续回放复核，不宣称有限采样保证任意时刻都正确。

最小SOP：准备场景与时间策略→正常执行并采样→关键事件前后加密→联合语义／像素评估→反向或复现失败区间→保存帧序列／回放与结构化结果。公共时间控制、捕获与导出由原模块／adapter提供，不为每个官网场景复制采样器或播放器。后续每项动画验收按此补齐证据；本条不把既有端点测试自动升级为完整过程验收。

## 10. 全局契约的约定：准备与执行、预算

收敛方案 §5.2 里“准备与执行”和“预算”两项是约定，不是库；形状由 `mlibs.error`（D-109、D-111）和 `mlibs.time`（D-110）承载，验收由 `mlibs.cts:prepare` 的契约用例承载。

### 10.1 准备与执行

1. **准备**：`prepare(description, limits) → std::expected<Prepared, Error>`。`Error` 是 `mlibs::error::Error<领域码, 位置>`。准备可以分配、可以慢，但有界（受 limits 约束）。
2. **计划不可变、可共享**：`Prepared` 是值，复制廉价（共享不可变数据），可跨线程读；改动产生新的计划（`retarget`、`prepare` 新描述），不改旧计划。
3. **执行**（`sample`、`step`、`record`）：`noexcept`，写入调用方提供的输出，热路径不分配；同一计划、同一输入，结果逐位相同。执行失败不改动输出以外的任何东西。
4. **拒绝不部分发布**：准备或发布（例如引擎的 `play`）失败时，调用方和引擎的可观察状态与调用前相同。
5. **按种类拒绝**：描述本身错（越界、非有限值、空、矛盾）→ `invalid-argument`；超出预算或容量 → `refused`；句柄过期 → `stale`；能力不支持 → `refused`（另带能力名）。包装下层错误的码取下层的种类（`wraps`）。

### 10.2 预算

1. **词汇**：每个 owner 一个 `<名词>Limits` 结构；`max_<名词>` 约束单项（每个对象、每个轨道），`max_total_<名词>` 约束 owner 的总量（整个程序、整个引擎）。
2. **逐层汇总**：外层的 `max_total_*` 约束内层用量之和，内层的限制约束每一项，二者互不放宽。外层包含内层时**嵌入内层的 Limits**（以内层名词为成员名，例如 `EngineLimits::effects`），不重复内层字段；同名字段只在作用域确实不同（单个程序的总量与整个引擎的总量）时出现，并在注释里写明作用域。
3. **拒绝**：超出预算的码命名为 `<名词>_budget`，槽位用尽为 `capacity`，种类都是 `refused`；不成立的限制（零、超过硬上限）是 `invalid_limits`，种类 `invalid-argument`。
4. **可观察**：拒绝的文字（`text()`）说出哪一项、在哪里；预算本身可以查询（`limits()`），Agent 无需试错就能知道边界。

### 10.3 验收

`mlibs::cts::prepare::add(suite, contract, samples)` 给一个引擎加上同一组用例：每个有效描述准备两次结果相同、执行两次逐位相同且执行为 `noexcept`；每个无效描述按 `invalid-argument` 拒绝，每个超预算描述按 `refused` 拒绝，且拒绝后状态不变。首批：hanim 的程序准备与引擎发布（`modules/projects/hanim/tests/cts/prepare_test.cpp`），细胞模拟的规则准备（`modules/projects/xengine/simulation/cellular/tests/prepare_test.cpp`）。这组用例第一次运行就发现了细胞模拟的两处种类错误（通道数超出限制报成“参数错”，同一通道写两次报成“超限”）和一个缺失的码（不成立的限制），已在同一检查点修正。
