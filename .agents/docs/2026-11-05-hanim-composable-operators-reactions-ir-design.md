# hanim 可组合内核：属性、状态、反应、动画与effect IR

2026-11-05。**架构补充／review，本文的完整IR与算子尚未实现。** 承接维护者要求：对象、属性、顶点、插值、变换、动画、相机及其运动均可控制；通用动画与effect通过自由组合构成复杂表现；hanim作为独立引擎，被UI／游戏／工具使用，并按需消费共享渲染、数值计算与HPC能力。

与[通用性／GPU比较](2026-11-04-hanim-generality-style-gpu-review-design.md)、[play与组合](2026-11-04-hanim-play-api-design.md)、[整体模拟架构](2026-11-04-omui-engine-framework-architecture-design.md)配套。本稿先确定需要表达的语义与约束，API名称仍为候选，不自行新增D-xx决策。

## 1. 统一基础：类型化数据域、算子与执行计划

**控制精度可以到属性／顶点，调度粒度保持阶段／批次。** 动画和effect共享数据／算子契约：动画组织时间、绑定与输出；effect修饰匹配、路径、属性、响应或呈现。复用同一数学／算子实现，通过typed adapter进入不同阶段。

| 基础概念 | 可控制的内容 | 执行约束 |
|---|---|---|
| 对象／表示 | 对象、部件、曲线、mesh、粒子、像素／场、rig及其资源版本 | 薄身份与按需表示；不同领域保留合适的数据布局 |
| 属性通道 | 位置、速度、质量、密度、电荷、颜色、透明度、约束权重等 | 类型、单位、空间、范围、默认值、读写权及传递语义明确 |
| 选择器／mask | 对象组、部件、顶点／粒子集合、属性、区域与采样权重 | 支持静态集合和动态mask；每元素不分配独立对象或虚调用 |
| 算子 | 匹配、插值、变换、噪声、场采样、约束、材料等 | 声明输入／输出、阶段、纯性／状态、后端能力及成本 |
| 动画表达 | 原语、嵌套编排、路径、参数动画、effect及场上下文 | 构造数据无副作用，统一prepare／play和查询语义 |
| 执行计划 | 时间／通道／数据／状态／资源依赖，布局与kernel批次 | 冷准备；热路径不解释builder／脚本，不逐顶点调用用户回调 |

例如同一个noise算子，可以经适配用于路径位移、匹配代价扰动、力场或材质。基础数学复用；输出单位和作用域分别声明，不能把位移直接当成力。effect的幅值、场的位置、路径控制点、响应权重也可由同一动画系统驱动，不各建时钟。

可控制地址由公开schema、选择器、对象／表示版本和属性通道确定；细分或重映射后的临时buffer下标不冒充永久身份。控制包括动态参数、约束／组合、播放及结构编辑；改变拓扑／schema／图结构可以要求重新准备并明确代价。

本文effect指动画过程／表现修饰，与openas授权所用的action effect保持不同类型。

### 1.1 相机、运动描述与参数也作为可动画目标

相机通过同一对象／属性adapter接入；不要求先转成可绘制mesh或轮廓。相机运动、镜头参数与视图结果分别提供typed端口，复用时间、路径、插值、约束、effect和控制协议。

| 目标／端口 | 可动画或施加effect的内容 | 组合要求 |
|---|---|---|
| 相机姿态／运动 | 位置、方向、轨道、跟随目标；shake、惯性、阻尼、重力响应 | 明确局部／世界空间、旋转策略、约束与相同通道的仲裁 |
| 镜头参数 | 焦距／视场、对焦距离、光圈、曝光等所选模型暴露的属性 | 参数单位／有效范围；相互派生的参数有一个权威模型 |
| 视图输出 | camera所产生视图的blur、景深、色调、畸变等 | 属于view/render作用域，经同一renderer处理，不当作相机位移 |
| 路径／场 | 路径控制点、场位置／范围／强度与参数 | 作为普通数据目标，依赖和版本进入相同计划 |
| 动画／effect描述 | 进度、权重、速率、noise幅值及其它可控参数 | 时间依赖可审查；动态值与需要重准备的结构编辑区分 |

例如camera follow使用一条可动画路径，再叠加同一个noise内核产生局部shake，同时驱动焦距，最后在其视图输出上加材料／后处理。复杂镜头由这些能力组合；camera不单独维护一套私有tween／effect系统。

pose、look-at约束、view matrix，以及焦距／视场／传感器参数之间的派生关系必须显式。可以选择不同输入模型，但不能让两个独立写入者互相覆盖派生结果。动画控制动画参数时，时间图也检查环；反馈需要明确延迟或求解契约。

renderer消费同一采样边界的CameraView／pose／镜头快照，并拥有其渲染资源。纯相机运动求值不依赖窗口／GPU；需要景深、motion blur等输出时校验所选renderer能力。motion blur的多时间采样不能重复推进同一物理状态或重复触发业务事件。

相机／路径／参数同样可经CLI／openas查询和控制，获得计划revision、实际采样值及真实离屏视图。2D／3D相机、镜头与后处理有能力边界；尚未实现的通用camera adapter及镜头效果不记作当前交付。

## 2. 主动／被动与执行阶段是两个维度

主动effect表示明确附加到动画／对象／通道的修饰；被动effect表示环境中存在影响源，参与者凭响应属性与作用域自动受到影响。两者可以复用算子，且都可能是纯求值或有状态求解。

| 阶段 | 主动绑定举例 | 环境参与举例 |
|---|---|---|
| 匹配／对应 | 修改代价权重、保持特征、锁定点／部件、指定对应 | 准备时以环境／属性快照作为匹配策略输入 |
| 路径／几何 | 弧线、旋转流、噪声、位移、局部变形 | 区域中的解析扭曲、位移或引导场 |
| 属性／响应 | 赋予质量／阻尼／电荷／响应mask，选择刚体或粒子域 | 已声明参与的物质自动连接兼容环境场 |
| 力／约束／状态 | 显式施力、弹簧驱动、目标跟随／钉住 | 重力、风、吸引、涡旋、碰撞及区域约束 |
| 材料／呈现 | blur、tone、材料mix、折射等 | 空间区域影响颜色／材质或后处理 |

因此不以ActiveEffect／PassiveEffect两套互不兼容的引擎实现。激活／绑定方式、处理阶段、数据域、状态性、作用域是正交契约。Houdini的POP Force会修改粒子force属性，Blender场可影响多种模拟域并按权重／范围选择；这些是可参考的已有能力，不作为本项目已经实现的声明。[POP Force](https://www.sidefx.com/docs/houdini/nodes/dop/popforce.html)、[Blender Fields](https://docs.blender.org/manual/en/latest/physics/forces/force_fields/introduction.html)。

## 3. A到B的默认路径与主动修饰

设对应计划给出源点a_i、目标点b_π(i)，统一时间映射给出s(t)。无effect时，默认轨迹可为：

```text
p_guide(i,t) = P_i(s(t))
P_i(s)      = (1-s) a_i + s b_π(i)       // 默认直线；对象域可有自己的默认
```

对象根变换与局部形变分别具有坐标空间。匹配负责“谁对应谁”，路径负责“对应后怎样运动”；路径修饰不必重做对应关系。

主动effect可以分开修改匹配策略和轨迹：

```text
MatchModifier : request / candidates / costs / constraints → MatchingPlan
PathModifier  : guide position / time / id / attributes     → modified trajectory
p(i,t)        = P_i(s(t)) + w(s(t)) D(i,s(t),seed)
```

`D`可为扰动、curl noise、绕轴、沿法线偏移等。若要求端点不变，可使用w(0)=w(1)=0的envelope；若还要求不额外改变端点速度，需w的端点导数为0，且扰动与时间映射具备相应连续性。比如归一化的16s²(1-s)²可作为一种包络。离散曲线／噪声不无条件承诺C1。

匹配规则按准备阶段编译。动态修改对应策略需要新revision、对应迁移或预先准备的时变方案，不能每帧无说明地重新随机匹配。纯外观变化不使几何匹配缓存失效；真正影响匹配输入的版本／策略才使其失效。

noise以稳定载体身份、seed及明确时间输入求值，不依赖帧数、遍历顺序或隐式随机状态。新noise实现继续复用共享math／随机基础。用户函数须是已注册的CPU批次kernel或可编译的函数IR；缺少GPU lowering时如实报告能力，不逐顶点解释脚本。

## 4. 顶点／粒子的属性需要明确载体

“顶点可控”包括曲线控制点、几何顶点、表面采样点、粒子等可选择的数据域；这些载体的物理含义不相同。刚体质量属于对象／身体，粒子质量属于物质采样，Bezier控制柄默认是几何控制量。给控制柄赋质量并不能自动获得合理的物理形变。

响应属性应按模型绑定：刚体／形变笼／粒子／软体／骨骼等，通过各自adapter生成呈现。共享拓扑端点有明确别名／约束，避免独立扰动后闭合曲线裂开；重合但互不连接的点保留不同身份。

| 属性类别 | 传递／重采样要求 |
|---|---|
| 质量／电荷等总量 | 明确分配与合并规则；需要守恒的模型保持总量 |
| 密度／温度等场量 | 声明加权／重建规则及单位，不一律线性混合 |
| 速度／动量 | 与质量、坐标及求解模型共同迁移 |
| 响应权重／mask | 与物理质量分开，作为无量纲选择／影响参数 |
| 离散资源／材料身份 | 明确归属、切换／混合或birth／death策略 |

重新采样后不能简单“每顶点质量都是1”，否则细分越多总质量越大，表现随表示精度变化。可按长度／面积／体积或显式物质样本分配质量，并定义新生／消失／分合时的属性迁移。

质量和“影响权重”不同。均匀重力g作用下F=mg，理想无阻力时a=g；轻重差异可来自阻力、弹性／约束、碰撞或明确的艺术化响应模型。PhysX文档也将场景重力定义为加速度，再乘质量得到力。[PhysX Gravity](https://nvidia-omniverse.github.io/PhysX/physx/5.4.0/docs/RigidBodyDynamics.html#gravity)。本项目不借此指定某个求解器依赖。

## 5. 被动反应：属性／状态参与，环境场作为实例

环境场只是一个刺激来源。通用模型是**属性＋当前状态＋刺激／条件→反应算子→下一状态／属性／输出**。刺激可以是事件、阈值、属性改变、接触、邻域／材料组合、时间、信号或空间场。纯路径／插值仍可直接求值，不必为了统一而经过事件系统。

ReactionSpec应明确目标域／选择器、输入和读写集、predicate、触发方式（持续满足／进入／离开／上升沿／变化／一次等）、状态schema、转移／输出图、事件、时间／顺序和预算。边沿／一次／冷却／滞回有相应状态；无此需求时不分配这些通道。

例如Noita类像素材料反应可由材料／温度／燃料等状态、邻域条件与迁移规则组合；这是通用反应能力的一个场景，不将其做成内核专用世界模型。本稿不声称复现该游戏的内部算法。大规模格点反应可编译为mask／邻域／数值kernel和分阶段状态更新，不逐像素发回调或分配事件对象。

同一tick的规则读取哪个状态版本、写冲突如何仲裁、产物何时可被下一规则消费、链式反应何时继续，必须明确。可用下一tick传播，或有界多阶段／固定点求解；超预算报告，不能无限递归回调或静默漏掉权威反应。CPU／GPU误差模式也要覆盖触发判定，不能仅凭颜色误差容差宣称状态历史一致。

### 5.1 环境场是该模型的一种输入

环境提供FieldSet：场的类型、空间范围／坐标、时间、强度／falloff、版本、mask和资源。参与者有ResponseProfile：物质模型、属性schema、接受的场类型、响应系数、作用域及状态所有者。常用effect／材料配方可一次提供属性和响应profile，之后穿过区域时自动计算影响，无需为每对对象／场写碰撞回调。

纯质量元数据也可能只用于匹配或统计；是否接入场由响应契约明确。无effect／无响应者的普通动画保持默认轨迹，编译时剔除场查询和求解，不引入模拟依赖或每帧全局扫描。

场输出类型至少区分：displacement、velocity、acceleration、force、constraint target、appearance。接收者以兼容的端口连接；force除以质量，acceleration不重复除质量，velocity／displacement各有适配。场在局部／世界空间的转换、单位与缩放语义明确。

典型被动响应：区域筛选→falloff／mask→场值→物质响应→合成／约束或积分。进入／离开区域由实际所选位置域判断：解析位移可采样guide位置，动力学场采样当前状态位置。动态反馈显式进入求解阶段，避免用一个没有求解规则的DAG环表示。

区域边缘可以连续衰减，也可以明确硬边界。高速穿越需要swept范围、子步或解析交段等相应质量策略，不能只测tick两端而静默漏掉中间影响。动力学影响离开场后可保留速度／形变，直到阻尼或约束消解；不能统一在出区域时清零。

## 6. 先定义路径与场的共同控制方式

| 模式 | A→B与场的关系 | 终点语义 |
|---|---|---|
| authored／kinematic | 以 authored轨迹为准；需要的解析路径修饰显式组合 | 可保证按契约到B；外力不会隐式改写钉住状态 |
| guided／受约束响应 | A→B给出目标／引导，场和约束共同决定当前输出 | soft target、精确到达或自由结束分别声明 |
| dynamic／物理驱动 | 场／碰撞／约束推进实际状态，B可以作为可选目标驱动力 | 不保证指定时刻正好到B |

不能先写死p=lerp(A,B)，再期待同一position通道同时服从自由动力学。guided模式可选择弹簧／PD驱动、轨迹约束或端点保持的视觉形变；这些算法由对应模块提供，不在每个effect里手写一份求解器。

“场明显改变运动＋规定时刻精确到B”需要显式边界策略：平滑包络、回归段、约束／优化求解等。不能最后一帧强制跳到B并称为连续；障碍或预算使要求不可满足时，按契约失败、延长或选择明确替代。纯物理与艺术化引导分别报告。

响应模式、到达／回归策略属于动画／求解描述，影响准备；播放config仍负责速率、暂停等控制，不用默认值暗中改写这些语义。

## 7. 完整IR：保留多视图并编译成批次

作者表达保持对象／动画／effect／环境关系；语义IR保留作用域；编译后才生成按域／kernel分组的执行与资源计划。分轨数组可作为一种调度视图，不能成为唯一事实来源。

~~~mermaid
flowchart TD
    Input[对象版本／动画／effects／环境] --> Typed[类型／单位／空间／作用域校验]
    Typed --> SourceAttrs[源与目标属性／匹配策略]
    SourceAttrs --> Match[匹配／对应计划]
    Match --> Transfer[载体与属性迁移]
    Transfer --> Guide[时间映射／引导路径／主动修饰]
    Fields[版本化环境场] --> Sample[区域筛选／场采样]
    Sample --> React[条件／trigger／反应]
    Stimuli[事件／接触／邻域／属性变化] --> React
    Guide --> Response[响应／约束与状态计划]
    React --> Response
    State --> React
    State[显式tick输入状态] --> Response
    Response --> Next[下一状态／当前几何与属性]
    Next --> Render[共享材料／效果／渲染图]
~~~

循环通过State[n]→State[n+1]等显式时间边连接，不用普通无约束回边。一个OperatorSpec至少声明：

- 稳定算子ID／版本，输入输出的域、类型、单位、空间、布局与数量关系；
- 属性／资源读写集、别名和组合规则、执行阶段与时间域；
- pure／stateful类别、状态schema、检查点／重建能力与事件语义；
- CPU／SIMD／GPU kernel能力、scratch／资源及数值／误差要求；
- 选择／mask、作用域、边界／reach、与原动画及对应关系的依赖。

IR因此需保留Bindings、Correspondence、Attributes、Time/Channels、EffectScopes/Responses/Triggers、State与Resources/Execution等互相关联视图；FieldSet是刺激／数据输入之一。写同一通道的算子有明确顺序／混合／求解关系。force／acceleration可按契约累计；位移合成、形变warp和后处理通常不能任意交换。权限和资源硬限制仍取有效约束。

源属性的准备、匹配后的载体属性迁移、运行时属性更新分别建模。例如匹配代价可读取源质量，而新采样点的质量由对应和分配规则生成，不能把这两个阶段混成循环依赖。

每项参数都可被控制，不意味着所有变化成本相同：幅值／强度等可走动态参数块；改变算子结构、属性schema、匹配或状态模型需要重新准备／迁移。控制入口、失效原因与计划revision可查询。

## 8. pure采样与stateful求解的时间契约

解析noise／路径／空间颜色场可由冻结输入直接sample(t)。状态力场采用固定tick的状态推进，或已有解析解／烘焙结果；重建需要输入历史、场／参数版本、seed、dt、求解器版本及检查点。主动／被动都可能属于任一类别。

hanim.core继续提供时间及显式不可变输入的纯求值；状态推进和数值求解由独立模拟／反应模块提供，hanim编排状态边或消费其结果。不能在纯插值内部暗中按帧积分。

环境时间与动画局部时间分别绑定。相同动画t、不同场景tick可得到不同合理结果；重现必须固定完整输入，不能暗读墙钟。seek接口报告direct、cached、replay-required或缺少历史；不能给有状态场承诺任意时刻O(1)计算。

状态区分owned visual state与external simulation domain。对独占状态可按计划控制；对共享外部世界，暂停动画驱动、暂停世界、恢复物理检查点和业务undo分别操作并受所有权限制。动画结束、模拟尾部消散和资源释放也分别定义。

重建状态反应与向外投递事件分开。seek／倒放／重复sample不得重复触发外部业务动作、网络请求或播放声音；事件投递有身份、幂等与明确的重放策略。

retarget以当前实际输出及所需速度／属性／状态为源。对应变更需要状态迁移；异步准备在提交时核对版本或rebase。场／求解状态不能靠一张当前颜色截图完整恢复。CPU暂存失败原子性也不等于外部物理世界、GPU与业务数据自动全局回滚。

## 9. 局部模块与全局复用的归属

| 所有者 | 应承担的职责 |
|---|---|
| 中立的IR／算子契约 | 动画库、effect库、编译器和后端共同的类型／端口／状态／能力描述，不依赖UI或具体RHI |
| hanim.core／共享math | 时间、数值、插值与确定性基础；继续遵守core只依赖标准库与math的边界 |
| hanim.object／领域adapter | 对象／载体／属性／版本与外部表示连接，不把renderer句柄或UI实现塞进纯契约 |
| hanim.library／hanim.effect | 动画／修饰／响应配方与对应算子，复用同一底层实现 |
| hanim.program／engine | 唯一编译／计划／控制体系；单对象便捷调用和复杂图同一播放器 |
| 通用数值／HPC／空间／模拟模块 | 字段、批量kernel、索引、积分／约束及检查点等公共能力，各自独立可复用 |
| renderer／RHI | 唯一设备、资源池、材料／呈现、compute／render提交及读回 |
| UI／游戏／工具 | 普通消费者、状态／输入／业务与交互语义，经公开adapter调用hanim |

为避免effect→program→effect循环，应让共同契约位于两者之下。可评估提取独立、可裁剪的hanim.ir（候选包），程序编译器仍由现有program演进；旧结构只做兼容适配，不同时维护第二套IR／匹配／播放器。core不因IR提取反向依赖UI／RHI／模拟。确定边界后才创建包，不先堆空壳模块。

FieldSet由所选环境／模拟域提供，hanim注入其视图与时间绑定；空间索引、属性存储、solver和RHI资源均复用公共能力。mcpp是构建／GPU与HPC插件工具，运行时算子由独立库提供。

跨帧数据反馈通过版本化端口／历史资源连接，包依赖保持单向。由中立契约、adapter和宿主组合连接引擎，不让UI／renderer／core直接互相import。相机曝光读取上一帧亮度、场影响下一tick运动等也遵守这条边界。

## 10. 性能、可观察与实施顺序

常量属性可broadcast，需要逐元素时才分配SoA通道；载体ID／属性／mask批量处理。区域／chunk／swept bounds筛选后采样候选场，静态对应缓存复用。没有效果时剔除相关节点、属性、场与求解工作。

GPU路径按能力融合相容的匹配／插值／场／效果kernel，几何／状态尽量驻留设备并供同一renderer消费；CPU保留参考及低延迟路径。严格求解／反馈有明确pass与同步，不能为少一个dispatch改变算法；设备选择、误差、分配、上传／读回和GPU时间分别计量。

Inspector／CLI／openas查询同一计划：某对象／顶点的对应、路径、属性、场权重及实际影响来源。大场景默认导出汇总和范围查询；逐点解释和真实离屏像素按有界请求采样，避免每帧全量JSON。

建议实施顺序：共同IR契约及编译校验→迁移当前严格morph／render效果适配→首批通用匹配修饰与路径扰动→属性／响应／条件与刺激（场是其中一例）→有状态反应／求解适配及检查点→GPU批次及真实消费者。相机／参数目标以同一协议接入。全程保持一个编译器／播放器与已有默认路径；UI迁移、40公共动画和20创意组合依此消费，完整原目标保留。

必需验收：无effect默认结果／成本；改匹配规则但对应合法；路径扰动端点／切线／seed及乱序seek；属性细分与质量守恒；区域／事件／阈值／邻域反应、边沿／持续／冷却与冲突；相机pose／镜头／视图作用域；刚体／粒子响应区别；离场后的状态；到达策略；完整输入重放／retarget状态迁移及外部事件幂等；CPU／GPU与实际区域像素；失败／能力不足／预算及纯模块依赖闭包。

当前源码核对：EffectSpec只有id及from/to数值参数链，ProgramKind只有binding／sequence／parallel／stagger等首批形变编排。尚无上述通用匹配modifier、路径kernel、属性schema、FieldSet、状态solver、完整作用域IR及hanim GPU evaluator。本稿为升级基线，不能把现有参数链改名后记作这些能力已交付。
