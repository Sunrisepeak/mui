## 1. 目标

**把框架和引擎的核心能力做到远超同类，用项目官网作为验收：官网的每一个维度经 codex 真实使用评估达到 90 以上。**

- 范围是本轮讨论定下的全部内容；按检查点 C0–C6 验证推进，不分批砍范围（D-91）。
- 不达标的作品不上官网，进[待办](2026-11-01-openmui-strategy-backlog-design.md) §4。

## 2. 定位（D-92）

| | 亮点 | 证明 |
|---|---|---|
| 基础 | **一棵语义树**：像素、无障碍、agent、测试是它的不同渲染 | 透视镜 |
| ① | **agent 原生且安全**：语义协议直接控制（不是 computer use）；openas 的效果、授权、撤销、日志；用户叫自己本机的 agent 就能操作任何 openmui 应用 | 访客的 agent 操作官网 |
| ② | **时间与确定性**：任意时刻可重现，逐位相同；倒放、回放、回溯；操作变测试 | 时间旋钮、即时回放、回溯条、哈希对照 |
| ③ | **通用动画**：组件 × 效果 × 动画任意组合，任意组件之间的变形达到 manim 的粒度，结果因组件本身而异 | 变形实验室、爆炸对比、动效工作室 |
| 前提 | **处处都快**：ESP32 到独立显卡，自动适配，开发者和用户可控 | 档位演示、对比基准 |

原则：**代码即一切**。

## 3. 总体架构

**2026-11-04 维护者补充的整体架构 review：**[独立引擎／UI／Agent 与高密度模拟](2026-11-04-omui-engine-framework-architecture-design.md)及 [hanim 完整产品](2026-11-04-hanim-animation-library-playback-design.md)将独立动画产品、共享 renderer、UI 普通消费者、rig／physics／fluid、硬件加速、Agent 控制与可观测性一并展开，并将 Noita 类像素反应负载纳入基础设施验收。下面原表中“hanim 仅时间内核、通用动画归 UI”的职责划分须按新契约迁移，不能据此收窄维护者目标；具体新包／接口仍为讨论稿，规范变更另走 OpenLifa 流程。

```
┌──────────────────── 作品与官网 ─────────────────────────────────┐
│ 官网（唯一验收对象）· 场景 · 影片是程序 · 时间线编辑器           │
├──────────────────── mgame（引擎）───────────────────────────────┤
│ 确定性 ECS · 模拟时钟 · 物理 · 输入 · 回滚联网 · 语义投影          │
├──────────────────── openmui（框架）─────────────────────────────┤
│ 模型   语义树 │ 组件 · 效果 · 动画（三维三级）│ 物质 │ 槽+策略 │ 时间 │
│ 编排   结构（builder / view 文档）· 时间（时间线文档）             │
│        帧（管线 DAG）· 策略（风格包 · 动效设定 · 档位）            │
│ 插件   组件 · 效果 · 动画 · 匹配器 · 渲染特性 · 宿主 · 后端 ·      │
│        编解码 · 脚本 · 传输 —— 每种：CTS + trace + 日志 + 代价声明 │
│ 授权   openas：actor · 效果 · 授权 · 撤销 · 日志 · 回溯           │
│ 接入   agent-link（Web 默认）· omui page / connect · agent.md      │
├──────────────────── 独立组件（modules/）─────────────────────────┤
│ base：math · hash · hanim · session · trace                        │
│ gfx：rhi · shader · raster · render（+ vector · particles）        │
│ content：text · layout · i18n · markdown │ media                   │
└──────────────────────────────────────────────────────────────────┘
```

**一帧的管线**（D-66 扩展；新增的三个阶段加粗）：

> 输入 → 状态 → 布局 → **物质提取 → 匹配 → 动画求值** → 效果链 → 光栅化 / GPU → 呈现

**构建配置档和运行档位**：规范里的发行版配置档（mcu / embedded-linux / mobile / full / engine / headless）决定**编译进来什么**；运行档位 T0–T4 决定**在配置档的上限内用多少**。对应关系：mcu ↔ T0，embedded-linux ↔ T1，mobile 和 Web ↔ T2，full ↔ T3、T4。

## 4. 新包放在哪里

遵守路径即包名（D-80）、依赖只向下（D-82）、独立组件不依赖 openmui（D-55）。

| 内容 | 包（路径） | 依赖 |
|---|---|---|
| 物质表示、匹配器、槽和策略、`morph`、组合动画库 | `openmui.motion`（`modules/ui/motion`） | view 的公开接口和管线的阶段接口；view 不反向依赖它，阶段插件由它注册（默认装上） |
| 时间映射、编排 | `hanim`（已有；`TimeMap`、`Timeline`） | 只依赖标准库和 `openmui.math` |
| 粒子和碎片 | `openmui.render.particles`（`modules/gfx/render/particles`） | render、rhi、shader；独立组件 |
| 代价声明、档位、预算调度 | `openmui.pipeline`（契约⑦扩展）+ 宿主的探测 | — |
| agent-link | `modules/ui/host/web` 的插件 | 总线、openas |
| 本地桥和 `omui page` | `openmui.cli`（`tools/cli`）的子命令 | agent 协议 |
| 交互扫描 | `openmui.cli` 的 `omui sweep` | agent 协议 |
| 新组件 | `components/base`（扩充）、`components/data`（表格、树）、`components/editor`（代码编辑器） | 契约优先：先写 `*.contract.omui.toml` |
| ESP32 宿主 | `openmui.host.esp32`（`modules/ui/host/esp32`） | 原生单元经 mwrap 用 ESP-IDF 的 C 接口 |

**规范的改动**（在 `spec/` 子模块里提交，推到 `openmui-design` 分支，按 D-78 的身份）：

- 语义里过渡中的状态（`animating`、离开中的节点不在树里）；
- 契约⑦的代价声明；
- agent 协议的 HTTP 长轮询传输绑定和配对；
- `rewind` 动词和按 actor 回溯的语义。

## 8. 规则（全部继续有效，这里列出和本轮最相关的）

- 不用宏，平台和特性用模块分区 + constexpr；全仓库只有 `spec/include/openmui.h` 一个头文件。
- 核心不用异常和 RTTI，用 `std::expected`；热路径没有虚函数，每帧零分配。
- 插件按阶段、按批调用，不按节点、不按像素；每个插件种类有 CTS、trace 类别、日志类别，现在再加**代价声明**。
- 脚本永远不进入每帧路径——片段脚本和组件脚本只声明。
- 组件契约优先，绑定由生成器产出；**组件不写动画**（lint `motion`）。
- 动画、布局、光栅器不用 fast-math 和浮点收缩；确定性数学在 `openmui.math`，随机数种子可追溯。
- 第三方 C 库经 mwrap；不用 GPL / AGPL。
- 平台相关代码经 `mcpplibs.os`；窗口和输入经 SDL3（桌面），ESP32 经它自己的宿主。
- 单一 PR（`openmui-design`），一个 commit 一个对象，全平台 CI 通过才推。

| 风险 | 影响 | 应对 |
|---|---|---|
| ESP32 上的 C++23 模块：xtensa 的 GCC 和 mcpp 的交叉构建是否支持；512 KB SRAM 能否装下运行时 | W9 可能卡住 | C1 先做工具链 spike；mcu 配置档只编译必需的部分；用 PSRAM；不行时换 ESP32-P4（RISC-V），作为 spike 的备选 |
| 动画迁移让所有展示的像素固定和 README 媒体变动 | CI 和固定值大面积改动 | 迁移时尽量保持画面等价；按检查点批量重新固定，每张都看过 |
| 官网 wasm 随展示增多变大 | 首屏预算 | 按页资源；重型页面单独加载（Q-38）；撤下不达标的作品 |
| GPU 结果在不同显卡之间不逐位相同 | "你的哈希 = CI 的哈希"不成立 | 对照用语义树哈希（与档位、GPU 无关）和 **CPU 参考渲染**的像素哈希（同一档位）；首帧图由 CPU 参考渲染，浏览器用 CPU 路径画第一帧，之后再切 GPU |
| 粒子和形状变形的观感 | "高质量"打折 | 匹配器只在有意义时变形；动效原则写进风格包；像素测试和人复核 |
| headless Chromium 里 WebGPU 跑不了 | 评估的 GPU 维度 | 有 GPU 的 runner，或本地 lavapipe（已有 `tools/ci/gpu.sh`）；记为已知限制 |
| 浏览器限制本地连接（Safari、Chrome 的本地网络权限） | 访客路径 | 先直连，失败时 agent 改用 `--serve`（Q-36 已定） |

## 10. 决策和待决

- 决策：D-91..D-98（[总体架构](2026-10-26-openmui-architecture-design.md) §13）。
- 已定：Q-32（GPU 自定义默认要有 CPU 参考实现；只有 GPU 版的声明 `deterministic = false`、不参与像素固定）、Q-35（ESP32，首选 ESP32-S3）、Q-36（先直连，失败改用 `--serve`）。
- 实测中：Q-33（player 和三个脚本宿主编译到 wasm，C2 前）、Q-34（首屏预算的最终数字，C2）。
- 新增：Q-37（按 actor 回溯的依赖规则）、Q-38（重型页面：Emscripten 动态链接，还是单独程序加页面跳转，C3 前由体积分析定）。

## 11. 自我评审

写完五份子设计后通读一遍，发现并处理了这些问题：

| # | 问题 | 处理 |
|---|---|---|
| 1 | "你的浏览器算出的哈希 = CI 的哈希"和"首帧图与浏览器第一帧逐像素相同"没有考虑档位和 GPU：不同显卡的 GPU 输出不逐位相同，不同档位的画面也不同 | 对照改为语义树哈希 + CPU 参考渲染在同一档位的像素哈希；首帧由 CPU 路径画（§9）；改了[定位](2026-11-01-openmui-positioning-site-design.md)和[性能](2026-11-01-openmui-performance-tiers-design.md)里的说法 |
| 2 | 新内容放在哪个包没有写，容易破坏分层 | 本文 §4；`openmui.motion` 通过管线阶段接口挂入，view 不反向依赖 |
| 3 | 动画迁移会让展示的固定值大面积变化，子设计没提 | §9 风险；迁移以画面等价为目标，批量重新固定 |
| 4 | 规范要改的部分（过渡中的语义、代价声明、传输绑定、回溯）没有列出 | §4 末尾；按 D-78 在子模块里提交 |
| 5 | 配对码的强度没写：本机的其他进程可能猜 | 配对码 8 个 base32 字符（40 位），桥和页面都限制尝试次数，10 分钟过期（[agent 接入](2026-11-01-openmui-agent-connect-rewind-design.md) §3.1） |
| 6 | 运行档位和规范里已有的发行版配置档是两套说法 | §3：配置档决定编译进什么，档位决定用多少，并给出对应关系 |
| 7 | 实验室、现场改代码要带三个脚本宿主，影片要带全部场景，都进主 wasm 会撑爆首屏 | Q-38；按页加载；C3 前定拆分方式 |
| 8 | 加载时 JS 画的语义树结构图和框架自己的"语义树镜头"是两套画法，变形接管时会跳 | 加载脚本按框架树镜头的同一份几何（构建时导出）画；接管时从树镜头变形到像素，是框架已有的镜头过渡 |
| 9 | 交互扫描会碰到不可撤销和对外的动作 | `omui sweep` 在全新状态里跑，先 dry run，可撤销的做完撤销，不可撤销和对外的只验证会要求确认、不执行 |
| 10 | 策略文档写的是"五份设计文档" | 改为六份（含本文） |
| 11 | 待办里的作品（格斗、打砖块）是否也算"全部要做" | 不在本轮范围；本轮范围是这次讨论定下的内容，待办里的事项暂停，C6 之后再排 |
