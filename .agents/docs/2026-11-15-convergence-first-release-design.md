## 0. 核心点（review 入口）

1. **发布范围由四个贯穿切片推导**（D-189）。一个切片是一个真实作品，纵穿多个引擎；引擎进发布的范围就是切片实际消费到的公开能力。四个切片：**应用**（文档墙、风格画廊）、**Agent 与 Live Design**（例子 13 与 07、冷启动任务、宣传片）、**2D 世界**（Kiln、组件打砖块）、**3D 世界**（Quay，Web 是它的一级平台）。
2. **三个互相独立的标注，单位是能力**：**稳定性**（稳定／预览／实验，§2.1）说接口承诺与过哪一套门；**验证状态**（实机／软件／未验证／不支持，§2.5，D-201）按平台说这项能力被什么证据支持。质量门对稳定与预览是同一套。
3. **实验模块随发布，如实标注**（D-199）：基本门是一级平台能构建、一条无头验证、README 写明目标、差距、已知局限、毕业条件。
4. **没有实机的，按契约做好并标“未验证”**（D-201）。未验证的格子不算通过，不能作为任何对外声明的证据，逐格列进发布说明；它不阻塞发布。macOS 的窗口上设备、Direct3D 12、无障碍桥与输入法的真机、集成显卡上的帧率都按这条处理。
5. **开发策略**（D-200）：核心功能优先；检查点的验证在后台；CI 的全量通过只在阶段节点与发布候选上验证，也在后台；最多并行一个子 Agent。
6. **推进按两个方向交叉**（§3.3）：功能沿切片纵向做（风险高的先做：3D → 2D 世界 → 应用 → Agent），收口沿层次横向做（自下而上：mlibs → xrender → hanim → omui → xengine → 作品），下层的接口先定，上层再收。同时在做的功能切片只有一个。
7. **收敛用八个计数器衡量，节点上只许变好**（§3.3）：包数、开着的红灯、lint、STATUS 行数、调试配置体积、未验证的格子、没有证据的声明、收口清单的通过数。范围只减不增；改标注是调整范围的唯一方式，每次都记录。
8. **文档各有唯一的职责，更新时机固定**（§3.4，D-202）：检查点更新 STATUS 的一行与提交正文；节点写一块节点记录并把已完成的行归档；决策变了才改本文并升版；规范才进 AGENTS。
9. **实施拆成 60 个任务，各有依赖与验收**（§7）：RC0 对账与现行化 → RC1 结构 → RC2 功能（N2a）与收口（N2b）→ RC3 工具、体验与文档 → RC4 作品与对照 → RC5 发布。关键路径是 RC0.2 → N0 → RC1.1 → RC2 的 3D 平台任务 → N2a → API 复查 → N2b → RC4 → RC5；发布通道（RC3.1）在 RC1.1 之后即可并行。预计约 150–200 个检查点。
10. **发布门十条，全部机械可查**（§8）：节点全绿、lint、收口清单、D-187 的帧率、开发者体验的四个数、三个冷启动任务、声明重跑、模板与例子从发布物构建、发布物齐全、规范打 tag。

**状态**：D-189–D-202 全部已确认；下一步是 RC0（§7.2）。

## 2. 发布的含义与范围

**目标。** 一个人或一个 Agent，在一级平台的任意一台机器上，用一条命令装上 `omui`，十分钟内做出一个带窗口、可被 Agent 操作、可无头测试的应用；并能装上、运行、读懂四个切片的作品，看到这套体系在 UI、动画、2D 世界、3D 世界上各自成立。

**非目标。** API v1 冻结（AGENTS §1 的毕业标准不因 0.1 满足）；任何实验模块达到它的顶级目标；官网完整重构（D-197）；M7 的“CI 稳定四周、多数维度领先”。

### 2.1 两个轴，三种标注（D-189）

| 标注 | 质量 | 稳定性承诺 | 对外声明 | 可以被谁依赖 |
|---|---|---|---|---|
| **稳定** | 全部质量门（§8） | 0.1.x 内源码兼容；规范层面的名字按规范版本 | 进声明台账 | 所有 |
| **预览** | 在声明的范围内，全部质量门——窄而完整 | 接口会变，变更逐条写进发布说明 | 进声明台账，范围写明 | 预览、实验、作品 |
| **实验** | 基本门：一级平台能构建；一条无头验证说明原理成立或基本可用；README 的“实验”节 | 无 | 不进台账；文档单列“实验”页，写目标与差距 | 只有实验与作品 |

- **单位是能力**：每个项目 README 的特性表里一行一个标注。包在 manifest 里写它默认公开面的标注（`[package.metadata.openmui] maturity = "stable" | "preview" | "experimental"`），包内个别能力低于包的，在特性表里单独标并由 feature 隔开。
- **lint `maturity`**：稳定不依赖预览或实验，预览不依赖实验（默认 feature 的闭包）；与分层 lint 是同一种检查，换一张表。
- **实验不是垃圾桶**：每个实验模块必须写毕业条件（到预览需要什么）；没有无头验证的不能标实验，只能不进发布。

### 2.2 四个贯穿切片：全局 × 局部

全局视角问：每个引擎是否都过同一套契约。局部视角问：每个引擎的招牌场景对它的最强者如何。切片是两者的交叉——一个作品纵穿多个引擎，同时检验契约与各自的水准。

| 切片 | 作品 | 穿过的引擎 | 它证明的全局主张 |
|---|---|---|---|
| **应用** | 文档墙、风格画廊；12 个例子 | omui、hanim、xrender 2D、mlibs、mpal | 一棵语义树多种渲染；动画只在 hanim；D-188 的缩放 |
| **Agent 与 Live Design** | 例子 13、例子 07；三个冷启动任务；宣传片（设计回放成为作品） | omui、`mlibs.agent`、hanim、命令行与 MCP | 人与 Agent 双第一优先级；端点自带引导；应用即设计器 |
| **2D 世界** | Kiln、组件打砖块 | matter、cellular、2D 刚体、audio、runtime、playtest、桥 `xengine.ui` | 物理管运动化学管状态；世界是值（分叉试玩）；因果可查；游戏无头、不依赖 omui |
| **3D 世界** | Quay | xrender 3D 核心、rigid3、导航、骨骼、粒子、空间音频、视口节点、Agent 玩家 | CPU 与 GPU 同一份契约；界面里的世界；人和 Agent 平等地玩 |

引擎进发布的范围 = 切片消费到的公开能力的并集，加上它们的契约。切片没有用到的能力，默认是实验，除非它自己过了预览的门。

### 2.4 按 D-185 的三级次序：发布这件事本身怎么做

| 级 | 试了什么 | 结论 |
|---|---|---|
| ① 原始性创新 | 发布范围与验收能不能用上本体系独有的东西：主线与验证线、Agent 在最底层、端点自带引导、一切可无头重现 | 采用三项：**范围由贯穿切片推导**（作品本来就是验证线，让它同时成为范围的定义）；**Agent 冷启动作为发布门**（D-192）；**声明即证据**（D-193）。都建立在已有的东西上（D-186 的冷启动测量、mtest、`tests/bench`、领先度台账） |
| ② 前沿加组合 | 能力级的成熟度标注作为依赖规则；构建溯源与校验和（`omui.yml` 已有） | 采用：标注进 manifest 与特性表并由 lint 把守 |
| ③ 业界通行 | 语义化版本、变更说明、候选版本、平台分级、实验性标记 | 采用作为底：`0.1.0-rc.N` → `0.1.0`；`CHANGELOG.md` |

### 2.5 验证状态：按契约做好，没有实机的如实标注（D-201，已确认）

**原则。** 一项能力在某个平台或后端上，按契约把理论上能做的做完整、做对；拿不到实机或运行环境来验证的，不因此不做，也不因此算通过——标“未验证”，写明缺什么。

| 状态 | 含义 | 在套件里 | 能否作为声明的证据 |
|---|---|---|---|
| **实机** | 在真实硬件或真实系统服务上跑过（RTX 4080、真实浏览器的 WebGPU、真实的读屏器） | 通过 | 能；性能数字只认这一档 |
| **软件** | 在软件实现或虚拟设备上跑过（lavapipe、SwiftShader、WARP、Apple Paravirtual） | 通过，注明设备 | 能证明正确性，不能证明性能 |
| **未验证** | 实现按契约写完，自身的单元与 CPU 参考对照通过，但这条路径在该平台没有可用的运行环境 | 跳过，写 `unverified: <缺什么>`，不计入通过 | 不能 |
| **不支持** | 能力查询返回不支持 | 跳过，写 `unsupported: <能力>` | 不适用 |

- **数据**：`docs/platforms.omui.json`——能力 × 平台（后端）一格一个状态，带证据（用例名、设备名、日期）或缺的东西；用户文档的平台表由它生成。领先度台账已有的 `pending_hardware` 并入“未验证”。
- **规则**：未验证不是失败，也不是通过；它不阻塞发布，逐格进发布说明。一级平台上稳定级能力的未验证格子要写明拿到环境后跑哪条用例（毕业条件）。CI 行上“必须有设备”的开关只约束该行确实有的那一类设备；行上没有的环境（窗口服务器、真机读屏器）对应的用例是“未验证”，不是红。
- **当前已知的未验证或待定**：

| 能力 | 平台 | 现状 | 处置 |
|---|---|---|---|
| 窗口里由设备画（`quay.desktop`） | macOS | CI 的行离屏设备可用（Apple Paravirtual，`device_test` 通过），窗口路径报没有后端 | 先查根因：若是实现的缺陷就修；若是行上没有窗口服务器，窗口路径标未验证，离屏路径是软件 |
| 设备后端 Direct3D 12 | Windows | 元胞内核在 WARP 上有一处与 CPU 不一致（红灯 11） | 这是失败不是未验证：修，或 Windows 上只声明 Vulkan，Direct3D 12 标不支持 |
| 无障碍桥真机 | Windows（UIA）、macOS（NSAccessibility） | Linux 的 AT-SPI 有 CI 用例 | 行上能起服务的写用例；不能的标未验证 |
| 输入法真机 | 三个桌面 | 有合成事件的用例 | 标软件；真机未验证 |
| D-187 在较弱机器上的 60 帧 | 集成显卡、移动设备 | 只有 RTX 4080 与浏览器的数据 | 浏览器是实机；集成显卡与移动设备标未验证，数字不写进声明 |
| Android 真机 | Android | CI 只构建与模拟 | 未验证（二级平台） |
| 手柄 | 全部 | 合成事件 | 标软件 |

## 3. 开发策略与收敛期的规则

### 3.1 开发策略（D-200，已确认）

1. **核心功能推进优先**。每个阶段内的次序：切片缺的功能 → 收口清单 → 文档。测试与验收的时间不超过约 1/4。
2. **检查点的验证在后台**。每个检查点只跑它触及的最小范围（所属包、直接消费者；GPU 包加 lavapipe 与真机各一次），经 `omui-devtools govern`、`--profile ci`，放后台；等待期间继续做不依赖它的工作，不编辑后台构建还没编到的包。
3. **CI 的全量通过只在节点验证**。阶段节点（RC0–RC5 的退出）与发布候选各等一轮完整 CI，由后台任务取回各行结论；节点之间推送照常，红灯记入清单并在后续检查点按根因修，不阻塞。等待 CI 的时间不算工作。
4. **最多并行一个子 Agent**，只用于与主线不相交的一条功能线，在它自己的 worktree 里；派出前核对磁盘；主线与子 Agent 的负载合计不超过本机 90%。
5. **检查点的大小不变**：一块完整的工作一个检查点；提交主题行不超过 100 个字符，范围与验收依据写在正文。

### 3.2 冻结方向，不冻结功能（D-190）

- **不开**：新的引擎、新的品类、第五个切片、新的作品。
- **照常做**：切片范围内缺的功能；实验模块到“基本可用”所需的功能；修红；收口；删减。
- **新能力的入口**：它属于某个切片的范围，或是某个实验模块的基本门，或挡住某条发布门。提交信息写明是哪一条。
- **在途工作的处置**：R11（热按质量与表面）继续，作为 Glade 实验模块的已知局限的解决路线，不是发布阻塞项——它没有结论时，量级问题连同实测数字写进实验节；T5.8b（Glade 无头与 Agent）做完，它就是 Glade 的基本门；红灯 97、R12 照做；M6.3 保真度表余下的场景、T5.8c–f 排在 0.1 之后或由子 Agent 的那一条线承担。

### 3.3 推进与收敛的规则（D-202，已确认）

**两个方向交叉推进。**

| 方向 | 做什么 | 次序 | 理由 |
|---|---|---|---|
| 纵向（全局）：沿切片 | 功能——切片跑通还缺的东西 | 3D 世界 → 2D 世界 → 应用 → Agent 与 Live Design → 实验模块的基本门 | 风险高、平台问题多的先暴露；应用与 Agent 一侧最成熟，放后面不耽误 |
| 横向（局部）：沿层次 | 收口——API 复查、错误出路、契约套件、基准、对照 | 自下而上：mlibs → xrender → hanim → omui → xengine → 作品 | 下层的接口先定，上层只收一次；与“依赖只能向下”同向 |

功能先于收口（节点 N2a 在 N2b 之前）：收口要对着已经定型的功能做，否则复查两遍。

**在制品上限。** 同时在做的功能切片一个；后台最多一条构建或测试、一个 CI 观察；子 Agent 最多一个，做与主线不相交的任务（§7 标了候选）。

**收敛的计数器。** 每个节点记录一次，写进 STATUS 的节点记录；除注明的外只许变好，变差要写原因并在下一个节点前恢复。

| 计数器 | 现在 | 0.1 的目标 |
|---|---|---|
| 包数 | 175 | ≤ 130 |
| 开着的红灯（一级平台，稳定与预览级） | 十余行 | 0 |
| lint 问题 | 0 | 0（含新增的 5 条） |
| STATUS 行数 | 407 | ≤ 200 |
| 调试配置体积 | 22 GB | ≤ 12 GB |
| 未验证的格子（一级平台） | 未统计 | 只减不增，逐格有毕业条件 |
| 没有证据的对外声明 | 未统计 | 0 |
| 收口清单的通过项（稳定与预览级，共约 12 个项目 × 10 项） | 未统计 | 全部，例外逐条写明 |

**范围的规则。**

1. 切片的范围只减不增；新发现的需求进 0.2 的清单（STATUS 末尾一节，一行一条，带发现它的任务号）。
2. 调整范围只通过改标注（稳定 → 预览 → 实验，或某平台 实机／软件 → 未验证／不支持）；每次改写进节点记录与发布说明。
3. 缺口回 owner 修（AGENTS §2 第 3 条）；作品里不写引擎代码；在下一级补上一级的缺是绕开（D-179）。
4. 一个任务超过它估计的两倍时停下来写三行：卡在哪、试过什么、是继续、换做法还是改标注——然后才继续。

**节奏。** 每个任务一个或几个检查点；每约 20 个检查点一次整体自我 review（AGENTS §6），结论进节点记录；每个节点重估下一阶段的检查点数。

### 3.4 文档的记录规则（D-202，已确认）

**每份文档一个职责，同一件事只写在一处。**

| 文档 | 职责 | 何时更新 | 形式 |
|---|---|---|---|
| `AGENTS.md` | 规范 | 一条决策成为长期规范时 | 一两句，带 D 编号 |
| 本文 | 发布的范围、规则、任务与门 | 决策变了，或节点上发现计划与事实不符 | 升版，版本记录写一行；任务表只改状态以外的东西（范围、依赖、验收） |
| `STATUS.md` | 进度：当前阶段、任务状态、节点记录、开着的红灯、能力矩阵、0.2 清单、下一步 | 每个检查点 | 任务一行：状态、证据指针（提交号、用例或基准名）、一句结果；≤ 600 个字符；全文 ≤ 200 行 |
| `STATUS-archive.md` | 已完成阶段的任务行、已关的红灯 | 节点 | 原样移入 |
| 提交信息 | 这一个检查点做了什么、怎么验的 | 每个检查点 | 主题行 ≤ 100 个字符；细节、数字、发现都在正文 |
| 项目 README | 一句话定义、特性表与标注、Agent 面、接口、已知局限、实验节 | 能力或标注变了的那个检查点 | 特性表一行一项能力 |
| `docs/platforms.omui.json` | 验证状态（§2.5） | 某格的证据变了 | 数据；平台表由它生成 |
| `docs/claims.omui.json` | 对外声明与证据（§6.4） | 加、改、删一句对外的话 | 数据 |
| 领先度台账、评估台账 | 并排对照的结论 | 做了一次对照 | 追加一行 |
| `CHANGELOG.md` | 用户看得见的变化；预览级的破坏性变更 | 改了稳定或预览级公开面的检查点 | 一行一条 |
| 用户文档 `docs/{en,zh}` | 怎么用 | 所述行为变了；RC3 集中重写 | 代码块引用仓库里的文件 |
| 设计文档（其他） | 某个领域的设计 | 该领域的设计变了 | README 的表里标有效／已被取代／历史 |

**节点记录**（每个节点在 STATUS 里一块，不超过 12 行）：日期与头；CI 的一轮（编号、各行结论）；八个计数器；本阶段改过的标注；新红与处置；偏离计划的地方与原因；下一阶段的重估。

**写法。** 只写事实，带日期；测出来的写数字与硬件；没核对的写“未核对”，没实机的写“未验证”；不写某个人的看法；进度的叙述不进设计文档，设计的理由不进 STATUS。机械检查：lint `status`（行数、行长、任务行必有证据指针）、`claims`、`maturity`（实验节齐全）、`docs-code`。

### 4.2 包的收敛（D-194）

规则沿用 D-99，补成可判定的三条：

1. **变体不是包**。`headless`／`picture`／`window`／`sim` 这类同一产品的不同入口，是一个包的多个 target 加 feature；必须由 lint `closure` 分开证明闭包的（例如“不链接 omui”）保留，并在 manifest 里写明所证明的闭包。
2. **CTS 套件随契约的 owner**。只被 owner 自己的测试使用的并回 `tests/`；被两个以上的包运行的保留为包。
3. **只有一个消费者的小包并回消费者**的 `src/<职责>/`。

目标 175 → 不超过 130。先出清单（消费者数、是否证明一个闭包、标注），再按项目各一个检查点合并；合并后重测调试配置的体积，目标不超过 12 GB，差额写明归 mcpp#874。

### 4.5 工具链与工程规范：子项目与总体两个视角（D-203–D-207）

仓库是多项目的工坊：每个项目能单独用、随时可拆；组合起来是一套体系（根 README）。工具链按同一个双视角组织。

**放置规则**：一个工具放在满足它全部依赖的最低一层。

- **项目工具包**放在各项目的 `tools/` 下，随项目走：例如 `hanim.studio`（已是库 `hanim-studio` 加程序 `hanim`）、`xengine-playtest`、omui 的命令行、MCP、生成器。
- **汇总工具链项目**放在 `modules/projects/` 下，是一个只做组合的薄项目：统一入口、工作台、跨项目的工程档案，不写领域逻辑。总体能做的每件事，都能在某个项目的工具包里找到。
- **根下 `tools/`** 只留仓库维护工具：lint、ci、dev、devtools、eval。

**工具包的形态**（D-203）：

| 部分 | 是什么 |
|---|---|
| 操作库 | 工作流以函数提供（L0–L4），结果结构化 |
| 操作目录 | 同一批操作写成 openas 操作与 TS 数据：名字、参数、说明、出路；命令行、MCP、GUI 的入口由它导出 |
| 贡献清单 | `[package.metadata.<前端>]`：贡献的命令、操作、模板与档案、检查规则、面板。前端的 `build.mcpp` 读 `mcpp::graph_file()`（解析后的整个依赖图，带每个包的元数据），在构建时生成登记表，运行时不扫描 |
| 薄程序 | `main` 加工具内核的命令行宿主，没有逻辑 |

同一个命令在任何入口下行为一样：单独的 `hanim …` 与汇总入口下的 `… hanim …` 调用同一个库函数。

**工具内核 T0**：在 mlibs 一级，与领域无关。它包括：

- 命令与操作模型；
- 工具包的发现；
- 工程模型与体检引擎；
- JSON 加退出码的输出；
- 由 openas 判定的权限。

各前端都是 T0 加上若干工具包：

- `omui` = T0 + omui 的工具包。它仍是框架的统一入口（D-150），只认识 omui 的档案。
- 汇总入口 = T0 + 全部工具包 + 工作台。

**跨项目的工具分四个角色**（D-204），Live Design 与 inspector 都按这个模式：

| 角色 | 放在 | 依赖 |
|---|---|---|
| 底座 | mlibs（Live Design 的 L1–L5 已在 `mlibs.agent`：历史、认领；D-160、D-173） | 只有 mlibs |
| 领域适配器（L6） | 各引擎的项目里，无头，各一份 CTS | 本引擎加底座 |
| 外壳 | omui：与领域无关的工作台界面（画布、Agent 指针、历史、认领、面板） | omui 加底座，不导入任何引擎 |
| 组合 | 汇总工具链项目，或需要它的上层项目 | 只做接线：一个工作区同时挂多个适配器 |

现状：

- `omui.designer` 同时是 UI 适配器和外壳，要拆成两部分。
- `tools/inspector` 依赖 `hanim.studio` 与 `xengine.cellular`，是组合，要迁入汇总工具链项目。
- 第二个适配器是 hanim 的文档与时间线，它是这次拆分的现时消费者。

**带界面的工具一律由 omui 自举**（D-205）：

- GUI 外壳是 omui 应用，工具本身也有语义树，可以被 Agent 操作、无头测试、Live Design。
- 自举的顺序是：构建 omui 所需的工具（lint、devtools、生成器）只用 T0，不依赖 omui 的界面。GUI 工具在 omui 之后构建。
- omui 之下的项目把 GUI 外壳放在 omui 之上（汇总工具链项目），不放在自己的项目里。

**脚本收敛进 C++**（D-206）：开发与辅助工具统一由 mcpp 管理的 C++ 实现，按 §4.5 的放置规则归位，以便复用。允许清单只有四类：

1. 平台要求的胶水：浏览器宿主的 JS、CI 工作流 YAML 里调用工具的一行；
2. 竞品对照里竞品自己的运行时：Lottie 的 Python 绑定、GSAP 的 JS，由 C++ 驱动并钉版本；
3. 给其他语言的客户端 SDK：`omui/agent/clients/python`；
4. 独立的参考实现：它刻意与被测代码用不同的语言，写明理由。

lint `scripts` 按清单检查。

**工程规范：通用规范加场景档案**（D-207）：

- 通用规范对所有工程成立，由 T0 的体检检查，包括：
  - 工程文件只有 `mcpp.toml`；
  - 工具在 `[xlings.workspace]` 里声明；
  - 包名就是模块名、路径就是包名；
  - 测试放在 `tests/`，用 mtest；
  - 数据文件按 `<名字>.<种类>.<品牌>.ts` 命名；
  - 元数据放在 `[package.metadata.<品牌>]`。
- 场景档案由领域的拥有者随工具包发布，只写比通用规范多出来的部分：
  - 应用；
  - 组件、原生模块、主题；
  - 游戏（xengine）；
  - 动画与成片（hanim）；
  - 多包工作区。
- 每份档案都有模板、可添加的部件（`add`）和体检规则。
- examples 与 showcase 是合规语料：CI 按它们各自的档案检查。

**名字与改名**（D-208）：

- 汇总工具链项目用内部代号 `xtools`，与 xrender、xengine 同类。包名和模块名不能带连字符，所以不写 `x-tools`。
- 已经定名、或到了产品级的工具链用自己的名字，例如 `omui`、`hanim`。
- 改名不能是麻烦事，名字分三级：

| 级 | 例子 | 出现在哪里 | 改名 |
|---|---|---|---|
| 契约名 | openmui、openas、协议字段、C ABI | 线上协议、持久化的数据、规范 | 不改；不能由代号或产品名派生 |
| 产品名 | omui、hanim | 包、模块、程序、文档 | 发布后按规范的弃用流程 |
| 内部代号（以 `x` 开头） | xrender、xengine、xtools、xdef | 包、模块、程序、目录、文档；进入持久化数据的只有 `xdef`，它随附迁移命令 | 仓库内一条命令改完；用户工程用迁移命令 |

- 每个项目的身份是一份数据：名字、显示名、包前缀、程序名、状态目录、元数据节。工具、帮助文字、文档从这份数据读取，不写死字符串。
- 改名用仓库维护工具的一个子命令完成：目录、包、模块、导入、文档一起改，再由 lint 验证。
- 现状里的耦合（2026-11-16 核对）：
  - hanim 有 24 个、xengine 有 18 个、xrender 有 5 个数据文件带 `.omui.` 后缀，例如 `hanim.ops.omui.ts`；
  - `mlibs.control` 的操作目录约定由 `omui-gen ops` 生成。

  数据求值与生成要下沉到工具内核（阶段 0），后缀改为与产品无关的 `.xdef.`，见 [xdef](2026-11-16-xdef-declared-data-design.md)（D-209）。

**可拆性要机械可查**：

- lint `tooling`：引擎不导入工具包；工具包不用引擎的内部分区；工具包是“库 + 薄程序”。
- lint `splittable`：一个项目只引用声明的依赖，不引用根下 `tools/`。
- CI 演练：只取 omui 与它的依赖，构建、测试通过。

### 4.6 文档

记录规则见 §3.4。结构上的收敛：

- **STATUS**：只留 §3.4 列的几节；M3–M6 的任务行与已关的红灯进归档。
- **设计文档**：README 的表加一列状态——有效（不超过 8 份）、已被取代（写明被谁）、历史。两份超过 10 万字节的各出一页不超过 150 行的现行摘要。
- **用户文档**：§6.3。

## 5. 局部：每个引擎与框架的收口

稳定与预览级过全部 10 项（预览级在它声明的范围内）；实验级过带 ★ 的 4 项。

### 5.2 各项目：切片还缺的功能，与发布前要补的缺口

### 6.2 终端用户

“应用基本功”清单，按一级平台列出通过与否，进发布说明：首帧时间；每个预览级作品与招牌场景达到 D-187；键盘可达与焦点可见（组件墙全量）；屏幕阅读器读例子 03 与 12；中英文输入法；高 DPI 与多显示器；关闭与休眠恢复不崩；手柄（Quay、打砖块）。

### 6.3 用户文档

- 成熟度表按 §2.3 重写，三种标注各有说明；“实验”单列一页，每个模块写目标、现状、差距。
- 上手从安装发布物开始；指南加“3D 世界”一篇（Quay 怎么做的）与“出了问题怎么办”各节。
- API 参考从契约与目录生成（D-145），不手写。
- 指南里的每段代码都是被 CI 编译并运行的文件（lint `docs-code`）。
- 中英文同步由 lint 检查标题结构。

### 6.4 声明台账（D-193）

`docs/claims.omui.json`：每条 `{id, 文档位置, 一句话, 类别, 证据(用例名|基准名|台账行), 日期, 硬件}`。对外文档里的数字与“领先／持平／快 N 倍”必须带 `claim:<id>` 并在台账里；台账里的证据必须存在；发布候选上全部重跑。实验模块只能写“目标是……，现在是……”，不进台账。

### 6.5 Agent 的体验（D-192）

三个冷启动任务，各 10 次，新会话，只给发布物、用户文档网址和一句任务：

| 任务 | 通过 |
|---|---|
| A 装好并做一个带列表与表单的小应用，有测试 | ≥ 9／10 |
| B 只凭一个运行中应用的端点完成它声明的两个任务 | 10／10，不越权 |
| C 用 `hanim` 做一段 5 秒动画并导出 | ≥ 9／10 |

另记录不设门的两项：在 Kiln 与 Quay 的端点上各玩一局。每次记轮数、新 token 与缓存读取（分开）、失败处；失败处回 owner 修文字与出路，不改任务。

### 7.3 依赖的要点

- **关键路径**：RC0.2 → N0 → RC1.1 → RC2 的 3D 平台任务（RC2.1、RC2.3）→ N2a → 自下而上的收口（RC2.14 → RC2.18）→ N2b → RC4 → RC5。
- **不在关键路径上、可以提前或并行的**：RC0.7、RC1.4、RC1.7、RC2.6、RC2.12（都没有前置）；RC3.1 在 RC1.1 之后即可开始，是子 Agent 的第一候选；RC3.5 的指南部分在 N2a 之后可以先写预览与实验的页。
- **必须串行的**：包的合并（RC1.5a–f）在 N0 全绿之后，并且一次一个项目——否则分不清红是合并带来的还是原有的；收口按层次自下而上，上层的 API 复查不早于下层的。
- **有上游依赖的**：RC1.2（mtest 的 `unverified`）、RC3.1（xlings、mcpp-index）、RC0.6 里的 65 与 82（mcpp）。上游的 PR 在任务开始时就开，本仓库先用替代并写明。
- **磁盘是子 Agent 的前置**：它的 worktree 需要第二份构建；RC1.5 把体积降下来之前，子 Agent 只做不需要全量构建的任务（RC3.1 的索引与打包、RC3.5 的文档）。

## 11. 风险

| 风险 | 征兆 | 应对 |
|---|---|---|
| 范围变宽后收不住（六个作品、三个实验模块、3D 进一级平台） | RC2 超过 90 个检查点 | 切片的范围只减不增；某项能力过不了预览的门就改标实验，不拖发布 |
| “实验”被滥用 | 新东西一上来就标实验 | 实验必须有无头验证与毕业条件（lint `maturity`）；不开新模块（§3.2） |
| 3D 把一级平台的全绿拖红（macOS 设备、Web、Direct3D 12） | RC0、RC2 节点等不到全绿 | 逐平台按根因修；某个后端确实不可得时，在该平台把 3D 核心标为不支持（能力查询返回不支持，套件记“不支持”），写进说明——不是跳过用例 |
| 节点之间的红灯累积到节点修不动 | 一个节点的对账超过 10 个检查点 | R12 让对账便宜；推送后后台取回结论，新红当下记录、就近修 |
| 包合并引出模块图问题 | 远端消费者编不过 | 每个项目的合并单独一个检查点，合并后必编 `showcase/fighting` 与一个仓外探针；先上 lint `module-closure` |
| 发布通道依赖上游 | RC3 等上游 | RC1 一结束就开上游的 PR；作为子 Agent 的那一条线提前做 |
| “未验证”掩盖了本可验证的缺陷 | 某格长期未验证，而 CI 的行其实能跑 | 标未验证前先查根因（RC0.3 的做法）；每格写缺什么；节点上逐格复核，计数器只减不增 |
| 自下而上的收口让上层等太久 | RC2.14–RC2.16 超过 25 个检查点 | 复查只定接口与错误，不扩功能；上层的非接口收口（对照、基准、文档）可以先做 |
| 记录规则本身成为负担 | 一个检查点花在文档上的时间超过一成 | 检查点只动 STATUS 的一行与提交正文；其余文档只在它所述的事实变了时动 |
| 磁盘 | 余量低于 10 GB | 子 Agent 的 worktree 需要第二份构建，磁盘不够时不派；先做 §4.2 的体积 |

## 12. 综合自我 review（第三版）

| 角度 | 看到的 | 结论 |
|---|---|---|
| 全局 × 局部 | 范围由切片定（全局），收口由各引擎的清单定（局部）；推进也按这两个方向分开：功能纵向、收口横向 | 两个视角各有落点，不互相替代。切片没用到的能力默认实验，避免无人消费的能力被承诺 |
| 架构与分层 | 没有新增层、包或引擎；三个标注（稳定性、验证状态、已有的分层）都是“表 + lint”同一种机制；收口的次序与依赖方向一致 | 一致。要核对的：包内含不同标注能力的包（如 `xrender.mesh`）是否真能由 feature 隔开——RC1.1 的验收里 |
