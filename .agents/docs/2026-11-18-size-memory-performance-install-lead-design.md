# 体积、内存、性能与上手：逐项对标最强者的优化方案

2026-11-18 起草，**第二版，草案，待 review**（D-211–D-219 为提议；第二版按第一轮 review 改：状态分三类、字体默认用系统回退、发布候选不为通而通、运行时共享的分发方式、终端宿主的体积目标、内存的拆分数据）。基线：`674d90ee`（PR #1）。

本文回答一个问题：omui 做出来的应用，在体积、内存、帧时间、启动和上手这几项上，怎样逐项不输本项最强的框架。它不新增方向，属于收敛方案里“应用”切片的收口（RC3.1、RC3.2 与收口清单第 8 项）。规则沿用 AGENTS §2 第 10 条：每项先找最强者并排实测，持平是低线；没有实测的不算持平；测不了的标“未验证”，不写数字。

## 0. 核心点（review 入口）

1. **现状是实测出来的**：最小的 C++ 应用可执行文件 26.7 MB，分发目录 36.5 MB。这不是框架本身大，而是三件事没做：链接时不去掉没用到的代码、能力没有按用途选择、字体整套打包。
2. **只加一个链接选项就减 31%**：同一批目标文件加 `--gc-sections` 重新链接，26.7 MB → 18.5 MB，程序照常运行（§1.2 的实验）。这是第一步，今天就能做。
3. **体积的主方案是“由应用自己推出它需要什么”**（D-212）：组件、字体字形、语言数据、图像解码器的集合从应用的声明里算出来，不靠开发者手工列 feature；feature 机制只做底下那一层开关。运行时生成界面的应用按 `omui.config.ts` 的开放程度保留完整目录。
4. **每一项都有一个最强者和一条并排基准**（§2）：体积与内存对 Slint，帧时间与列表对 Flutter，Web 首屏对 Flutter Web 与 React，上手对 Flutter 与 Tauri。对手的同一个应用放进 `tests/bench/competitors/apps/`，和我们的在同一台机器、同一个任务里测。
5. **上手的主方案是“TS 应用不需要编译就有第一个窗口”**（D-215）：发布的 `omui` 自带预编译的播放器；`omui new` 加 `omui dev` 不下载编译器。C++ 编译只在 C++ 模板和发布构建时发生。
6. **状态分三类，不混着说**（§1.5）：已做；确定可做、只是还没做（写明等什么）；需要设计或有风险。发布通道、一条命令安装、一分钟出窗口、从安装开始的文档、Agent 凭端点操作应用，都属于第二类，不是设计问题。
7. **目标先写成上限，由实测收紧**（§2）：最小应用的可执行文件 ≤ 8 MB、分发目录 ≤ 10 MB；数字在并排基准跑出来之后改成“不大于最强者”。
8. **TS 应用可以只有几 KB**（D-218）：应用是 `app/main.ts` 加资源，运行时是装一次、多个应用共用的 `omui`；另一种分发方式才把运行时打进应用。
9. **字体默认不整套随带**（D-214）：主流框架都用系统字体；我们默认带一个小的界面字体子集，其余回退到系统字体，逐字节一致的像素留给测试与声明了 `bundled` 的应用。
10. **终端应用的目标是 1 MB 以内**（D-219）：终端宿主不需要窗口、光栅、字体与图形设备；C++ 的最小终端应用以 ≤ 1 MB 为目标，对 ratatui 与 FTXUI 并排。

## 1. 事实底稿（2026-11-18 实测，Linux x64，GCC 16.1，`dist` 配置：`-O3 -ffunction-sections -fdata-sections`）

| `examples/03-counter` | 29.3 MB | 12.7 MB | 39.2 MB | 22 MB |
| `examples/12-notes` | 30.1 MB | 13.1 MB | 39.9 MB | 未取得（程序提前结束） |

- 带窗口（SDL 的离屏视频驱动）：首帧冷 170 ms、热 60 ms；内存峰值约 160 MB，其中图形驱动占多少没有拆分。

- `--release` 配置在本机失败（mcpp 2026.11.17.2：“previous compiler unit is occupied or unknown”），待报上游；本文的数字来自 `dist`。

### 1.2 体积去了哪里

hello 的链接输入是 1408 个目标文件，全部进了可执行文件，链接行没有 `--gc-sections`，也没有 LTO。

| 做法 | 可执行文件 | gzip | zstd -19 |

| 现状 | 26,694,368 B | 11.49 MB | 9.03 MB |

加了之后的程序无窗口与带窗口都正常运行（首帧 69.5 ms）。去掉无用代码之后剩下的 18.5 MB，按链接图归到包：

| 包 | 大小 | 为什么在 |
|---|---|---|
| SDL3 | 3.08 MB | 全部子系统（音频、手柄、相机、传感器、各 GPU 后端）都编了进来 |
| `omui.ui.base` | 1.84 MB | 组件经注册表被引用，用不用都留下（去掉无用代码之前是 11.8 MB） |
| AccessKit | 1.72 MB | 系统无障碍桥 |
| `omui.view` | 1.27 MB | |
| `xrender.vector` | 1.17 MB | |
| HarfBuzz、FreeType | 0.99、0.73 MB | 文字 |
| openkal、libstdc++ | 0.83、0.80 MB | 运行时 |
| `openmui.spec`、`omui.agent`、`omui.core`、`mlibs.i18n`、`omui.sdk`、`omui.viewdoc` | 0.54–0.32 MB | |
| 其余约 40 个包 | 约 4 MB | |

另有两处：`.eh_frame` 等展开表约 2.3 MB（核心代码不用异常）；hello 的链接输入里有 `xengine.dynamics`、libwebp（123 个文件）、libjpeg-turbo（121 个文件），一个只显示文字和按钮的应用用不到它们。

### 1.3 框架级的对照现在是空的

领先度台账里 omui 的 12 个指标（冷启动、万行列表、万行内存、输入延迟、热重载、Web 首屏的时间与字节、Agent 任务等）全部是“计划中”。已有的自测（1012 个节点的仪表盘改一个标签 0.77 ms、全部标签 1.98 ms、挂载 4.4 ms）没有对手的数。

### 1.4 内存的拆分（同一个 hello，稳定后读 `/proc/<pid>/smaps`）

| 运行方式 | 常驻 | 其中 |
|---|---|---|
| 无窗口（`--serve`） | 22.7 MB | 可执行文件自身被映射的 9.6 MB；堆 5.2 MB；匿名映射 5.3 MB。私有脏页只有 10.6 MB |
| 带窗口、CPU 渲染（SDL 离屏驱动） | 111 MB | Mesa 的软件驱动 51.8 MB（libLLVM 40.9、gallium 10.9）；堆 30 MB；可执行文件 13.2 MB |
| 同上，关掉 Agent 端点与无障碍桥 | 109 MB | 只少 1.7 MB：这两项几乎不占内存 |
| 带窗口、`--gpu`（离屏驱动） | — | 段错误，待查根因（记入红灯清单） |

读法：我们自己的常驻量在 20 MB 上下，其中近一半是可执行文件的映射，体积降下来它跟着降。带窗口多出来的约 90 MB 里，至少 52 MB 是这台无显示器的机器上的软件图形驱动；堆从 5 MB 到 30 MB 的 25 MB 是谁分配的（驱动还是我们的表面与缓存）还没分开。另一个发现：选了 CPU 渲染，窗口仍然加载了图形驱动。

### 1.5 状态的三类

| 类 | 含义 | 本文里的例子 |
|---|---|---|
| 已做 | 有代码、有证据 | 单文件 `omui` 的构建流程；65 个包的发布清单与演练；`omui new` 从发布物取模板；应用自带 Agent 端点，Agent 凭端点发现并操作（D-186） |
| 确定可做，未做 | 做法确定、没有未知，写明等什么 | 打 tag 出四个平台的 `omui`、`xlings install omui`、65 个包进索引（等发布）；从安装开始的上手文档（等发布）；链接去掉无用代码（OP1，已实验）；字体按语言随带（OP3） |
| 需要设计或有风险 | 有未知，要先定方案或先测 | 闭包的自动推导（OP2 上层）；系统字体回退（现在没有读系统字体的能力）；终端宿主（计划中，未实现）；带窗口内存里我们自己的那部分；`--gpu` 在离屏驱动下的崩溃 |

对外说明与文档按这三类写：第二类写“未做，等 X”，不写成问题或缺陷。

## 3. 体积

### 3.1 按三级次序（D-185）

- **① 原始性创新：由应用推出闭包（D-212）。** 本体系里界面是声明出来的：组件有契约，TS 源码是唯一事实来源，视图文档、主题、语言都是数据。别的框架靠开发者手工配置或链接器猜；我们可以在构建时从这些声明算出应用实际用到的组件、字形、语言与解码器，生成只含它们的注册表与数据。这是主方案。
- **② 前沿加组合：** 链接期优化（`--gc-sections`、相同代码折叠、LTO）与字体子集化都是成熟技术，和 ① 组合：① 决定“哪些可达”，② 把不可达的去掉。
- **③ 业界做法：** Flutter 的 tree shaking（图标字体按用到的字形裁）、Slint 的编译期界面、Qt 的模块选择。这是低线：我们至少做到这一级。

### 3.2 OP1：链接期（D-211）

1. 发布类配置（`release`、`dist`）的链接加 `--gc-sections`；Windows 与 macOS 用各自等价的选项（`/OPT:REF,ICF`、`-dead_strip`）。先写在工作区的配置里，同时向 mcpp 提议作为发布配置的默认。
2. 相同代码折叠（LLVM 行用 lld 的 `--icf=safe`）。
3. LTO 作为 `dist` 的选项：先量构建时间与体积，只在收益超过 10% 时默认打开。
4. 不用异常的包不生成展开表（核心代码已经不用异常与 RTTI）：约 2 MB。先核对第三方库与崩溃报告对它的依赖。
5. 浮点规则不变：动画、布局、光栅仍禁用 fast-math 与浮点收缩；LTO 不得改变 CPU 参考的字节（像素哈希的用例就是检查）。

预期：26.7 → 约 15 MB。已实测的部分是第 1 步的 18.5 MB，其余是估计，以实测为准。

### 3.3 OP2：能力按用途选择（D-212、D-213）

**底层：feature。** 按 D-99，在所属包里用 feature 选择，不新建包。

| 能力 | 现在 | 改为 |
|---|---|---|
| SDL3 的子系统 | 全部 | `compat.sdl3` 的 feature：视频与事件必选；音频、手柄、触感、相机、传感器、各 GPU 后端可选；SDK 只开应用声明要用的 |
| 图像解码器（PNG、JPEG、WebP） | 全部 | `mlibs.image` 的 feature；由应用的资源与 `image` 的用法推出 |
| 系统无障碍桥（AccessKit） | 必带 | 默认带（语义树是本体系的身份）；feature `a11y` 可关，面向游戏与嵌入式 |
| Agent 总线、MCP、视图文档、表达式 | 必带 | 默认带；`omui.config.ts` 的开放程度为 `none` 时不链接总线（规范 §14 已允许构建时去掉） |
| `xengine.dynamics` 等经间接依赖进来的 | 带 | 查清是谁引入的，改成用到才依赖 |
| GPU 路径 | 必带 | 默认带；`renderer = "cpu"` 的应用不链接设备后端与着色器 |

**上层：推导，不手写。** `omui build` 的构建插件做三件事：

1. **组件**：注册表由“全部登记”改为“按用到的生成”。C++ 的构造函数直接引用组件，去掉无用代码后自然只留用到的；TS 与视图文档的应用，由构建插件扫出用到的组件种类，生成只登记它们的表。
2. **运行时生成**（D-144）：应用在 `omui.config.ts` 里开放了运行时生成界面，就保留完整目录（或开发者列出的那一部分）。开发模式永远是完整目录。
3. **报告**：`omui build --release` 结束时打印体积的构成（每项能力多少、为什么在），并给出“关掉哪项省多少”。体积的预算进应用自己的测试（`omui test` 可以断言上限）。

三个预设给不想细调的人：`full`（开发模式，全部）、`app`（发布的默认：推导出的闭包，带 Agent 与无障碍）、`lean`（推导出的闭包，不带总线与无障碍桥）。预设只是 feature 的组合，走同一条路径。

预期：`app` 预设的最小应用约 8–10 MB，`lean` 约 5–6 MB。都是估计，门按 §2。

### 3.4 OP3：字体与随带的库（D-214）

**别的框架怎么做**（按公开资料，未在本机核对）：

| 框架 | 默认的文字字体 | 随应用带的 |
|---|---|---|
| Flutter | 系统字体（桌面与移动）；Web 上按需下载 | 只有图标字体（按用到的字形裁剪）与开发者声明的字体 |
| Qt、SwiftUI、Compose、Electron、Tauri | 系统字体 | 不带，除非开发者加 |
| Slint | 系统字体；嵌入式目标在编译期把用到的字形烘进程序 | 不带，除非开发者加 |
| Dear ImGui、egui | 自带一个小字体（几十 KB 到 1 MB 级） | 就是那个小字体 |

主流都是系统字体。我们整套随带 7.5 MB，是为了“跨平台逐字节相同的像素”这一项；但这项保证真正被用到的地方是测试、Agent 审查和无窗口渲染，多数应用的终端用户并不需要。

**改为一个默认集合，其余可选：**

1. **默认集合**：一个界面字体的常用子集（Inter 的拉丁子集，约 100–300 KB）常驻，保证品牌观感与基本可用；其余文字（中日韩、阿拉伯文、表情）在运行时回退到系统字体。
2. **`fonts = "bundled"`**：声明的语言对应的全量字体随带，像素跨平台逐字节一致。要这项保证的应用自己选；官网、作品与我们的测试用它。
3. **测试与无窗口渲染**：固定的那套字体作为开发依赖存在，不进发布物；所以像素基线不变。
4. **字形子集**：选了 `bundled` 的应用，静态文字用到的字形在构建时子集化。
5. **Web**：已经是“全量字体按需下载”（RC2.9），与桌面用同一套声明。
6. **X11 的库不随带**：SDL 在运行时按需加载系统的库；查清为什么把 2 MB 的 X11 库复制进分发目录，去掉。

前提：系统字体回退需要“枚举并读取系统字体”的能力，现在没有（属于第三类）。它归 `mpal`（按用途的系统服务），xrender 的文字只管成形与光栅。在它做好之前，默认仍是 `bundled`，但按声明的语言随带（不声明中文就不带 4.15 MB 的 NotoSansSC）——这一步是第二类，立刻可做。

预期：最小英文应用的字体从 7.5 MB 到 0.3 MB 以内。

## 4. 内存（OP4）

§1.4 的拆分已经回答了一半：我们自己的常驻量约 20 MB，带窗口时的大头是图形驱动。剩下要分析和要做的：

1. **把驱动与我们的分开**：同一个应用在软件驱动、真实显卡（RTX 4080）与不加载任何图形驱动的 CPU 窗口三种方式下各测一次；对手的应用用同样的三种方式测，否则驱动的差别会盖过框架的差别。
2. **CPU 渲染的窗口不该加载图形驱动**：现在加载了（多出约 52 MB）。查清是 SDL 的离屏驱动带来的，还是我们创建设备带来的；是我们的就改成用到才创建。
3. **堆多出的 25 MB 归类**：按字体、字形缓存、显示列表、窗口表面、线程栈归到各自的拥有者；量法走 mtest 的监测。
4. **已经看得见的几处**：字体整份读进内存（改成映射，回退字体用到才开）；可执行文件的映射随 §3 的体积一起降；万行列表是否只为可见行建节点（OP5b 的用例同时量内存）。
5. **门**：最小应用与万行列表两项，对 Slint 与 Flutter 并排；每帧零分配已有预算（AGENTS §4），这里加的是常驻量的预算，进 `tests/bench/budgets.bench.xdef.json`。

## 5. 上手与安装

### 5.1 发布通道：确定可做，等发布

方案 §6.1 的门是：一条命令装上 `omui`，出第一个窗口。四个动作都属于“确定可做，未做”，没有设计上的未知：

| 动作 | 已做的 | 未做的（等发布） |
|---|---|---|
| 四个平台的 `omui` 可执行文件 | `omui.yml`：打 `omui-v*` 的 tag 就构建单文件程序与校验和并建 release | 打 tag |
| `xlings install omui` | — | 向 xlings 的包索引提一条 `omui`，指向上面的 release |
| 库进 mcpp-index | `omui-devtools release index`：模板的闭包 65 个包，外部依赖 21 个都已在索引里；`mcpp publish --dry-run` 通过 | 发布这 65 个包（一次索引 PR）与国内镜像的地址 |
| 模板从发布物解析依赖 | `omui new` 已能从发布物取模板 | CI 加“干净机器上一条命令装上并新建项目”这一行 |
| 从安装开始的上手文档 | 上手文档其余各节与 Agent 一节已有；应用自带端点，Agent 不装任何东西就能发现并操作（D-186） | 第一节由“克隆并编译”改成“安装”（等发布） |

### 5.2 OP6：什么时候发（D-216）

不为了走通而发。发布物对外可见、版本不好收回，所以发的条件是内容够完善，而不是通道需要验证：

- **通道的验证不依赖公开发布**：CI 加一行，在干净的机器上从本次构建的产物（单文件 `omui`、`release index` 生成的本地索引目录）安装、新建项目、出第一个窗口。它检查的是同一条路径，只是索引在本地。
- **公开的候选**在 N3 的其他条件都满足之后才发：体积到 §2 的上限附近、上手文档按安装写好、三个桌面平台的应用基本功有结果。候选用预发布版本号（`0.1.0-rc.N`），不占用 `0.1.0`。

### 5.3 OP7：TS 应用就是一个文件加共用的运行时（D-215、D-218）

现在的 TS 模板已经是这个形状：应用是 `app/main.ts`（几十行）加一个指向播放器的 `mcpp.toml`，没有 C++。差的只是播放器现在要在本地编译。

- **① 原始性创新：** 开发模式本来就是“宿主进程持有窗口，应用是 TS”（D-154）。发布的 `omui` 自带预编译的播放器与开发宿主：`omui new` 加 `omui dev` 不下载编译器、不编译任何 C++，第一个窗口的时间只剩下载 `omui`。
- **两种分发方式**（D-218），同一个应用、同一条执行路径：
  - **共用运行时**：应用包只有 TS、资源与清单（几 KB 到几百 KB），由已安装的 `omui` 运行（`omui run`，或系统里登记的启动项）。运行时装一次，多个应用共用，按版本并存。
  - **自带运行时**：`omui package` 把播放器与应用打成一个可分发物（§3 的体积目标说的是这一种）；发布时可选把 TS 原生化（D-146）。
- **② 组合：** C++ 路径上，SDK 随发布提供预编译的模块产物，首次构建只编应用自己的代码。这依赖 mcpp 对预编译产物的支持范围，先核对；不支持的部分写明并报上游。
- **③ 业界做法：** Flutter 预编译引擎；Tauri 与 WebView2 用共用的系统运行时；.NET 分“依赖框架”与“自带运行时”两种发布。这是低线。

门：TS 路径从空机器到第一个窗口 ≤ 1 分钟（宽带），C++ 路径 ≤ 10 分钟，三个桌面平台实测（RC3.2 的四个数之一）。状态：TS 路径是第二类（等发布）；预编译的模块产物是第三类。

### 5.4 OP8：终端宿主与 1 MB（D-219）

终端宿主（TUI）在 `omui/host` 的 README 里是计划中的宿主，还没有实现；工具的“可选 TUI 界面”（D-61）要用它。

**为什么 1 MB 以内是合理的目标。** 终端应用不需要 hello 里最大的那些部分：

| hello 里的部分（去掉无用代码之后） | 终端应用 |
|---|---|
| SDL3 3.08 MB、X11 | 不需要 |
| 光栅与矢量（`xrender.vector` 1.17 MB 等）、图形设备、着色器 | 不需要：画的是字符格 |
| HarfBuzz 0.99 MB、FreeType 0.73 MB、字体文件 | 不需要：字形是终端的；只要字符宽度与字素边界（`mlibs.unicode`，0.21 MB） |
| 图像解码器、AccessKit 1.72 MB | 不需要（终端的无障碍走终端自己） |
| 语义树、布局、状态、组件的行为 | 需要：这是同一棵树的又一种渲染 |

需要的部分今天加起来约 3–4 MB（`omui.view` 1.27、`omui.core` 0.40、用到的组件、`openmui.spec` 0.54、语义与布局，加上静态链接的 libstdc++ 0.80 与 openkal 0.83）。到 1 MB 还要做三件事：`omui.view` 里与像素有关的部分（绘制、动画的像素表示）在终端目标下不链接；按体积优化编译并做 LTO；运行时库的取舍（动态链接系统的 C 与 C++ 库，或只算我们自己的代码）。

**对标**（公开资料的量级，待并排实测）：Rust 的 ratatui 与 C++ 的 FTXUI 的最小应用都在 1 MB 以内或上下；Go 的 Bubble Tea 是几 MB；基于 Node 的 Ink 要带整个 Node。所以 1 MB 是“不输最强者”的线。

**我们能超出的地方**（① 级）：终端只是同一棵语义树的又一种渲染，所以终端应用天然带 Agent 端点、可无头测试、可录制回放，同一份 TS 或 C++ 界面可以同时出窗口和终端两种——这是 ratatui 与 FTXUI 没有的。带 Agent 总线的终端应用会超过 1 MB（总线、JSON、规范类型约 1 MB），所以目标分两档：`lean` 的 C++ 终端应用 ≤ 1 MB；带 Agent 端点的 ≤ 2 MB。TS 的终端应用另加脚本引擎约 1 MB，或用共用运行时（应用本身几 KB）。

**范围**：这是一个新宿主。0.1 冻结方向、不冻结功能，终端宿主早已在计划里、不是新方向；但它不在四个切片的关键路径上。建议：0.1 里只做设计与体积预算，实现放在 0.1 之后的第一个任务，或在 OP2 把 `omui.view` 的像素部分拆成可选之后顺势做（那一步是它的前提）。

## 6. 性能的并排基准（OP5）

1. `tests/bench/competitors/apps/` 下放 Flutter 与 Slint 的三个对照应用（最小应用、万行列表、1012 节点仪表盘），版本钉住；Web 的对照是 Flutter Web 与一个 React 应用。
2. 度量：可执行文件与分发目录的字节、冷启动到首帧、常驻内存、滚动与更新的帧时间分布、Web 首帧前的字节与时间。同一台机器、同一个任务、轮流跑，结论取比值的 95% 区间（领先度台账的既有规则）。
3. 进 Bench 工作流；结果写入领先度台账与声明台账。落后的项留在台账里并转成任务，不删、不改口径。
4. 需要显示器、采集设备或移动设备的项（输入延迟、移动端首屏）标“未验证”。

## 8. 提议的决策

| 编号 | 内容 |
|---|---|
| D-211 | 发布类配置的链接默认去掉无用代码并折叠相同代码；LTO 按实测的收益决定；CPU 参考的字节不因此改变 |
| D-212 | 应用的闭包由它的声明推出（组件、字形、语言、解码器）；feature 是底层开关，预设是 feature 的组合；运行时生成的应用按开放程度保留目录 |
| D-213 | 语义树、Agent 总线与无障碍桥在默认预设里保留；`lean` 预设可以去掉总线与无障碍桥，并在应用的清单里写明 |
| D-214 | 字体有一个默认集合：小的界面字体子集常驻，其余回退到系统字体；`fonts = "bundled"` 才随带声明语言的全量字体并保证跨平台逐字节一致；测试用的固定字体是开发依赖，不进发布物。系统回退做好之前，默认是按声明的语言随带 |
| D-215 | 发布的 `omui` 自带预编译的播放器与开发宿主；TS 应用的开发不需要编译器 |
| D-216 | 通道的验证用 CI 上的本地索引，不依赖公开发布；公开的候选在内容完善之后才发，不为走通而发 |
| D-217 | 体积、内存、启动、帧时间各有并排基准与预算；上限由实测收紧，落后的项留在台账并转成任务 |
| D-218 | TS 应用有两种分发：共用运行时（应用只有 TS、资源与清单）与自带运行时（一个可分发物）；同一条执行路径 |
| D-219 | 终端宿主是同一棵语义树的又一种渲染；C++ 最小终端应用 ≤ 1 MB，带 Agent 端点 ≤ 2 MB，对 ratatui 与 FTXUI 并排；状态与进度的说明按“已做／确定可做未做／需要设计”三类写 |

## 9. 风险与未定

- **按用到的生成注册表会不会破坏 Live Design**：开发模式始终是完整目录；只有发布构建裁剪。运行时生成的发布应用按 D-212 保留目录，体积相应变大，报告里写明。
- **LTO 与确定性**：逐位一致是硬约束；LTO 若改变任何像素哈希就不默认打开。
- **对手应用进 CI 的成本**：Flutter 与 Rust 的工具链让 Bench 任务变慢；只在 Bench 工作流里跑，不进每次推送的行。
- **预编译模块产物**：取决于 mcpp；不支持时 C++ 路径的首次构建仍然慢，数字如实写。
- **系统字体回退与确定性**：回退到系统字体的文字在不同机器上像素不同；测试与 Agent 审查始终用固定字体，所以基线不受影响，但“窗口里看到的”与“无窗口渲染的”在这些文字上会有差别，要在文档里写明。
- **共用运行时的版本**：应用声明它要的运行时版本范围，运行时按版本并存；没装对应版本时的提示与安装走 `omui`。
- **第一轮 review 已定**：核心点 1–4 同意；`a11y` 只在 `lean` 里可关；0.1 不等 OP2 的推导；上限数字先按本文。
- **还要定的**：终端宿主的实现放 0.1 之内还是之后（本文建议之后）；系统字体回退是否进 0.1（本文建议标预览）。
