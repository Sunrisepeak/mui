# omui 与 meng 的顶层设计：两个产品、三层依赖、先达标再拆分

## 0. 核心点（review 入口）

1. **两个面向开发者的产品，一个共用的基础。** omui 是 UI 框架，给做应用的人；meng（内部代号 xengine）是游戏引擎，给做游戏的人。两者共用基础层：通用库（含 Agent 内核）、渲染、动画。
2. **omui 就是 meng 的 UI 框架，同时可以独立使用。** 依赖只有一个方向：meng 依赖 omui。meng 的核心无头、不认识 omui；只有界面桥与工具认识它。
3. **meng 对外是一个整体，加多个经依赖使用的子系统，再加同形的开发工具链。** 每个子系统可以单独依赖、单独发布；一次发布是一组钉好版本的子系统。
4. **依赖按三层划分，只许向下**：基础层 ← 框架层（omui）← 引擎层（meng）。测试依赖也算，由 lint 检查。现在违反它的只有三条边，先切掉。
5. **先在内部仓库里达到发布标准，再拆仓。** mui 是内部研发仓库。现在就按三层的规范做，功能、性能、质量过了发布门，拆分才作为一次机械的导出发生；拆开之后更新的成本变大，所以不提前拆。
6. **发布分两波**：第一波是高品质的 omui 与它依赖的基础层；第二波是 meng。第一波的目标是品质，不是日期。
7. **品质的总原则：分级、可选、默认最好；每一项对最强者并排实测，持平是低线。** 能力分五级，默认集合是对大多数应用最好的组合；运行时可以静态链接、动态共用、复用系统已有的；凡是影响确定性的永远用我们自己的那一份。
8. **官网重做：由 Agent 用 Live Design 和 TS 做出来，简单、不卡；它的设计过程导出成动画视频**（D-235）。一件作品、两个产出。
9. **SEO 用本体系自己的办法解决**（D-236）：页面的语义树在构建时投影成静态的语义 HTML，画布叠在它上面。HTML 是同一棵树的又一种渲染，这是框架的通用能力，不是官网的特例。
10. **状态按三类写**：已做；确定可做、未做（写明等什么）；需要设计或有风险。没做不等于做不了。
11. **验证在本机做**：开发机就是实机（独立显卡、三台显示器），需要的是把桌面会话接给 Agent 的会话。输入延迟需要采集设备，0.1 不测，如实标注。

## 1. 两个产品与共用的基础

### 1.1 关系

| | omui | meng |
|---|---|---|
| 一句话 | 用一棵语义树同时驱动像素、动画、无障碍、Agent 与测试的 UI 框架 | 人和 Agent 地位对等地开发与游玩的 Agent 原生游戏引擎 |
| 给谁 | 做应用的开发者 | 做游戏的开发者 |
| 入口 | `omui` 命令行与 `import omui;` | 引擎自己的入口与伞包（第二波做）；最简单的“运行这个游戏”不要求了解 omui |
| 依赖 | 基础层 | 基础层与 omui |
| 发布 | 第一波 | 第二波 |

omui 在 meng 里承担三个角色，方向都是 meng → omui：游戏内的界面（HUD、菜单）；窗口与应用壳（桌面、Web、Android 上的窗口、输入、生命周期）；工具与编辑器的界面。窗口与输入的宿主留在 omui，不下沉：窗口与输入只有一个拥有者，游戏的界面与状态进同一棵语义树，Agent 用同一套方式操作应用和游戏。代价（带窗口的游戏都带着 omui 的下半部分）用能力分级压到最小：meng 只依赖 omui 的核心、语义、视图与宿主，不带组件、脚本与设计器。重新考虑的条件：出现一个不能带 omui 宿主的目标平台，或体积预算实测达不到。

### 1.2 子系统

| 族 | 子系统 | 层 | 谁直接用 |
|---|---|---|---|
| 基础 | 通用库：Agent 内核、数学、布局、文字、图像、声明式数据等（内部分组名 mlibs） | 基础层 | 全部 |
| 渲染 | 二维、三维、效果、设备后端（内部代号 xrender） | 基础层 | omui、meng |
| 动画 | 通用动画、时间线、骨骼（hanim） | 基础层 | omui、meng |
| 界面 | omui：UI 框架、窗口与应用壳、Live Design | 框架层 | 应用开发者；meng 经桥 |
| 模拟 | 动力学、物质与化学、场、粒子、格点 | 引擎层 | meng；可单独依赖 |
| 媒体 | 音频、视频 | 引擎层 | meng、工具 |
| 游戏核心 | 世界、运行时、输入映射、导航、试玩、界面桥 | 引擎层 | 游戏开发者 |

子系统的资格沿用已有的毕业条件：能单独使用；只向下依赖；有自己的 Agent 面、测试、基准与工具包；一句话说得清是什么。gongfu 只依赖基础层，按第三方的中间件对待，不在两波的范围之内。

### 1.3 工具链层

结构与子系统同形，依赖也只许向下：工具内核在基础层；每个子系统的工具包（库、薄程序、操作目录、贡献清单）随子系统走；总入口是引擎层的一个只做组合的薄项目，在构建时经贡献清单发现各工具包，不反向编入；构建与分发用 mcpp 与 xlings，按版本钉住。

## 2. 依赖的规范

**三层，只许向下**（D-231）：

| 层（将来的仓库） | 内容 | 可以依赖 |
|---|---|---|
| 基础层 | 通用库、渲染、动画、下沉的通用求解器、仓库维护工具 | 只有规范与第三方 |
| 框架层 | omui | 基础层 |
| 引擎层 | meng 的内核、游戏核心、工具链总入口、游戏作品 | 基础层、框架层 |

**为什么层与层之间必须单向**：包一级没有环还不够。若下层依赖上层某个已发布的包，而上层又依赖已发布的下层，那么上层的一次构建里同一个模块就有新旧两份，无法链接；每次发布也要来回各发一半。

**现状**（按清单统计，细目见 part 2 §2.3.1）：omui 对基础层有 158 条依赖，方向正确；引擎一侧几乎全部依赖 omui 一侧，方向正确；反方向只有三条——hanim 默认用引擎的软体求解器（1 条），`omui` 命令行的 `video` 子命令用引擎的视频工具（2 条）。

**切法**：hanim 用到的只是求解器的通用部分，下沉成基础层里一个与领域无关的库，引擎的动力学依赖它（搬家，不是复制）；`omui` 命令行不再编入视频工具，由引擎的工具包经贡献清单接入；加一条按层的 lint。

**meng 内部**同样四层只许向下：领域内核 → 游戏核心 → 桥与呈现 → 工具与作品；只有桥、工具与带窗口的作品认识 omui。

## 3. 怎么开发，什么时候拆

**先达标，再拆**（D-232）。在内部仓库里按三层的规范做没有额外成本，一次提交仍然可以同时改三层；跨仓库联动的成本只在真的拆开之后才有。所以规范现在执行，物理的拆分放到最后。

“按规范做”是五件事：依赖只许向下并由 lint 检查；每一层单独能立住，拆分演练由一行改成三行；框架层按发布之后的样子验证（基础层从本次构建的本地索引按版本取，而不是走源码路径）；跨层接口的改动在每个节点数出来；内部资料不进任何一层的导出物。

拆的条件（全部满足）：第一波的发布门在内部仓库里通过，候选从导出物构建；跨层接口连续两个节点没有破坏性改动；对外的名字都已定。之后：导出 → 新仓库的第一次提交 → 在新仓库重跑全部门 → 从新仓库发公开的候选与 `0.1.0`。内部仓库改为钉住新仓库的版本。物理上是两个仓库还是三个，到那时按跨层改动的频率定。

**两波**（D-222、D-223）：第一波 = 基础层 + 框架层；第二波 = 引擎层。拆仓之前仍是一个仓库、一个 CI，第二波成员的失败照记照修，但不计入第一波的门；第一波期间第二波只修失败、跟随接口、做后台验证。

**名字**：引擎对外叫 meng（全称 meng engine，可写作 mengine，缩写 ME），模块、包前缀与仓库都是 `meng`；内部代号 `xengine` 用已有的改名命令一次改完，不留别名（D-234）。其余内部代号（渲染、通用库的分组名、声明式数据、工具链总入口、下沉的求解器库）的对外名字是拆仓的前提，尚未定。

**公开发布不为走通而发**（D-216）：通道的验证在 CI 上用本地索引完成；公开的候选在内容完善、拆仓之后才发。

## 4. 第一波的品质目标

### 4.1 总原则

- **分级、可选、默认最好**（D-220）：能力分五级——核心（语义树、状态、布局、组件行为）、像素、设备与效果、Agent 与无障碍、脚本与设计。默认集合带 Agent 与无障碍，不带用不到的解码器与子系统。选择有预设、能力开关、由应用的声明自动推出三种粒度，走同一条构建路径。
- **运行时的三种取得方式**（D-221）：静态链接再裁剪；动态共用（共用的运行时是 xlings 的包，按版本并存，应用声明它要的版本）；复用系统已有的。界线只有一条：影响确定性的——成形、光栅、数学、布局、动画、语义树——永远用我们自己的；系统只提供窗口、输入、驱动、运行库、系统服务与作为数据的字体。
- **每项对最强者并排实测**（D-217）：对手的同一个应用放进仓库，同机同任务测；落后的留在台账并转成任务；到门上仍落后的，该项能力降一级标注并写进发布说明。

### 4.2 现状与上限

| 指标 | 现状（实测） | 上限（并排数据出来后改为“不落后于最强者”） | 对手 |
|---|---|---|---|
| 最小应用的可执行文件 | 26.7 MB；只加链接选项即 18.5 MB | ≤ 8 MB | Slint |
| 最小应用的分发目录 | 36.5 MB（字体 7.5、窗口库 2.0） | ≤ 10 MB | Slint |
| TS 应用自身（运行时共用） | 源码几 KB | ≤ 100 KB | Tauri |
| 最小终端应用（C++） | 没有终端宿主 | ≤ 1 MB；带 Agent 端点 ≤ 2 MB | ratatui、FTXUI；TS 的对 Ink |
| Web 首帧之前的字节 | 1.94 MB | ≤ 1.2 MB | Flutter Web、React |
| 无窗口的常驻内存 | 22.7 MB | 并排后定 | Slint、Flutter |
| 带窗口的常驻内存 | 111 MB，其中软件图形驱动 52 MB，未在真实显卡上拆分 | 先拆分 | 同上 |

## 5. 官网与动画

### 5.1 为什么重做，做成什么样（D-235）

现有的官网是 19,079 行 C++ 加 313 行 TS，内容多、结构复杂、有卡顿。它证明了框架能做复杂的东西，但不适合当第一印象。重做的原则：

- **简单**：一条主线——omui 是什么、装上它、Live Design 加动画加 Agent 的那一个招牌过程、文档的入口。作品的展示以后再加。
- **不卡**：真实浏览器里 p99 ≤ 16.7 ms，交互没有可感的停顿；交付在预算内（§4.2 的 1.2 MB）。这两条是它的门，不是愿望。
- **由 Agent 用 Live Design 和 TS 做出来**：界面是 TS，性能敏感的部分才用 C++（已有的方向）。TS 源码是唯一事实来源，人随时接手。
- **设计过程就是动画视频**：设计历史可以提交、回放、编辑并导出成作品（D-151）；官网的设计过程经剪辑导出，放在官网上。一件作品、两个产出，同时证明 Live Design 能做真实产品、hanim 能呈现设计过程、Agent 是执行者。

**官网能不能用 Live Design 和 TS**：能，TS 应用由播放器运行是已有的路径（例子 02、13）。有一处要先解决：脚本引擎进浏览器约 1 MB，与首帧前 1.2 MB 的上限冲突。办法按 D-185 的次序：① 发布构建把 TS 原生化（D-146）或把静态的界面在构建时求值成视图文档，页面上不带脚本引擎；② 只有真正需要运行时脚本的那一页按需加载引擎；③ 低线是整站带引擎并接受更大的首屏——不取。

### 5.2 SEO：HTML 是同一棵语义树的又一种渲染（D-236）

画布里的内容搜索引擎读不到，这是所有自绘框架的通病（Flutter Web 至今如此）；对手里做得最好的是服务端渲染的 React 一类。我们的办法来自本体系独有的东西：

1. **构建时把每个路由的语义树投影成静态的语义 HTML**：标题层级、段落、链接、列表、图片的替代文字，作为页面的文档本身。爬虫与不执行脚本的访问者拿到的是完整的内容。
2. **画布叠在它上面启动**；运行时已有的语义 DOM 镜像接着保持两者同步。静态的 HTML 与镜像是同一个投影，所以“爬虫看到的”与“人看到的”按构造一致，不存在两套内容。
3. **每个路由是真实的地址**，带标题、描述、规范地址、分享卡片的元数据、中英文互指、站点地图与结构化数据。
4. **首屏先出文字**：静态 HTML 的文字就是最大内容绘制，早于 wasm 加载；画布的位置预留，布局不跳动。
5. **文字可选、可复制、可页内查找**，经同一个镜像。
6. **检查进 CI**：不执行脚本抓取每个路由，文字内容与语义树的文字一致；搜索与性能的评分有下限。

这是框架的通用能力：任何 omui 的 Web 应用在 `omui build` 时都得到每个路由的静态 HTML，归 Web 宿主。官网是它的第一个使用者，不写官网专用的代码（AGENTS §2 第 1 条：作品遇到缺口回主线实现）。

动工之前写一页官网的设计：内容与路由、设计过程的镜头、对回放与导出能力的要求。

## 6. 验证

- **本机就是实机**：开发机有 RTX 4080、接着三台显示器。Agent 的会话跑在隔离的容器里，看不到桌面会话；接通显示的套接字与会话总线之后，真实显示器上的窗口与首帧、真实显卡上浏览器里的帧时间、无障碍桥（经系统的无障碍接口读回语义对照）、输入法都可以在本机验证。睡眠与恢复要真的让机器睡眠，需要维护者同意并选时间。
- **输入延迟 0.1 不测**，平台表里如实写“未测”。
- **Windows 与 macOS** 上需要人在场的项，靠 CI 的平台行加维护者手上的机器；没有的标“未验证”。
- **发布门**：part 1 的十条按波取范围，另加三条——体积与内存的预算、并排基准没有“落后”、默认集合之外的组合各有一条冒烟（part 2 §5）。

## 7. 阶段与次序

| 阶段 | 内容 | 出口 |
|---|---|---|
| A 对账与规范 | 修掉这一轮 CI 的失败并推送；三层的 lint、切三条边、拆分演练改三行；meng 改名；`--gpu` 崩溃的根因；上游问题报出去 | 第一波成员一轮全绿，规范由检查守住 |
| B 体积与分级 | 链接期、字体、能力分级与开关、闭包推导、体积报告 | 最小应用 ≤ 8 MB，像素不变 |
| C 并排与性能 | 对 Slint、Flutter、React 的并排基准；内存拆分；描边、Lottie、Agent 任务的差距 | 台账里 omui 的指标都有数，没有“落后” |
| D 平台与基本功 | 本机接通桌面会话后的实机项；系统字体回退；规范的增补 | 平台表每格是实机、软件、未验证或未测 |
| E 通道与上手 | CI 的“干净机器”行；TS 应用免编译；共用运行时 | 一条命令到第一个窗口，TS ≤ 1 分钟 |
| F 终端宿主 | 字符格的渲染与输入 | 同一个例子出窗口与终端；≤ 1 MB |
| G 官网与动画 | Web 的静态 HTML 投影（框架能力）；官网用 Live Design 重做；设计过程导出成视频 | 官网在预算内、不卡、可被检索；视频在官网上 |
| H 候选、拆仓与发布 | 内部过门 → 定名 → 拆仓 → 新仓库重跑 → 公开候选 → `0.1.0` | 全部发布门 |

A 至 F 是核心框架与运行时；G 在它的一页设计确定之后排入，其中“静态 HTML 投影”是框架能力，可以提前到 D 或 E。估计 A–F 约 70–90 个检查点，G 另计。

## 9. 多视角自我 review

| 视角 | 看到的 | 结论 |
|---|---|---|
| 架构 | 两个产品、三层、引擎内四层、工具链同形，是同一条“只许向下”的规则用了四次 | 规则只有一条，容易守也容易查；现有的违反只有三条边 |
| 与已有决定的一致 | 窗口与输入留在 omui、游戏无头、只有桥认识 omui、全部渲染归一个拥有者，都与 D-161、D-162 一致 | 不改已有的分层决定；改的只是“求解器的通用部分下沉”与“视频命令归它的拥有者” |
| 先求超越 | 裁剪、共用运行时、服务端渲染式的 SEO 都是业界已有的做法 | 超出的三处来自本体系独有的东西：闭包由声明推出；终端、窗口、无头、HTML 都是同一棵树的渲染；官网的设计过程本身是可回放的作品。三处都要用对照证明，否则只算持平 |
