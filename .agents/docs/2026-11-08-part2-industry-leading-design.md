# 第二部分（Part 2）：各项目达到业界领先，标志性特性远超顶尖——设计与实施方案

> 状态：草案，待维护者 review。
> 上位文档：[顶层收敛方案](2026-11-06-top-level-assessment-convergence-design.md)（M0–M7）。本方案是其中 M5 后半、M6、M7 的展开，不改动 M0–M4 已定的架构与命名。
> 一句话：**主线（引擎、框架、组件、库、规范）逐项对标最强竞品，同机测量，指标胜出；每个项目另有 2–4 项标志性特性，做到竞品没有或差一个数量级；应用只作为验证线，证明主线的能力。**

---

## 0. 核心点（review 入口）

1. **“领先”要有可复现的定义。**
   - 每个项目选 6–10 个指标，每个指标对照该项目最强的 1–3 个竞品，在同一台机器、同一工作负载下测量。目标是“不差于最强者”，其中至少一半指标“明显胜出”（≥1.2×）。
   - 所有数字进入 `tests/bench/competitors`，以及新的**领先度台账**（`lead.ledger.omui.jsonl`）。不引用竞品自述的数字。
2. **“远超”只给标志性特性。**
   - 每个项目选 2–4 项竞品没有、或差一个数量级的能力（例如“任何 UI 都能被 agent 在授权下操作并逐步撤销”）。
   - 每项要有招牌镜头（可在 headless 下确定重现）、对照证据和一个真实任务。不追求全面“远超”。
3. **先补短板，再放大长板。** 现在最弱的是性能与交付：xrender 的光栅比 Skia 慢 1.6–2.9 倍，Web 首屏可用 1.9 s，wasm 10.5 MiB。其次是质感，最近评分 62–65。这两项进入第一期（P2-A、P2-B）。
4. **对标对象按项目确定**（§3）。
   - omui 对 Flutter、Compose、SwiftUI、React+DOM、Slint；
   - hanim 对 GSAP、Motion（Framer）、Rive、Lottie、Manim；
   - xrender 对 Skia/Graphite、Vello、Blend2D、ThorVG、resvg；
   - xengine 对 Godot 4、Bevy，物理对 Box2D v3、Rapier、Jolt；
   - gongfu 对 GGPO/GGRS、商业格斗引擎的公开指标；
   - mlibs 各库对 HarfBuzz+SkParagraph、Taffy/Yoga、md4c、ICU4X、wgpu。
5. **每个项目的标志性特性**（§3 各节详述）：
   - **omui**：Agent 原生的语义树（任何应用都能被授权操作、留下记录、逐步撤销）；页面时间回放；通用动效（任何变化都能平滑过渡，被打断也连续）；像素可审查。
   - **hanim**：Agent 写动画（意图 → 程序 → 计划读回 → 修改）；任意形状之间的拓扑对齐形变；一个引擎同时服务 UI、视频和游戏，且逐位确定。
   - **xrender**：CPU 与 GPU 同源、差异 ≤1/255；每个像素都能追溯到节点；矢量截图。
   - **xengine**：Agent 与人在同一套感知和反应约束下平等游玩，可逐位回放；引擎开发全部可通过 ops 由 agent 完成。
   - **gongfu**：可回滚的“角色即数据”，以及 Agent 陪练。
   - **规范**：第一份把 UI 语义和 agent 授权统一起来的标准，且有两个独立实现。
6. **应用都是验证线**（§4）：官网、风格画廊、组件打砖块、格斗游戏、宣传片、Markdown 墙、时间线编辑器、反应实验室、PPet。每个应用对应它要证明的主线结论，并有招牌镜头。应用不写引擎代码，遇到缺口就回主线补。
7. **评审体系**：评分 ≥85 是 M5 的退出条件，≥90 是 M7 的；“质感”和“性能”单独计分。codex 是评审者之一，同时有维护者评审和量化指标；评分记入现有的 `ledger.eval.omui.jsonl`。
8. **分期**（§6）：
   - **P2-A 基线与台账**（约 1 周）
   - **P2-B 短板**（约 3–4 周）：xrender 光栅、omui 按页交付、质感
   - **P2-C 标志性特性**（约 4–6 周）
   - **P2-D 应用验证**（与 P2-C 并行）
   - **P2-E 复评与收口**（约 2 周）

   每期有退出条件；对应 M5 退出、M6 的一部分和 M7 的准备。
9. **需要维护者确认的事项**（§9），共 6 项：
   - 竞品清单；
   - “领先”的阈值（不差于最强者，且一半指标 ≥1.2×）；
   - 每个项目的标志性特性是否选对；
   - 真机 GPU 测试机；
   - Agent 任务集的来源；
   - 应用的优先顺序。

## 1. 目标与定义

### 1.1 三级目标

| 级别 | 含义 | 证据 |
|---|---|---|
| **L-1 达标** | 能力完整，无明显缺陷；功能覆盖与主流竞品相当 | CTS、功能清单对照 |
| **L-2 业界领先** | 每个选定指标同机测量，不差于最强竞品；至少一半指标胜出 ≥1.2×；评审分 ≥85 | 领先度台账、基准 CI、评审记录 |
| **L-3 远超顶尖** | 只针对标志性特性：竞品做不到，或差一个数量级（≥10×、成功率 +30 个百分点等） | 招牌镜头（headless 可重现）、对照实验、真实任务录像 |

### 1.2 规则

- **同机同负载**：竞品用其推荐的发布配置，版本固定在 `tests/bench/competitors/*/package-lock` 或 `mcpp.toml` 里。负载两边都由同一份数据生成。每次测量记录机器、版本和提交号。
- **不挑指标**：每个项目的指标清单先定、先评审，再开始测量。没有胜出的指标如实写进台账，不删。
- **质量与速度一起计**：画质（相对参考的误差）、正确性（CTS 通过率）、体积、启动时间和速度同等重要，不能用画质换速度。
- **作品不写引擎代码**：应用暴露的缺口回主线解决（AGENTS §2.1）。
- **确定性优先**：凡是标“逐位”的结论，必须在 Linux x64/arm、macOS、Windows、Web 五个平台的 CI 上都成立。

### 1.3 领先度台账

新文件 `.agents/docs/evaluation/lead.ledger.omui.jsonl`，一行一个测量：

```json
{"date":"…","project":"xrender","metric":"raster.fill_large.ms","ours":3.1,"best":{"name":"skia-m131","value":3.4},"others":[{"name":"blend2d-0.12","value":2.9}],"machine":"ci-linux-x64-8c","commit":"…","verdict":"behind|par|ahead|far_ahead"}
```

- 生成：`tests/bench/competitors/run.sh` 加上 `--ledger`，每周在 CI 的 bench 通道跑一次。
- 呈现：官网文档区新增一页“领先度”，直接读台账显示最新结论，包括落后的指标。
- 新增 lint：一个项目的标志性特性如果没有对应的招牌镜头测试和台账条目，就报警。

## 3. 各项目方案

每个项目统一分四部分：**对标**、**指标与目标**（L-2）、**标志性特性**（L-3）、**实施要点**。表中的“最强竞品”在 P2-A 期间由同机测量确定，不预设数字。

### 3.1 omui：UI 框架

**对标**：Flutter 3.x（含 Impeller 和 Web 版）、Jetpack Compose、SwiftUI、React 19 + DOM（Chrome）、Slint、Qt Quick。

**指标与目标（L-2）**

| 指标 | 负载 | 目标 |
|---|---|---|
| 冷启动到首帧（桌面） | 同一个设置页（40 个控件） | 不慢于 Slint 和 Flutter 中的最快者 |
| Web 首屏 / 可交互 | 官网首页，Fast 3G 加 4× CPU 节流 | 首屏 ≤ 0.8 s，可交互 ≤ 1.5 s；优于 Flutter Web，与同类 React SSR 页面相当 |
| Web 体积 | 官网单页 gzip | 每页首包 ≤ 1.2 MB；整站按页加载 |
| 帧时间 p99 | 10,000 行虚拟列表滚动、200 个同时动画 | ≤ 4 ms（60 Hz 预算的 ¼）；优于 Flutter 和 Compose |
| 布局 | 5,000 节点 flex 加 grid 嵌套的全量布局 | 不慢于 Taffy |
| 输入延迟 | 按下到像素变化（桌面，120 Hz） | ≤ 1 帧 |
| 内存 | 10,000 节点的应用 | 不高于 Flutter |
| 无障碍 | NVDA、VoiceOver、Orca、TalkBack 走一遍标准任务 | 4 个读屏全部通过；ARIA 映射与 AccessKit 等价或更好 |
| 文字 | 中文排版（GB/T 15834 标点挤压、禁则）、IME、双向文字 | 中文排版优于 Flutter 和 Compose；IME 与系统原生一致 |
| 开发体验 | 热重载（改一个组件到画面更新） | ≤ 100 ms；四种语言（C++、TypeScript、Python、Lua）都一样 |

**标志性特性（L-3）**

1. **Agent 原生的语义树**
   - **能力**：任何 omui 应用都可以被访客自己的 agent 在授权下操作，读到的是语义，不是截图。每一步都有执行者、回执和撤销；权限由人掌握。
   - **对照**：基于截图或 DOM 的 computer-use（Playwright 加 VLM，浏览器 agent）。
   - **目标**：在同一组 100 个 UI 任务上，成功率比截图式 agent 高 30 个百分点以上，步数和 token 降一个数量级；每一步都可以撤销，误操作 0 次越权。
2. **页面时间回放**
   - **能力**：任意时刻都能逐像素重画；可以按执行者（人或 agent）倒回；可以开分支。
   - **对照**：React DevTools、Redux 时间旅行、Flutter DevTools，都只能回放状态或部分 UI，做不到像素级。
   - **目标**：任意一帧可重建，与当时的像素逐位一致；重建 1 秒的 60 帧不超过 50 ms。
3. **通用动效**
   - **能力**：任何属性、布局、文字的变化都能自动平滑过渡；被打断时速度连续；减弱和关闭动效的分级一致。
   - **对照**：SwiftUI 的 matchedGeometry、Framer layout，都需要手工声明，而且打断后不连续。
   - **目标**：37 类组件全部 0 声明就能过渡；打断时的速度阶跃为 0（CTS 测量）。
4. **像素可审查**
   - **能力**：headless 下的像素与浏览器中的像素逐位一致；每个像素可追溯到节点（object id），agent 可以直接审查画面。
   - **对照**：传统像素快照测试，跨平台通常差几个像素，而且无法归属到节点。
   - **目标**：五平台像素逐位一致；像素到节点的归属准确率 100%。

**实施要点**：
- 按页拆分交付（D5）：首页只带首页、视图和字体子集；其余页面按需加载。
- 冷启动剖析，把初始化挪出关键路径。
- 虚拟列表和长列表基准（新增 `ui/frame/list-10k`）。
- 四个屏幕阅读器的实机脚本。
- 中文排版规则补齐（标点挤压、行首行尾禁则、避头尾）。
- 热重载计时进 CI。
- Agent 任务集：100 个任务，来源于官网、示例和打砖块，同时跑截图式基线（§9 待确认）。

### 3.2 omui 组件库与质感

**对标**：Material 3、Fluent 2、Apple HIG（含 iOS 26 的 Liquid Glass）、shadcn/ui + Radix、Ant Design。

| 指标 | 目标 |
|---|---|
| 覆盖 | 常用组件 ≥ 60 类（现在 37）：补齐表单校验、命令面板、菜单栏、上下文菜单、日历、图表基础、文件上传、虚拟表格、富文本、通知中心、导航抽屉的各种变体等 |
| 状态完整度 | 每个组件都有悬停、按下、聚焦、禁用、加载、错误、空、只读状态，并逐项测量（质感清单 B4–B6 扩展） |
| 质感评审 | 每个组件对照 Material 3 和 HIG 的同类组件，维护者加 codex 两路评审，≥ 85；“细节”一项 ≥ 85 |
| 无障碍 | 每个组件都有键盘路径和读屏脚本，通过率 100% |
| 主题 | 令牌覆盖率 100%，组件里没有硬编码的颜色、尺寸、时长 |

**标志性特性**：
1. **真正液态的玻璃**：会折射、能融合、跟随运动，所有平台都有（含 Web，没有 GPU 时退化为 CPU 路径）；iOS 26 只在苹果平台上有。目标：同一场景在 Web 上 60 fps，融合连续，没有接缝。
2. **组件即画布对象**：任何组件都可以放在无限画布上，缩小时依然是活的（官网的设计师画布）。目标：画布上同时有 1,000 个活组件时，帧时间 ≤ 8 ms。
3. **风格包对所有组件生效**：一个风格包同时改变质感和动效配方，不只改颜色；切换时有过渡动画。

**实施要点**：
- 按优先级补齐组件，每补一个都走契约、CTS、质感清单和读屏脚本。
- 画布上大量活组件的性能：活节点池、远处的纹理层。

### 3.3 hanim：动画引擎

**对标**：
- UI 动画：GSAP 3、Motion（Framer Motion）、Web Animations API；
- 设计交付：Rive、Lottie（lottie-web、rlottie、ThorVG）；
- 程序化动画：Manim、Motion Canvas；
- 游戏动画：Spine、Unity Animator。

| 指标 | 负载 | 目标 |
|---|---|---|
| 每帧开销 | 10,000 个值，每 30 帧重定向一次 | 原生和 wasm 都比 GSAP、Motion 快 ≥ 2×（现在约 2×，需要扩展负载并固定下来） |
| 形变质量 | 字形 A→B、带孔、多轮廓 | 视觉评审优于 GSAP MorphSVG 和 flubber；没有自交 |
| 文件与播放 | 同一段 10 秒的品牌动画 | 动画文档体积 ≤ Lottie 的 ½；播放帧时间不高于 Rive 运行时 |
| 确定性 | 任意时刻跳转 | 五平台逐位一致（GSAP 和 Lottie 都没有这个承诺） |
| 物理感 | 弹簧、掉落、软体 | 弹簧求值与解析解的误差 ≤ 1e-9；软体在 300 个顶点下 0.2 ms 以内 |
| GPU 批量 | 100 万个控制点的形变 | 一帧内完成；CPU 与 GPU 差 ≤ 1e-5 |
| Agent 写作 | 100 个动画任务（自然语言 → 动画文档） | 成功率 ≥ 95%（现在 24/24）；对照用 Lottie 或 AE 脚本的 agent 基线 |

**标志性特性**：
1. **Agent 写动画**
   - **能力**：意图 → 程序 → 读回计划（每段的开始和结束）→ 精确修改（“晚 0.3 秒、弹一点”），每一步都可以撤销。
   - **对照**：Lottie、AE 由 agent 编辑 JSON 或脚本，没有计划读回和语义。
   - **目标**：同一组任务，成功率高 30 个百分点以上，修改轮数 ≤ 1/3。
2. **任意形状间的拓扑对齐形变**
   - **能力**：处理轮廓数和孔数不同的情况、字形、描边与填充互变，可以加约束和噪声。
   - **对照**：GSAP 只对单路径，flubber 不支持孔。
   - **目标**：100 对随机字形和图标全部无自交；评审优于两者。
3. **一个引擎同时服务 UI、视频和游戏**：同一个程序可以在 UI 里交互、在视频里逐帧导出、在游戏里定步长推进，三处结果逐位一致。
4. **配方作为标准词汇**：openmui 规范里登记的 presence 和配方 id，任何实现都能播放同一份动画文档。

**实施要点**：
- 弹性体后半：笼形形变、运动导出的形变。
- GPU 求值：通道采样、配方批量。
- 对照基准：GSAP、Motion、Lottie、Rive（tests/bench/competitors 增加 rive-wasm、lottie-web）。
- 100 个 Agent 动画任务集（扩展 `tools/eval/animate.py`）。

### 3.4 xrender：渲染引擎

**对标**：Skia（含 Graphite）、Vello、Blend2D、ThorVG、resvg，以及 Rive 渲染器。

| 指标 | 负载 | 目标（CPU） | 目标（GPU） |
|---|---|---|---|
| 大面积填充 | 1024²，100 个大路径 | 不慢于 Blend2D 和 Skia 中的最快者（现在慢 1.6–2.9×） | 不慢于 Vello 和 Graphite |
| 渐变 | 线性、径向、锥形 | 同上 | 同上 |
| 描边 | 1,000 条描边，含虚线和端点 | 同上 | 同上 |
| 小图元 | 10,000 个小矩形和圆 | 保持领先 ≥ 2× | 领先 |
| 文字 | 5,000 个 CJK 字形 | 不慢于 Skia | 不慢于 Skia |
| 画质 | 五个场景对参考的误差 | 平均通道差 ≤ 0.5 | CPU 与 GPU 差 ≤ 1/255 |
| 体积 | wasm 光栅核心 | ≤ ThorVG | — |

**标志性特性**：
1. **CPU 与 GPU 同源**：同一份渲染图，两条路径的差异 ≤ 1/255，五平台逐位钉住。竞品的 CPU 和 GPU 渲染器是两套实现，结果不一致。
2. **像素可追溯**：每个像素归属到语义节点（object id buffer），因此 agent 可以问“这个像素是谁画的”，并直接定位到代码。
3. **矢量截图**：任意一帧导出 SVG，每个节点是一个有标记的组；做不到的效果作为像素岛单独列出；resvg 绘制的误差 ≤ 0.1。

**实施要点**：
- 光栅器改造：稀疏条带（sparse strips，参考 Vello CPU 和 Blend2D 的思路），按行扫描的 SIMD 合成，渐变查表。
- GPU：真机测试（见 §9），对照 Vello 的 compute 管线。
- 毕业条件：至少 2 个独立消费者（omui、hanim 已有，再加打砖块或格斗游戏），API 冻结，CTS 完整。

### 3.5 xengine：Agent 原生游戏引擎

**对标**：Godot 4、Bevy 0.15；物理对 Box2D v3、Rapier、Jolt（2D 部分）；元胞对 Noita 式的落沙模拟；网络对 GGRS。

| 指标 | 目标 |
|---|---|
| 2D 刚体 | Box2D v3 官方基准场景（金字塔、大量翻滚体、链条）步进时间不慢于 Box2D v3；五平台确定 |
| 软体与约束 | XPBD 1,000 个约束 ≤ 0.5 ms；稳定性评审 |
| 元胞 | 4096² 的场在 GPU 上 60 fps；CPU 与 GPU 逐位一致（现在已经一致） |
| ECS 与世界 | 10 万实体迭代不慢于 Bevy |
| 工具 | 场景、关卡、素材的编辑与热重载 ≤ 200 ms |
| Agent 开发 | 引擎的所有能力都可以通过 ops 完成；agent 从零做一个小游戏的成功率有记录 |

**标志性特性**：
1. **人与 Agent 平等游玩**
   - **能力**：agent 和人在同一套感知限制、反应时间和操作频率下玩；一局可以逐位回放，并检查 agent 在每个时刻看到了什么、为什么那样做。
   - **对照**：一般游戏 AI 是作弊式 AI，或者专门训练的 bot。
   - **目标**：打砖块和格斗都有人类档 Agent 玩家；10,000 局回放逐位一致。
2. **Agent 原生的引擎开发**：引擎、工具、素材全部有 ops 和 skill，不开 GUI 也能完成一个小游戏，并用真实离屏像素自审。
3. **全游戏可回滚**：每个游戏都可以免费获得回滚和重放（模拟层强制确定性）。

**实施要点**：
- 动力学 P1：2D 刚体（对标 Box2D v3 的求解器设计，soft step、连续碰撞）、角色控制器、高度场水面。
- 世界与 ECS 的基准。
- 关卡工具。
- Agent 做游戏的任务集。

### 3.6 gongfu：格斗框架

**对标**：GGPO/GGRS（回滚网络），商业格斗引擎的公开指标（SF6 的回滚帧数、输入延迟）。

| 指标 | 目标 |
|---|---|
| 回滚开销 | 回滚 8 帧并重算的时间 ≤ 1 ms（桌面），≤ 4 ms（Web） |
| 确定性 | 五平台 10 万次回滚逐位一致 |
| 输入延迟 | 本地按键到画面 ≤ 3 帧（对齐 SF6） |
| 数据驱动 | 改一个招式的帧数据到可玩 ≤ 1 s（热重载） |
| 作品质量 | 格斗评分表每项 ≥ 8（现在低于 8） |

**标志性特性**：
1. **角色即数据，加 Agent 陪练**：任何角色、任何难度的陪练都由 agent 在人类档的约束下扮演，并能解释自己的选择（读回放）。
2. **回放即教程**：任何一局都能逐帧解释（框、帧优势、取消），由 agent 自动生成解说。

### 3.7 mlibs：通用库

| 库 | 对标 | 目标 |
|---|---|---|
| `mlibs.text`（塑形、排版） | HarfBuzz + SkParagraph、ICU | 塑形和排版速度不慢于 SkParagraph；中文排版规则覆盖优于它 |
| `mlibs.layout` | Taffy、Yoga | flex 和 grid 一致性：WPT 相关子集通过率 ≥ Taffy；速度不慢于 Taffy |
| `mlibs.markdown` | md4c、cmark-gfm | CommonMark 规范 100% 通过；GFM 扩展通过；速度不慢于 md4c |
| `mlibs.i18n` | ICU4X | 数据体积 ≤ ICU4X 同等覆盖的 ½ |
| `mlibs.rhi`、`mlibs.shader` | wgpu、SDL_GPU | 同等功能下 wasm 体积更小；五后端 CTS 通过 |
| `mlibs.math`（det） | 无直接竞品 | 跨平台逐位确定的初等函数（标志性：wasm、ARM、x64 结果相同） |
| `mlibs.cts` | — | 所有契约 owner 的一致性套件统一框架；结果分为通过、失败、不支持 |

### 3.8 规范：openmui 与 openas

**对标**：WAI-ARIA 与 AccessKit（语义），MCP 与 A2A（agent 协议）。

**标志性**：第一份把 UI 语义、agent 操作和授权（openas）统一起来的开放标准。

**目标**：
- 一个独立的第二实现（例如用 TypeScript 写的 DOM 版 openmui 语义适配器）通过规范 CTS ≥ 90%；
- MCP 桥接：任何 omui 应用自动成为 MCP 服务端。

## 4. 应用：验证线

每个应用都要回答“它证明了主线的哪一条结论”。招牌镜头必须能在 headless 下确定重现，并进 CI。

| 应用 | 证明的主线结论 | 招牌镜头 | 验收 |
|---|---|---|---|
| 官网 | omui 交付性能、质感、Agent 原生、通用动效、设计师画布 | 访客的 agent 由 Mui 带着完成一次授权操作；画布上 1,000 个活组件；文本复制 | 首屏 ≤ 0.8 s；评审 ≥ 85；浏览器 CI 全绿 |
| 风格画廊 | 风格包、液态玻璃 | 两滴玻璃融合 | 评审 ≥ 85；Web 60 fps |
| 组件打砖块 | 组件即游戏对象、Agent 玩家 | 人类档 agent 通关并回放 | 10,000 局逐位回放 |
| 格斗游戏 | gongfu、hanim 的游戏动画、xrender | 一气、二气、三气的超必杀；回滚联机 | 评分表每项 ≥ 8 |
| 宣传片 | hanim 的视频用途、确定性 | 60 秒影片逐帧确定导出 | 重渲染时间优于 Remotion 和 Motion Canvas |
| Markdown 墙 | 画布、文本 | 10,000 篇文档同屏 | 帧时间 ≤ 8 ms |
| 时间线编辑器 | 时间、撤销、agent 编辑 | agent 编辑后人撤销 | 每个编辑都有逆操作 |
| 反应实验室 | 元胞、CPU 与 GPU 一致 | 4096² 场 | 60 fps，逐位一致 |
| PPet | 插件、多语言、生成式能力 | 现场生成服装 | 热重载 ≤ 200 ms |

规则：应用发现的缺口一律回主线修，并在台账里记录“由哪个应用发现”。

## 5. 基准、证据与评审体系

1. **基准**：`tests/bench/competitors` 扩展为按项目分组。
   - 各组的竞品：
     - ui：flutter、compose-desktop、slint、react；
     - motion：gsap、motion、lottie-web、rive；
     - raster：skia、vello-cpu、blend2d、thorvg、resvg；
     - physics：box2d-v3、rapier；
     - text：harfbuzz + skparagraph；
     - layout：taffy、yoga；
     - markdown：md4c、cmark。
   - 每组有 `run.sh` 和固定版本。CI 的 bench 通道每周跑一次，结果写进领先度台账。
2. **招牌镜头**：每个标志性特性一个 headless 测试，输出过程帧条带（端点、中间态、打断），进入 CI 并钉住。
3. **Agent 任务集**：
   - `tools/eval/` 下分 ui、animate、game 三组，每组 100 个任务；
   - 两种基线：我们的语义接口，以及截图式的 computer-use；
   - 记录成功率、步数、token、越权次数。
4. **评审**：
   - 维护者、codex 和量化指标三路；
   - 维度包括架构、API、组件、文字、动效、质感、性能、无障碍、Agent；
   - 质感和性能单独计分；评分写入 `ledger.eval.omui.jsonl`。
5. **官网展示**：文档区的“领先度”页直接读台账，显示每个指标的我方与最强竞品；落后的也显示。

## 6. 实施分期

| 期 | 内容 | 时长（估计） | 退出条件 |
|---|---|---|---|
| **P2-A 基线与台账** | 各项目指标清单定稿并评审；竞品基准补齐（ui、motion、raster、physics、text、layout、markdown 七组）；领先度台账、bench 通道、官网“领先度”页；Agent 任务集骨架 | 1 周 | 每个指标都有第一次同机测量；台账在 CI 每周生成 |
| **P2-B 补短板** | xrender 光栅改造（填充、渐变、描边）；omui 按页交付与冷启动；质感（组件清单逐项）；组件补到 50 类 | 3–4 周 | xrender 五个场景不慢于最快 CPU 竞品；官网首屏 ≤ 0.8 s、可交互 ≤ 1.5 s；质感评审 ≥ 80 |
| **P2-C 标志性特性** | 各项目的标志性特性做成招牌镜头和对照实验（§3）；Agent 任务集跑满并记录基线；hanim 弹性体与 GPU；动力学 P1 刚体 | 4–6 周 | 每项标志性特性有招牌镜头、对照证据和真实任务；台账里标为“far_ahead” |
| **P2-D 应用验证** | 与 P2-C 并行：每个应用按 §4 达到验收；缺口回主线 | 同上 | §4 每行验收通过 |
| **P2-E 复评与收口** | 三路复评；落后项再迭代；文档、skill、ops 补齐；CI 连续稳定 | 2 周 | 每个项目评分 ≥ 85（M5 退出）；台账中“落后”项 ≤ 10% 且有计划；之后进入 M7（≥ 90） |

与顶层路线的对应关系：
- P2-A、P2-B 和 P2-E 的前半是 **M5 的退出**；
- P2-C 中的动力学 P1 和 Agent 游玩属于 **M6**；
- P2-E 之后的 ≥ 90 循环是 **M7**。

**节奏**：每个检查点是一项完整能力。每 10 个检查点对账一次 CI。长任务放到后台，不空等。

## 7. 归属与架构约束（不变）

- 单一归属：数学和随机在 `mlibs.math`，动画在 hanim，渲染在 xrender，设备抽象在 `mlibs.rhi`；优化做在 owner 里，不在消费者里抄一份。
- 依赖只能向下；作品不写引擎代码；不留兼容层。
- 新能力先定契约，再实现；每类插件都有 CTS、trace 和日志。
- 性能优化不能破坏确定性；标“逐位”的结论五平台都要成立。

## 8. 风险与取舍

| 风险 | 应对 |
|---|---|
| 某些指标难以超过成熟竞品（例如 Skia 的 GPU 路径） | 规则是“不差于最强者，且至少一半指标明显胜出”，不要求每项都赢；落后项如实记录 |
| 竞品基准搭建成本高（Flutter、Compose 的构建环境） | P2-A 先做 CPU 侧和 Web 侧；桌面框架用官方示例，固定版本 |
| 标志性特性的对照实验不公平 | 任务集和基线公开；截图式基线用社区最强的公开方案 |
| GPU 真机测试缺失 | 需要维护者提供或确认一台真机（§9） |
| 范围膨胀 | 每期退出条件锁定；新想法进待办，不插队 |
| 磁盘和构建资源紧张（target 约 20 GB） | 定期清理旧的构建缓存；必要时向 mcpp 上游提 issue |

## 9. 待维护者确认

1. **竞品清单**（§3、§5）是否合适，要增删哪些？
2. **领先阈值**：“不差于最强竞品，且至少一半指标 ≥ 1.2×”是否认可？
3. **标志性特性**：每个项目 2–4 项（§0 第 5 条）是否选对，哪些要换或加？

5. **Agent 任务集来源**：100 个 UI、动画、游戏任务，由我们根据现有应用编写，还是需要外部任务集（例如 OSWorld、WebArena 的子集）一起对照？
6. **应用的优先顺序**：建议官网 > 风格画廊 > 打砖块 > 宣传片 > 格斗 > 其余；格斗的美术依赖素材管线，放在 P2-D 后段。
