## 0. 核心点

1. **TS/JS 是 omui 唯一的上层语言，砍掉 Lua 和 Python（D-138）。** TS 同时是代码、配置和数据：JSON 是 TS 对象字面量的子集，只导出字面量的 TS 模块就是数据，带函数就是代码。所有 TS 先求值，求值后的 JSON 快照是规范形式（校验、预演、差异、版本、事务都以它为准）；TS 源保留下来，用于编辑。
2. **分层（D-139）**：C++ 负责引擎、组件和性能敏感部分，并给脚本暴露 API；TS 是最薄的一层（组合、状态、事件、胶水），不进入每帧路径，可以热重载；契约、操作目录、主题、动画都用 TS 写（“TS 进、数据出”），构建期用内嵌的 QuickJS 求值，不需要 Node。只允许可擦除的 TS 语法，转写器自己实现，不依赖外部工具。
3. **应用即设计器，Live Design 是头号亮点（D-149）。** 开发者/设计器模式是一种启动模式（`omui dev`），默认可视，headless 可选；release 可以关闭，并在编译期去掉设计器模块。**TS 源码是唯一的事实来源**：Agent 直接发 TS 代码或结构化操作，框架**只重新求值受影响的组件模块**，按语义 ID 调和，**≤ 1 帧生效**；设计过程由 **hanim 呈现成精致的动画**（线稿到填色、从 Agent 的位置生长、共享元素过渡、方案卡片展开、撤销倒放），呈现与状态分离，不拖慢 Agent。三种预演（直接应用、原地预演、替身方案板）；人随时接手（S-14），Agent 把期望写成可执行的检查，对照人的操作记录逐条核对事实；演示即测试。`design.*` 操作进入 openas 目录。
4. **`omui` 命令行是唯一的顶级入口（D-150、D-153）**：面向框架和创作者的上层入口，统一管理创建、开发（设计器模式）、构建、测试（mtest）、打包、依赖、辅助工具和 Agent 接入，所有命令输出 JSON。omui 专属的构建步骤（契约、嵌入、TS 求值等）都是 mcpp 插件，所以直接用 mcpp 构建结果完全一样；程序员可以直接用 mcpp，非程序员不必了解它。
4a. **设计历史与设计回放（D-151）**：每一次设计改动都是一次“设计提交”（作者、意图、TS 源码差异、语义差异、缩略图），可以分支、切换、回退、对比，和时间线融合成一张图；切换节点时界面用 hanim 过渡到那个状态。设计回放是一等能力：节奏、镜头和字幕都可以编辑，可以导出视频，设计过程本身就能做成一部动画作品。
4b. **统一的创作模式（D-152）**：服务有动手能力的创作者、UI/UX 设计师和应用开发者；UI、应用、动画、动画视频都用同一套 Live Design（内容时间线和设计历史两条轨道）；Live Design 是主推方式，让 Agent 直接写代码、或者 TS 与 C++ 混合开发同样是一等方式。
4c. **开发宿主持有窗口，应用是渲染输出目标（D-154）**：`omui dev` 的宿主进程持有窗口、输入、设计器和设计历史；改 C++ 时，框架自动增量构建受影响的包，新版本按语义 ID 接回状态，在离屏画好第一帧后交叉淡化切换，旧版本在构建期间一直可用，编译错误贴在对应的元素旁边。
5. **运行时生成默认支持代码，开发模式下是顶级能力（D-144 修订）。** 人、Agent 和框架一起，在运行中的应用里动态设计 UI、交互、动画和组件，覆盖 PPet 的全部范围（UI、动作和技能、资产、挂载 UI）。开发模式下不只是全开，还提供完整的辅助数据（布局与约束、样式解析链、动画时间线、性能预算、源码映射）。发布时，开发者在 `omui.config.ts` 里选择开放程度（全开、有限能力、只接受数据、关闭），再与用户配置取交集。安全由四层保证：沙箱上限、能力表、提交前预演、可撤销；分发的包要签名。
6. **可选的原生化（D-146 修订）**：属于 release 构建，不属于设计流程（`omui build --release --native`，P3）。设计确认的基线（语义轨迹、逐字节像素、动画采样）作为前提；可编译的子集自动翻译成 C++，其余由框架生成骨架和对照表供 Agent 重写；必须通过逐字节等价校验，不通过就继续以 TS 发布。大多数应用不需要。
7. **人 × Agent × 框架协同与事实确认（D-148）。** 框架记录人和 Agent 的每一次交互，以及从输入到效果的因果链：输入、命中结果和原因、分发的动作、处理函数、状态和语义变化、动画、帧、日志。人说“点了没反应”，Agent 不靠人的描述，而是经 openas 查询记录（`ui.timeline`、`ui.explain`）确认事实，例如“点击被 Save 上方的透明覆盖层吞掉了”；再把这次记录导出成可以逐字节回放的场景，作为回归测试。记录分五级（off / errors / actions / interactions / full），开发模式是 full，release 的建议默认值是 errors，在 `omui.config.ts` 里配置；读取人的记录需要授权，文本脱敏，只存在本机。
8. **界面全平台自绘（D-140）**；窗口和系统集成面（边框、菜单栏、托盘、通知、文件对话框）可选原生或自绘；补齐输入法、无障碍桥、平台行为、平台风格包。
9. **webview 只作外部表面组件（D-141）**，不做 Web 前端模式；HTML 子集作为内容输入按需支持。
10. **观察三模态，不做 computer use（D-142）**：语义优先，按需截任意区域，要精确就读 SVG；用对照实验证明 token 和步数少一个数量级。**自描述取代 skills 和 llms.txt（D-145）**。**AVX2 运行时分派（D-143）**。
11. **测试整体换成 mtest（D-147）**：mcpp 升到 2026.11.8.1；mtest 是测试的唯一归属，`mlibs.testing` 删除；初期只做局部测试，用 `mtest plan` 自动选出受影响的用例，全量交给 CI 对账。
12. **特性表（§3，61 项）、优先级（§4）、实施（§5）**：P0 是 W0（mcpp 与 mtest）、**W14（Live Design，排第一）**、W15（`omui` 命令行）、W1（TS 顶级化）、W2（热重载）、W3（自描述）、W4（两组对照实验）、W12（交互记录与事实确认）；P1 是 W5（生成管线的发布侧）、W6–W8；P2 是覆盖面；P3 是生态和可选的原生化（W13）。

## 2. TS 顶级化的设计（D-138、D-139）

### 2.1 现有基础（`omui.lang.js`）

- QuickJS-ng 经 mwrap 引入（`mcpplibs.mwrap.quickjs_ng`），模块 `openmui`。
- 组件构建函数、信号、表达式（**帧内不运行 JS**）、区域、动词、模型、原生模块（`openmui:native/*`）、主题。
- 热重载：`Script::reload` 在 200 ms 内完成，第 n 个 `signal()` 保留原来的值。
- `.d.ts` 从契约生成（`spec/stubs/core.d.ts`）。
- **缺口**：
  - TS 转 JS 依赖外部 esbuild，运行时生成和分发都受影响；
  - 没有沙箱限额，没有签名；
  - 配置还是 TOML；
  - 没有 `describe --api`；
  - CTS 和示例里有三种语言并存。

### 2.2 “TS 即代码也即数据”

| 模块形态 | 例子 | 求值结果 |
|---|---|---|
| 只导出字面量 | `export default { kind: "button", id: "save", text: "Save" }` | 数据（JSON 快照，与写 JSON 等价） |
| 带类型的声明 | `export default defineContract({...}) satisfies Contract` | 数据，加上完整的类型检查 |
| 带函数的组合 | `export const Counter = () => column(...)` | 构建出的视图树（数据）加上事件处理函数（代码） |
| 运行时生成 | AI 写出的 TS 或 JSON | 在沙箱里求值成数据快照，经过预演和提交 |

- **规范形式**：求值后的 JSON 快照。schema 校验、预演、差异、版本、事务、跨语言生成都只认它。JSON 文件可以直接作为输入，也就是和 JSON 配合。
- **源与快照**：源（TS）用于人和 Agent 编辑；快照用于执行和验证。二者带同一个版本号；改了源就要重新求值，快照不能手改。
- **确定的求值**：配置和生成内容求值时，没有 I/O、没有真实时间、没有随机数（需要的话由宿主注入确定的版本，归 `mlibs.math`）、没有网络。同一个源总是得到同一个快照。

### 2.3 TS 转 JS 不依赖外部工具

- **只允许可擦除语法**：类型标注、`interface`、`type`、`satisfies`、`as` 这类去掉就能运行的语法。`enum`、`namespace`、参数属性这类需要转换的语法不允许，`omui check` 会报出位置和改法。
- **C++ 的擦除器**：归 `omui.lang.js`（`src/ts/`），作为运行时和 `omui-gen` 共用的转写器。按词法擦除类型、保留列号（错误位置能对上源码）。
- **类型检查**：开发期和 CI 用 `tsc`（有 TS 7 原生版就用原生版），由 `omui check` 调用，结果统一成 omui 的诊断格式（机器可读，附修复建议）。
- **esbuild**：只在“把多个模块打包进可发布的应用”这一步可选使用；热重载和运行时生成都不依赖它。

### 2.4 用 TS 写契约、操作目录、主题（“TS 进、数据出”）

- `defineContract`、`defineOps`、`defineTheme`、`defineMotion`（动画文档）、`defineView`。
- `omui-gen` 用内嵌的 QuickJS 求值，得到 JSON，再生成 C++ 胶水、`.d.ts`、目录清单和文档。**C++ 用户不需要装 Node。**
- **迁移**：先试点一个组件契约（`button`）和一份操作目录（`studio.ops`），验收标准是生成的产物与现有 TOML 生成的**逐字节一致**；然后一次性迁完，不保留 TOML（按“不留兼容层”的原则）。

### 2.5 TS 应用层“尽量薄”的约束

- 不进入每帧路径（已有：表达式由运行时同步求值）。lint 规则 `script-frame` 检查动画、布局、绘制回调里有没有 JS。
- 计算密集的部分写成 C++ 原生模块，经 `openmui:native/*` 暴露。
- 一个应用的 TS 部分如果超过某个规模（例如 2,000 行），由 `omui check` 提示把哪些部分下沉到契约或原生模块。

### 2.6 热重载与 Agent 版热重载

- **低线**：TS 和视图文档改动后 ≤ 100 ms 生效，状态按稳定的语义 ID 和信号键保留（目前是 ≤ 200 ms）。
- **亮点**：每次重载后，自动回报**语义差异**（新增、移除、改变的节点）、**像素差异**（变化区域加局部截图）和**动画采样差异**（按时间采样的关键帧）。Agent 不用再截图对比，直接拿到“这次改动改变了什么”。
- 经 MCP 的 `ui_reload` 和协议的 `reload` 提供；CLI 是 `omui dev`。

### 2.8 动态设计的开放程度与配置（D-144、D-148）

**场景**：产品经理或设计师说“做一个订阅设置页，开关切换时卡片要有弹性的展开动画”。Agent 在运行中的应用里生成 TS（UI、交互、动画），热重载，给出预演；人看画面、点一点、提意见；Agent 再改。整个过程不需要重新编译，也不需要开发者介入。

**开发模式下是顶级能力，意味着：**
- 代码在应用里直接运行（QuickJS 沙箱，有上限，开发模式下上限宽松）；
- 宿主能力按开发模式开放（D-136：开发模式对可信会话开放全部已声明能力）；
- 每次改动都是一个可以撤销的步骤，可以并排出分支方案（`vary`），也可以在工作台里指认和调参；
- **人和 Agent 的每一次交互都被记录下来**（§2.9），Agent 随时能拿到真实状态；
- **辅助数据完整**：布局盒和约束、样式解析链（这个颜色来自哪个令牌、哪个风格包）、动画的时间线和采样、性能预算和重绘区域、每个节点对应的 TS 源码位置。

**各模式的配置写在 `omui.config.ts` 里**（TS 即配置，D-138）：

```ts
export default defineApp({
  modes: {
    development: { designer: true, generation: "all", recording: "full" },
    release: {
      designer: false,       // 设计器模块在编译期去掉
      generation: "limited", // all | limited | data | off
      recording: "errors",   // off | errors | actions | interactions | full
      native: false,         // 可选的原生化（D-146）
    },
  },
});
```

**发布时运行时生成的四档开放程度**，再与用户配置、会话约束取交集：

| 档位 | 运行时生成能做什么 | 典型用途 |
|---|---|---|
| 全开 | 代码和数据都可以，能力按清单 | 设计工具、内部工具、PPet |
| 有限能力 | 代码可以运行，但只能用声明过的组件、动词和数据源 | 让用户的 Agent 定制界面 |
| 只接受数据 | 只接受 JSON（或只导出字面量的 TS），不运行逻辑 | 严格的企业环境 |
| 关闭 | 不允许运行时生成 | 固定界面的应用 |

### 2.9 交互记录与事实确认（D-148）

**问题**：人验收时说“点了按钮没反应”。现在的 Agent 只能根据这句话去猜：是事件没绑定？按钮被禁用了？被什么挡住了？还是处理函数报错了？这就是信息差。

**做法**：框架记录从输入到效果的完整因果链，Agent 经 openas 查询事实。

| 环节 | 记录内容 | 现状 |
|---|---|---|
| 输入 | 谁（人或 Agent，带执行者）、什么（指针、按键、文本；密码类字段只记长度）、在哪里、什么时候（时间戳和帧号） | ✗ 没有记录原始输入 |
| 命中 | 落到了哪个节点；**没落到目标时的原因**：被别的节点遮挡、`pointer_events: none`、禁用、在边界外、手势被别的节点捕获、焦点不在 | ◐ 有 `hit_test`，没有原因 |
| 分发 | 触发了哪个动作，或者为什么没有触发（没有对应动作、被冲突规则拒绝、被权限拒绝） | ◐ 动作日志只记执行过的 |
| 处理 | 调用了哪个处理函数和动词，结果如何，有没有抛错 | ◐ 有日志，没有关联 |
| 效果 | 状态变化、语义差异、启动或打断的动画、重绘的区域 | ◐ `changes` 和帧历史分散在各处 |

每条记录带一个**因果链 ID**，把同一次输入引起的所有事情串起来。

**查询接口**（协议、MCP 和 openas 操作目录都提供）：
- `ui.timeline {actor?, node?, kind?, since?, last?}`：按执行者、节点、类型、时间过滤的记录；
- `ui.explain {event | node}`：一次输入的完整因果链，并指出**断在哪一环**、原因是什么。

**事实确认的流程**：
1. 人说“点了没反应”。
2. Agent 查 `ui.timeline {actor: "person", kind: "pointer", last: 5}`，找到那次点击。
3. Agent 查 `ui.explain`，得到事实，例如“点击落在 `main/overlay` 上（透明，但会接收指针），没有到达 `main/actions/save`”。
4. Agent 修复（例如把覆盖层设成 `pointer_events: none`），热重载。
5. Agent 把这次记录导出成场景，回放验证修复（逐字节一致），并作为回归测试保留。

**隐私与权限**：读取人的交互记录是一项能力（openas），开发模式下开放，发布后默认关闭，由用户授权；文本内容脱敏；记录只存在本机的环形缓冲里；导出需要人确认。

### 2.10 可选的原生化（D-146 修订，release 构建的选项）

| 阶段 | 做什么 | 产出 |
|---|---|---|
| ① 动态设计 | Live Design（§2.12） | TS 源 |
| ② 冻结基线 | 人确认后，框架录下该界面的**语义轨迹**（场景步骤和每一步的语义状态）、**按时间采样的逐字节像素帧**和**动画采样** | 基线（mtest 的用例和快照） |
| ③a 自动编译 | `omui build --release --native`（或 `release.native: true`）：把可编译的子集翻译成可读的 C++（视图组合、信号、表达式、动画程序、主题，以及简单的处理函数，如赋值、调用动词、条件分支）。生成的 C++ 带回 TS 源的映射。子集外的部分保留为 TS，或标记出来交给 ③b | C++ 组件，带映射 |
| ③b 辅助参考 | `omui build --native-reference`：生成 C++ 骨架、TS 到 C++ 的逐项对照表（每个 TS 构造对应的 C++ API、契约、令牌）、基线和等价测试，供 Agent 或开发者重写 | 骨架、对照表、测试 |
| ④ 等价校验 | 同一个场景分别跑 TS 版和 C++ 版：语义轨迹、像素帧和动画采样必须**逐字节一致**；不一致就用 `ui.explain` 和 `ui_drew` 定位 | 通过或不通过，附差异 |
| ⑤ 混合发布 | TS 和 C++ 组件共存，可以按组件逐个原生化；等价校验不通过就继续以 TS 发布 | — |

原生化不属于设计流程，大多数应用不需要（TS 不进每帧路径，动画也是先求值成 hanim 程序再原生执行）。只在极致性能、不带 JS 引擎、保护源码或平台合规时使用。最小 SOP（skill）随框架提供：什么时候值得原生化、两种方式怎么用、等价校验失败时怎样定位。

### 2.11 测试：mtest 与局部测试（D-147）

- **mcpp 升到 2026.11.8.1**（`.xlings.json`）；从这个版本起，测试文件可以只声明用例对象，不写 `main`。
- **mtest 是测试的唯一归属**，删除 `mlibs.testing`（不留兼容层）。API 的对应关系：`Suite` 加 `s.test(...)` 改为 `"名字"_test = [] {...}` 或 `UTest` 对象；`check` 和 `check_eq` 改为 `expect(...)` 和 `expect(eq(...))`；不再需要 `s.run(argc, argv)`。写一个机械转换脚本，被触及的包整体迁移，最后集中迁完剩余的包。
- **局部测试**：每个检查点只跑 `mtest plan --since` 选出的用例（受影响的包和直接消费者）；不做全量，不大范围重新钉住基线；全量交给 CI，约每 10 个检查点对账一次。
- **标签和资源**：`gpu`、`pixel`、`slow`、`display` 这些标签对应现在的 GPU 环境和像素测试。
- **W0 的调研结论**（mtest 0.5.0，mcpp 2026.11.8.1 已于 11-08 发布）：
  1. **影响判定**：用例上次实测时执行过的文件（覆盖映射）、用例声明的 `file:` 产物、所属程序的源文件，与 `git diff --name-only <base>...HEAD` 求交；说不清自己读什么、映射里也没有的用例一律算受影响（宁多勿漏）。`mtest plan` 说明每个用例为什么被选中。
  2. **断言**：`eq`、`ne`、`lt`、`le`、`gt`、`ge`、`near`、`contains`、`throws`、`nothrow`、`fatal`，足够覆盖现有用例。
  3. **快照**：`e2e::golden(文件, 文本)`，`MTEST_GOLDEN=update` 时更新。像素钉值本来就是哈希文本，直接用；需要 PNG 级别的对比时再在上游补。
  4. **CTS**：`kind::cts` 加 `clause{}`（条款）、`skip_if`（不支持）、`known_gap{原因, 到期日}`（已知缺口），比 `mlibs.cts` 的三态还多一种；`cts::coverage` 能检查每个条款都有用例。**结论**：`mlibs.cts` 只保留各契约的套件内容，执行、选择、报告交给 mtest。

### 2.12 应用即设计器与 Live Design（D-149，头号亮点）

**定位**：人看着 Agent 用 TS 代码，在真实运行的应用里实时设计界面、交互和动画。每一步当帧生效，有精致的过渡动画，可以预演、可以撤销；人随时可以接手操作，再让 Agent 拿事实核对结果是否符合预期。应用本身就是设计器，不需要另做一个。

**启动模式**：

| 模式 | 命令 | 设计器 | 用途 |
|---|---|---|---|
| 开发者/设计器模式 | `omui dev`（默认可视） | 开启：设计叠加层、Agent 在场、变更历史与分支、交互记录视图、测试面板 | 设计、开发、验收 |
| headless 设计 | `omui dev --headless` | 开启，没有窗口 | Agent 自己批量试方案、跑测试 |
| release | `omui run`、`omui build --release` | 关闭；模块在编译期去掉 | 发布 |

#### 2.12.1 Agent 直接发 TS 代码，≤ 1 帧生效

TS 源码始终是唯一的事实来源，运行时永远只是 TS 的求值结果。实时性来自**组件级的增量求值**，不来自把运行时状态反推成代码。

| 步骤 | 做什么 | 耗时目标 |
|---|---|---|
| 1. 编辑 | Agent 发 **TS 代码**（替换一个组件模块，或针对某个节点的代码片段），或**结构化操作**（插入、改属性、改样式、改动画、改布局）；结构化操作由框架转成对 TS 源码的编辑 | — |
| 2. 求值 | 自研转写器去掉类型；QuickJS 沙箱**只重新求值受影响的组件模块** | ≤ 2 ms |
| 3. 调和 | 按稳定的语义 ID 对比新旧树，状态和信号保留 | ≤ 2 ms |
| 4. 呈现 | 新状态当帧生效；变化由 hanim 呈现（§2.12.2） | 当帧开始 |
| 5. 回报 | 给 Agent 返回语义差异、变化区域的截图、动画采样 | — |

整条链路 ≤ 1 帧（16 ms）。每个节点记录它来自 TS 源码的哪个位置（C++ 部分已有 `Runtime::origin`，TS 部分要补），源码和运行时双向对应：改了源码立即反映到界面；在界面上指一个元素，就能定位到源码。

#### 2.12.2 用 hanim 呈现设计过程：精致、惊艳，而且不拖慢 Agent

设计过程本身就是一段好看的动画。这是框架的默认设计语言，以 hanim 配方的形式提供（`design.*` 配方，风格包可以覆盖），不是作品专属的效果。

| 设计事件 | 呈现方式（hanim） |
|---|---|
| 新增元素 | **从 Agent 在场的位置生长出来**：先用描边路径的裁剪动画画出线稿（`trim`），再填色、填内容（弹簧缩放加淡入）；子元素按错峰依次出现 |
| 改属性和样式 | 颜色和渐变平滑过渡（感知均匀的颜色空间），尺寸和圆角用弹簧，阴影和模糊渐变；改动的元素短暂描一圈高亮 |
| 改布局 | 所有受影响的元素用**共享元素过渡**移到新位置（按语义 ID 识别同一个元素），不跳变 |
| 移除元素 | 收缩并溶解，回到 Agent 在场的位置 |
| 改动画 | 先把新动画的时间曲线叠加显示在元素旁边，再播放一遍 |
| 代码与画面的联系 | 被编辑的那段 TS 以浮动代码卡片的形式贴在元素旁边，改动的值高亮，然后淡出 |
| Agent 在场 | Agent 的“身体”（官网的 Mui，或通用的光标）平滑移动到正在设计的位置，留下淡淡的轨迹；意图写在旁边（D 的在场组件） |
| 原地预演 | 幽灵叠加层，可以前后切换，也可以用划动的分屏对比 |
| 方案板 | 几个方案卡片扇形展开（错峰）；选中的方案以共享元素过渡飞回原位 |
| 撤销 | 把这一步的动画**倒放**回去（hanim 的时间是确定的，可以反向） |
| 设计回放 | 整段设计过程是一条可以拖动的时间线，逐字节确定，可以导出成视频（复用 `omui video` 和宣传片的管线） |

**呈现与状态分离**：状态在当帧就是新的，动画只是呈现层。headless 的 Agent 不受动画拖慢，拿到的就是最终状态。人看到的节奏可以调：

- 速度可以调快、调慢；
- Agent 改得太快时，呈现自动排队、合并成可读的节奏，不会闪成一片；
- 遵守“减少动态效果”的系统设置，这时用简短的淡入淡出代替；
- 动画时长和曲线遵守质感规范（起点感知、打断连续、可以反向）。

#### 2.12.3 三种预演

| 方式 | 效果 | 什么时候用 |
|---|---|---|
| 直接应用 | 当帧生效，是可撤销的一步 | 小改动、连续微调 |
| 原地预演 | 显示在预演层里，不提交；人说“可以”才提交 | 结构性改动 |
| 替身方案板 | Agent 在 headless 替身里出几个方案，并排展示；选中的经预演后应用 | 风格、布局这类见仁见智的选择 |

#### 2.12.4 “我来操作一下，你看看符不符合预期”

1. **Agent 先把期望写成可执行的检查**：语义断言（开关打开后卡片可见、高度 240 px），加上时间上的断言（展开在 300–400 ms 内完成、回弹不超过 10%）。
2. **人说“我来试试”，或者直接上手**：Agent 的编辑流自动暂停（S-14），会话进入“人在操作”的状态，交互记录器完整记下这一段（§2.9）。
3. **人说“好了，你看看”**：Agent 用 `ui.timeline` 取出这一段，对照检查逐条回报事实。例如：“你点了 2 次开关；第 1 次卡片 340 ms 展开到 240 px，符合；第 2 次在动画中途点击，从当前位置反向收回，没有跳变，符合；回弹 18%，超过了你说的‘轻微’（上限 10%），建议把阻尼从 14 调到 20，要我直接改吗？”
4. **演示即测试**：这段操作一键存成 mtest 的场景用例，以后每次改动都自动回归。

#### 2.12.5 接口（openas 操作目录、协议、MCP 三处同时提供）

| 操作 | 作用 |
|---|---|
| `design.begin {intent}` | 开始设计会话，说明意图（在场组件显示） |
| `design.edit {code \| ops, target?, mode: apply \| preview}` | 发 TS 代码或结构化操作；直接应用或预演 |
| `design.commit` / `design.discard` | 提交或放弃预演 |

### 2.13 `omui` 命令行：唯一的顶级入口（D-150）

mcpp 仍是底层的构建和包管理系统；`omui` 是产品层的统一入口（如同 Expo 之于 Metro 和 Gradle、`nsh` 之于 Cargo）。

| 命令 | 作用 | 底层 |
|---|---|---|
| `omui new <名字> [--template]` | 创建项目：最小应用，同时也是设计界面 | 生成 `mcpp.toml`、`omui.config.ts` |
| `omui dev [--headless] [--with 模块…]` | 开发者/设计器模式，Live Design 和 MCP 打开 | mcpp 构建加 omui 宿主 |
| `omui run` | 按 release 方式运行 | mcpp |
| `omui build [--release] [--native]` | 构建；`--native` 是可选的原生化 | mcpp |
| `omui test [--plan]` | 测试；默认只跑受影响的用例 | mtest |
| `omui package` | 签名、公证、自动更新 | mcpp 加 omui |
| `omui add <依赖>`、`omui deps` | 依赖，包括运行时依赖 | mcpp |
| `omui tools [list \| open \| close] <工具>` | 辅助开发工具和设计器面板的开关 | omui |
| `omui mcp`、`omui agent` | Agent 接入 | 已有 |
| `omui check`、`omui fmt` | 类型、契约、格式 | 已有，接入 tsc |
| `omui eval` | Agent 任务评测 | `tasks.py` 产品化 |
| `omui describe --api` | 自描述导出 | D-145 |
| `omui doctor` | 检查环境：工具链、GPU、依赖 | 新增 |

**约定**：所有命令都输出结构化 JSON，退出码明确（D-61）；读取 `omui.config.ts`；Agent 也可以经 MCP 调用，`package` 这类会写出产物的命令属于需要人回答的操作（openas）。

### 2.14 设计历史与设计回放（D-151）

**设计提交**：每一次设计改动（Live Design 的一步、人的一次调参、一次撤销之外的回退）都是一次提交：

| 字段 | 内容 |
|---|---|
| 作者 | 人或 Agent（带 openas 的执行者和委派链） |
| 意图 | 这一步要做什么（来自 `design.begin` 和 `design.edit` 的说明，或人的一句话） |
| 源码差异 | TS 源码的变化（唯一的事实来源） |
| 语义差异 | 新增、移除、改变的节点 |
| 缩略图 | 改动区域的截图 |
| 时间点 | 在设计过程中的位置，用于回放 |

**操作**（`design.*` 加上 `omui design …`，人和 Agent 用同一套）：

| 操作 | 作用 |
|---|---|
| 提交 | 自动（每步一次），也可以把几步合并成一次 |
| 分支 | 从任意提交分出去；方案板的每个方案就是一条分支 |
| 切换 | 切到任意提交或分支；界面用 hanim **从当前状态过渡到目标状态**（按语义 ID 做共享元素过渡） |
| 回退 | 回到某个提交，之后的提交保留在原分支上，不丢失 |
| 对比 | 任意两个提交并排、叠加或划动对比，附语义差异和源码差异 |
| 合并 | 两条分支的结构化合并；冲突交给 Agent 处理，人确认 |
| 标记 | 给重要的提交打标签（“评审版”“定稿”） |

**与时间线融合的可视化**：一张图，横轴是设计过程的时间，每条分支是一条泳道，提交是节点（带缩略图）。拖动时间轴，就在提交之间回放设计过程的动画；点击节点就切换过去；选中两个节点就进入对比。动画和视频项目还有**内容时间线**（作品自己的时间），两条时间线上下叠放，各管各的，不混淆。

**设计回放是一等能力，设计过程本身就能成为动画作品**：
- 回放是逐字节确定的 hanim 时间线，可以任意拖动、倒放、变速；
- 可以编辑：节奏（压缩空闲、放慢关键步骤）、镜头（自动聚焦到正在改的元素，可以手动调）、字幕（来自每次提交的意图和说明）、Agent 在场的身体（例如 Mui）；
- 导出视频（复用 `omui video` 和宣传片的管线），或者导出成一个可以交互播放的“设计过程”文档；
- 用途：评审、教学、作品集，以及官网和 README 的演示。

**存储**：项目内的 `.omui/design/`，内容寻址（`mlibs.hash`）、只追加；源码快照只存差异。`omui design sync` 可以把定稿的提交压缩成普通的 git 提交，或者完整导出到 git 的独立引用。不引入 libgit2（它是带链接例外的 GPL，不符合许可规则），需要时调用系统的 `git` 命令。

### 2.15 统一的创作模式与服务人群（D-152）

| 人群 | 主要做什么 | 主要方式 |
|---|---|---|
| 有动手能力的创作者 | 小应用、小工具、互动作品、动画、动画视频 | Live Design；完全不碰代码和 mcpp |
| UI/UX 设计师 | 界面、交互、动效、设计系统 | Live Design；需要时看源码差异 |
| 产品经理 | 原型、验收 | Live Design，人接手后由 Agent 核对事实 |
| 应用开发者 | 完整应用 | Live Design、让 Agent 写代码、自己写 TS 或 C++，三者混合 |
| 框架和组件开发者 | 组件、引擎能力 | C++ 加契约；用 mcpp 或 `omui` |

**同一套模式覆盖所有创作类型**：

| 作品类型 | 内容是什么 | 用 Live Design 做什么 |
|---|---|---|
| UI 和应用 | 视图、交互、状态 | 设计界面和交互，验收，测试 |
| 动画 | hanim 动画文档（TS 写的 `defineMotion`） | 设计动画，在内容时间线上调时间和曲线 |
| 动画视频 | 场景、镜头、配乐（宣传片的管线） | 设计每个场景，回放、导出 |
| 设计过程本身 | 设计历史 | 编辑回放，导出成作品（§2.14） |

**三种开发方式都是一等的**：Live Design（主推）、让 Agent 直接写代码（`design.edit` 发代码，或者直接改文件）、混合开发（TS 与 C++ 同时在改，§2.16）。

### 2.16 开发宿主持有窗口，应用是渲染输出目标（D-154）

**为什么要这样**：改 TS 能做到当帧生效；但混合开发时改了 C++，传统做法是重启应用：窗口闪一下、状态丢失、设计器和设计历史也跟着重来。要做到“无感”，窗口和设计器就不能属于被替换的那部分。

**进程结构**：

| 部分 | 进程 | 持有什么 |
|---|---|---|
| 开发宿主 | `omui dev` 进程，一直运行 | 窗口、GPU 表面、输入、设计器叠加层、设计历史、交互记录、Agent 接口 |
| TS 部分 | 宿主进程内（QuickJS） | 应用的 TS 源码和求值结果 |
| C++ 部分 | 子进程（需要时） | 应用的原生组件和逻辑 |

应用把显示列表交给宿主，宿主用同一套 xrender 画出来，所以像素与直接运行时逐字节一致；输入由宿主分发回应用。**渲染输出目标是统一的抽象**：窗口、headless、Web 画布、视频导出，都是同一份显示列表的不同输出目标。

**改 C++ 时的流程**：

| 步骤 | 做什么 | 人看到什么 |
|---|---|---|
| 1. 监视 | 文件改动触发 | 设计器角落出现一个细小的构建指示 |
| 2. 增量构建 | mcpp 只构建受影响的包 | 旧版本继续运行、可以交互 |
| 3. 启动新进程 | 新的 C++ 子进程 | — |
| 4. 接回状态 | 按语义 ID 和信号键把状态迁移过去（模型、信号、滚动位置、焦点、输入框内容） | — |
| 5. 离屏首帧 | 新进程先在离屏画好第一帧 | — |
| 6. 切换 | 宿主从旧帧交叉淡化到新帧，变化的元素用 hanim 过渡 | 一次平滑的切换，没有闪烁 |
| 出错时 | 编译错误或启动失败 | 错误以卡片贴在对应元素旁边（源码位置可点），旧版本继续运行 |

**为什么用进程替换，不用动态库热替换**：C++ 模块、静态初始化、ABI 都让动态库热替换很脆弱；进程替换配合状态迁移更可靠，也和渲染输出目标的抽象一致。release 构建里没有宿主这一层，应用直接持有窗口。

### 2.17 工程结构：语义清晰、一眼能懂（D-156，待维护者 review）

**问题**：现在的工程布局各写各的：
- TS 代码有的在 `logic/`，有的在 `gifts/`、`code/`；
- 视图文档在 `ui/`，契约在 `contract/`；
- ops 目录和 skill 文件放在包的根目录；
- 作品的根目录下摊着 music/、sounds/、sim/ 等一串目录；
- 纯 TS 应用还要带一个手写的一行 `src/main.cpp`。
人和 Agent 打开一个工程，很难一眼看出"代码在哪、数据在哪、什么是生成的"。

**原则**：
1. **根目录只放约定的入口**：`mcpp.toml`（构建和身份）、`omui.config.ts`（运行方式：授权、记录）、`README.md`；有构建步骤时加 `build.mcpp`；有操作时加 `skill.omui.md`。其余内容都进命名清楚的目录。
2. **每类内容只有一个归宿**：目录名说明用途，`.<种类>.omui.ts` 后缀说明种类（工具按后缀找文件）。同类文件不散落在多个目录。
3. **源码和生成物严格分开**：
   - 构建产物在 `target/`；
   - 必须提交的生成物只放在名为 `generated/` 的目录（例如 `src/generated/`、`stubs/` 的约定改为 `generated/stubs/`），并且标明"不要编辑"；
   - 框架自己的本地状态（设计历史等）放在 `.omui/`，不手改。
4. **集合用复数，角色用单数**：`contracts/`、`tests/`、`assets/`、`examples/` 是一组同类文件；`app/`、`src/`、`native/`、`design/` 是一个角色的位置。

**应用工程**（`omui new`）：
```
my-app/
├─ mcpp.toml          构建；[package.metadata.openmui] 是应用的身份（id、标题、尺寸、入口）
├─ omui.config.ts     运行方式：开发与发布各自的 Agent 授权、记录等级
├─ README.md
├─ app/               应用本身（TypeScript）：main.ts 是入口，其余模块按路径导入；Live Design 编辑的就是这里
├─ design/            外观与动效的数据模块：*.theme.omui.ts、*.style.omui.ts、*.motion.omui.ts、*.view.omui.json
├─ contracts/         应用自己组件的契约（*.contract.omui.ts，有 C++ 组件时才有）
├─ native/            C++（只在需要时）：组件实现、*.native.omui.ts 及其实现
├─ assets/            字体、图片、声音等二进制资源
├─ tests/             mtest 用例、*.scenario.omui.json（演示即测试）
└─ .omui/             框架的本地状态（设计历史），不手改
```
纯 TS 应用不再有手写的 C++：`omui.entry.player` 声明一个 `kind = "entry"` 的目标，应用的可执行目标写 `main = { from = "omui.entry.player/player" }`（mcpp 2026.10.26.2 起支持由依赖提供程序入口），工程里不出现 `src/main.cpp`。

**框架包**：
```
<package>/
├─ mcpp.toml、README.md（第一行是一句话定义）、build.mcpp、skill.omui.md
├─ src/               C++，按职责分 src/<职责>/；必须提交的生成物在 src/generated/
├─ contracts/         *.contract.omui.ts
├─ native/            *.native.omui.ts
├─ ops/               <product>.ops.omui.ts，以及生成的清单（ops/generated/）
├─ design/            主题、风格等数据模块
├─ generated/stubs/   生成的脚本存根
├─ tests/  examples/  media/（README 用的图片和视频）
```

**落地步骤**：
1. app-ts 模板和 `omui new` 先按新布局生成；lint `layout` 增加规则：根目录出现约定以外的文件或目录、同类数据文件分散在多处，都报出来，并给出应当放的位置。
2. 现有的包和作品逐个迁移：`contract/` → `contracts/`（契约插件的默认目录随之改）、根目录的 `*.ops.omui.ts` → `ops/`、`logic/` → `app/`、`ui/` → `design/`。每个包迁移后，核对生成物逐字节不变（omui-gen 的“生成物是最新的”测试），并运行该包的测试。
3. 作品里的资源目录（music/、sounds/、gifts/ 等）按内容并入 `assets/` 或 `app/`。

### 2.18 脚本导入按层面分：`openmui` 是规范，`omui` 是实现（D-157，已确认）

**原则**：沿用"公开名按层面取"（AGENTS §1）。脚本里导入什么，就说明这段代码依赖到哪一层。

| 导入 | 层面 | 内容 |
|---|---|---|
| `"openmui"` | 规范（脚本绑定 §5.2） | 构建函数、信号、表达式、区域、`mount`、`verb`、`model`、`find`/`act` 等；运行时注册的每个组件的构建函数（规范规定如此，包括 omui 自带的组件和应用自己的组件） |
| `"openmui:native/<名字>"` | 规范（native 机制 §8） | 应用自己的 native 模块 |
| `"openmui/define"` | 规范定义的数据格式 | `defineContract`、`defineNative`、`defineView` |
| `"omui/define"` | 实现 | `defineConfig`（`omui.config.ts`）、`defineOps`、`defineStyle`、`defineMotion`、`defineTheme`（主题格式进入规范之前） |
| `"omui"` | 实现 | 以后给脚本用的开发、设计辅助；目前为空，需要时才出现 |

**组件不按模块拆分**：组件都从 `openmui` 导入。可移植与否取决于组件来自哪个包，由工具检查：
- 生成的 `.d.ts` 为每个构建函数注明来源包，并标出它是否属于规范注册表；
- `omui check --portable` 列出用到的非规范组件和 `omui` 导入；
- lint 检查标为可移植的包里没有 `omui` 导入。

**晋升路径**：omui 的扩展证明有价值后，先进入规范（规范仓库的 openmui-design 分支），再把导入改成 `openmui`，一次改完，不留别名。

**落地**：
1. `lang.ts` 的数据模块求值同时提供 `openmui/define` 和 `omui/define`，`define*` 函数按上表分到两处；`omui.config.ts`、ops 目录、风格包、动效配方改从 `omui/define` 导入。
2. 存根生成器把规范的 `openmui.d.ts` 和实现的 `omui.d.ts` 分开生成，并加上来源标注。
3. 补上 `omui check --portable`（W1 第 5 步接入 tsc 时一起做）。

- 分层（维护者决定，2026-11-10）：openkal → `mcpplibs.os`（系统原语：文件与其 watcher、进程、本地连接、环境）→ **`mpal`**（`modules/mpal`，操作系统给应用的服务，不限桌面：桌面、移动、Web、嵌入式；按用途分区：notify、pick、transfer、launch、shell、secrets、power）→ omui（自绘版本与原生/自绘的选择）。输入（键盘、指针、触摸、手柄、输入法）随窗口进入宿主，不是 mpal 的服务；通知是“告诉人一件事并收回答复”的服务，答复作为该服务自己的事件返回，不走输入。
- 第二块完成：`mpal` 建立，第一项服务 `notify`。Linux 上经会话总线调用 freedesktop Notifications：D-Bus 线格式（`mpal:dbus`：按签名与对齐编码、EXTERNAL 认证、Hello、方法调用与回复）用 `mcpplibs.os` 的本地连接自己实现，不用 libdbus（许可）和 sd-bus。其他平台如实返回 unsupported。桌面宿主把它接入 `Runtime::NativeSurfaces.notify`（暂时只用于不带动词的通知：人的答复还没有读回）。mpal 的 notify_test 用测试自己的总线（本地 socket）核对：消息布局符合规范的对齐、认证三步、Hello 的唯一名、Notify 的每个参数位置和返回的 id；没有会话总线时报告 unavailable。
- openkal 生态（维护者要求，高优先级）：mpal 是一个构建、所有系统通用——后端用 `mcpplibs.os` 的平台问题选择（原生构建在编译期 `if constexpr (os::can_run_on(...))`，ok 镜像在加载时 `os::host()`）；按协议说话的服务（D-Bus，以后 openbus）就是普通代码，在镜像里同样可用：`mcpp test -p mpal --target x86_64-openkal` 以镜像运行全部测试并通过，CI 的 Linux x64 行加了这一步。需要系统头文件的（WinRT、Cocoa）放进最小的 native 单元，镜像里在 openkal 或 Luban 的总线承载之前如实返回 unsupported。os 与 mpal 的划分写在 mpal 的 README（原语 vs 服务）；绘制两者都不做：mpal 收像素，若要“给像素、收事件”的表面服务，另设 gfx 层的 `mpal.surface` 依赖 xrender，mpal 本身留在 base 层。
- 第三块完成：通知答复读回。`mpal:dbus` 按匹配规则（AddMatch）接收信号，调用等待回复期间到达的信号按序保留；`mpal::Notifier` 显示通知并读回人的答复（`Answer`：选了某个动作（按键名）、被人关闭、到时消失、被应用收回），只返回自己显示的通知的答复；`Notifier::listen()` 在第二条连接上听所有通知的答复，供不能在显示处等待的程序在自己的线程里听。mpal 不启动线程，按拉取读答复。桌面宿主在界面线程显示、在自己的线程里听：带动词的通知也走系统通知（“default” 动作即按下通知本身），按下后把动词投递到界面线程执行；`Runtime::NativeSurfaces.notify` 增加 `pressed` 回调。验收：mpal 的测试用自己的总线核对 AddMatch 的规则、另一个应用的通知关闭在 Notify 回复之前到达也被保留并略过、选择动作、被人关闭、CloseNotification 后的收回、之后没有更多答复；另有一例对真实的 `dbus-daemon`（测试自己的会话总线）：认证、Hello、AddMatch 被总线接受，`dbus-send` 发出的 ActionInvoked、NotificationClosed 经总线路由后读回，其他接口的信号不被路由（机器上没有 dbus-daemon 时跳过）；原生构建和 `x86_64-openkal` 镜像都通过。os 的 COM／WinRT 与 ObjC 运行时方案见 [2026-11-10-mcpplibs-os-com-objc-design.md](2026-11-10-mcpplibs-os-com-objc-design.md)（待维护者 review，未向 os 提交）。
- 第四块完成：mcpplibs.os 0.4.4（mcpplibs/os#24，维护者批准方案后提交、CI 全绿、整体评审后合入并发布，mcpp-index#746）给平台模块加入系统的对象模型 `windows::com`（COM 与 Windows Runtime）和 `macos::objc`（Objective-C 运行时），按 os 的 R0–R7：每个目标都声明、只在自己的平台定义、镜像里不定义，库在首次使用时加载，不加链接输入。mpal 用它们写了两个系统的通知（`mpal:native`，各自的单元只为该系统构建，没有系统头文件）：macOS 经 UserNotifications（需要 bundle 标识符，裸程序如实返回 unavailable；询问一次权限，拒绝时带系统给的原因；动作和关闭经委托类回到 `Notifier::next`）；Windows 经 Windows Runtime 的 ToastNotificationManager（未打包的程序由开始菜单快捷方式带上应用身份，缺少时用 COM 的 IShellLinkW／IPropertyStore 创建；Activated、Dismissed 事件经 `com::delegate` 回到 `Notifier::next`）。新增 `mpal.yml` 工作流：改动 mpal 时在 Linux、macOS、Windows 上几分钟内跑 mpal 的测试（全矩阵约两小时）。验收：macOS 用例先确认裸程序得到 unavailable，再把测试程序复制进一个临时 .app 运行，通知中心回答“已显示”或“拒绝 + 原因”；Windows 用例显示一个 toast（或拒绝 + 原因），并确认快捷方式已创建。

## 7. 风险与取舍

| 风险 | 应对 |
|---|---|
| 删除 Lua 和 Python 会失去已有的 CTS 交叉验证（三种语言记录同一条轨迹） | CTS 改由 JS 加 C++ 两条路径交叉验证；轨迹钉值不变 |
| “只允许可擦除语法”可能让一部分 TS 写法不能用 | 只限制编写 omui 内容时的语法；`omui check` 给出改写建议；模型对这一子集同样熟悉 |
| 求值的 TS 配置可能写出不确定的结果 | 求值环境没有 I/O、真实时间和随机数；同一个源两次求值，快照必须逐字节一致（加入 CTS） |
| 运行时下发代码的安全问题 | 签名、沙箱限额、openas 能力表；默认只接受数据形式，只有拿到授权才运行逻辑 |
| 自绘的平台行为做不到位，用户会觉得“不像原生” | D6 逐项对照评审；平台风格包；先覆盖输入法、文本选择和滚动这三项最影响感受的 |
| TS 迁移牵涉面大 | 先试点，逐字节一致后再全量迁移；按包分批，每批只跑受影响的用例（D-147），全量交给 CI |
| 交互记录涉及隐私 | 读取人的记录是需要授权的能力；发布后默认关闭；文本脱敏；只存在本机；导出要人确认 |
| 自动编译 TS 到 C++ 的范围不好控制 | 只编译明确定义的子集；子集外的部分保留 TS 或交给辅助参考；所有结果都要通过等价校验，不通过就不算固化 |
| 测试框架迁移和 TS 迁移同时进行，风险叠加 | W0 先完成三个包的迁移再开始 W1；转换脚本机械化，迁移前后的用例数和结果必须一致 |
| 组件级增量求值做不到 ≤ 1 帧 | 先测：QuickJS 求值一个中等组件模块的耗时、调和的耗时；不达标时，结构化操作走直接的运行时编辑（同样回写源码），代码编辑走一帧以上的快速路径 |
| 结构化操作转成源码编辑，可能弄乱人写的代码 | 编辑只发生在 Agent 正在设计的组件模块里；按语法树做最小改动；每次编辑都是一步可撤销的源码变更，人能看到差异 |
| 设计过程动画好看但打扰人 | 节奏可调、可以关闭、遵守“减少动态效果”；呈现与状态分离，任何时候都可以跳到最终状态 |
| 设计历史膨胀 | 只存源码差异和缩略图，内容寻址去重；可以压缩合并旧提交；回放从源码状态重新求值，不存帧 |
| 结构化合并两条设计分支不可靠 | 合并只作为辅助：冲突交给 Agent 处理，人确认；默认操作是切换和挑选，不是合并 |
| 进程替换时状态迁移不完整 | 只迁移按语义 ID 和信号键能识别的状态；迁移不了的明确列出来；新进程起不来就保留旧版本 |
