# 终端宿主：字符格是显示列表的又一个后端（F1，一页设计）

2026-11-19 起草，**已定**（2026-11-19 review）。任务 F1（[实施方案](2026-11-18-omui-meng-implementation-plan.md)），挡着 F2–F4；决策 D-249。背景与体积的估计见[体积与性能方案 §5.4](2026-11-18-size-memory-performance-install-lead-design.md)（D-219）。

## 1. 要定的

终端里一个 omui 应用画什么、怎么输入、与语义树是什么关系、体积的两档（C++ 最小终端应用 ≤ 1 MB，带 Agent 端点 ≤ 2 MB）怎么达到。

## 2. 事实（2026-11-19，`d8894152`）

- 宿主有四个：`android`、`headless`、`sdl3`、`web`；终端宿主在 `host/README.md` 里是计划中的。
- 无头宿主已有不出像素的级别：`HeadlessLevel::semantics`（只建树）与 `layout`（有边界与命中，不出像素）。所以运行时在没有像素时已经能跑；但这是运行时的选择，链接进来的东西没有少。
- 组件不直接画像素：`paint_node` 把节点的背景、边框、组件的 `paint` 钩子写进一个 `xrender::DisplayList`（矩形、圆角矩形、文字、裁剪、变换、图层）。
- `omui.view` 的依赖里与像素有关的：`xrender.text`、`xrender.raster`、`xrender.vector`、`hanim.visual`、`mlibs.image`、`mlibs.text`（成形）、`mlibs.rhi`。
- 文字的量度现在来自成形（HarfBuzz、FreeType）；终端里一个字素占一格或两格，量度只需要 `mlibs.unicode`（0.21 MB）。

## 3. 按三级次序（D-185）

**① 原始性创新：字符格是显示列表的又一个后端，不是另一套组件。**

- 终端的每一帧是一个值：`cols × rows` 的格子，每格是一个字素、前景色、背景色与样式位。它由同一份显示列表算出来：矩形填背景色；边框与描边落到制表符；文字按字素落格；裁剪与滚动的位移按格取整；图层的不透明度在格的颜色上混合。
- 所以**现有的组件不改就能出现在终端里**，窗口与终端是同一棵树、同一份布局、同一份显示列表的两种光栅。这是 ratatui、FTXUI、Ink 都没有的：它们的组件是为格子另写的一套。
- **布局以格为单位**：终端宿主把一格当作一个设备单位的宽，行高是两个单位（比例由宿主给，可配），缩放的机制是已有的 DPR；文字的量度由“格的量度”提供。主题另给一份终端的令牌（间距按格取整、圆角为零、阴影不画），是风格包的数据，不是组件里的分支。
- **帧是值，所以可以逐字比对**：终端画面的基线是文本文件，CTS 直接比；同一帧可以由我们自己的渲染器画成图片（等宽字体），Agent 不开终端也能审查画面、无头也能录成视频。
- **输入**走已有的事件模型：键、粘贴、鼠标（SGR 模式）、尺寸变化、焦点；终端的转义序列在宿主里解析成同一组事件。焦点、命中、滚动、Agent 的操作都不知道自己在终端里。
- **差分输出**：前后两帧的格子求差，只写变了的格；同步输出（DEC 2026）包住一帧，避免撕裂。

**② 前沿加组合：终端里的真实像素。** 支持图形协议的终端（kitty、iTerm2、sixel）可以显示位图。同一份显示列表里，标了“要像素”的节点（图片、图表、画布）由 CPU 参考光栅成位图，按协议放进它占的那几格；其余仍是字符。这是“同一棵树”在终端里的上一级。**0.1 不做**：只留节点上的标记与宿主的能力查询；重启条件是字符格这一级稳定、且有一个要用它的工具。

**③ 业界做法（低线）**：差分刷新、同步输出、备用屏幕、SGR 鼠标、真彩色降到 256 色与 16 色、宽字符与组合字符的宽度、尺寸变化的信号。全部要有。

## 4. 结构

| 部分 | 归属 | 说明 |
|---|---|---|
| 显示列表 → 格子 | `xrender` 的一个新的小包（暂名 `xrender.cells`） | 渲染归 xrender（AGENTS §2 第 8 条）。只依赖显示列表的类型、`mlibs.unicode`、`mlibs.math`；不依赖光栅、矢量、成形 |
| 文字的量度 | `omui.view` 的一个槽（`mlibs.compose`）：成形的提供者与格的提供者 | F2 的核心：终端目标下不装成形的提供者，HarfBuzz、FreeType、字体文件不进链接 |
| 终端宿主 | `omui/host/terminal` | 时钟、输入的解析、差分输出、尺寸与能力查询；终端的原始模式经 `mcpplibs.os`（缺的先向上游补） |
| 世界 | `omui.sdk` 的 feature | `terminal`（不带 Agent）与 `terminal` 加 `agent` 两档；走 compose 的同一条路径 |

Agent 面（先写，lint `agent-surface`）：状态是那一帧的格子与语义树；观察有 `ui.tree`（已有）与 `terminal.frame`（格子，或由渲染器画成的图）；控制是已有的输入注入；时间是宿主的时钟；因果沿用视图的记录；身份与授权同别的宿主。

## 5. 体积怎么到

| 档 | 构成（估计） | 办法 |
|---|---|---|
| ≤ 1 MB | 核心、语义、布局、视图的非像素部分、用到的组件、格子后端、宿主 | F2 把成形、光栅、矢量、图像、设备做成不装的提供者；按体积优化编译；C 与 C++ 的运行库动态链接系统的（D-221 允许） |
| ≤ 2 MB | 上一档加 Agent 端点（总线、JSON、规范类型约 1 MB） | compose 已有的 `agent` 能力 |

今天这些部分加起来约 3–4 MB（体积方案 §5.4），所以 1 MB 是有风险的目标；F2 做完量一次，F4 再与 ratatui、FTXUI 并排。

## 7. 风险与降级

| 风险 | 应对 |
|---|---|
| 1 MB 到不了 | 降级写法（五项）：目标 1 MB；实测值；试过的（提供者拆分、体积优化、动态运行库）；为什么不成（余下的在哪几个包）；毕业条件。终端宿主标预览，体积一格写实测 |
| 现有组件在格子里难看（间距、圆角、阴影为像素设计） | 终端的主题令牌；基础组件逐个过一遍文本基线，哪个不成样子就在风格包里给它终端的规则，不在组件里分支 |
| F2 改动视图层的面大 | 先做文字量度一个槽并量体积，再决定其余的引用逐个做还是按包做 |

## 8. 已定的（2026-11-19 review：下列各条同意）

1. 第 ① 级的方向：终端是显示列表的后端、组件不另写。
2. 格子后端放在 xrender（`xrender.cells`）而不是宿主里。
3. 图形协议（第 ② 级）0.1 只留标记、不实现。
4. 1 MB 达不到时按 §7 降级为预览。

## 9. F2 的做法（2026-11-20 补，待 review）

**核对的事实**：
- HarfBuzz 只在 `mlibs.text` 的 `src/native/`（字体 583 行、成形 384 行、字形轮廓 85 行）。
- `FontCollection` 本身也建在 HarfBuzz 上，包括读字体、度量、轮廓与 `hb_font`。
- `omui.view` 与组件直接用 `Paragraph` 与 `FontCollection`，约 130 处。
- 成形之外的部分（SheenBidi 的双向、字素、词、断行、省略号）与 HarfBuzz 的类型写在同一个函数里。

**排除的做法**：用 feature 在 `mlibs.text` 里二选一编译 `native/` 或 `cells/`（同 `tests/features` 的互斥来源）。
- 工作区构建会合并 feature。只要终端宿主是成员，`--workspace` 就会两份同时编译、链接失败。
- `check features` 正是在验证这种“两个同时被拒绝”。

**提议**：按 compose 的同一条路径，把成形与字体做成槽，两个提供者都编译，由组合根安装一个。没被安装的，链接器回收。
1. `mlibs.text` 只留与引擎无关的部分：双向、字素、词、断行、段落与行的布局、查询、编辑，以及 `FontCollection` 的接口。
2. 槽 `mlibs.text.shaper` 的一个提供者，提供字体的读入与选择、度量、一段文字的成形、字形轮廓与彩色层。按段落调用，不进逐像素的路径（AGENTS §2 第 6 条）。
3. 提供者 `mlibs.text.harfbuzz`：今天的 `native/` 原样移过去，默认世界安装它，像素基线不变。
4. 提供者“格”：每个字素按东亚宽度占 1 或 2 格，一格宽 1 个单位、行高 2 个单位，与字号无关；没有轮廓。它与 `xrender.cells` 一起放在终端那边。
5. `omui.view` 经槽取 `FontCollection`。`omui.sdk` 的 `terminal` 世界安装“格”的提供者。

**分步**：
- ① 拆出与引擎无关的部分，`mlibs.text` 与 `xrender.text` 的测试与像素基线不变。
- ② 槽与两个提供者，加一个只装“格”的构建，量它的链接清单与体积。
- ③ `omui.view` 对光栅、矢量、图像、设备的引用。另外要先把显示列表的类型从 `xrender.vector` 里分出来，`xrender.cells` 只依赖类型。

**风险**：`mlibs.text` 是稳定级，接口的移动要一次改完（不留兼容层）。拆分后整个 UI 栈要重编，像素基线全量核对一次。
