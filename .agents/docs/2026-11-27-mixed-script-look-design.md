# 写在程序之前的页面与画布：中文行里的拉丁词、行内代码的底、有序列表的序号、图片的密度（UI5）

状态：第 1、2 节已实现，第 3 节是测量与提议（2026-11-27）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 UI5；相关：[带样子的投影](2026-11-27-styled-projection-loading-design.md)（D-288）、[表格随视图变窄与一段一个行高](2026-11-27-markdown-table-narrowing-design.md) 的第 2 节。

量法：`omui-devtools check takeover`（无头 Chromium 159，文档模板带引擎，三个宽度 × 页面顶部与滚到 700 px；界：中位数 ≤ 1 px、最大 ≤ 2 px、换行 0、至少 50 个词）；逐词的探针（同一量法，另外列出每个词的位移、它在页面上的字体与 CDP 的 `CSS.getPlatformFontsForNode`），临时放在工作树的 `target/`，量完删掉。

## 1. 中文行里的拉丁词（`/zh/` 的 3 px）

### 1.1 事实（改前）

- `/zh/` 在 1280 宽：动得远的都是横向、都在写在程序之前的页面一侧——文档层的词按引擎画它的位置摆（词盒的左边就是那个位置），页面上的词却偏了：`HTML，给` +0.73 px，`Agent` +3.39，下一行的 `先取` +2.47、`llms.txt` +2.59；纵向的差都在行内。
- **原因一：块的字体。** 样子给一个画了文字的节点写“它大多数字形的字体”：中文段落写的是 `'omui-notosanssc'`。段落里的拉丁词是没有元素的纯文字，只能取块的字体，浏览器于是用 Noto Sans SC 自带的拉丁字母排它们（CDP：这一段 Noto Sans SC 61 个字形，Inter 只有链接里的 4 个）。宽度：`Agent` 在页面上 40.44 px、画布上 41.95 px；`HTML` 短 2.25 px。后面的词跟着差。
- **原因二：空格。** 引擎（`mlibs.text.harfbuzz` 的 `shape.cpp`）让空格取它前一个字素的字体，使一段不被空格切开：中文后的空格是 Noto Sans SC 的（15 px 时 3.375 px），拉丁词后的是 Inter 的（4.219 px）。浏览器按字体列表逐字取第一个有这个字的字体：只把块的字体改成 Inter 在前时，中文后的每个空格在页面上宽 0.84 px，一行往后累计（`/zh/` 首段一行有四个这样的空格，最多 3.4 px）。在 Chromium 159 与 Firefox 159 里实测（字体列表 Inter、Noto Sans SC）：中文后的空格与拉丁词后的一样宽（Chromium 4.234，Firefox 4.0；Noto Sans SC 单独 3.367）——两个浏览器都不看前邻。
- **字间的空隙。** 引擎默认在汉字与拉丁字母、数字之间加 1/8 em（`TextStyle::autospace`，CSS Text 4 的 `text-autospace: normal`），没有哪个组件关掉它；Chromium 159 与 Firefox 159 的默认值是 `no-autospace`（计算值实测），只在页面要求时才加（`由oweb构建` 在 15 px 下宽 3.75 px = 2 × 15/8，Firefox 3.77）。文档模板里中文与拉丁之间都写了空格，这一项在本语料上没有位移，换一种写法的文档就有。
- **标点挤压**（未改，见 1.5）：引擎挤“闭＋闭／中”与“开前是开／中”以及非首行行首的开标点；Chromium 的 `text-spacing-trim: normal` 还挤“闭＋开”（`写成（甲）。（乙）` 在 Chromium 里 120 px，不挤是 135）；Firefox 159 不支持这个属性，一个也不挤。本语料没有相邻的全角标点。

### 1.2 三级次序（D-185）

**① 原始性：次序也从那一帧量出来。** 样子本来就是引擎第一帧的投影。字体的次序同样是那一帧的事实：一个字体画了另一个字体也有的字，它就排在那个字体前面（否则那个字会由另一个画）。按这个偏序排出的列表交给浏览器逐字回退，每个非空白的字由画它的同一个字体画——由构造一致，样子不需要知道段落样式写了哪些字体，也对任何字体组合成立（中文、阿拉伯文、emoji）。空白不按字体次序取（引擎按前邻），所以只有“浏览器按列表会给另一个字体”的那几段空白单独写成带字体的行内元素：元素里只有空白，不切开任何词，查找、选中与读回都不变。

**② 前沿与组合。** 查过的：

| 做法 | 与这里 |
|---|---|
| CSS Fonts 4 的逐字匹配（§5.3）：按 `font-family` 列表，每个字取第一个有它的字体 | 就是浏览器这一侧；列表的次序由上面的偏序给出 |
| `@font-face` 的 `unicode-range`（Google Fonts 按区段切子集的做法） | 能把中文字体限在中日韩区段，但空白仍按列表取，前邻规则写不出来；不取 |
| 两个浏览器对空白的取法（实测，上面） | 都按列表；所以把空白写明，不依赖哪个浏览器的启发式 |

组合：站点的字体子集（CF3）与样子用同一份字体文件，覆盖相同，偏序在两边成立。

**③ 低线。** 服务端渲染加水合的站点前后是同一个渲染器，天然一致。这里是两个渲染器，靠“同一份字体、同一个回退次序、写明的空白”一致。

**另一条路（未取，作为提议）：** 让引擎的空格也按字体列表取（CSS 的规则），页面就不需要写空白。代价：中文里的空格变宽 0.84 px（15 px），而且行上多出 Inter 的下降，按行取字体的段落里含空格的中文行高一点（21.75 → 22.83 px）——画布上所有中日韩夹空格的文字都动，钉住的画面随之重钉。它与[表格方案](2026-11-27-markdown-table-narrowing-design.md) §2.5 第 3 条（把 CSS 的行盒规则作为框架的默认，25 个钉）是同一类有意的改动，应一起决定。

### 1.3 设计（已实现）

- **块的字体是一个列表**（`omui.semantic` 的 `look.cpp`）：同一设置（字号、字重、倾斜）的各段字形用到的字体，按“画了对方也有的字的在前”排；排不进同一次序的（彼此都有对方画的字：与正文同字号的代码）不在列表里，它的段照旧是有自己样式的部分。空白不参与排序。字号、字重、颜色仍取字形最多的那一段。
- **部分（`Look::spans`）**：写在行内元素上的字体也是它那一组的列表；与块的列表相同就不写。`line-height:0` 只给首个字体（页面的支柱）或字号不同的部分。
- **写明的空白（`Look::apart`，新）**：一段字形里的空白，若页面按它所在元素的字体列表会取另一个字体，就记下它的字节范围与它的字体（`font-family:<画它的字体>;line-height:0`）；`static_html` 把纯文字在这些范围切开，包成只含空白的 `span`。
- **文档层读回页面时**（`omui_web.js` 的 `projection`）：一个元素“只有文字”的判断把这种 `span`（只有 `style`，不是节点也不是标记）当作文字——否则只有一个标签的链接（`开始 →`）读不出文字，阅读程序画不出它。
- **字间的空隙**：样子的基础规则写 `text-autospace:normal`（引擎的行为）。
- 引擎、文档层的位置、检查与界都没有改。

### 1.5 欠项

- 标点挤压在三处各不相同（上面）。Chromium 与引擎只差“闭＋开”一类；要一致，先定引擎的规则以 CSS Text 4 的哪一条为准，再决定页面写 `text-spacing-trim` 的哪个值（Firefox 不支持，只能不挤或接受差）。到有这样的文档时做。
- 检查的词数下限（50）对短的中文页不够，归检查自己定（主线）。

## 2. 行内代码的底与有序列表的序号

### 2.1 事实（改前；1280 宽，同一页接管前与接管后各截一张自己的无头页面）

- **行内代码**：画布在代码的字下面画一块圆角浅底（主题的 `surface_variant`，浅色 #f1f5f9；半径 4 px；比字左右各宽 2 px；从行顶下 1 px 到行底上 1 px）。写在程序之前的页面上没有：样子把画了文字的节点画在自己盒子局部的色块当作“页面上是元素自己的事”略去，而 `<code>` 元素上没有写。`/start/` 顶部的 `app/main.ts`，滚到 700 px 时表格里的 `omui dev`、`omui run`、`omui test`、`omui build` 与 `--headless`；`/ui/` 滚到 700 px 时的两个 `undo`；`/` 的 `index.md`。按底色找像素：接管前的截图里一个也没有。
- **有序列表的序号**：`/start/` 与 `/ui/` 没有有序列表，`/` 与 `/zh/` 有。画布在每一项左边画 `1.`、`2.`……（正文的字体与字号、等宽数字 `tnum`、`text_muted` 色，右对齐到内容左边 6 px）。写在程序之前的页面上**没有序号**——也不是浏览器自己的序号：样子的基础规则是 `list-style:none`，列表项又按布局写成弹性盒（不是 `list-item`），浏览器的序号不出现。
- 同一组截图里还看得到、不属于这一节的（记下，未改，除注明的）：
  - 删除线：基础规则去掉了每个元素的装饰，`<del>` 在页面上没有线，画布有——基础规则补一条 `del, s { line-through }`（已改）；
  - 强调：页面斜体，画布正体（Inter 没有斜体字面，引擎不合成），引擎与主题的事；
  - 表格的行线：单元格是文字节点，它画在自己底边的 1 px 线同样被当作文字的局部色块略去；
  - 代码块的“复制”按钮、搜索框的占位字、视图的滚动条；
  - 页面的底：接管前 #f8fafc（样子写的主题底色），接管后画布是 #ffffff（逐点取色，五个路由相同）。

### 2.2 三级次序（D-185）

**① 原始性。** 底与序号都是那一帧的事实：底是文字节点画在某一段字形下面的形状，序号是列表项自己画的一段字形。把它们归到页面上对应的那个元素，用元素自己的方式画出来，并且不改排版：
- 底归它下面那一段字所在的行内元素（`<code>`），用元素自己的背景：横向用内边距加等量的负外边距（不占行宽），纵向用内边距补到那一帧的底的上下边（按字体的上升与下降）；每行一段各自带内边距与圆角（`box-decoration-break: clone`），与画布逐行画一致。
- 序号是列表项生成的框（`li::before`），内容是那一帧画的字，位置与字体由自定义属性给出——生成的内容不是文档的文字，查找、选中、复制、读回都不变。写之前把候选文字（编号加 `.` 或 `)`，等宽数字开或关）用同一字体排一遍，字形与画的逐个相同才写；颜色是自定义属性，深浅两帧的合成（`by_schemes`）照常起作用。

**② 前沿与组合。** 查过的：

| 做法 | 与这里 |
|---|---|
| `::marker` 与 `list-style`（浏览器自己的序号） | 字体、位置、数字形式由浏览器定；列表项写成弹性盒时不显示。不取 |
| CSS 计数器 `counter(list-item)` | 弹性项不累计 `list-item` 计数器，`start` 也要另写。不取（编号由树给出：列表的 `start` 加前面的项数） |
| 注册的自定义属性（`@property`，`inherits: false`）挡住嵌套的项继承序号 | 试过：生成框里的 `var()` 在生成框自己身上求值，不继承就取不到。改用只匹配“自己写了序号”的项的选择器 |
| 行内元素的背景对齐行盒（CSS Inline 3 的 `text-box-edge` 用在行内框上） | 浏览器还没有对行内框的背景实现；所以纵向用内边距按字体的上升与下降补 |

**③ 低线。** 服务端渲染的文档页用浏览器自己的 `<code>` 样式与 `<ol>` 序号，与画布不是一个样子。

### 2.3 设计（已实现，`omui.semantic` 的 `look.cpp`）

- 读显示列表时，每一段字形另记下各字形的编号与第一个字形在节点盒子里的位置（基线上）；文字节点画在盒子局部的纯色形状记为“底”。同一行上相叠的底合成一块（画布把 `index.md` 的底画成两块：第一个字一块、其余一块，各宽出 2 px）。
- 一块底归“第一个字形落在它里面、离它左边最近”的那一段（代码后面的字也从底里开始——底比代码宽出 2 px——但离左边更远）。那一段的部分写：`background-color`、`border-radius`、`padding:上 2px 下 2px`（上下为那一帧的底边到基线的距离减字体的上升或下降，不小于 0）、`margin:0 -2px`、`box-decoration-break:clone`。
- 有序列表的项：节点的角色是列表项、父节点是 `ordered` 的列表、只画了一段字形、候选文字的字形与之逐个相同时，项的声明里写 `--omui-marker:"1."`、位置（`--omui-marker-left`、`--omui-marker-top` = 基线减上升）、字体（`--omui-marker-font`：字重、字号、行高 = 上升加下降、字体列表）、颜色，等宽数字时加 `--omui-marker-numeric:tabular-nums`。
- 样子的基础规则：`li[style*='--omui-marker:']::before` 按这些属性画序号（只有自己写了序号的项，嵌套在里面的项继承属性但不画）；`del, s` 有删除线。文档层接手时去掉 `data-omui-look`，这些规则随之不再作用，画布画序号与底。

## 3. 图片的密度（只量与提议，未实现）

### 3.1 事实（2026-11-27，无头 Chromium 159，设备像素比 2，`/ui/` 的标志，1280 宽）

- 写在程序之前的页面：`<img src="../media/mark.svg">`，浏览器按设备像素把矢量画成 200 × 200。
- 接管之后：阅读程序向页面要这张图的像素（`omui_web_picture`），页面按它的自然大小（100 × 100）画进一块 2D 画布再读出；程序把这 100 × 100 的位图放到 100 × 100 的盒子里，画布按设备像素放大到 200 × 200。
- 软的程度（标志所在的 200 × 200 设备像素里，介于墨与底之间四分之一到四分之三的像素数）：接管前 667，接管后 2,332（3.5 倍）；设备像素比 1 时 302 对 331（相同）。截图并排看，接管后的边缘是放大的模糊。

### 3.2 三级次序与提议

**① 原始性。** 图片的位图是页面替程序解码的；页面知道设备像素比，矢量图可以直接按设备像素画。提议：图片带一个密度（每个布局像素几个位图像素）。页面按 `naturalWidth × devicePixelRatio` 画 SVG（位图图片仍按自然大小：放大位图不增加细节），连同密度交给程序；程序按“位图大小 ÷ 密度”排版、按位图画，像素比变了（缩放、换屏）就重新取一次。离屏与 Agent 截图的像素比由截图请求决定，同一条路径。

**② 前沿与组合。** `<img srcset>`／`image-set()` 的“分辨率描述符”就是这个密度的含义（CSS Images 4 的 `resolution`）；Flutter 的 `ImageInfo.scale` 同样把位图大小与布局大小分开。取它们的模型，不取实现。

**③ 低线。** 浏览器自己的 `<img>`：它在设备像素上栅格化 SVG。

**为什么这一步没有做：** 不在本线的范围内——`Picture` 是 `omui.view` 的公开结构（加一个密度字段是它的接口改动），图片原语的固有大小在 `omui.view` 的 `primitives.cpp`，Markdown 的图片按图片的固有大小排；要改的是 `omui.view`、`omui.ui.markdown`、`omui.host.web` 三处，且 `omui.view` 的接口改动要跑它的全部消费者。改法：`Picture` 加 `float density = 1`；图片原语的固有大小取 `width / density`（`loaded` 事件仍报位图大小，另报布局大小）；页面脚本对 SVG（或 `currentSrc` 以 `.svg` 结尾、`naturalWidth` 来自 `viewBox` 的）按像素比画，监听 `matchMedia('(resolution: …dppx)')` 的变化重新取；验收：设备像素比 2 时上面的软像素数与接管前持平（±10%），设备像素比 1 时位图逐字节不变，`check takeover` 不变。
