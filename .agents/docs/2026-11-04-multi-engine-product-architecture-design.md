## 1. 总项目由独立产品组成

2026-11-05补充：[可组合effect／场／相机](2026-11-05-hanim-composable-operators-reactions-ir-design.md)将hanim的局部基础落到类型化数据／算子与计划，UI／游戏／工具仍是普通消费者；数值、HPC、空间／模拟及renderer／RHI按独立模块提供能力。共享IR契约位于动画／effect库与编译器之下，避免包依赖环和重复实现；场／相机的跨帧反馈由版本化端口及宿主组合连接。

omui、hanim、渲染、模拟、计算和音频在**产品层对等**。产品可消费另一产品的公开能力，代码依赖仍保持有向、可裁剪和可验证；对等地位与单向依赖同时成立。

| 层面 | 产品／库 | 拥有的职责与状态 |
|---|---|---|
| 开放规范 | openmui、openas；其它标准沿既有 OpenLifa 流程维护 | 协议、语义、格式、兼容规则和 CTS，不依赖某个产品实现 |
| 通用基础库 | math、geom、memory、hash、unicode、log、trace、session、pipeline；按实际需求提取 task／spatial 等 | 基础算法、数据、执行与观测机制；各自可独立依赖 |
| 计算／HPC 能力 | 数值／图像／几何／场算子、执行计划与优化、CPU／SIMD／GPU 后端 | 数据视图、执行／资源驻留、批次、同步、数值等级和代价 |
| 渲染引擎 | 共享设备／资源／渲染图，2D／3D／文本／粒子／场等渲染特性，分块与损伤管理 | 图形资源、pass、呈现与读回，不拥有 UI 或玩法状态 |
| 动画引擎 hanim | core、对象、动画库、效果绑定、播放器、资源生命周期 | 对象表示、准备计划、时间映射、批量求值及播放控制 |
| 模拟引擎 | 固定步长、输入日志、状态推进、检查点、回放／烘焙；物理、化学、元胞等模型接入 | 权威模拟状态与求解规则，不由可视帧或编辑器私有状态决定 |
| 音频引擎 | DSP、声音／乐器、音序、总线／效果、设备、离线输出；MIDI 等独立库及适配 | 音频图、采样时钟、声音事件与设备缓冲 |
| AI／Agent（可选） | 通用决策port、规则与有界编排、llmapi模型调用、openas外部Agent委派 | 任务／观察／意图；领域状态、动作授权和实时执行仍归各owner |
| UI 框架引擎 omui | 状态、布局、输入、焦点、语义、无障碍、Agent 动作与 host | UI 的行为事实；经公开适配消费动画、渲染及可选其它引擎 |
| 基于引擎的库 | UI 组件、公共动画、材料／风格包、求解器、算子、内容适配、编解码器 | 可组合的领域能力，不重复实现底层引擎 |
| 工具与作品 | 编辑器、Inspector／profiler、时间线、音频／MIDI 工具、算子工作台、官网、游戏与创意工具 | 工程／内容的创作与操作流程，复用下面的公共产品 |

“每项可独立成为产品／库”落实为清晰公开 API、独立 mcpp 包、版本、依赖、文档、CTS、示例和发布边界；无需先使用 UI 才能使用动画／音频／计算。现有 `openmui.*` 技术导入名在迁移中保留，产品归属由公开契约和依赖确定；新产品的最终品牌／包命名需一致规划，不在目录整理时顺手批量更名。

### 1.1 两条顶层硬约束

进一步抽出的统一准则见[局部能力中心×全局契约组合](2026-11-05-local-global-composable-architecture-design.md)，已纳入根AGENTS.md。hanim以可动画数据／算子为中心，audio以声音／信号／调制为中心；通用基础共享，领域时间／实时性保留，经公开契约与adapter协作。环境场仅是属性／状态触发反应的一个输入；事件、邻域／材料规则及Noita类场景按同一反应模式扩展，不把这些场景写死进内核。

**按需承担复杂度与体积。** 只用动画或只用 UI，都能选择对应的最小完整能力；随后按需增加模块、组件、风格、算子或后端。UI 默认动效消费 hanim 的轻量公开子集，不把像素重组、模拟、音频、MIDI、3D 或全部编辑器一起带入。默认 Agent 能力通过轻量契约／provider 和宿主聚合实现，纯数学库不因此依赖 UI 或网络服务。

**同职责单一权威实现。** 复用已有高质量模块和生态依赖；相同算法、规则或资源管理收敛到一个 owner。产品 façade、兼容薄导出与领域 adapter 复用该实现；生成物有唯一生成源，后端变体共享契约与 CTS。不同领域的状态模型、音频／视觉／模拟时钟实例及必要的硬件专用路径分别保留其语义，不强塞进万能对象。

下面是目标依赖关系，省略共同基础库及可选边；线表示消费者依赖公开能力，不表示产品所有权。

    Sim --> Compute
    H -. 可选算子 .-> Compute

- omui 通过公开 hanim adapter 请求动画、接收呈现结果；hanim 不导入 omui Runtime、UI 控件或 UI 规范。
- 2D 与 3D 作为同一渲染架构的特性，共用资源／纹理池／渲染图及观测；独立场景、相机和空间表示按各自需求设计。
- 模拟状态、UI 语义、HObject、RenderGraph、AudioGraph 和 ComputePlan 保持各自类型，通过稳定引用、版本和适配关联；不强迫它们成为同一种节点。
- 计算库不依赖窗口、UI 或渲染场景。GPU 计算后端可复用共享设备／资源／同步；纯 CPU 计算无需创建 GPU。
- 工具依赖引擎；引擎不依赖工具。编辑器关闭后，同一工程仍能由 CLI／Agent／无界面程序运行、测试、渲染或导出。

## 3. 引擎、模型／算子和优化的分工

### 3.1 动画与模拟

hanim 的纯计划给定输入、资源版本、种子和时间即可采样。骨骼／字形／像素等域选择各自算法；解析轨道、采样素材和有状态模拟分别声明求值性质，不能把所有场景都等同线性插值。

模拟引擎拥有固定 tick、输入顺序、状态版本、检查点与重建机制。物理、化学、元胞规则可以作为独立模型／求解器库使用，也可接入统一模拟运行时：

| 模型／库 | 具体边界 |
|---|---|
| 物理 | 刚体／柔体／碰撞／约束／流体等分模块；单位、求解顺序、稳定条件、误差和状态明确 |
| 化学／材料反应 | 离散材料规则、反应扩散场与更精细科学求解分别声明模型及适用范围；不把视觉反应称为已验证的真实化学 |
| 元胞自动机 | 格点状态、邻域、边界、更新顺序、冲突及随机规则；可独立无界面运行，不必关联一个游戏 |
| 空间／场基础 | chunk／tile、halo、稀疏活动域、区域查询、版本、连通域等可复用能力，不内置游戏材料规则 |

动画可驱动模拟的外力、发射器或参数；模拟提供状态与表现数据；渲染负责成像。视觉 seek、恢复检查点后的重放、物理时间反演与业务 undo 分别定义。有状态模拟通常依靠输入日志和检查点重建，不能承诺任意 t 的 O(1) 解析采样。

Noita 类材料反应／连锁破坏继续作为通用基础设施的压力场景：一个大 field／若干区域视图代表大量单元，避免逐像素构造 HObject、UI 节点或 JSON。完整要求和验收负载见[引擎细案 §5](2026-11-04-omui-engine-framework-architecture-design.md#5-noita-类负载的通用基础)。这不将整个项目做成特定游戏，也不宣称该性能已经达到。

### 3.2 计算／HPC 与计算优化

建议分成可替换的三部分：

1. **算法与算子库**：类型、shape／stride、单位、参数、读写集、确定性等级、数值误差和 CPU 参考；不要求所有业务对象变成 tensor。
2. **计划与优化**：批次、算子融合、布局／驻留、SIMD／设备选择、增量工作集、变体选择和预热缓存。优化遵守显式数值与顺序约束，记录选择及版本。
3. **执行后端**：CPU 线程／SIMD、支持 compute 的 GPU 后端，以及确有需求时的可选专门后端。按批执行，不逐元素调用脚本或虚接口。

图形与计算共享兼容的设备、buffer、队列和同步底座。资源声明 owner、generation、memory domain、layout 和访问方式；支持的组合直接共享，否则产生显式可计量的复制／转换。跨设备、跨后端与跨进程的零拷贝分别验证，不能只因名字都叫 GPU buffer 就互相使用。

离线 HPC 吞吐、交互渲染延迟、固定步长模拟和实时音频具有不同调度预算。运行时优化、编译、资源准备、日志格式化和大规模读回不进入音频回调或不可控的逐帧热路径。近似视觉 kernel 与要求逐位确定的权威求解器分别选择；GPU CPU-submit 时间不冒充设备执行时间。

### 3.3 分块渲染与空间分块

| 分块 | 划分什么 | 自己拥有的策略 |
|---|---|---|
| 模拟 chunk | 世界空间及状态／活动域 | 邻域、halo、休眠／唤醒、提交与边界一致性 |
| 渲染 tile／band | 屏幕、目标或缓存区域 | 可见性、damage、采样 reach、缓存键、裁切与合成 |
| HPC tile／workgroup | 存储／运算和设备工作组 | 内存布局、局部缓存、并行调度与同步 |

它们通过资源／区域视图及坐标映射关联，尺寸可以不同。静止像素不意味着模拟状态静止；模拟休眠也不意味着缓存可忽略相机、字体或风格变化。

分块渲染须保留跨 tile 的滤镜采样、玻璃背景、描边和透明合成；输入采样范围与输出 damage 范围分开。整图参考与多种 tile 尺寸、边界穿越、动态背景、局部失效、字体／DPI／设备重建的输出相比较，不能靠裁掉越界内容得到“无缝”。现有 CPU band 一致性可复用，完整 tiled renderer 仍需独立验收。

## 4. mcpp 构建图与运行时图分开

| mcpp／构建插件负责 | 运行时库／引擎负责 |
|---|---|
| C++ Modules、shader／kernel 多目标编译、变体生成、反射／绑定与资源处理 | 数据、对象／场景、执行计划、设备及资源生命周期 |
| 声明工具／输入／输出、增量构建、缓存、打包与目标能力元数据 | CPU／GPU 批次、同步／fence、内存驻留、降档与错误 |
| 测试／bench 工程、部署构件及构建诊断 | 操作、采样、状态推进、实时预算及运行时诊断 |

GPU／HPC 库和算子各自是独立 mcpp 包。其构建插件随子系统发布；编译 kernel 的工具链／SDK 属于构建依赖，运行时依赖只包含真正需要的执行库和后端。现有 shader/rules 是可复用的工程模式，不据此声称已经交付完整通用 HPC 产品。

运行时包不 import mcpp；工程文件继续只有 mcpp.toml，构建扩展经 build.mcpp 和既有构建插件机制。变体的能力、精度、内存和实现版本进入构件元数据，供运行时计划器选择；构建成功与目标设备上实际能运行分别验证。

## 5. 跨平台、设备与宿主能力

平台、宿主、设备和后端是不同维度。一个运行配置应说明 OS／环境、窗口或离屏 surface、输入／音频／文件能力、图形／计算后端、档位和交付格式；按能力选择，不能只判断“手机”或“Web”。

| 目标组合（架构方向，非全部已验证） | 宿主及呈现 | 能力与验证边界 |
|---|---|---|
| 桌面原生 | OS 服务、SDL3 窗口／输入、选定图形与音频后端 | Linux／macOS／Windows 分别验证设备、窗口、多屏、输入、恢复及实际帧预算 |
| Android／iOS | 移动 host、触摸／IME、生命周期与原生 surface／音频后端 | 暂停恢复、方向／DPI、温度／功耗、权限和资源重建；不能由桌面 SDL 成功推断全部完成 |
| Web | wasm host、WebGPU／WebGL2／CPU 能力路径及浏览器音频适配 | 后端能力／内存／设备丢失／浏览器与输入限制分别声明；兼容路径明确拒绝或替代不支持的 compute |
| TUI／终端 | 独立终端 host／字符单元 renderer，复用状态、语义、动作及适合的布局 | 字符宽度／组合字形、颜色档位、键盘／鼠标、焦点、resize 与增量输出；像素效果按能力替代或拒绝 |
| bilibili Toy 等 Web SDK 平台 | Web 下的宿主／SDK 子后端，复用所选 Web 运行时与渲染路径 | 平台桥接、权限、生命周期、配对、存储、输入、导航和交付预算独立验收，不另造图形 API |
| headless／批处理／CI／服务器 | 无窗口，选择 CPU 或无 surface 的 GPU／音频离线后端 | 动画采样、模拟、HPC、渲染、导出及 Agent 控制均可按需运行 |
| 小设备／低档 | 选择能落地的核心与静态／简化后端 | 标准库、内存、工具链及能力实际验证；不默认完整编辑器、对象资源或全部风格都可用 |

OS 相关服务继续经 mcpplibs.os，图形窗口默认宿主的窗口与输入遵守 SDL3 基线；终端 I/O 由终端 host 经 OS 抽象提供并映射为共同输入／动作，不向上层泄露平台句柄或终端转义序列。第三方 C 库经 mwrap／native 分区。图形、音频和设备插件各有 CTS；抽象不要求不同平台提供相同能力或成本。

**Web 是首批重点目标，约束从架构阶段纳入。** 单列 wasm／资源体积、首帧与交互就绪、运行帧成本、峰值内存、按需交付、输入／IME／触摸／剪贴板、音频启动与调度、设备丢失恢复及 Agent 接入。WebGPU 路径和 WebGL2／CPU 兼容路径有明确能力矩阵，浏览器主线程／worker、后台节流和实际传输各自测量；桌面跑通不替代真实浏览器验证。

**后端先定契约、单平台验证，再逐步扩展。** 每项新增上层能力先选一个参考平台／后端，验证公共模块、资源与生命周期、输入／控制及完整工作流；其余目标先明确契约、能力缺口和 CTS，再按优先级实现。当前已有 native／Web 的回归继续保留，不要求每项新能力等所有平台实现才推进。参考后端验证不证明其它后端已支持，也不能把平台专用类型带进上层 API。新增后端以相同核心 CTS＋专用能力 CTS 验证，上层业务、引擎计划和工程格式应尽量复用。

运行时后端与输出目标分别设计：host 管环境／输入／生命周期，render／compute／audio backend 管设备执行，SDK 子后端管平台桥接，packager 管资源布局、清单及交付封装。同一引擎可以输出不同运行与打包组合；bilibili Toy 是 Web SDK 子目标，不能把 Toy 的包预算、权限或桥接规则写死到通用 Web／引擎层。目标描述声明所需能力与实际选中插件，构建插件生成对应产物和可审计元数据；初期实现参考产物，后续增加平台插件，不另写上层产品。

TUI 是交互呈现后端，CLI 是命令调用入口，两者可以消费同一操作模型。TUI 不把图形帧逐像素当作唯一输入：共享 UI 状态、语义和动作，终端适配负责 cell 布局／字形／颜色、输入映射和损伤输出。尺寸以逻辑约束与目标测量协作，不能把像素直接等同字符列；动画保留共同时间／状态契约，并按终端刷新预算量化。可用语义控件应保持可操作，必须依赖图像／3D／玻璃背景的内容声明所需能力及替代视图。多后端目标是上层业务和公开操作尽量不变，不承诺所有后端逐像素同貌。

## 6. Agent 原生横贯开发与使用

Agent 能力按职责进入系统：

- **纯基础库**：可发现的契约、版本、参数／失败语义、测试／bench 入口和观测点；保持轻量依赖。
- **有状态引擎**：对象／资源寻址、describe／query、公开动作、暂停／单步／seek／重放、参数、profile、诊断和导出等 control provider；只暴露实际支持的操作。
- **宿主／SDK**：默认聚合已选模块的 provider，产生 agent.md／能力目录，提供 local API／CLI／桥接等所需 transport，并绑定可信会话。
- **开发工具**：创建／构建／运行／测试／调试／资源定位等操作可由人与 Agent 使用；mcpp 构建任务也是工具链公开操作。
- **最终应用／游戏／内容工具**：默认保留人／Agent 双用户视角，使用相同状态和动作实现，记录 actor、来源与结果。

开发 preset 对全部已注册能力预授权，常规开发操作不逐次要求确认；开发者和用户显式限制仍有效。发布默认保留 Agent 能力，由构建／发行、项目／开发者、宿主／用户、会话四层配置限制实际开放范围。openas 提供共同的 actor／effect／grant／决定与记录语义，实际请求使用 decide；JSON 自称 dev／person 不能获得开发授权。真人专属语义与明确标记的开发 fixture 分开。

控制接口属于中立产品边界，独立 hanim／音频／计算不能为了 Agent 接入而依赖 UI Runtime。UI 的语义动作是一个专门 provider；Inspector 的 GUI 是 provider 的消费者。每个模块无需各开一个网络服务或在每个函数携带 JSON；宿主聚合接口，高频操作使用 native 批次，有状态变更在 owner thread／明确边界提交。

命令区分 accepted／applied／settled，带对象版本／作用域和结果；权限撤销、失效句柄及并发修改在变更前校验。查询采用范围、分页、聚合与有界订阅，像素／场／音频原始数据按明确请求读回。独立多引擎 provider、资源范围／期限／持久配置和完整关联链仍是实施项；现有 UI Agent 实现不能代替这些验收。

## 7. 风格与场景作为组合库

像素、液态玻璃、墨纸、霓虹等风格包，由下列内容组成：

1. 通用材料／效果、颜色／采样／光照／合成规则，复用唯一 renderer 实现。
2. 适用的公共动画条目和参数规则，经 hanim 编排，不自建时钟。
3. 几何、资源、背景捕获等能力要求，成本、性能档位及 reduced／off／低能力替代。
4. 输入、可读性和呈现约束；形变后的几何与命中、agent 可见边界协调。
5. 内容／UI 适配。组件提供语义、状态、命名部件和真实绘制；配方按类型、形状、用途选择，换风格无需逐个修改组件。

通用风格可用于图形、文字、动画对象、游戏或 UI。UI theme 负责把令牌、状态与部件映射到这些通用库。已有风格位于 UI theme 及 renderer，通用 shader／材料与 UI 映射仍需按职责继续提取，不复制两套效果。

像素风格的栅格化／量化，与元胞／材料反应的状态模拟分别提供。玻璃可要求背景采样；材质过渡作用于同一当前几何。无满足条件的部件／资源时返回能力结果或声明的降档，不假定任意匿名绘制都能自动得到完整高质量风格。

## 8. 工具／编辑器基于 omui 实现双视角

**建议工具与编辑器统一使用 omui 构建人类界面，同时提供读取同一状态、调用同一操作的 CLI／Agent API。** 每个工具也是框架及各引擎的真实消费者。

完整编辑器、编曲等核心创作工具安排在相应引擎能力之后，逐步作为能力验证产品实现；前期保留开发和验收所需的最小 inspector／控制／测试工具。工具必须通过公共引擎接口完成真实工作，并反向检验接口、性能、观测、跨后端及 Agent 操作；发现缺口修复到所属公共模块，避免在编辑器内补一套私有动画、渲染或求解器。需要跨后端运行的工具采用相同项目／操作模型，图形 Web、原生和 TUI 呈现分别声明适用范围。

核心工具建议收敛为 Inspector／性能工作台、UI／交互／风格设计器、动画／时间线编辑器、音频／MIDI 编曲、模拟／材料实验室、Shader／算子工作台六类，共用工作台基础；编译／生成／资源与打包能力复用既有工具和 mcpp 插件。各工具的真实任务、人和 Agent 共同操作模型、可审查过程及分期见[双视角工具与场景验收细案](2026-11-04-dual-user-tools-validation-design.md)。

面向完整独立游戏，再补素材资源、场景／关卡、玩法／内容三类工具，详见[游戏生产链补充](2026-11-04-indie-game-tools-assets-design.md)。**所有工具完整任务均须只用CLI／API完成，GUI可选；无GUI时也能经公共控制接口请求真实离屏渲染与指定区域像素，用于Agent审查。** 捕获按版本、时间、视口／区域、资源与后端记录结果，复用同一renderer／输出能力；最小CLI可按需调用渲染worker，不让纯引擎／库依赖GUI。当前各工具对这一完整要求的支持仍需逐项实现和验证。

| 工具 | 主要消费能力与操作 |
|---|---|
| UI／组件／风格工作台 | omui、hanim、renderer；编辑约束／部件／配方，比较语义与呈现，生成可用工程 |
| 动画／场景／时间线编辑器 | HObject、公共动画库、播放器、2D／3D renderer；寻址、打断、资源、离线导出 |
| 模拟／物理／反应／元胞编辑器 | 模型库、模拟运行时、HPC 和 renderer；画刷／边界／规则、单步、状态查询、检查点和性能 |
| 音频／MIDI／编曲工具 | 音频、MIDI 库、时间线和 omui；事件／轨道／设备路由、试听、录入、自动化和离线输出 |
| Shader／材料／算子工作台 | mcpp 构建插件、计算／render 后端；编译诊断、热更、CPU 对照、设备能力及代价 |
| Inspector／profiler／回放工具 | 各 provider、trace／logs／bench／session；跨请求、引擎、帧和资源定位问题 |

工具的工程／场景／资源数据使用引擎公开的版本化契约，UI 布局／面板状态另行保存。人拖动、Agent 命令、CLI 和测试修改同一模型与事务历史；引擎不把编辑器私有格式作为唯一入口。构建失败保留可用资源，资源重载在明确边界提交，错误可定位和重试。

编辑器可有自己的 UI Runtime；独立引擎、MIDI 解析／路由、求解器和算子不导入这个 Runtime。预览通过公开呈现／surface 契约共享资源，避免编辑器再实现一套 renderer／动画／DSP。

音频使用 sample clock，音乐事件使用 beat／tick 与 tempo map，模拟使用 fixed tick，视觉使用采样／预计呈现时间。明确时间映射、缓冲、延迟和漂移策略；音频回调不等待 UI 或 GPU。MIDI 支持应单列事件／文件、设备与录入／路由层，已有音序器和 MIDI 音高数值不等于 MIDI 设备或文件协议已完成。

## 9. 规范、公共契约和独立交付

openmui 标准当前位于独立 OpenLifa 仓库，经 spec 子模块使用；openas 是独立标准／依赖。标准的 schema／CTS／版本独立维护，不依赖本仓库实现；实现负责适配标准。规范变更继续按 D-78 在标准仓库提交，再更新指针。

引擎 API、资源、计划、算子、风格及项目格式先具有版本化公共契约与 CTS；出现跨实现标准化需求时按相应规范流程推进。多语言 façade 从契约生成，不手写相互漂移的接口。独立引擎 ABI 的形式需与当前“全仓唯一生成 C 头”的规则一并 review，此稿不新增头文件或修改标准身份。

每个可拆产品至少具备：

- 独立包与清晰公开出口、最小依赖和可用示例；无跨成员相对源文件引用。
- 外部干净工程的真实构建／运行和解析后依赖闭包，证明不隐式拉入 UI／网站。
- 自己的 CTS、错误、trace／日志类别、bench 与预算，明确未覆盖平台／能力。
- 资源、句柄、版本、线程／队列、销毁／取消／设备重建契约。
- 默认 Agent 开发／使用入口与可配置策略；CLI／GUI 共享操作。
- 发布／许可证／支持矩阵和依赖版本策略；先在 monorepo 验证独立性，再按需要拆仓。

可裁剪维度覆盖产品／功能／后端／能力档位／资源／工具。代码目录的 base／gfx／content／media／ui 是当前依赖层，并非产品所有权。先保持 D-82 与 lint 一致；若以后改变物理分组，依赖规则、构建和文档同步迁移。

### 9.1 四层裁剪与增量成本门禁

| 层 | 必须落实的机制 | 不能仅凭什么认定达标 |
|---|---|---|
| 包依赖 | 默认小入口＋显式增量包，运行时与构建依赖分开；每个最小产品检查实际解析闭包 | 只有目录拆分、manifest 看起来简洁 |
| 可达代码／注册 | 静态默认插件或选定动态插件；生成选定工厂／能力表，重型实现分包；同一公共实现可被多方使用 | 只依赖 LTO／链接器，而全量注册表仍强引用所有组件、效果或后端 |
| 资源交付 | 字体、模型、声音、shader／kernel 变体和内容按目标／页面／任务请求；共享租约与缓存 | 可执行代码小，但完整字体／素材／所有变体仍随首屏下载 |
| 运行时 | 只初始化选中引擎／设备／provider；显式缓冲与容量，增量加载／卸载、能力及错误可查询 | 未使用的后台线程、设备、扫描、全局 registry 或定时器仍默认运行 |

至少保留以下真实消费者矩阵：纯时间／数值 core；最小可播放动画＋所选 renderer；有默认动效及 Agent 能力的最小 UI；逐项增加风格、音频／MIDI、像素动画、3D、模拟和算子。每次记录新增依赖、release 代码／动态依赖／资源体积、Web 实际压缩传输、初始化／工作集和相关延迟，比较增量前后。包含字体的可用批次单列；不靠删掉默认动画或 Agent 能力缩小“最小 UI”。

公开 umbrella 应服务常用小配置；重型域、后端和工具仍可单独选择。最终 SDK／feature 语法根据 mcpp 真实支持的机制落地并测试，不在讨论稿伪造已可用的配置字段。先测基线再确定数值预算；**包数量本身不是体积，实际交付和初始化成本才是门禁**。

### 9.2 单一实现的归属与去重出口

| 职责 | 权威 owner 与消费者关系 |
|---|---|
| 确定性数学／随机／哈希 | math／hash 一份；动画、DSP、模拟、renderer 直接复用，不抄常量／公式 |
| 日志／trace | 独立 log／trace；引擎用类别与上下文，UI 旧入口可薄导出；不每个产品各建 logger |
| 句柄／槽位／arena | memory 提供共享机制，领域保留 typed handle／owner／版本／生命周期语义 |
| 任务／管线 | 提取可被多方使用的 executor／调度基础；UI、渲染、HPC 的阶段策略和实时音频约束分别适配 |
| 授权／会话／控制 | openas 标准＋中立策略／session／provider 基础；UI Agent 只保留语义动作适配 |
| 动画／材料／风格 | hanim 与共用 renderer／style 库持有算法；组件与 UI theme 保留状态／部件／令牌映射 |
| shader／kernel／绑定 | 公共源或公共 IR／契约、参数及一致性样本；平台产物由构建插件生成，专用后端实现由同一逻辑 owner 管理 |
| 编解码／OS／第三方 | 优先现有独立包、mcpp-index 与 mwrap；调用点不各写一份解析器、设备包装或平台探测 |

这里的“一个模块”是每项职责具有一个权威 owner，不是把所有公共能力合成一个大包。math 保有数值原语、确定性算法和 CPU 参考，计算库复用它们并提供算子契约、计划与执行；不另建第二套向量、随机数或基础数学。UI、渲染和计算可以有不同领域图，但共用确有相同语义的执行机制；日志和 trace 共享关联标识，分别保留事件与时序职责。资源的 CPU 内容缓存、设备副本缓存与临时纹理池属于不同生命周期层，不能为了表面去重抹掉这些边界。

已有具体成果是 hanim.core 的单份算法、math 的确定性实现与独立 log 的 UI 薄导出。后续源码已将 **memory SlotMap 与 ObjectRegistry 的重叠槽位机制收敛**：现有 memory 内的 SlotStorage 统一实现容量、空闲链、代次和耗尽退休；旧 SlotMap 薄包装仍使用 32＋32 位 Handle 和原 bits／C ABI，HObject 对象／部件使用同一机制的 64 位代次配置。ObjectRegistry 保留 owner、命名关系、图验证、版本和不可变快照；删除其自管空闲表、存活计数和代次算法。工厂先准备再消费槽位，部件表在独立副本中修改并交换提交。代次耗尽时旧 SlotMap 也改为安全退休，明确是修复旧回绕行为。

对象身份测试覆盖失败 fresh／recycled create、满额反复换名、全部键替换、输入次序与失败后的下一次分配序列。共享存储用 uint8 跑完 255 代证明退休；旧 Handle 固定 bits／布局有编译期断言。适配增加的中间对象移动经真实 RED 定位后已消除；这是局部机制收敛，不代表全项目任务执行、授权、资源和风格提取均已完成。相应本地证据与限制记录到 hanim 细案。

每项收敛先定位调用者和语义差异，补足共享模块契约，再迁移消费者、验证精度／ABI／性能及资源生命周期，最后移除旧实现或仅保留薄适配。避免为抽象而提前造没有第二个真实消费者的巨型通用层。性能声明仍需正式 bench／预算；局部 CTS 的零分配证明不代替完整引擎或整帧性能验收。

## 11. 建议的实施顺序与 review 出口

1. **公共依赖边界与去重**：在 core／日志／首批对象和共享槽位基础上，继续真实外部消费者与公开生命周期验收；保留原算法／像素／ABI，再补默认 Agent 与观测所需中立契约，按证据收敛其它重复机制。
2. **小配置与统一播放纵切**：建立实际依赖／体积／初始化基线并加入增量门禁；独立非 UI 程序经公开 Engine 接口完成真实形状＋材质／效果、暂停／seek／倒放／打断；omui 使用同一 API，并验证真实输入／呈现一致。
3. **计算与模拟纵切**：独立 field／元胞／材料反应模型＋CPU 参考，按既定场景接 GPU／分块；加入 profile／控制／检查点，不扩成特定游戏内核。
4. **公共库和风格**：至少 40 个可复用条目、按组件类型／形状／用途组合的默认配方、通用风格与至少 20 个真实创意工具；移除官网独有的动画实现依赖。
5. **音频／MIDI 与工具**：可复用事件／设备／时间映射和一个真实双视角编辑工具纵切；其它编辑器按同样方式扩展，不把 UI 当引擎依赖。
6. **交付和完整验收**：干净工程、多语言、目标设备、后端、资源与权限矩阵；本地真实验证先推进，跨平台 CI 异步反馈；保持全部 R0–R6／C2–C6 及 Manim／Noita 范围，不用纵切替代最终标准。

本次 review 应先确认产品矩阵、依赖边界、共享设备／时间／控制契约及迁移顺序，再确定新增产品的最终命名和具体 API。后续代码检查点继续只追加到 openmui-design／PR #1；同时活跃的 subagent 不超过 2。
