# 用不到 GPU 的窗口不建设备（UI10，一页设计）

状态：已实施第一步（2026-11-27），待 review。决策：D-290（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) §7 的 UI10；沿用 D-70（帧只在需要时出）、D-184（CPU 与 GPU 是同一份契约的两条路径）、D-187（帧的低线）、[UI9 的首帧方案](2026-11-27-gpu-window-first-frame-design.md)。旁及：红 154（设备在时驱动的线程醒）、红 156（hello 静止时的内存）、红 158（指针在别处移动唤醒主线程）。

## 1. 事实

量法：`omui-devtools bench apps --screen HDMI-0 --no-build --dry-run --rounds 3`，本机桌面的 X 服务器（RTX 4080，NVIDIA 580.178.04，HDMI-0 2560×1440 120 Hz），能耗偏好 `performance`，2026-11-27 03:20–03:25，1 分钟负载 1.1–3.0。omui 的窗口由程序自己放到屏幕 2（`--position`），指针没有动。内存是首帧 5 s 后进程外的 `pmap -XX`；按部分拆开的是同一份映射按“是什么”归类（`memory_parts`：驱动的文件与设备节点、程序本身、其他库、堆、匿名）。同一个 hello 程序的几种跑法互相对照，差就是那一部分的份额。

| hello 的跑法 | 私有脏页 MiB | USS MiB | 静止时每秒唤醒 |
|---|---:|---:|---:|
| GPU（UI9：首帧后建设备，接管） | 19.9 | 71.6 | 113.8（驱动的无名线程 99–100，`[vkrt]` 10，`[vkps]` 4） |
| 不建设备（`--cpu`） | 9.2 | 20.3 | 0–4.8（只有主线程，桌面上的事件） |
| 不建设备，无无障碍桥 | 9.0 | 19.0 | 0–6.4 |
| 不建设备，无 Agent 端点 | 9.2 | 20.3 | 0–2.8 |
| 不建设备，两者都无 | 8.9 | 19.0 | 0–7.6 |
| GPU，两者都无 | 19.7 | 70.2 | 114.2 |

- **设备的份额**：私有脏页 10.7 MiB（驱动的文件映射 6.1，匿名多 3.3，堆多 1.2），USS 51.3 MiB（驱动的库 45.3——只有本进程映射它们，读过的页都算私有——匿名 3.3、堆 1.2、程序自己多读的代码页 0.8）；外加三条驱动线程每秒 113.8 次唤醒（红 154）。
- **无障碍桥的份额**：私有脏页 0.2 MiB，USS 1.3 MiB（其中 1.1 是程序里桥的代码页）。**Agent 端点的份额**：量不出（私有脏页 0–0.1，USS 0.0）。
- **字体的份额**：hello 的世界只带 Inter（856 KB），按需整个读进堆（不映射文件）；不建设备时的 2.0 MiB 堆里包括它。
- **其余**：程序自己的代码页 8.5–9.6 MiB（USS 里的私有干净页：17 MB 的程序只有它自己映射），匿名 6.7–6.9 MiB（CPU 那一帧 800×600×4 = 1.9 MB、窗口的帧缓冲 1.9 MB、运行时与树），库 1.8 MiB。
- **并排**：Slint 的 hello 在 RM1 里是 USS 33.8、私有脏页 18.3 MiB（GPU 画）。不建设备的 hello 是 20.3 与 9.2。注意 Slint 的数是 RM1 那一轮的（2026-11-26/27），同一时段的并排重跑要借指针放 Slint 的窗口，留给台账的重跑。
- **追踪会抬高内存**：带 `--trace` 的一轮，每条线程的追踪缓冲（`events_per_thread` 65536 个事件）让 hello 的私有脏页显成 18.2（`--cpu`）与 25.9（GPU）；上面的数都不带追踪。
- **CPU 一帧的代价**（带追踪的一轮，光栅加呈现）：hello 800×600 由 CPU 逐行画的首帧 2.3–3.5 ms（光栅 1.2，呈现 1.1–2.3）；用光栅线程池时首帧 5.1–8.9 ms（池起线程）。行情板 1896×1030 的首帧 10.1 ms（光栅 2.6，呈现 7.5）。呈现是整窗送给 X 服务器：800×600 是 1.9 MB，1896×1030 是 7.8 MB，它与窗口的大小成正比，与这一帧变了多少无关。
- **放掉设备的线索**（未查实）：在 bench apps 自己的 Xvfb 上（没有 NVIDIA 的 X 驱动），GPU 的 hello 首帧后照 UI9 开始建设备，5 s 后进程里却没有驱动的映射，静止时 0 次唤醒，私有脏页 6.2 MiB（同一程序 `--cpu` 6.8）：设备没有留下，驱动的库与线程也不在。是建到一半失败还是建好后认领失败被放掉，这一轮没有分辨。

## 2. 三级次序（D-185）

**① 从本体系出发。** CPU 与 GPU 画同一张显示表（D-184），CPU 是确定的参考；UI9 已经让 `automatic` 窗口的首帧由 CPU 画、设备在静止时接管而不重画。所以“机器有 GPU”不必等于“窗口建设备”：设备是窗口按需取用的资源，取不取由**窗口自己的帧说了算**——CPU 画一帧（光栅加呈现）要多久，是每一帧都量得到的事实。CPU 画得够快的窗口（对话框、表单、计数器、hello）一直由 CPU 画，不加载驱动、不建设备；帧贵的窗口在第一次显得贵时开始建设备，就绪后照 UI9 在静止时接管。**结论：取这一级。**

**② 前沿与组合。** 查过的做法与取什么：

| 做法 | 现状 | 取什么 |
|---|---|---|
| 首帧前建好 GPU 上下文（RM1 并排的 Slint、Flutter、NSH） | 三家在本机上都由驱动画第一帧，进程里映射了驱动；窗口小、内容静止也一样 | 不取：设备的内存与驱动线程由“有 GPU”决定，不由内容决定 |
| 整个程序选一次渲染器（Firefox 的软件 WebRender、Slint 的软件渲染器、Chromium 的软件合成） | 按机器、配置或黑名单选，一个进程一种；不按窗口的帧代价随时换 | 取其中“CPU 画得好时不用 GPU”的判断；换的粒度改成窗口、依据改成量到的帧代价 |
| 光栅按内容挑 CPU 或 GPU（Chromium 的 GPU 光栅化判定） | 设备已经在；挑的是谁来光栅，不是建不建设备 | 不取 |

组合：**UI9 的 CPU 首帧与静止时接管 + 每帧量 CPU 的代价 + 以 D-187 的帧预算为界。**

**③ 业界通行的做法**（有 GPU 就在首帧前建好设备）不取：hello 这样的窗口为它付出的内存与唤醒（第 1 节）换不来任何一帧。

## 3. 设计

### 3.1 什么时候建设备

- `automatic` 窗口照 UI9 由 CPU 画首帧（窗口自带帧缓冲：X11、Windows、offscreen）。CPU 每画完并呈现一帧，宿主量它的耗时（光栅加呈现，`cpu_frame_ms`）。**运动中一帧的预算是显示间隔的一半**：120 Hz 是 4.2 ms，60 Hz 是 8.3 ms。D-187 的低线是一帧整个不超过一个间隔，CPU 的光栅与呈现占一半，另一半留给运行时自己的布局与绘制。
- **大窗口在首帧时就开始建设备。** 一百万像素以上的窗口，每次整窗重画（滚动、改大小、翻页）都要给 X 服务器送 4 MB 以上：本机上送 1896×1030 的 7.8 MB 要 4.4–18.9 ms，单这一项就超过 120 Hz 一帧的预算。所以它在首帧（或长到这么大的那一帧）之后就开始建设备——走 UI9 的路，接管落在第一次静止，不落在第一次滚动的中途。最初按首帧的代价判（大窗口超过半个间隔、小窗口超过一个间隔），列表的首帧不带追踪时落在界线下面（带追踪时 7.1–23.5 ms，追踪本身让它变慢），设备要等到第一次滚动才建，接管就会落在滚动中途；窗口的大小是首帧之前就确定的事实，所以按大小判。
- **单独一帧不作数。** 首帧大半是只做一次的事（字形第一次光栅化、帧缓冲第一次建、与显示服务器的头几次往返），一个样本里机器的负载与窗口的代价分不开：按“小窗口首帧超过一个间隔”判的那一版，本机桌面上 hello 在 95 轮里有 1 轮建了设备（1 分钟负载 4–8，那一轮的原因没有记下），这一条因此去掉。
- **其余的窗口等它运动中的帧**：最近十帧运动中的帧（这一帧之前循环没睡，首帧不算）里有三帧超预算，才开始建设备；建好后照 UI9 在静止时接管，一直在动的在就绪一秒后接管。
- 窗口为什么建了设备，是它最近的记录里一条 `info`（`ui.logs` 读得到；以前是 `debug`，不打开调试日志就读不到），每个窗口一次。
- 静止的窗口、只有小块变化的窗口（悬停、按压、计数器、表单）永远用不到设备：不加载驱动，没有设备的内存，没有驱动线程的唤醒。
- 只有设备画的内容照旧在构造时开始建设备，首帧等它：程序的效果目录，坚持 GPU（`renderer = gpu`）。画在设备上的世界（`meng.ui` 的视口）在没有设备时画成像素；这类程序写 `renderer = "gpu"`（UI9 的风险表已说）。
- `DesktopOptions::device_when`：`needed`（默认，本节）或 `first_frame`（UI9 的：首帧之后就开始建，需要设备早就绪的程序与 UI9 的测试用）。`Desktop::gpu_pending()` 改为“设备正在建、或建好待接管”；追踪里有 `device.needed`（标记）与 `device.begin`（区间）。

### 3.2 CPU 的帧只送变了的行

- 窗口自带的帧缓冲以前每帧整窗换算像素、整窗送给 X 服务器（`SDL_UpdateWindowSurface`）：800×600 是 1.9 MB，1896×1030 是 7.8 MB，与这一帧变了多少无关（第 1 节：行情板首帧的呈现 7.5 ms）。现在只换算并送损伤跟踪给出的那几段行（`SDL_UpdateWindowSurfaceRects`）；首帧、改大小、帧缓冲换了的时候整窗。悬停、按压、计数器这类小变化的代价随之变小，CPU 能画好的窗口更多，用不到设备的也更多。
- X 服务器丢了窗口的内容（没有合成器替它留着）时，SDL 报 `SDL_EVENT_WINDOW_EXPOSED`，宿主把帧缓冲里那一帧整窗再送一次。

### 3.3 放掉设备（这一步不做）

- 一个曾经需要设备的窗口回到静止，可以放掉设备、回到 CPU 的帧缓冲：CPU 那一帧由同一张表重画，与 GPU 的帧在 UI9 钉住的界限内。SDL_GPU 认领时把窗口标成 Vulkan 窗口；放掉之后 X11 的窗口能不能再取帧缓冲（`SDL_GetWindowSurface`）没有试过。
- 这一步不做：放掉要先知道驱动放掉了什么（线程停不停、内存还不还），并且要有“多久不动算不再需要”的依据；否则反复建、放的代价（建 200–260 ms 在设备线程上，接管 75 ms 在主线程上）会比留着更大。重启条件：量到放掉设备后驱动的线程与内存确实回去（第 1 节 Xvfb 上的事实是一个线索），并有真实程序的“动一阵、长时间静止”的使用记录。

## 4. 验收与结果

量法同第 1 节，五轮，2026-11-27 03:4x，1 分钟负载 1.0–5.7。

| 项 | 判据 | 结果 |
|---|---|---|
| hello 不建设备 | 静止时没有驱动的映射、没有驱动的线程；内存进程外量 | 驱动 none；静止时只有主线程醒 0–1.6 次每秒（桌面上的事件）；私有脏页 8.1 MiB（之前 19.9），USS 19.4 MiB（之前 71.6）。同一程序 `--cpu` 是 9.2、20.4：`--cpu` 用光栅线程池，池的线程多占约 1 MiB |
| 要 GPU 的窗口照旧有设备 | 行情板（1896×1030，60 Hz 一直在动）建设备并接管；它的数不变 | 驱动 nvidia；私有脏页 30.9、USS 89.9（之前 31.0、89.9）；启动冷 66.0、热 26.4 ms（之前 69.4、28.5） |
| UI9 的启动数不变 | `automatic` 窗口到第一个呈现帧不晚于 CPU 窗口加一帧（8.3 ms） | hello 冷 73.6 ms（p90 82.1）、热 41.8（p90 51.9）；同一轮 `--cpu` 90.5、45.5；UI9 记录的是 86.3、45.8 |
| 宿主的测试 | `omui.host.sdl3.gpu`：lavapipe 与 RTX 4080 | 各 10 例全过；新的两例：240×160 的窗口静止加一秒小变化（62 帧）不建设备；3840×2160 整窗每帧都变（CPU 光栅 8.9–10.0 ms 一帧）建设备，lavapipe 上是软件设备、放掉，RTX 4080 上接管 |
| 大窗口首帧就建，单独一帧不作数（第二步） | 列表与行情板（1896×1030）不等输入就建设备；hello 照旧不建 | 本机桌面屏幕 2，程序自己放窗口、指针不动，首帧后 3.5 s 看映射，原因从 `ui.logs` 读：列表 5/5、行情板 5/5 映射了驱动，原因是“the window is 1896 x 1030: every full redraw sends 7.8 MB”；hello 40/40 没有驱动（04:18–04:22，1 分钟负载 4.1–6.7）。之前按首帧判的那一版：列表 0/5 不等输入就建，hello 95 轮里 1 轮建了。`omui.host.sdl3.gpu` 两个 GPU 上各 10 例、`omui.host.sdl3` 15 例全过 |

## 5. 风险与欠项

| 项 | 现状与应对 |
|---|---|
| 一帧的代价有起伏 | 大窗口按大小判（首帧之前就确定），其余的要运动中十帧里三帧超过半个间隔，单独一帧的抖动不会让窗口建设备。按首帧判的那一条正因为是单独一帧而去掉（3.1） |
| 小窗口第一次大动作时才建设备 | 设备在自己的线程上建（200–260 ms），CPU 照画；接管在下一次静止，一直在动的在就绪一秒后停一次（约 75 ms，UI9）。量到的窗口里没有落在这一格的：hello 不动，行情板与列表按大小在首帧就建 |
| 一百万像素这条界 | 略小于它的窗口（1280×720 是 0.92 百万像素，整窗 3.7 MB）整窗重画时可能超过半个间隔，靠运动中的三帧才建设备，第一次滚动由 CPU 画完。界线来自本机 X 服务器送 7.8 MB 的 4.4–18.9 ms；别的机器、Windows 的 GDI 没有量过 |
| 画在设备上的内容（世界的视口、画布 `content: auto`） | 没有设备时画成像素；需要设备的程序写 `renderer = "gpu"`，或 `device_when = first_frame` |
| 列表滚动（红 155）没有在桌面上重量 | 列表按大小在首帧后建设备，静止时接管（上表）；`bench apps` 的滚动要借指针转滚轮，滚动时的帧间隔留给借指针的那一轮确认 |
| 放掉设备 | 见 3.3，未做 |
| Windows 与 macOS | Windows 的窗口自带 GDI 帧缓冲，同一套规则；macOS 与 Wayland 没有帧缓冲，照旧等设备（UI9）。都没有在本机验证 |
