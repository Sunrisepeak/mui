# 带样子的投影与引擎的加载策略（UI5）

状态：草案，待 review（2026-11-27）。决策：D-288（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 D-259、D-260、D-284；上游：[文档层](2026-11-26-web-document-layer-design.md)（UI3、UI4）；下游：ST2（每个路由的投影与加载策略）、ST3。

## 1. 事实（2026-11-27）

- 一个页面在程序接管之前显示的是静态投影：同一份映射写出的 HTML（UI1），样子是固定的一段样式——系统字体 16 px、行高 1.6、最宽 760 px。接管之后是画布画的。两个样子不同（顶层方案 §1.4 的“接管前后是两个样子”）。
- 接管之后文档层与静态投影是同一批元素（UI3：按 id 接手），文字透明，画布画看得见的。
- 一篇 10 节的文档（完整播放器，未切分）：页面 53.0 KB（gzip 12.5），启动脚本 gzip 54.5 KB，程序 gzip 2.34 MB，两份字体 1.02 MB。读者要读的内容在前 12.5 KB 里。
- 引擎现在总是立刻加载（`<script defer>`）。

## 2. 三级次序（D-185）

**① 原始性：样子从引擎自己的第一帧量出来。** 构建时页面本来就在无头宿主上求值一次（写静态投影）。那一帧里每个节点的样子是已知的事实：文字的字体、字号、字重、行高、颜色、对齐；它与上一个兄弟的间距、在父节点里的缩进、最大宽度；它自己画的底（纯色、圆角、边线）。把这些量出来写成样式，文字用引擎带的同一份字体文件，浏览器按自己的流排版——不同宽度下不需要引擎也能重排，而换行与引擎的几乎一样（同一份字体、同样的宽度）。不手写第二套样式，也不引入第二个渲染器：样式是第一帧的投影，由像素比对约束。量不成样式的画（矢量图形、图片、渐变、效果）用同一份显示列表按节点导出的 SVG 片段（mrender 的 SVG 输出，顶层方案 §5 已列）。

接管是逐元素的交接：同一个元素，文字从看得见变成透明，画布在同一处画出同样的字。差多少可以按词量（UI3 的探针已经在量词与墨迹的偏差）。

**② 前沿加组合。** 查过的（2026-11-27）：

| 做法 | 现状 | 取舍 |
|---|---|---|
| HTML-in-Canvas（WICG；把 DOM 画进画布） | 只在 Chromium 的 origin trial 里，接口名在 2025–2026 年间改过两轮（`drawElement` → `drawElementImage`／`texElementImage2D`，`layoutsubtree` → `content="drawable"`）；Firefox 与 Safari 没有表态 | 不依赖。它是反方向（DOM 进画布）；我们是画布的内容投影成 DOM，三个引擎今天都能用 |
| 岛屿与可恢复（Astro 的 `client:idle`／`client:visible`、Qwik） | 成熟 | 三档加载策略取这个思路；这里的“岛”是整块画布，“恢复”是把文档层读回成文档（D-284），不带序列化的状态 |
| 事件重放（先记下交互，代码到了再回答） | Qwik、Wiz 在用 | 取：`interaction` 策略下，引发加载的那一次按下记下来，引擎到了由文档层已有的激活通道回答 |
| View Transitions（两个状态之间由浏览器做过渡） | Chromium 与 Safari 有，Firefox 较新 | 第一步不用；样子对齐之后交接本身不需要过渡 |

**③ 低线。** 文档站的常规做法是服务端渲染加水合：前后是同一个渲染器，样子天然一致。画布框架（Flutter Web）接管之前没有内容，查找、选中要靠另外隐藏的文字。我们的低线是“接管之前可读、之后不跳”，目标是偏差按词可量并且有界。

## 3. 设计（D-288）

### 3.1 样子

- `omui.semantic` 在写投影时可以带上样子：每个节点一份量出来的样式（去重成类），连同引擎字体的 `@font-face`。量的来源是那一帧的运行时（文字的样式、行盒、节点的盒子与它自己画的底），不是组件各写一份。
- **三个来源，都是运行时已有的事实**（查过，2026-11-27）：
  - 布局：每个节点的布局样式（`mlibs.layout` 的 `Style`）本来就是 CSS 的弹性盒与网格模型——方向、间距、内外边距、宽高与最大最小、伸缩、对齐、定位。写成 CSS 是一比一的投影，浏览器照同一个模型排，不需要从盒子反推。
  - 文字：显示列表里每个节点的字形命令带着字体、字号与颜色；行高取行盒的高。
  - 节点自己画的底：显示列表里落在节点盒子上的填充、描边与阴影（第 3 步）。
- 宽度相关的不写死：换行交给浏览器。固定大小的（图片）写宽高比。
- 第 2 步定下的写法（2026-11-27）：
  - 画了文字的节点写成块（`display:block`），文字与其中的链接照行内流排；“叠放”容器写成一格的网格，格子就是容器自己的盒子（`grid-template:minmax(0,1fr)/minmax(0,1fr)`），里面的滚动视图才滚得动、不被内容撑高。
  - 一个节点的文字取它大多数字形的字体、字号、颜色；其余的字形段（链接的颜色、行内代码的字体）按它们在文字里的字节范围写在各自的行内元素上。字形命令带着每个字形的字节位置，不靠坐标对。
  - 字距（`letter-spacing`）：那一帧最后一行的宽度，减去同一段文字不带字距排出来的宽度，除以字素数。
  - 量样子的那一帧什么都不略过（`Runtime::set_draws_unseen`）：平时滚动视图只画视口前后各一屏，更远的节点没有字形可读。
  - 页面的基础规则只有一处（Web 包的页面）：盒子按边框算、清掉浏览器自带的边距与底色、字体与颜色继承、`font-optical-sizing:none`（引擎按字体的默认光学字号排，浏览器会按字号自动换）、滚动视图不显示浏览器的滚动条（它占 15 px 宽，引擎的滚动条浮在内容上）。弹性项的最小尺寸保留 CSS 的 `auto`，`mlibs.layout` 算的是同一个（Flexbox §4.5）。
  - 带“复制”按钮的代码块：节点的盒子是包住 `pre` 与按钮的一个元素，按钮按它定位。
  - Markdown 的文字块与代码块的高度不再向上取整到整像素：块高等于它的各行之和，与浏览器里同样几行的块一样高。取整时每段多出不到 1 px，往下累积（10 节的文档到底差约 10 px）。
- Web 包的页面在有样子时不再套那段固定样式。
- 深浅色：两种主题各量一次，深色的那份放进 `prefers-color-scheme: dark`（UI4 的方案决定页面是否跟随）。

### 3.2 加载策略（D-260）

每个页面一个值，三档都支持：

| 档 | 什么时候取程序 | 适合 |
|---|---|---|
| `eager` | 立刻（今天的行为，默认，直到有数据再定文档页的默认值） | 应用 |
| `idle` | 页面载入并空闲之后 | 文档：先读，稍后有交互 |
| `interaction` | 读者第一次操作一个只有程序能回答的元素（按钮、输入框、开关……），或页面自己调用 `omuiLoad.start()` | 只读的文档；可能始终不取 |

- 取程序之前页面是完整可用的文档：自己的滚动、查找、选中、链接、打印。**阅读不算操作**：滚轮、滚动的按键、选中、查找、点链接都不取程序——否则“只读的文档可能始终不取”就不成立。
- `interaction` 下引发加载的那次按下，记下它的节点（投影元素上的 `data-omui-target`）；程序呈现第一帧后由文档层的激活通道回答一次（`omuiLoad.takePress()` 只交出一次）。落在链接上的按下由浏览器自己处理。
- 记下的只是一次可信事件（`isTrusted`）落在哪个节点上，页面脚本合成的事件不记。页面里的脚本本来就能包住监听器，这条通道不比现有的边界更宽；它不经过 Agent 的总线。
- 页面的加载状态多一个阶段 `waiting`（`omui-load` 事件与 `omuiLoad.phase`），等待时不显示加载中的占位。
- 策略是页面的数据：先是 Web 包的一个选项，ST2 里成为路由表的一列。

### 3.3 接管时读者的位置

读者在程序到来之前可能已经往下读了。程序在第一帧显示之前每帧向页面问一次“读者把哪个视图滚到了哪”，页面按已有的滚动通道回答，所以第一帧就画在同一处；第一帧显示的那一刻页面再记一次，文档层接手那个视图时若与程序的不同，以读者的为准并告诉程序。投影的元素被文档层接手时，样子写的行内样式到此为止（文档层按那一帧摆它）。

### 3.4 不变的

- 文档层（UI3）、接手的条件（程序确实呈现了一帧）不变。
- 不做 HTML 模式（D-259）：样子只是第一帧的投影，没有交互与动画；可操作的东西在引擎到了之后才是活的。

## 4. 验收与测量

| 量 | 怎么量 | 界 |
|---|---|---|
| 接管前后词的位移 | 同一页、同一宽度，接管前投影里每个词的盒子与接管后文档层同一个词的盒子之差；1280、768、390 三个宽度；Chromium、Firefox、WebKit | 先量，再钉（目标：中位数在 1 px 内，换行不同的行数为 0） |
| 接管前后变了的像素 | 两张自己窗口的截图逐像素比 | 先量，再钉 |
| `interaction` 下交互之前的传输 | 浏览器的请求记录 | 没有程序与它的字体之外的大文件：只有页面与样子用到的字体子集 |
| 记下的按下 | 页面脚本的用例与浏览器里按一次按钮 | 引擎到了回答一次，不多不少 |

实测（第 1 步，2026-11-27；xlings 的 Chromium 159、Firefox 159、WebKit 27.2，有界面，屏幕 2；10 节的文档加一个计数按钮，策略 `interaction`，本机的服务器）：

| 量 | 结果（三个浏览器相同，除注明的） |
|---|---|
| 交互之前的请求 | 1 个：页面自己，55,711 字节；程序、启动脚本、字体都没有取 |
| 等待时的页面 | 文档显示着（1212 个词、13 个链接），浏览器的查找找得到词，加载占位不显示，阶段是 `waiting` |
| 阅读之后（滚轮、PageDown） | 仍是 1 个请求 |
| 按一下按钮 | 取了启动脚本、程序与两份字体；到程序呈现第一帧 518 ms（Chromium）、542 ms（Firefox）、638 ms（WebKit）；计数是 1（回答了一次），静态投影让开 |

实测（第 2 步，2026-11-27；同样的三个浏览器、有界面、屏幕 2；同一篇文档，构建时在 1280 宽量的样子，`omui build --web --look`）。量的是屏幕上看得见的词：接管前投影里的位置与接管后文档层里同一个词的位置之差（左边缘与行的中线）。

| 浏览器 | 宽度 | 页面顶部：中位数／p95／最大（px） | 先滚到 700 px 再接管 | 换到另一行的词 | 变了的像素 |
|---|---|---|---|---|---|
| Chromium | 1280／768／390 | 0.1／0.5／0.9，0.5／0.8／0.9，0.8／0.8／0.9 | 0.3／0.8／0.9，0.3／0.5／0.9，0.3／0.3／0.9 | 0 | 6.7%–10.7% |
| Firefox | 1280／768／390 | 0.4／0.4／0.8（三个宽度相同） | 0.4／0.4／0.8，0.2／0.4／0.8，0.2／0.2／0.8 | 0 | 3.7%–6.1% |
| WebKit | 1280／768／390 | 0.4／0.8／1.0，0.5／0.8／1.0，0.4／0.8／1.0 | 0.4／0.8／1.0，0.5／0.9／1.0，0.4／0.8／1.0 | 0 | 3.1%–5.0% |

- 768 与 390 宽没有另量样子：浏览器照同一份布局模型自己重排，结果与引擎在那个宽度排的差不到 1 px。
- 变了的像素主要是字的边缘（浏览器与引擎是两个光栅器），其次是第 3 步才有的底：按钮的描边、代码块的底色。
- 据此钉的界：词位移的中位数 ≤ 1 px、最大 ≤ 2 px，换到另一行的词为 0。
- 这一步的探针还量出文档层（UI3）的三处偏差，一并修了：带空行的代码块没有按行摆（空行宽度为 0 被当成没画），行尾跟在链接后面的词掉到下一行，代码行的缩进与首词算成一个词（首词偏 12 px）。
- 样子的代价：页面 64,247 字节（gzip 13,480；不带样子时 53.0 KB、gzip 12.5 KB）；它用的两份字体在程序之前就取，843,896 + 174,896 字节。字体是大头：只带投影用到的字的子集（CF3）之后再量，量过再定带样子是否是文档页的默认。
- 未做的：按钮与代码块的底（第 3 步）；“复制”按钮在投影里写的是它的名字（Copy code），画布上是 Copy；浏览器的滚动条隐藏后，接管前没有可见的滚动条。

| 步 | 内容 |

| 2 | 最小的样子：布局、文字的字体字号颜色行高字距从第一帧量出，同一份字体；接管时读者的位置；量位移与像素差，据此定界（已做，上表） |

## 6. 风险

| 风险 | 应对 |
|---|---|
| 浏览器的换行与引擎的不同（字距、连字、断行规则） | 同一份字体；量换行不同的行数，不为 0 时把行盒写进投影（按参考宽度）作为退路，只在视口与参考宽度一致时生效 |
| 样子用的字体让交互之前的传输变大 | 只带投影用到的字的子集（已有的子集机制）；量过再定是否默认带 |
| 量样子要动每个组件 | 只读运行时已有的事实（文字样式、行盒、盒子、显示列表）；组件不改 |
| `interaction` 下读者以为页面是坏的（按钮按了没反应） | 记下的按下在引擎到了之后回答；加载中有可见的状态 |
