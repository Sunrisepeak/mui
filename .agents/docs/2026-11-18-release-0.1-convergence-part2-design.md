# 0.1 发布的顶层收敛方案（part 2）：分两波，第一波是高品质的 omui

2026-11-18 起草，**第四版，草案，待 review**（D-222–D-232 为提议；第四版按第三轮 review 改：依赖按三层划分（方案 B）作为规范，现在就在内部仓库里照它做；拆仓放到最后，内部仓库里功能、性能、质量达到发布标准之后才拆（§2.3.2）。第三版加：两个仓库之间的依赖关系按清单实测、必须单向、要切的两条边与切法（§2.3.1）。第二版：第二版按第一轮 review 改：第一波先集中在核心框架与运行时；作品里只有官网与动画确定要做，其余延后并可能重新设计；第一波的 omui 将独立成自己的仓库，mui 是内部研发仓库，§2.3）。基线：`fa99971f`（PR #1）。

本文接在[收敛与发布方案](2026-11-15-convergence-first-release-design.md)（下称 part 1）之后，回答一个问题：part 1 做到 N0 之后，剩下的工作怎样收成一次高品质的发布。它做三件事：把发布分成两波（第一波是 omui 框架和它依赖的一切，第二波是游戏引擎）；把[体积、内存、性能与上手方案](2026-11-18-size-memory-performance-install-lead-design.md)（下称优化方案）的 OP1–OP10 全部并进第一波；把 part 1 里没做完的功能与能力按波重新排进一张任务表。part 1 的规则（标注、验证状态、开发策略、记录规则、发布门的写法）全部沿用，本文只改范围的划分、任务的次序与节点。

## 0. 核心点（review 入口）

1. **发布分两波**（D-222）。第一波 **omui 0.1**：openmui 与 openas 规范（已发布）、mlibs、xrender、hanim、omui（组件、语言、SDK、模板、命令行与工具）、它们依赖的引擎内核包。先集中把核心框架与运行时做好；框架之上的作品里，确定要做的只有官网与动画，做法另行讨论；文档墙、风格画廊、例子的公开形态延后，可能重新设计（D-229）。
2. **依赖按三层划分，现在就照它做；达到发布标准之后才拆仓**（D-230–D-232，§2.3）：基础层（mlibs、xrender、hanim）← 框架层（omui）← 引擎层（其余）。mui 是内部研发仓库；在它里面用 lint、按层的拆分演练和按发布物的验证守住这条规范，功能、性能、质量过了发布门再做一次机械的导出。第二波 **xengine 0.1**：游戏层、其余的引擎内核、gongfu、xtools 的总入口、2D 与 3D 世界两个切片的作品。
3. **第一波的目标是品质，不是日期**：每项对外的指标对最强者并排实测，持平是低线（AGENTS §2 第 10 条）；现在实测落后的两项（描边、Lottie 播放）与没有数据的十二项（omui 的框架级指标）都在第一波里补上。
4. **优化方案的 OP1–OP10 全部在第一波**（D-224）：链接期、分级与可选、字体、内存、并排基准、通道与免编译上手、共用运行时、系统字体回退、终端宿主。进 0.1 不等于标“稳定”：每项在发布门上按实测取标注。
5. **第二波的工作不停、不删、不挡第一波**（D-223）：仓库与 CI 仍是一个，全量照跑；第二波成员的红照样记入清单并修，但不计入第一波的发布门。引擎内核里被 omui 与 hanim 依赖的包随第一波发布，标注照它们自己的。
6. **状态按三类写**（D-219）：已做；确定可做、未做（写明等什么）；需要设计或有风险。§2 的清单逐项标了。
7. **第一波八个阶段、三个节点**（§4）：对账 → 体积与分级 → 并排与性能 → 平台与基本功 → 通道与上手 → 终端宿主 → 作品与官网 → 候选与发布。估计 75–95 个检查点。
8. **层与层之间只许向下依赖**（D-231，§2.3.1）：现在 omui 一侧有三条边指向引擎内核（hanim 的软体求解器、`omui` 命令行的 `video`），切掉之后第一波的发布物里没有 `xengine.*` 的包。
9. **需要实机的项如实处理**（D-201）：输入法、系统无障碍桥、睡眠与恢复、输入延迟、Direct3D 12 需要带显示器的机器；有机器就测，没有就标“未验证”，不算通过也不挡发布。
10. **需要 review 时定的**（§8）：拆仓的四件事；官网与动画做什么、怎么做；实机从哪里来。

## 1. 为什么分两波

- **依赖的方向本来就是这样**：mlibs ← xrender、hanim、引擎内核 ← omui ← 游戏层 ← 类型框架与作品（AGENTS §2 第 8 条）。omui 这一层和它下面的可以独立成立；游戏层在它上面。
- **收口的进度不同**：收口清单 55/64 里，mlibs、xrender、hanim 已过；omui 欠并排对照一格与发布物探针；xengine 欠并排对照，它的度量还没有基准的骨架。四个切片里，应用与 Agent 两个切片离发布门近，2D 与 3D 世界还有需要显示器与真机的门（Quay 在 Web 上的帧时间、D-187 的实测）。
- **一次发布承诺的东西越少，越容易做到每一项都好**：part 1 的规则是“调整范围只有一种方式：改标注”；分波是同一个思路用在发布的批次上——目标与门不变，变的是哪一批先兑现。

### 2.3 omui 独立成仓库（D-230）

mui 是内部研发仓库；第一波的 omui 要独立成对外的项目仓库。已有的基础：`omui-devtools split omui` 能把 omui 和它经路径依赖到的一切导出成一个独立的工作区（91 个成员：规范、mlibs、xrender、hanim、被依赖的引擎内核、构建插件；1,942 个文件；omui 之上的东西一个都不带），CI 有一行每次都在这个导出物上构建并跑测试，现在是绿的。所以“能不能拆”是已做；要定的是“怎么拆”：

| 要定的 | 选项 | 建议 |
|---|---|---|
| 拆了之后以哪个仓库为准 | ① 新仓库为准，mui 像用规范那样依赖它（子模块或发布物），第二波在它之上做；② mui 为准，新仓库是每次导出的镜像 | ①。只有一个事实来源；第二波“在 omui 0.1 的发布物之上做”（D-228）正好成立；②会让对外仓库的提交、issue 与 PR 都是二手的 |
| 怎么划分 | 见 §2.3.1：基础层（mlibs、xrender、hanim）← 框架层（omui）← 引擎层（其余） | 三层作为依赖的规范，现在就在内部仓库里执行 |
| 内部代号对外叫什么 | `xrender`、`xengine`、`xtools`、`xdef` 以及 `mlibs` 都是内部代号或内部分组名（D-208：以 `x` 开头的都是代号）；包一旦发布到索引，名字就收不回 | 发布之前逐个定：保留、还是定名。改名的子命令与演练已有（RC3.14），技术上是确定可做；需要的是名字本身 |
| omui 这一侧指向引擎内核的边 | 三条（hanim 的求解器、`omui` 命令行的 `video`） | 切掉，仓库之间只留单向（§2.3.1）；切完后第一波没有 `xengine.*` 的包 |
| 历史 | ① 新仓库从一次干净的导入开始；② 带过滤后的历史 | ①。内部仓库的提交信息、STATUS 与设计记录是内部的；对外仓库带用户文档、CHANGELOG 与它自己的协作规范 |
| 什么时候拆 | ① 现在；② 内部仓库里达到发布标准之后、公开候选之前 | ②（§2.3.2）：拆开之后更新的成本变大；公开的 tag、release、索引里的仓库地址仍然从第一天就指向真正的项目仓库，因为公开的候选是拆完之后才发的 |
| 内部的东西留在哪 | 设计记录、STATUS、评估与领先度台账的原始记录留在 mui；基准与并排对照的代码随被测的项目走（对外的数字要能在对外仓库里重跑，D-193） | 如左 |

#### 2.3.1 依赖关系：实测、方向与要切的边（D-231）

按各包清单里的路径依赖统计（含测试依赖与 feature 下的依赖），项目之间的边：

| 从 → 到 | 条数 | 说明 |
|---|---|---|
| omui → mlibs、xrender、hanim | 103、44、11 | omui 的硬依赖；改动经常同时落在这几处（例如边框的像素对齐一次改了 xrender、hanim、omui 与组件） |
| hanim → xrender、mlibs | 8、51 | |
| xrender → mlibs | 86 | |
| **hanim → 引擎内核** | **1** | hanim 默认的 `engine` 特性用 `xengine.dynamics` 的软体求解器（xpbd、平面与边沿碰撞），不带 `matter` 特性 |
| **omui → 引擎内核** | **2** | `omui` 命令行的 `video` 子命令（73 行）用 `xengine.video` 与它的工具 |
| 引擎内核 → hanim、xrender、mlibs | 4、10、87 | 媒体内核（video、audio.timeline）用 hanim 的核心与时间线 |
| 游戏层 → omui | 4 | 桥 `xengine.ui` 用 `omui.core`、`omui.semantic`、`omui.view`、无头宿主 |
| 游戏层 → xrender、mlibs | 5、29 | |
| gongfu → hanim、xrender、mlibs | 1、4、9 | |
| xtools → omui、hanim、xrender、引擎内核、gongfu | 8、4、2、4、1 | 总入口，组合各家的工具 |

**包一级没有环**（lint `project-dag` 一直守着：xrender ← 模拟内核 ← hanim ← 媒体内核 ← omui ← 游戏层）。但按“omui 仓库”与“引擎仓库”两个仓库来看，现在是**双向**的：引擎仓库的几乎一切都依赖 omui 这一侧，而 omui 这一侧有上表加粗的三条边指向引擎内核。

**仓库之间必须单向：引擎仓库 → omui 仓库，反向一条都不留。** 包一级无环还不够，原因是版本：若 omui 仓库的 hanim 依赖引擎仓库里某个已发布的 `xengine.dynamics`，而引擎仓库的游戏层又依赖已发布的 omui，那么游戏层的一次构建里就同时有“仓库里最新的内核”和“omui 当时编进去的旧内核”两份同名模块，无法链接；每次发布也要两个仓库来回各发一半。单向之后，引擎仓库只需钉住 omui 仓库的一个版本。

**哪些子引擎可以放进引擎仓库。** 判据只有一条：omui 依赖不依赖它。

| 项目 | omui 是否依赖 | 放哪里 |
|---|---|---|
| mlibs、xrender、hanim | 是（103、44、11 条） | omui 仓库。它们若放进引擎仓库，omui 就得反过来依赖引擎仓库，又成双向 |
| 引擎内核（matter、field、particles、cellular、audio、video、dynamics 的引擎部分）、游戏层、gongfu、xtools、游戏作品 | 否（切掉下面两条边之后） | 引擎仓库 |

所以“其他子引擎先放进引擎仓库”对 omui 不依赖的那些成立；xrender 与 hanim 是 omui 的下层，只能和 omui 在一起，或者在它下面单独成库（下一段）。

**两个仓库还是三个仓库。**

| 方案 | 内容 | 好处 | 代价 |
|---|---|---|---|
| A 两个仓库（建议现在用） | omui 仓库 = mlibs、xrender、hanim、omui；引擎仓库 = 其余 | omui 与它的渲染、动画一起改一起测，一次提交；单向 | omui 仓库里不止 omui；xrender、hanim 的独立身份暂时不显 |
| B 三个仓库 | 基础仓库 = mlibs、xrender、hanim ← omui 仓库 ← 引擎仓库 | 分层最干净，omui 仓库只有 omui | omui 与 xrender 之间 44 条边、接口还在变，每次联动都要跨仓库发版与对齐；现在做会明显拖慢 |
| C omui 单独一个仓库，其余全在引擎仓库 | — | omui 仓库最小 | 双向依赖，上面的版本问题无解；不可取 |

**定为 B，作为依赖的规范**（第三轮 review）。B 的代价是跨仓库联动的成本，而这个成本只在真的拆开之后才出现；在内部仓库里按 B 的规则做，一次提交仍然可以同时改三层，没有额外成本。所以现在就按三层约束依赖，物理上的拆分放到最后（§2.3.2）。

| 层（将来的仓库） | 内容 | 可以依赖 |
|---|---|---|
| 基础层 | mlibs、xrender、hanim，下沉的通用求解器；仓库维护工具（lint、devtools 只依赖 mlibs，随这一层） | 只有规范与第三方 |
| 框架层 | omui（核心、组件、语言、SDK、模板、命令行与工具、构建插件） | 基础层 |
| 引擎层 | 引擎内核、游戏层、gongfu、xtools、游戏作品 | 基础层、框架层 |

第一波 = 基础层 + 框架层；第二波 = 引擎层。按这张表，现在违反规则的正是下面三条边。

**要切的三条边，各自的切法：**

1. **hanim → `xengine.dynamics`。** hanim 用到的只是求解器的通用部分：软体环、xpbd 的步进、平面与边沿的碰撞，不涉及材料与世界法则。按“放到它成立的最通用的一级”（D-179），这一部分下沉成一个与领域无关的库，随 omui 仓库走；`xengine.dynamics` 留在引擎仓库，保留刚体、三维刚体、场景、与材料的耦合、Agent 面，并依赖下沉的那个库。是搬家不是复制：求解器仍只有一份，owner 换到更通用的一级。新包的理由是仓库与依赖的隔离（D-99 允许的理由）。它叫什么属于定名的那一批（§8）。
2. **`omui` 命令行 → `xengine.video`。** part 1 已经定了“`video`／`audio` 归各自 owner 的命令”（RC3.3）；这 73 行是没搬完的尾巴。`omui` 命令行不再编入它；引擎的工具包装上之后，经工具内核的贡献清单（D-203）把 `video` 这类命令贡献出来，没有编译期的依赖。
3. **检查。** lint `project-dag` 之外加一条按仓库的规则：归 omui 仓库的包，依赖闭包里不出现归引擎仓库的包（测试依赖也算）。拆分工具的导出物里现在的 91 个成员，切完之后应当不再含任何 `xengine.*`。

切完之后第一波的发布物里没有 `xengine.*` 的包，前面“随第一波走的引擎内核包”这个问题也就不存在了。

#### 2.3.2 先在内部仓库里达到发布标准，再拆（D-232）

拆开之后每一次跨层的改动都要跨仓库发版、对齐、各跑各的 CI，成本比现在高得多。所以次序是：**现在就按三层的规范做，功能、性能、质量在内部仓库里达到发布的要求，最后才拆。** 拆分本身应当是一次机械的导出，不带任何还没做完的工作过去。

**“按规范做”在内部仓库里具体是五件事：**

1. **依赖只许向下，由 lint 检查。** 三层的归属写成数据（lint 的“路径 → 层”表旁边加一张“路径 → 将来的仓库”表）；上层不得出现在下层的依赖闭包里，测试依赖也算。先切掉现有的三条边。
2. **每一层单独能立住，由 CI 检查。** 拆分演练现在只有 omui 一行；改成三行：基础层单独；基础层加框架层；全部。每一行只用它自己和下层的成员构建并跑测试。
3. **按发布之后的样子验证。** 框架层那一行里，基础层不经路径、而是从本次构建产出的本地索引里按版本取（OP6 的“干净机器”行就是这条路）：这才是拆开之后的真实情形，版本、清单、发布物里缺什么都会在这里露出来。
4. **层与层之间的接口是显式的。** 各包已有接口快照（`omui-devtools api`）；节点记录里加一个数：这一段里跨层接口改了多少处。它既是评审的入口，也是“能不能拆”的信号。
5. **内部资料与产品分开放。** 设计记录、STATUS、评估原始记录不进任何一层的导出物；基准与并排对照的代码随被测的项目走。导出物里出现内部资料算 lint 的问题。

**什么时候拆（全部满足）：**

- 第一波的发布门（§5，十三条）在内部仓库里通过，候选是从拆分演练的导出物构建出来的；
- 跨层接口的改动数连续两个节点为零或只有增补；
- 对外的名字都已定（内部代号、下沉的库、仓库与组织）。

满足之后：导出 → 新仓库的第一次提交 → 在新仓库里重跑全部门 → 从新仓库发公开的候选与 `0.1.0`。内部仓库改为钉住新仓库的版本。物理上拆成两个仓库还是三个，到那时按跨层改动的频率定：基础层与框架层之间若仍然频繁联动，可以先同放一个仓库（目录与规则仍是两层），不影响依赖的规范。

拆分之后的日常：框架与运行时的开发在新仓库；mui 继续做第二波与内部研发，钉住新仓库的某个提交或发布物，像现在钉规范一样。

### 2.5 omui 与游戏引擎的关系（待讨论确定）

两个都会是直接面向开发者的独立项目：omui 给做应用的人，引擎给做游戏的人。它们共用基础层（mlibs 含 Agent 内核、xrender、hanim）与规范（openas）。

**现状（按清单实测，与 D-161、D-162 一致）：**

- 引擎的 13 个包里只有一个依赖 omui：桥 `xengine.ui`，用的是 `omui.core`、`omui.semantic`、`omui.view` 与无头宿主，不用组件。模拟、世界、运行时、输入映射、导航、试玩都不依赖 omui，游戏可以无头运行。
- 带窗口的游戏（Kiln、Quay、Swarm 的 window 包）是“omui 的应用壳 + 桥 + 引擎”：窗口、输入、帧节奏来自 omui 的 SDK 与宿主。
- gongfu 不依赖引擎的游戏层，也不依赖 omui：它只用 mlibs、xrender、`hanim.core`，是与引擎并列的类型框架。
- xrender 的三维部分（mesh、scene、particle）与 hanim 的骨骼只被引擎一侧使用，但按“全部渲染归 xrender”留在基础层。

**omui 在引擎里承担三个角色**，依赖方向都是引擎 → omui：

| 角色 | 内容 | 谁依赖 omui |
|---|---|---|
| 游戏内界面 | HUD、菜单、设置：omui 的组件画在游戏画面里，带语义与 Agent 可操作性 | 桥 |
| 窗口与应用壳 | 桌面、Web、Android 上的窗口、输入、生命周期 | 游戏的 window 包（经 SDK 与宿主） |
| 工具与编辑器的界面 | 带界面的工具一律用 omui 自举（D-205） | xtools 与各引擎的工具 |

所以“omui 是引擎的 UI 框架”成立，而且现在它还是引擎的窗口与应用壳。

**引擎自身不止一个框架**，按依赖分四层，规则与全局的三层一样只许向下：

| 引擎内的层 | 内容 | 依赖 omui |
|---|---|---|
| 领域内核 | 动力学、物质与化学、场、粒子、格点、音频、视频：各自可单独使用的库，各有 Agent 面 | 否 |
| 游戏核心 | 世界、运行时、输入映射、导航、试玩：无头的游戏 | 否 |
| 桥与呈现 | `xengine.ui`（唯一认识 omui 的），各内核的呈现包 | 只有桥 |
| 类型框架、工具、作品 | gongfu（并列的框架）、xtools、游戏 | 工具与带窗口的作品 |

**要定的一个架构问题：窗口与输入的宿主放在哪。**

| 方案 | 内容 | 好处 | 代价 |
|---|---|---|---|
| ① 留在 omui（现状） | 带窗口的游戏依赖 omui 的下半部分（核心、语义、视图、宿主），不必带组件与脚本 | 窗口与输入只有一个拥有者；游戏的界面与状态天然进同一棵语义树，Agent 用同一套方式操作应用和游戏 | 任何带窗口的游戏都带着 omui 的下半部分；引擎作为产品不能说“完全不依赖 omui” |
| ② 下沉到基础层 | 窗口、输入、呈现做成与 UI 无关的宿主，omui 与引擎并列地用它；桥是可选的第三方 | 引擎可以完全不带 omui 开窗口；两个产品对等 | 宿主被拆成两半（与 UI 无关的部分、UI 的部分），事件分发、焦点、输入法、无障碍这些本来就属于 UI 的东西要重新划线；现有的分层决定（D-161、D-162）要改 |

建议 ①，并用优化方案的分级（T0–T4）把它的代价压到最小：引擎只依赖 omui 的 T0 与 T1（核心、语义、视图、宿主），组件、脚本、设计器都不带；最小的带窗口游戏的体积进预算。重启 ② 的条件：出现一个不能带 omui 宿主的目标（主机、嵌入式），或 ① 的体积预算实测达不到。

**对开发者的两个入口**：做应用的人用 `omui`；做游戏的人用引擎自己的入口（经工具内核从目录导出命令行，D-203），`run(game)` 这一级不要求他了解 omui，只有做界面时才用到它。

### 2.4 分波的规则（D-223）

1. **拆仓之前一个仓库、一个 CI**：全量照跑；第二波成员的失败记入红灯清单并按根因修，不计入第一波的门。拆仓之后两个仓库各有自己的 CI，mui 钉住新仓库的提交，升级钉住的提交时跑自己的全量。
2. **第一波的发布物不含第二波的包**：`omui-devtools release index` 的闭包以第一波的模板与作品为根；第一波的包不依赖第二波的包（lint `project-dag` 已经保证方向，加一条按波的检查）。
3. **两波各有自己的节点记录与计数器**，STATUS 里分两节；第一波的行排在前面。
4. **第一波冲刺期间，第二波只做三类事**：修它在 CI 上的红；第一波改动共享接口时跟着改；不需要主会话时间的后台验证。不开第二波的新功能。
5. **发布之后**：第一波的补丁版本只修不增；第二波在 omui 0.1 的发布物之上做，同时是对它的第一次外部式使用。

## 7. 风险

| 风险 | 应对 |
|---|---|

## 8. 需要 review 时定的

1. **拆仓的条件**（§2.3.2 的三条）是否合适：发布门在内部通过、跨层接口连续两个节点不再破坏性改动、名字已定。
2. **定名**（拆仓的前提之一，不急）：内部代号的对外名字、下沉的求解器库的名字与分组、新仓库的名字与组织。
4. **omui 与引擎的关系**（§2.5）：omui 是引擎的 UI 框架、窗口与应用壳、工具界面；引擎核心无头且不依赖 omui；窗口与输入的宿主留在 omui（建议）还是下沉到基础层。
3. **官网与动画**：确定要做；“动画”指什么（现有的宣传片、官网上由 hanim 驱动的动画、还是两者）、官网是在现有站点上改还是按 Live Design 重做，需要单独讨论并写一页设计。其余作品与例子延后。
4. **实机**。输入法、无障碍桥、睡眠与恢复、输入延迟、Direct3D 12 需要带显示器的 Windows、macOS、Linux 机器各一台。有的话 W1-D 能把这些格子从“未验证”变成“实机”。
5. **终端宿主的并排对象**。本文写的是 ratatui 与 FTXUI；要不要加一个带脚本的对手（例如基于 Node 的 Ink），与 TS 的终端应用比。
