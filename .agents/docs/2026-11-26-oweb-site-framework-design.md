# oweb：基于 omui 的站点框架（ST1，一页设计）

状态：草案，待 review（2026-11-26）。决策：D-284、D-285（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) §4.4 与 D-259–D-261、D-264、D-265、D-274、D-275；下游：ST8（立项）、ST2–ST7、AG5、RL5。身份、位置、与 omui 的分界见顶层方案 §4.4，本文不重复，只写它留给 ST1 定的五件事。

## 1. 事实（2026-11-26）

- 现在的官网是一个包（`omui.site`）：`app/main.ts` 一页、`omui.config.ts`、`design/` 的历史；构建是 `omui build --web`，产出页面、wasm 与一份静态 HTML 投影。没有路由、没有内容管线。
- 投影已不丢东西（UI1，同日）：树 → HTML 读回后与源文档整篇相等；树 → Markdown 再解析后与源文档相等，仓库 `docs/` 的 34 页全部通过（UI2）。`mlibs.markdown` 的 `from_html`（463 行，不带 md4c）能把这份 HTML 读回文档模型。
- 一篇指南（`ui.md`）的 HTML 投影 15.4 KB，gzip 3.9 KB；引擎首帧前的一半 gzip 约 1.07 MB。
- 页面里已有给 Agent 的入口：`agent.md`、端点的自述、WebMCP、配对（G9）。

## 2. 三级次序（D-185）

**① 从本体系出发。** 一次无头的求值得到每个路由的语义树，四种读者各取一种渲染：人看画布，搜索引擎读 HTML 投影，只会抓取的 Agent 读 `.md`，接入的 Agent 走语义协议。因为投影不丢东西，**页面自己的 HTML 就是它的数据**：引擎到达后把文档层的 HTML 读回成文档，不必再带一份 Markdown 源、一份序列化的状态或一个解析器。路由表是唯一的来源，导航、站点地图、站点自述、搜索索引都由它生成。**结论：取这一级。**

**② 前沿与组合。** 查过的做法与取什么：

| 做法 | 取什么 |
|---|---|
| 岛屿式（静态 HTML 加按需激活的组件） | 每页的加载策略；我们是三档（D-260） |
| 可恢复式（状态序列化在 HTML 里，不重放激活） | “HTML 带着状态，不带第二份”——我们由无损投影直接得到 |
| 服务端组件的数据流 | 不取：HTML 之外另带一份内容，正是要避免的重复 |
| 给 Agent 的 `llms.txt`、每页的 `.md` 孪生、按 `Accept: text/markdown` 协商 | 取 `.md` 孪生与站点级的索引；协商需要服务器，静态托管做不了，只在适配器支持时开 |
| 页内向 Agent 暴露工具（WebMCP） | 已有（G9），站点的操作目录照这条路进去 |

**③ 业界通行的做法**（静态生成加整页激活：HTML 一份、脚本里的内容再一份）不取。

## 3. 设计

### 3.1 目录约定

```
my-site/
  mcpp.toml            包；构建阶段是 oweb 的插件
  omui.config.ts       开放程度、记录、设计器（omui 的，不变）
  oweb.config.ts       站点的配置（§3.2）
  pages/               路由按目录生成：*.md 是文档，*.ts 是用视图写的页面
  layouts/             可选：TS 写的外壳，带槽
  theme/               可选：主题包
  public/              原样拷贝
  design/              可选：设计历史与演出
```

只有一页的站点没有 `pages/`，入口仍是 `app/main.ts`（现在官网的样子），其余相同。

### 3.2 配置与路由表是两种数据（D-285）

- **`oweb.config.ts`**（`defineSite`，xdef 种类 `site`，拥有者 oweb）：预设（`page`、`docs`、`site`）；标题、基地址、语言；路由的取法（没有／按目录／声明）；用哪些模块及各自的选项；文档页默认的加载策略；部署的适配器；预算。
- **路由表**（xdef 种类 `routes`，由构建生成，也可以手写或由脚本生成）：每个路由一条——地址、来源、标题、语言、外壳、加载策略、世界、各级标题与锚点、上一页与下一页。它是导航、`sitemap.xml`、站点自述（`site.describe`）、搜索索引的唯一来源；自定义的导航读的也是它。

### 3.3 页面在交互之前带什么（D-284）

每个路由产出一个目录：

| 文件 | 内容 | 谁读 |
|---|---|---|
| `index.html` | 外壳与正文的 HTML 投影（带样子，UI5），加一段小的加载脚本 | 人（引擎到达之前，以及之后的文档层）、搜索引擎 |
| `index.md` | 同一棵树写成的 Markdown（`markdown_of`） | 只会抓取的 Agent |
| 引擎 | 不在这个目录：按世界共用，按策略加载 | 需要画布时 |

- **不带**：Markdown 源、序列化的文档或状态、Markdown 解析器。引擎到达后由文档层的 HTML 读回文档（`from_html`），往返相等由 UI1 的检查保证；“阅读”世界因此不含 md4c。
- 用视图写的页面（`*.ts`）照旧由脚本构建界面；它的投影同样进 `index.html`，`index.md` 由树写出。
- 预算的依据：文档页在引擎到达之前要取的只有 `index.html` 与样式。`ui.md` 的投影 gzip 3.9 KB，所以“可读之前 100 KB”这个假设值留有余地；实际的数在 UI5 之后量。

### 3.4 模块的契约

一个模块是四样东西的组合，各自可选，用一份清单声明（xdef 种类 `site-module`）：

| 一样 | 例 |
|---|---|
| 构建阶段的贡献 | 搜索：由每个路由的树生成索引 |
| 组件，以及它填外壳的哪个槽 | 导航：侧栏填 `nav` 槽 |
| 操作目录 | 搜索：`docs.search` |
| 数据种类 | 路由：`routes` |

内置的模块：内容、路由、导航（侧栏、面包屑、上一页与下一页）、页内目录、搜索、高亮、国际化、主题、Agent 的门、演出、Pages 适配器。预设只是选好的一组。清单同时说明模块往页面的闭包里加什么，Web 上的世界由它推导（UI6、UI7）。外壳是一份 TS 布局，槽有 `header`、`nav`、`content`、`toc`、`footer`；换掉任何一个槽里的东西就是自定义。

### 3.5 构建的七步

收集（配置与 `pages/` → 路由表）→ 求值（每个路由在无头宿主上装好外壳与内容并静止）→ 投影（HTML、Markdown）→ 索引（搜索、站点地图、站点自述）→ 引擎（按世界与策略打包）→ 清单（每个文件的字节、gzip 后的字节、对预算的结论）→ 适配器（Pages：基地址、`404.html`、`.nojekyll`）。每一步是 oweb 的 mcpp 插件里的一个阶段，可以单独运行与检查。

### 3.6 最小核心文档集（D-274 的清单）

| 页 | 覆盖 |
|---|---|
| `index.md` | 一到三级标题、带全部行内格式的段落、页内锚点与跨页链接 |
| `start.md` | 从安装到第一个窗口（RL3 的那一页）：有序与嵌套的列表、命令行的代码块、一张表 |
| `ui.md` | 三种语言加无语言的代码块、图片、引用、HTML 注释 |
| `agent.md` | 带对齐的表格、任务列表 |
| `reference/ops.md` | 由契约生成的参考（ST3 把生成变成公开能力） |
| `live.md` | 带一个现场示例的页（加载策略 `idle`） |
| `long.md` | 一篇长页（三十屏以上） |
| `zh/index.md`、`zh/start.md` | 中文的两页（国际化的路由、非 ASCII 文字） |

它是 `docs` 模板的样例，也是往返 CTS、搜索的检查、冷启动评测的问题集、并排对照时两边构建的同一批内容。

### 4.1 引擎按路由加载的做法（ST2 第 5 步，2026-11-27 实施）

- **页面自己的 HTML 是数据（D-284）的落地**：引擎到达后向页面要两样——每个写出的节点（id、元素的名字 `aria-label`、地址、只含文字的元素的文字，`omui::shown_document()`）与文档节点的标记（`shown_document(id)`）；外壳的各部分（站点的页面、本页目录、上一页与下一页）和文档都从这里读回。不取路由表，不带序列化的状态，不带 Markdown 源与解析器。
- **一个视图函数，两处用**：`oweb.shell` 的 `page(parts, layout)`；构建器由路由表得到 `Parts`，页面加载的程序由页面读回得到 `Parts`。节点的 id 因此在“写出的页面”与“画出的页面”里相同（都挂在应用的挂载点 `main` 下：`main/page/nav/r0`、`main/page/main/doc/b3`），文档层按 id 一对一接手。检查：最小文档集的每一页从自己的 HTML 读回再写一遍，与原先写出的逐字节相同（带样子与不带样子）。
- **世界是一张等文档的页面**：`omui-gen dist-toy --world` 产出的 `index.html` 有四处位置（字体是第五处，见下）——页头（`<!--omui:head-->`）、文档（`<!--omui:document-->`）、世界的文件所在的目录（`var omuiRoot = "";`）、何时取程序（`var omuiTakes = "eager";`），另有标题与语言。oweb 只替换文字，不依赖生成器的代码；世界的其余文件在站点里只存一份（`engine/`）。这样的页面里 `#` 之后是文档里的位置，不是程序的参数，也不为它重新载入；按语言取的字体看文档自己的语言。
- **阅读程序 `oweb.reader`**：不带脚本引擎与运行时生成的 C++ 应用（SDK 的 `app` 世界），所有路由、所有用默认外壳的站点共用。
- **滚动**：带引擎的页面写成窗口大小的滚动视图（画布不随窗口滚动），与 UI5 量过的形态相同。更好的做法是“应用的根滚动视图就是窗口的滚动”（画布固定、文档层撑开窗口的高度、两者同步），移动端的地址栏收起、返回时恢复位置都随之而来；它要改 Web 宿主的文档层，记为待做，重启条件是 ST4 的模板定稿之前。
- **页面的图片就是程序的图片**：程序画图片时先问宿主（`Runtime::set_picture_reader`），Web 宿主由页面文档里同一个 `src` 的 `<img>` 取浏览器解码好的像素；阅读程序不带解码器，也不再取一次文件。页面等文档里的图片到齐（或失败）再取程序，第一帧就有图。
- **页面的字体就是程序的第一份字体**（红 163）：世界页面的第五处位置 `var omuiFaces = null;`，oweb 填入本页所用字体的站内文件（按站点所显示的字符裁好、文档已经取过的那几份；裁剪保留 ASCII 与省略号，视图在文字之外会画它们）。加载器在站点页面里先用它们，世界自带的整份字体——以及文档没用到的字体——只在某个字符需要时才取（加载器原有的“先用裁剪版、之后换完整版”）。于是程序的第一帧就排在页面所用的字体上，接管前不为字体多取一个字节。
- **给丢失地址的页面**（`404.html`）不取程序：它在任何地址下被送出，只负责可读并带回首页。

### 4.2 自己的导航与外壳（ST2 第 6 步，2026-11-27 实施）

- **外壳是“各部分 → 视图”的一个函数**（`oweb.shell` 的 `View`）：默认的是 `page`；站点自己的可以把页面列表放到侧边、把本页目录放到正文旁、去掉某一部分，用的是默认外壳自己用的那几块（`navigation`、`links`、`document`、`view`）。同一个函数给构建器（`SiteOptions::view`；自己的构建程序是 `oweb::Sites{view}` 接在同样的三个入口后面）和页面加载的程序。
- **读回不依赖摆放**：各部分按自己的名字认（`nav`、`toc`、`turn`、`doc`），不按它在树里的位置；一个部分之下任意深度的链接都是它的。所以任何视图写出的页面都能读回成同样的 `Parts`，D-284 不因自定义而破例。对视图的唯一要求是保留这几个名字，并且对读回的各部分再做一遍得到同一棵树（检查即此）。
- **三级次序**：① 用本体系独有的——页面的 HTML 即数据、一个视图函数两处用——使“自定义导航”不需要第二份数据也不需要模板语言；② 槽位式布局（Astro、VitePress 的 layout 与 slot）是参照，它们的自定义在构建时与运行时是两套（服务端模板与客户端水合组件），这里是一套；③ 不需要退到这一级。
- **验收**：文档模板换成“侧边导航、目录在其下、没有上一页下一页”的视图，七个路由的 `index.md` 逐字节相同，文档的 HTML 除位置外相同，读回的各部分与默认外壳读回的相同，读回后再写与写出的逐字节相同，整站构建通过（`template_test`）。
- **未做**：用 TS 写的外壳（`layouts/*.ts`）与用视图写的页面（`pages/*.ts`）走同一个接缝——视图函数由脚本求值得到——需要带脚本引擎的世界；默认样式表只认默认外壳的摆放，自定义视图的站点用 `look` 或 `engine`。

### 4.3 文档里的现场示例（ST3 第 3 步，2026-11-27 实施）

- **示例是一份视图文档**：Markdown 里语言为 `view` 的代码块就是 `omui.viewdoc` 的文档——组件、信号、表达式、事件设置什么，全是数据。页面把它显示两次：运行着的示例在上，它的源码在下，同属一个块。所以**读者看到的源码就是在运行的东西**，阅读程序不带脚本引擎也能运行它。
- **三级次序**：① 本体系独有的做法——界面可以是数据（视图文档）、一棵语义树多种渲染——使现场示例不需要第二种语言的运行时，也不需要“示例代码”与“演示程序”两份东西；② 参照的是文档站的 live code（Docusaurus 的 live codeblock、Storybook、MDX 的内嵌组件）：它们在浏览器里带一个编译器或打包好的组件，Agent 抓到的 Markdown 里只有源码字符串，无脚本时什么也不显示；这里无脚本时示例以初始状态的静态投影显示，Agent 拿到的是可以检查、可以运行的视图文档；③ 不需要退到这一级。用 TS 写的示例（需要脚本引擎的世界）走同一个槽，按语言再加一个提供者，未做。
- **树里的形状**：块是一个 `figure`，里面是标了 `output` 的一组（示例自己的节点，与任何节点一样可读可操作）和 `code`（源码）。`output` 是规范新增的节点属性（openmui 0.4.14，S-16）：渲染时显示，写回文档源码时略过——块自己说了它。于是 `index.md` 仍只是那个代码块；HTML 里示例带 `data-output`，读回（`from_html`）时整段略过；搜索的小节文字不含示例里的字。
- **谁来运行是槽里的提供者**：`omui.ui.markdown` 的槽 `omui.ui.markdown.live`（按语言，多个）；视图文档的提供者在这个包的 feature `views` 里（`omui.ui.markdown.views`，带上 `omui.viewdoc`）。不开这个 feature 的程序只显示源码，不多带一个字节。只有应用自己的文档（`origin: app`）运行它的块：人输入的、远端来的文本只显示，不运行。
- **构建时就知道示例能不能运行**：文字不是视图文档的，页面在示例的位置写出哪里不对（行、列、建议），站点不构建（“1 example of the site's pages cannot run”）。
- **加载策略**：带现场示例的路由写 `load: "idle"`；按到示例上的按钮而程序还没到，是 `interaction` 策略已有的行为（UI5 第 1 步量过）。
- **验收**：样例的 `/live/`（一个计数器）——无程序的页面里有示例的按钮与初始文字、标了 `output`，源码是那个代码块；`index.md` 与 HTML 读回的文档相同且不含示例的字；从页面自己的 HTML 读回后操作：按两次“Add one”文字变为“Presses: 2”，“Reset”复位；一个写错组件名的示例使构建失败并指出建议（`template_test`）。

### 4.4 长页（ST3 第 4 步，2026-11-27）

- **语料**：仓库里现成的七篇指南（`docs/en/guide`）在测试里接成一页（5,928 词、48 个标题），不拷贝、不另写；指南之间的链接在这一页里只留文字。
- **实测**：带样子的 `index.html` 150,967 字节，gzip 后 23,090（预算 100,000）；HTML 读回与 Markdown 都等于源文档（`template_test`）。带引擎在无头 Chromium 159 里：页面顶部与滚到 700 px 六组全在界内（中位数 0.03–0.05 px）；滚到 15,000 px 处接管，1280 与 390 宽的中位数都是 0.4 px、最大 1.5 px、换行 0——位移不随页面长度累计。
- **红 164**：真实窗口（屏幕 2，RTX 4080，120 Hz）里用滚轮连续滚这一页，约 530 帧里有 19–21 帧占两个以上的间隔（p99 33–42 ms，线是 8.3 ms）；同一轮里短页面为 0，长页面静止时 0–2。测量时机器上有别的构建在跑，数字要在安静的机器上重量；文档层的元素随滚动从 1,169 个增到 2,623 个，是先要看的地方。

### 4.5 页面上的搜索框（ST5 第 2 步，2026-11-27 实施）

- **一份索引、一个查询函数**：索引的读写与查询（`search_json`、`sections_from`、`search`）归 `oweb.shell`，构建器与页面加载的程序用的是同一份代码；`oweb` 的 `docs.search` 与页面上的框因此对同一批词给出同一批小节、同一个次序，不是两份实现对齐出来的。
- **页面说索引在哪**：每个路由的 `<head>` 有 `<link rel="search" type="application/json" href="…site.search.xdef.json">`（相对地址，站点放在子路径下也成立）。程序不知道站点的结构，只问页面“search 这个关系指向哪”，只会抓取的 Agent 读同一行。
- **只在用到时取**：框里第一次有字时才取索引（一次，之后每次输入都在本地答复）；没有引擎的页面没有框（没有程序就没有人答复它），索引与那一行链接仍然在。
- **宿主的两个通用能力**（不是搜索专用）：`omui::shown_link(relation)` 读页面文档里某个关系的地址；`omui::shown_file(address, done)` 经页面取本站的一个文本文件（不同源的地址不取，答复说明原因）。桌面与 Android 上没有页面，前者为空、后者答复不可用。
- **树里的形状**：外壳多一个部件 `search`（一组，名字来自页面：`Search`／`搜索`），里面是文本框 `box` 与结果 `results`；每条结果是一个链接（小节的标题，地址到锚点）加一行说明（所在的标题路径与含有这些词的那一行）。没有结果时说“名字 · 0”——程序自己不带任何一种语言的话，页面说什么都来自页面。
- **晚到的答复不显示**：答复只属于提问时的那批词；框里的词变了，旧答复丢掉。
- **实测**（无头 Chromium 159，`docs` 模板带引擎）：打字之前不取索引；第一次输入取一次 `site.search.xdef.json`，之后的输入不再取；`agent` 八个小节、`live example` 三个、`搜索` 一个、`zzzz` 为“Search · 0”，与 `oweb::search` 同序；按第一条结果到达 `/live/#a-live-example`。框在页面顶部占 56 px；`/`、`/start/`、`/ui/`、`/agent/`、`/live/` 的接管六组仍全在界内。
- **红 165（同一步发现并修复）**：程序接管之后，站点自己的链接（`../ui/`、页内的 `#锚点`、上一页与下一页）在画布上按了没有反应——运行时只放行 http、https、mailto，而页面自己的链接是从页面所在处写的相对地址。修法：没有 scheme 的地址属于被呈现的文档自己的站点，由呈现文档的宿主解析并跟随（`Runtime::set_url_opener(open, relative)`；Web 宿主在本标签页里走浏览器自己的一步，历史与后退照常；桌面窗口没有自己的地址，仍然拒绝；`javascript:`、`file:` 始终拒绝）。正文里的链接是同一个缺陷的另一半：Markdown 组件只把按下的链接作为事件交给应用，外壳没有接；现在外壳把它交给“跟随者”（`Layout::follow`，reader 给的是运行时的 `open_url`）。实测：导航 `../ui/`、目录 `#3-the-everyday-commands`、搜索结果、正文里的 `../ui/` 都在本标签页到达，正文里的外链开新标签页。`check takeover` 从此在接管后按一个通往另一页的链接，浏览器必须到达它的地址。
- **文本框在带样子的页面里的高度**：文本框里没有页面排的字（值与占位文字是画出来的），按样式写出的块只有它的最小高度（36 px），程序画出来是 40 px，框下面的每个词因此在接管时移动 4 px；样子现在按画出的高度写（`min-height`）。

### 4.6 站点是一个包：构建规则与 `docs` 模板（ST4 第 1 步，2026-11-27 实施）

- **站点就是一个 mcpp 包**：`build.mcpp` 只有一行——`oweb::rules::site()`（包 `oweb.rules`，项目自己的构建规则，与 `gongfu.rules` 同形）。`mcpp build`（因此 `omui build`）把站点写进 `target/site`；规则是构建图里的一条边：输入是配置与 `pages/`、`public/`、`theme/`、`layouts/` 下的每个文件，页面改了才重跑，加页或删页时构建程序重跑。命令拒绝的（路由超预算、示例跑不起来）就是构建的失败。
- **规则不链接构建器**：`oweb.rules` 只依赖 `mlibs.build`；站点的包在自己的 `[build-dependencies]` 里把命令声明成工具（`oweb = { …, tools = ["oweb"] }`，只要程序、不要库）。先试过让规则依赖 `oweb`：整个 omui 的闭包都会成为每个站点构建程序的库（并撞上 mcpp 的模块名扫描把 `omui.gen` 源码里字符串中的一行当成模块声明），所以改成这样。父包与子包同时出现，子包的键要加引号（`"oweb.rules"`）。
- **模板**：`modules/projects/oweb/templates/docs` 是 mcpp 的包模板（`template.toml`、`mcpp.toml.in`、`build.mcpp.in`、`README.md.in`），内容就是最小核心文档集本身——样例与模板是同一份文件，不拷贝。`omui new NAME --template oweb:docs`：`omui new` 认 `<包>:<模板>`，原样交给 mcpp；哪个包带哪些模板由包自己说，命令行不登记（经汇总工具链的贡献清单列出，留给 RL）。
- **reference 路由在新工程里也成立**：样例原来写 `reference: "../../oweb.ops.xdef.ts"`（仓库里的相对路径），新工程里没有这个文件。现在路由可以写 `reference: "oweb"`——构建这个站点的命令自己的目录，随构建器带着（`src/catalog/oweb.ops.md` 由构建规则嵌入库中）；产品自己的目录仍然写文件路径。
- **验收**：`omui-devtools check templates --only oweb:docs`——模板按 `mcpp new` 的方式渲染、指向本仓库、作为临时成员构建：8 个路由各有 `index.html` 与 `index.md`，四张表都在；改一页再构建，站点里的那一页跟着变。
- **`oweb.reader` 分成库与薄程序**：`omui doctor` 报它没有身份、没有无头测试（这两条从 ST2 第 5 步起就在，当时没跑 `omui.cli` 的用例）。现在 `view` 与搜索的 `finder` 在模块 `oweb.reader` 里，`tests/reader_test.cpp` 无头驱动：索引只在第一次输入时取一次，途中问的在它到达时答复，取不到或页面没有声明时不再去取。
- **还没有的**：`page` 与 `site` 两个预设要等“页面是视图”的路由（应用作为路由，带自己的世界）；带引擎的站点在新工程里要等预置的世界（UI7、RL）；候选产物里随带 `oweb` 命令、免编译构建（RL）。

## 5. 不做的

- 不做服务器端的任何东西：产物是静态文件。
- 不做 HTML 模式与 webview 前端（D-259）；不带第二份内容。
- 博客、多版本文档、个人主页与项目主页的专门预设：0.1.0 只保证能由模块拼出。
