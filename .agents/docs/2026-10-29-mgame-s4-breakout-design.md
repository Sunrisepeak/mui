# mgame 核心与 S4《组件打砖块：openmui 巡礼》（草案）

状态：草案。接[结构、渲染、Web 与游戏设计](2026-10-28-openmui-structure-render-web-game-design.md)的 R8（§7、§13），和[实施计划](2026-10-26-openmui-implementation-plan.md)的 S4（§“S4 特色小游戏”、§19.3 验收）。

## 1. 要什么

- **mgame 的第一批服务**：世界（实体和组件）、模拟循环、输入、物理、openmui 接入。第一个用户是 S4，第二个是格斗游戏（它已经有自己的核心 gongfu，以后在 mgame.sim / mgame.input 上重新接一遍）。
- **S4**：一个真正好玩的打砖块。每一关的玩法就是一项框架能力（D-50）。同时它是一个确定性的 agent 评测环境：给定种子和输入就能精确回放，agent 通过语义 API 玩它。
- **验收**（实施计划 §19.3）：
  - 120 Hz，输入延迟不超过 1 帧；
  - 给定种子和输入，三个平台的回放哈希相同；
  - 最近 30 秒内可以倒流到任意时刻，倒流后继续游戏的结果和直接回放相同；
  - 三种语言写的道具都能热重载（< 200 ms）；
  - 脚本化的 agent 能通过第 5 关；
  - 每一关都让玩家明白它演示的是哪项能力；作为游戏本身好玩。

## 2. 决定

| 编号 | 决定 | 理由 |
|---|---|---|
| G-1 | **Q-25：`mgame.world` 自写列存储**，不用 EnTT / flecs。组件是纯数据，每种组件一列定长数组，实体是“下标 + 代数”，存在与否用位图；整个世界是一块可平凡拷贝的数据 | 回滚和倒流要求“整块拷贝即存档”。EnTT 的 registry 和 flecs 的 world 内部是堆上的稀疏集和表，拷贝要逐个遍历，也不是逐字节确定的；定长列可以 `memcpy`，校验和就是字节的哈希 |
| G-2 | **玩法物理用 `mgame.physics` 自己的扫掠碰撞**（圆和轴对齐盒），不用 Box2D 的世界。数值用双精度，只用 IEEE 754 精确舍入的加减乘除和平方根，不收缩、不用快速数学、不调用 libm 的超越函数（lint 的 determinism 规则检查），和 hanim 一样三平台逐位相同 | Box2D v3 的世界不能序列化成一块数据，倒流和回滚都做不了。打砖块的球在两次碰撞之间是直线：按事件推进（求下一次碰撞的精确时刻），既确定、又能解析地求任意时刻的位置——这正是实施计划写的“时间倒流靠分段解析解”。没有用定点：圆和角的相交要求平方和开方，Q16.16 在 64 位里会溢出，而上面这几种运算在双精度下本来就是确定的。Box2D v3（mwrap 已在 mcpp-index）留给不需要回滚的游戏（碎片、布娃娃），以后接 |
| G-3 | **模拟和呈现分开**：模拟 120 Hz 定步长，数值规则同 G-2；呈现按显示器刷新率插值 | 和格斗框架同一套思路；120 Hz 让输入延迟在 1 帧（8.3 ms）以内 |
| G-4 | **倒流 = 快照 + 输入记录 + 重新模拟**：每 60 帧（0.5 秒）存一次快照，30 秒 60 个；任意帧 = 最近的快照 + 之后的输入重放。倒流后继续，丢弃那一帧以后的输入，从这里开新的分支 | 快照是整块拷贝（G-1），重放是确定的（G-2、G-3），所以“倒流后继续”和“直接回放”逐字节相同，可以测试 |
| G-5 | **砖块是真实的 openmui 组件**：关卡是一个视图（按钮、开关、滑块、Markdown 卡片……），布局由 openmui 算出；关卡开始时把每块砖的布局矩形读进模拟，之后模拟只认这些矩形 | 布局是确定的（A 级），所以同一关卡在三个平台上得到同样的矩形、同样的模拟；砖块被打的时候组件真的收到动作（按钮被“按下”、开关被“切换”），语义树真的变化 |
| G-6 | **游戏的语义就是 agent 的接口**：场地、挡板、球、每块砖都是语义节点；动作 `move_to(x)`、`launch`、`rewind(frames)`、`step`。第 5 关的 AI 挡板只用这些 | agent 原生（D-61）；评测环境的接口和人看到的一致 |

## 3. mgame 的包

| 包 | 内容 | 依赖 |
|---|---|---|
| `mgame.world` | `World<N, Components...>`：定长列、实体下标 + 代数、位图；按下标顺序遍历；`checksum`；整块拷贝 | 标准库 |
| `mgame.sim` | 定步长循环（累积器、追帧上限、插值比例）；`Timeline<Game>`：快照环、输入环、`seek(frame)`、倒流后继续开分支；模拟时钟和呈现时钟分开 | 标准库 |
| `mgame.input` | 动作映射（键盘、手柄、指针 → 按钮动作和定点轴）；每帧采样成一块纯数据；录制和回放 | 标准库 |
| `mgame.physics` | 圆和盒的扫掠：“这一步里何时第一次碰到、哪一面、法线”（四个面外推半径，四个角是半径的圆弧）；已经重叠又继续向里的立即碰到；只用精确舍入的运算（G-2） | 标准库 |
| `mgame.ui` | openmui 接入：在运行时的时钟上驱动 `mgame.sim`；openmui 的按键和指针事件 → `mgame.input`（UI 没有消耗的才给游戏，D-76）；读一个视图里节点的布局矩形 | openmui、上面四个 |

前四个只依赖标准库（和 gongfu 的核心一样，可以原样拆出）；`mgame.ui` 是唯一认识 openmui 的。

## 4. S4 的玩法

### 4.1 基础

- **场地**：1280 × 720 的逻辑坐标。下面是挡板，上面是关卡视图（砖块），左右和上面是墙，下面掉出去就丢一个球。
- **球**：半径 8，速度按关卡从 6 到 9 像素 / 帧（120 Hz 下 720–1080 像素 / 秒）。打到挡板时按击中点偏转（边缘最多 60°），挡板移动时把一部分速度传给球（“搓球”）。
- **砖块**：每块有耐久（按组件种类：按钮 1，开关 2，滑块 3，卡片 1）。被打时组件收到对应的动作（按钮被按下、开关切换、滑块的值减少），耐久到 0 时溶解（`pixel_effect` 的 dissolve）并喷出粒子，然后露出下面那张 Markdown 卡片：一两句话讲这一关演示的能力。
- **道具**：碎砖有一定几率掉落胶囊（按种子决定）：变长、多球、慢动作（第 4 关的时钟倍率）、穿透。第 6 关的道具由脚本写。
- **分数和连击**：连续不碰挡板打碎的砖越多，分数越高；丢球断连击。

### 4.2 六关

| 关 | 能力 | 这一关怎么玩 |
|---|---|---|
| 1 语义 | 语义树、显式 ID | 按 Tab 打开“语义透视”：每块砖显示 role 和 ID，砖被打时侧栏实时显示语义树的变化（`toggled`、`value`、`removed`）。有几块砖是“隐形”的——画面上看不见，只有语义透视里看得见 |
| 2 风格 | 风格包、着色器效果 | 每打碎一排，整个关卡换一种风格（玻璃 → 霓虹 → CRT → 水墨 → 液态）；物理和语义完全不变——用同一局回放在五种风格下得到同一个哈希来证明 |
| 3 画布 | 无限画布、缩放 | 场地是一块无限画布：球飞出视野时镜头拉远，露出整面 Markdown 墙；有的砖只有放大到某个级别才“实体化”（缩放级别是玩法的一部分） |
| 4 时间 | 动画是时间的纯函数 | 按住 R 倒流（30 秒以内任意时刻），松开就从那里继续；“慢动作”胶囊把模拟时钟的倍率调成 0.5。关卡里有必须倒流才能过的机关：一扇只在某个时刻打开的门 |
| 5 Agent | agent 原生 | AI 控制第二块挡板（`paddle2.move_to(x)`），它的每个动作实时显示在“动作日志”里；可以选合作或对战。脚本化的 agent 必须能过这一关（验收） |
| 6 多语言 | 三种脚本语言、热重载 | 道具由 TS、Python、Lua 写，保存后立即生效；官方的三个道具三种语言各写一个；玩家可以改它们 |

### 4.3 好玩的部分

- 手感：挡板跟手（输入延迟 ≤ 1 帧），击球有打击感（停顿 1–2 帧、屏幕轻震、声音由 `openmui.audio` 合成）。
- 每关 2–3 分钟，有明确的“啊哈”时刻：看不见的砖（1）、风格切换而球不变（2）、拉远后发现整面墙（3）、倒流打开门（4）、和 AI 配合（5）、改一行脚本道具立刻变（6）。
- 试玩反馈作为验收的一部分（§19.3）。

## 5. 模拟（`showcase/widget-breakout` 的核心，只依赖 mgame 的前四个包）

- **状态**：一块纯数据——世界（球、挡板、砖、胶囊、粒子发射器的种子）、分数、连击、关卡帧、随机数状态。
- **一帧**：读输入 → 挡板按输入移动（限速）→ 每个球按事件推进：求这一帧内最早的碰撞（墙、挡板、每块活着的砖），推进到那一刻、反射、记录事件，直到这一帧的时间用完 → 胶囊下落、被接住 → 砖块耐久 → 事件。
- **事件**：砖被打（哪块、剩余耐久）、砖碎、球掉落、胶囊、关卡完成。呈现和 openmui 组件读事件（组件收到动作、溶解、粒子、声音）。
- **哈希**：每帧状态的字节哈希；回放、倒流、三平台对照都用它。

## 6. 实施顺序

1. **mgame 核心**：`mgame.world`、`mgame.sim`（定步长、`Timeline` 的快照和重放）、`mgame.input`、`mgame.physics`（扫掠碰撞），各自的测试（确定性、回滚和倒流逐字节一致、三平台哈希）。
2. **S4 的模拟**：状态、事件推进的球、挡板、砖、胶囊；无界面的测试（回放哈希、倒流后继续和直接回放相同、120 Hz 下挡板延迟 ≤ 1 帧）。
3. **`mgame.ui` 和 S4 的第 1 关**：openmui 视图里的砖块（真实组件）、布局矩形读进模拟、语义透视；无头测试的像素固定。
4. **第 2–4 关**：风格切换、画布拉远、倒流和门。
5. **第 5 关**：AI 挡板、动作日志；脚本化 agent 过关（CI）。
6. **第 6 关**：三种语言的道具和热重载。
7. 声音、打击感、试玩反馈。

每一步一个提交；主观的部分（关卡的玩法和“啊哈”时刻）定稿前请 codex 评价一次。

## 7. 评审记录（2026-10-29，codex，作为参考之一）

**采纳，关卡：**

- **第 1 关**：看不见的砖不能让人觉得不公平。先在安全的位置出现一块，语义透视要能揭示一条路线；发现过的砖保持描边。
- **第 2 关**：本身只是“看”。改为玩家随时可以切风格（击球途中也行），轨迹和瞄准线连续；HUD 实时显示这一帧状态的哈希，切风格时它不变——“物理和语义不变”从测试变成肉眼可见。
- **第 3 关**：缩放由玩家控制（滚轮、按键），有上下限，实体化有提示；缩放级别是模拟状态的一部分（输入改变它），回放和倒流都确定。
- **第 4 关**：同样的发球倒流后还是同样的结果，所以谜题要求倒流后打出不同的球；门的开合周期画在画面上。
- **第 5 关**：AI 有自己的“职责”——场地上方的第二块挡板，负责不让球从上面出去；动作日志旁边同时显示它读到的观察（球的位置、速度，来自语义树），过关条件、超时和动作频率上限写清楚。
- **第 6 关（最弱）**：改成“工坊”。在一次击球前暂停，三种语言写的同一个道具各有一个标出来的参数，改一个、预览轨迹、再去打一个目标排列；有预设、一键撤销、看得见的重新加载状态。

**采纳，模拟：**

- 挡板按相对运动做扫掠（球的位移减去挡板的位移），移动的挡板不会被穿过。
- 同一时刻的多个碰撞按实体下标排定。相邻两块砖接缝处的角，按面处理（不按对角线弹）。每帧最多 8 次碰撞，用完时停在原地，不前进穿过几何体。
- 扫掠只认“朝面里移动”的接触（擦过、离开的不算），避免零时刻反复碰撞。角的根用不抵消的形式 c / (−b′ + √disc)（已改，有测试）。
- 倒流时重新模拟的帧不重放声音和特效：呈现只读当前帧的事件，倒流的画面另有自己的表现。
- 砖块的碰撞几何和风格无关（砖块组件用显式的宽高，风格只改外观）。
- 道具脚本按版本保存（内容哈希）。重新加载是一条记录在输入里的事件，倒流到它之前就用旧版本。
- 验收的补充：
  - 输入延迟按“这一帧开始时采样，这一帧的模拟就用上”来测；
  - 每帧模拟和 `seek` 的最坏耗时进基准和预算；
  - 第 5 关的观察时机、动作上限、种子、胜负和超时写进测试；
  - “任意时刻”指任意一帧（120 Hz）。

**没有照搬：**

- “可平凡拷贝不等于字节规范”：世界的组件按概念要求没有填充，释放的槽清零，分配和遍历顺序确定，哈希只读这些字段。所以这一点已经满足，不需要改成逐字段哈希。
- 双精度的其余顾虑（舍入模式、x87 中间精度、次正规数、FMA）：
  - 在 x86-64（SSE2）、arm64 和 wasm 上，我们从不改舍入模式；
  - 没有 x87，不开快速数学，所以次正规数不会被冲成零；
  - 用 `-ffp-contract=off` 禁止 FMA；
  - 不产生 NaN（零向量归一化返回零）。
  - 这些写进 `mgame.physics` 的 README。
- G-3 写的“定点数”和 G-2 矛盾，这一处是对的，已改成同 G-2 的规则。
