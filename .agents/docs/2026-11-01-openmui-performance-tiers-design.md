# 性能分档与自适应

2026-11-01 定（D-94）。这是[定位](2026-11-01-openmui-positioning-site-design.md)里的前提"处处都快"。它约束[通用动画](2026-11-01-openmui-universal-motion-design.md)的每个对象，也约束官网的加载。已有的规则继续有效：热路径没有虚函数、每帧零分配、插件按阶段按批调用（D-65）、静止时零开销（帧需求，D-69）、性能声明要有 `tests/bench` 的基准和 `budgets.bench.omui.json` 的预算（D-59）。

---

## 1. 设备分档

| 档 | 设备 | 渲染 | 动画与效果的上限 |
|---|---|---|---|
| **T0** | MCU：ESP32，首选 ESP32-S3（带 PSRAM 的屏幕开发板） | 局部重绘的 CPU 光栅化 | 节点层过渡；没有粒子和重效果 |
| **T1** | 嵌入式 Linux（树莓派一级，弱 GPU 或没有） | CPU 参考渲染或 GLES | 节点层、字形层；粒子几百；轻效果 |
| **T2** | Web 和手机 | WebGPU、WebGL2 或 wasm 里的 CPU 渲染 | 加形状层；粒子几千；中等效果 |
| **T3** | 只有核显的电脑 | GPU 或 CPU | 全部，档次居中 |
| **T4** | 有独立显卡的电脑 | GPU | 全部最高档：粒子 2 万以上、液态玻璃、自定义着色器 |

范围完整（D-91）：五档都要做到。T0 在 C1 做工具链 spike（xtensa 的 GCC 能否编译 C++23 模块、mcpp 交叉构建、运行时能否装进内存），C3 有一个能跑的界面；如果 S3 不行，换 ESP32-P4（RISC-V）作为备选（Q-35 已定 ESP32）。

运行档位和规范里的发行版配置档是两件事：配置档（mcu / embedded-linux / mobile / full / engine / headless）决定**编译进来什么**，档位决定**在配置档的上限内用多少**。mcu ↔ T0，embedded-linux ↔ T1，mobile 和 Web ↔ T2，full ↔ T3、T4。

## 2. 编译期裁剪

- 平台和特性用清单选择的模块分区 + `inline constexpr` + `if constexpr`（沿用现有规则，不用宏）。
- T0 的构建不含 GPU、粒子、重效果的代码；包的清单声明它支持的档。
- 每档的二进制大小进预算（T0 的 flash 和 RAM、T2 的 wasm）。

## 3. 代价声明

每个插件（动画、效果、组件、渲染特性、匹配器）声明：

| 项 | 内容 |
|---|---|
| 每帧 CPU、GPU 代价 | 按输入规模的量级（例如每千个粒子多少微秒） |
| 内存 | 缓存、纹理、快照 |
| 支持的档 | T0–T4 |
| 降档序列 | 从高到低的替代，最后一级总是"淡化"或"直接到终态" |

声明进 CTS：每个插件种类的 CTS 用 bench 验证声明的代价不被超出；没有声明的插件不能注册。

**降档序列的例子**（爆炸）：GPU 粒子 2 万，带物理和拖尾 → CPU 碎片 2000 → 碎几块后淡出 → 淡出。物质的粒度一起降（粒子数、点的密度、快照分辨率）。

## 4. 运行时的选择

### 4.1 档位探测

启动时由宿主探测：GPU 后端和能力、CPU 核数、内存、屏幕和刷新率、是否省电模式、系统的"减少动态效果"。得到一个**设备档位**和每类资源的上限。

### 4.2 帧预算调度器

- 每帧按阶段计时（已有），算出余量；余量持续不足时降一档，持续充足时升一档，带滞后，不来回抖。
- 静止时零开销：没有动画就不出帧（已有的帧需求）。
- 一帧里同时进行的动画按优先级（焦点附近、用户刚操作的优先）分配预算。

### 4.3 选择是输入

档位和每次降档都是**明确的输入**，记进会话。同样的输入得到同样的结果：重放、测试、`omui-promo render` 都用记录的档位，逐位相同；不同设备可以选不同的档。

## 5. 三层控制

| 层 | 谁 | 能做什么 |
|---|---|---|
| 自动 | 运行环境 | §4 的探测和调度 |
| 开发者 | 应用 | 策略（每个槽在各档用什么）、上下限、**决定把哪些开关暴露给用户** |
| 用户 | 设置界面（开发者暴露时） | 动效：完整 / 精简 / 减少 / 关闭；效果档位；渲染器 |

系统的"减少动态效果"总是生效。agent 经 openas 能读写暴露出来的设置。官网的设置面板就是这一层的演示。

## 6. 预算

现有的预算（`tests/bench/budgets.bench.omui.json`）继续有效：1000 个节点的界面 CPU 渲染 1080p 每帧 ≤ 16.7 ms（全部动画中也一样）；画布 10 万节点平移每帧 CPU ≤ 1 ms；10 个液态玻璃面板 GPU ≤ 8.3 ms。新增：

| 名字 | 档 | 预算 |
|---|---|---|
| `motion/morph-500` | T3、T4 | 500 对匹配的变换，120 Hz 下每帧 ≤ 8.3 ms |
| `motion/morph-500-cpu` | T1 | 同样的变换，降档后 60 Hz |
| `motion/particles-20k-gpu` | T4 | 2 万粒子带物理和拖尾 ≤ 8.3 ms |
| `motion/particles-2k-cpu` | T1、T2 | 2000 碎片 ≤ 16.7 ms |
| `motion/extract` | 全部 | 物质提取（含快照）在过渡开始的那一帧里完成，不掉帧 |
| `motion/idle` | 全部 | 静止时每秒的 CPU 时间接近零（帧需求） |
| `tier/t0-*` | T0 | 内存、flash、局部重绘的帧时间（C3 之后按板子定） |

每档在 CI 里有对应的配置（T1 用限制核数和关闭 GPU 的 runner 模拟；T2 用浏览器；T3、T4 用有 GPU 的 runner，软件设备只报告不卡）。

## 7. Web 的交付

现状（2026-11-01，`site/delivery.budget.omui.json`）：wasm 压缩后 3.5 MB，字体 3.3 MB（Noto Sans SC 2.7），首帧前 7.0 MB；20 Mbit/s 下首帧 3.1 s。

| 做法 | 内容 |
|---|---|
| 分四批 | 见[定位](2026-11-01-openmui-positioning-site-design.md) §6：极小的加载脚本 + 首屏语义树 JSON + 构建时渲染的首帧图 + HTML → 核心 wasm + 拉丁字体子集 → 中文字体子集 → 各页资源 |
| 字体子集 | 构建时知道每页的文字，按页面用字做子集（预计 200–400 KB）；完整字体只在需要输入时取 |
| 首帧图 | 构建时由 CPU 参考渲染画出；浏览器接管后的第一帧也走 CPU 路径，逐像素相同（不闪），之后再切 GPU |
| 资源按页 | `omuiFetchLater` 已有；扩展成按页取 |
| wasm 变小 | ① 撤掉官网上不达标的作品；② -Oz、wasm-opt；③ 用体积分析找出大头；④ 重型页面（影片播放、游戏）做成单独的 wasm，进入时加载；⑤ 程序本体拆成 side module 和 C++ Modules 配合的风险高，最后再考虑 |
| 预算 | 首屏可见 ≤ 1 s、可交互 ≤ 2.5 s（4G，Q-34 定最终数字）；分批的字节数各自有上限；浏览中帧 p95 和长帧数 |

## 8. 对比基准

性能是前提，不是没有证据的亮点。对照 Flutter、Qt Quick、Slint，Web 端再加 React：

| 项 | 内容 |
|---|---|
| 应用 | 同一个应用用各框架各写一份：设置页 + 1000 项列表 + 一组动画 |
| 指标 | 冷启动、内存、帧时间（静止、滚动、全部动画）、包体积、Web 的首屏 |
| 设备 | T1（树莓派一级）、T3、T4，Web |
| 产出 | `tests/bench/compare/`，结果写进官网的性能报告，每个数字可复现（脚本、版本、设备） |
