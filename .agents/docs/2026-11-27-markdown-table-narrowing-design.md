# Markdown 表格随视图变窄（红 162）；夹着拉丁词的中文行的行高

状态：第 1 节已实现；第 2 节实现了 Markdown 的一段一个行高（2.5 的第 1 条），其余是提议（2026-11-27）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 UI5；相关：[带样子的投影](2026-11-27-styled-projection-loading-design.md) 的“实测（第 4 步的后半）”。

## 1. 表格不再总是按最宽排（红 162）

### 1.1 事实（改前）

- `omui.ui.markdown` 的表格是一个横向滚动视图里的一组行。每个单元格的 basis 是它那一列最宽内容的宽（最大内在宽度加 2×10 的内边距，记作 hi），最小宽度是这一列最长的词（lo），不增长，按 (hi − lo) / hi 收缩。
- 滚动视图的横向是滚动轴，`mlibs.layout` 在滚动轴上从不压缩内容；表格自身是自动宽度，取它的最大内容宽度。所以表格总是 Σhi + 2（边框）宽，lo 与收缩系数从来用不上。
- 文档模板的操作参考（`/reference/ops/`，7 列、单元格里是句子）：表格在引擎里五千多像素宽，一个单元格是一行 3,779 px，读者要横着滚过一行一行的段落。`check takeover` 在这个路由的六组都在界外，离群的是它的单元格（中位数 0.41 px）。
- 写在程序之前的页面（UI5 的样子）按 `mlibs.layout` 的样式写 CSS：收缩在浏览器与引擎里分得不同——浏览器按“系数 × 内容盒的 basis”分（Flexbox §9.7 的 inner flex base size），引擎按“系数 × 边框盒的 basis”分；单元格左右各有 10 px 内边距，两边的列宽会差开。增长两边都只按系数分。

### 1.2 三级次序（D-185）

**① 原始性。** 表格的列宽在构建这棵树时就全知道（每列的 lo 与 hi 是组件量出来的事实），所以表格的宽可以直接写成自己的样式：自然宽 Σhi，最窄 Σlo，最多是滚动视图的 100%。列宽用“从 lo 起、按 (hi − lo) 的比例分剩下的宽”表达——这正好是一组只增长的弹性项，`mlibs.layout` 与浏览器按同一个式子算，写在程序之前的页面与画布逐像素同宽（同一份样式，一个模型）。没有为表格另起一套表格布局，也不需要两遍布局。

**② 前沿与组合。** 查过的（2026-11-27）：

| 做法 | 它怎么排 | 与这里 |
|---|---|---|
| CSS 自动表格布局（CSS Tables 3 §3.9） | 自动宽度的表格：宽 = max(min(GRIDMAX, 容器宽), 表格的最小宽（≥ GRIDMIN）)；列宽在两个相邻的“猜测”之间线性插值——对自动列，就是 min-content 与 max-content 之间同一个比例：列 = lo + t·(hi − lo) | 同一个结果：列宽 lo + F·(hi − lo)/Σ(hi − lo)，F 是行宽减 Σlo |
| GitHub 渲染的 Markdown（`github-markdown-css`） | `table{display:block;width:max-content;max-width:100%;overflow:auto}`，单元格 `padding:6px 13px`：表格是最大内容宽但不超过栏宽，里面的匿名表格按自动布局在这个宽里排（换行），Σmin 超过栏宽时整块横向滚动 | 同一个行为。我们的表格是滚动视图里的一个元素，结构、语义节点不变 |
| Flutter 的 `flutter_markdown`（原生 Markdown 视图） | 默认 `tableColumnWidth: FlexColumnWidth()`：各列平分宽度，与内容无关，窄屏上句子被挤成一字一行；横向滚动只在 `IntrinsicColumnWidth`／`FixedColumnWidth` 下才有，此时又不换行 | 我们两样都要：按内容分宽，并且在 Σlo 之下才滚动 |

**③ 低线。** 业界的低线就是 CSS 自动表格布局（GitHub 即是）。这里与它同一个结果，另外得到的是：画布与写在程序之前的页面同宽（因为只用增长），以及 Agent 读到的语义树不变（表格、行、单元格、对齐，节点与 id 都不变）。

### 1.3 设计（已实现）

- 表格（`Group` 的 `table`）在样式里写：`width = Σhi + 2`、`min_width = Σlo + 2`、`max_width = 100%`（滚动视图的内容宽）。列在第一次要样式时量（`mount` 之后、`compose` 之前），只量一次，样式与行的列宽出自同一份。
- 单元格：`basis = lo`，`grow = hi − lo`（都是整像素，写进 CSS 时不丢精度），收缩保持默认（行宽从不小于 Σlo，用不上）。
- 结果：视图宽 ≥ Σhi + 2 时表格是自然宽、每列 hi（与改前逐像素相同）；Σlo + 2 ≤ 视图宽 < Σhi + 2 时表格与视图同宽、句子换行、不滚动；视图更窄时表格保持 Σlo + 2，横向滚动多出来的部分。
- 写在程序之前的页面不用改 `look.cpp`：它本来就照样式写 `width`、`min-width`、`max-width`、`flex-basis`、`flex-grow`。
- 局限：不齐的行（少于列数的行，只有从 HTML 读入时才可能，md4c 会补齐）把自己的余宽分给自己有的格子，与别的行不对齐；CSS 的表格按网格对齐。归 `omui.ui.markdown`，到有这样的文档时再做（给短行补一个占位的空格子）。

## 2. 夹着拉丁词的中文行：每行的高不一样

### 2.1 事实

- 行高在 `mlibs::text::Paragraph::layout`（`modules/content/text/src/paragraph.cpp` 的“Vertical metrics”）里定：行上的每一段字形按它**实际用到的字体**（回退的字体也算）取上升与下降，各加半个行距（样式的行高减上升加下降，再除以 2）；行的上升、下降各取最大，行高是两者之和。
- 正文是 Inter 15 px、行高 1.45（21.75 px）。各字体加半行距后的上升／下降（由下面量出的四种行高反推）：Inter 16.33／5.42；Noto Sans SC 17.41／4.34；行内代码 JetBrains Mono 13.5 px 14.65／4.93。于是同一段正文的行有四种高：只有 Inter 或只有中文的 21.75，中文夹拉丁词的 22.83（取 Noto 的上升、Inter 的下降），中文夹行内代码的 22.34，只剩行内代码的一行（表格里逗号分开的一串代码的最后一行）19.58。
- 写在程序之前的页面（UI5 的样子）给每个块写一个行高：那一帧的第一行的高；另一种字体或字号的行内片段写 `line-height:0`，不撑高它所在的行。所以浏览器里一个块的每一行一样高，而引擎里不一样，长页面往下累计。
- 用临时探针（`omui.ui.markdown` 的一个用例，量完删掉）在引擎里排仓库的文档，看每个多于一行的文字块里各行是否一样高，以及“各行之和”与“第一行 × 行数”（页面上的高）之差：

| 文档（栏宽） | 多于一行的块 | 各行不一样高的 | 一个块里最大的差 |
|---|---|---|---|
| `docs/zh/**` 17 页（358 px，约 390 宽的窗口） | 1,408 | 414 | 10.83 px（`experimental.md`） |
| `docs/zh/**` 17 页（736 px） | 884 | 286 | 4.33 px |
| 文档模板的 `zh/index.md`、`zh/start.md`（358 px） | 3、5 | 2、3 | 1.08 px |
| 文档模板的英文页（358 与 736 px） | 36、14 | 1、0（`404.md` 里夹着一个中文链接的那段） | 2.17 px |

  `docs/zh/reference.md` 的 80 个里多数是表格：一格是逗号分开的一串行内代码，最后一行只剩代码（19.58，前面的行 21.75）。

### 2.2 最强的做法

| 做法 | 一行有多高 |
|---|---|
| CSS（CSS 2.1 §10.8.1，CSS Inline 3） | 行高不是 `normal` 时：块的“支柱”（块的第一份可用字体，按块的行高与半行距）与每个行内盒（按它自己的第一份可用字体与行高）的并；某个字形从回退字体画出来，不改变它的盒。所以一个样式的块，每行就是行高 |
| Skia 的 SkParagraph（Flutter） | 默认与我们一样，取行上各段实际字体的最大；`StrutStyle` 打开时支柱是每行的下限，`setForceStrutHeight(true)` 时每行就是支柱的高 |
| Core Text／TextKit | `CTLine` 的上升下降取各段实际字体的最大；要统一行高时把段落样式的最小行高与最大行高设成同一个值 |
| DirectWrite | `DWRITE_LINE_SPACING_METHOD_UNIFORM` 给每行同一个行高与基线 |

### 2.3 三级次序（D-185）

**① 原始性。** 画布与写在程序之前的页面是同一棵树的两个渲染，行高的规则应当只有一份：写在段落样式里（`mlibs.text` 是它唯一的归属），引擎照它排，样子照它写，两边由构造一致，而不是事后对齐。另一条路——把每一行的盒写进投影——只在参考宽度下成立，换宽度就失效，不取。

**② 前沿与组合。** Skia 的强制支柱、Core Text 的“最小＝最大行高”、DirectWrite 的 uniform 都能让行一样高，但基线落在哪由各自的规则定；与浏览器排出来一致的只有 CSS 的行盒规则。组合点在“同一份规则、两个渲染器”：引擎取 CSS 的规则，页面本来就是 CSS。

**③ 低线。** CSS 的行盒规则本身（上表第一行）。

### 2.4 测量：会动多少钉住的画面

做法：在 `Paragraph::layout` 里临时加一个只在环境变量下生效的开关（量完已撤回，未提交），同一份二进制按三种行模型各跑一遍；范围是链接 `mlibs.text`、并在用例里钉了 64 位像素哈希的 23 个成员（示例 02／03／04／05／08／09／10／12，`mrender.text`，`omui.view`、`omui.viewdoc`，`omui.ui.base`／`canvas`／`markdown`／`timeline`，`omui.gen`，展示的 fighting、markdown-wall、promo-video、style-gallery、swarm/window、widget-breakout，`site`），共 88 个钉住的哈希。不开开关时 23 个成员全过。

| 行模型 | 文档里各行不一样高的块（`docs/zh/**` 与文档模板，358 px） | 变了的钉 |
|---|---|---|
| 今天：每段按画它的字体 | 1,452 个多于一行的块里 420 个 | — |
| 强制支柱（Skia 的 `forceStrutHeight`）：每行就是段落样式第一份可用字体的高 | 0（按构造） | 25 个（8 个成员：`mrender.text` 1，`omui.view` 2（像素与显示列表），`omui.ui.base` 3，示例 02 1，fighting 5，markdown-wall 1，promo-video 3，widget-breakout 9） |
| CSS 的行盒：支柱加每个样式自己的第一份可用字体，回退的字形不算 | 0 | 同上 25 个 |
| 一段一个行高：一段里所有用到的字体（回退的也算）的最大上升加最大下降，每行都是它 | 0 | 1 个（`mrender.text` 的“mixed scripts and emoji”，320 宽里中文、阿拉伯文、emoji 混排的两行） |

- “一段一个行高”在文档里的结果与 CSS 的规则一样（每块的行一样高，等于页面写的行高），动的钉少得多：今天的行高只在“一段里各行用到的字体不同”时才不一样，钉住的画面里这样的段落很少。它与 CSS 的规则不同在行高的值（一段里有中文就整段取中文与拉丁字体相遇的高，22.83 而不是 21.75）与基线（取各字体加半行距后最大的上升）；页面写的就是引擎那一帧的行高，所以两边的行盒仍一致。
- 两条 CSS 式的规则动的 25 个钉在 8 个成员里；它们为什么动（哪些画面里有回退字体或另一种字号的片段）没有逐个看。

### 2.5 做了的与提议

1. **已做：** `mlibs.text` 的段落样式加 `uniform_lines`（默认关，今天的行为不变）：开着时一段的每一行都是这一段所有字形段（回退的字体也算，各按自己样式的行高与半行距）里最大的上升加最大的下降，与断行无关，同一段在任何宽度下行高相同。`omui.ui.markdown` 的文字块（段落、标题、单元格、原样的 HTML）与代码块打开它。它只在一段里用到不同字体时才与今天不同：依赖 Markdown 组件的 10 个钉了像素的成员（示例 02／04／05／08／09／12、`omui.ui.markdown`、markdown-wall、promo-video、`site`）与 `mrender.text` 实跑全过，其余 12 个成员不经过它、代码路径不变——88 个钉一个不动。新用例：`mlibs.text.harfbuzz` 里中文夹 `openmui` 的一段（开着时每行都是最高那一行的高，换宽度也是），`omui.ui.markdown` 里一段中文与一格最后一行只剩代码的表格（每块的行一样高）。
2. **实测（`check takeover`，文档模板，打开之后）：** `/zh/start/` 390 宽两组的位移回到界内（中位数 1.38／1.28 → 0.37／0.38 px，最大 3.42／3.41 → 1.91／0.93 px），只因比较的词不到 50 个（43、45）仍记为不过；`/zh/` 六组的中位数 0.82／0.39 → 0.30／0.24 px，最大仍是 3.41／2.6 px——是中文串里拉丁词（“Agent”“llms.txt”）横向差 2.6–3.4 px，文档层的欠项，不是行高；`/` 390 滚动后那组（1.16／1.41）与此无关（离群的是图片后的段落），不变。`/start/`、`/ui/`、`/agent/`、`/reference/ops/` 与只改表格时相同。42 组里在界内的仍是 30 组。
3. **提议：** 是否把 CSS 的行盒规则作为全框架的默认——一次有意的改动，25 个钉随之重钉、各写原因；同时 `omui.semantic` 的样子把块的字体写成段落样式的第一个字体（今天写的是“字形最多的那个字体”，中文段落是 Noto Sans SC），页面与画布的支柱才是同一个字体、基线一致。`check takeover` 的词数下限（50）对短的中文页不够用，归检查自己定。
