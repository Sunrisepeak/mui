# 体积、内存、性能与上手：逐项对标最强者的优化方案

2026-11-18 起草，**第一版，草案，待 review**（D-211–D-217 为提议）。基线：`674d90ee`（PR #1）。

本文回答一个问题：omui 做出来的应用，在体积、内存、帧时间、启动和上手这几项上，怎样逐项不输本项最强的框架。它不新增方向，属于收敛方案里“应用”切片的收口（RC3.1、RC3.2 与收口清单第 8 项）。规则沿用 AGENTS §2 第 10 条：每项先找最强者并排实测，持平是低线；没有实测的不算持平；测不了的标“未验证”，不写数字。

## 0. 核心点（review 入口）

1. **现状是实测出来的**：最小的 C++ 应用可执行文件 26.7 MB，分发目录 36.5 MB。这不是框架本身大，而是三件事没做：链接时不去掉没用到的代码、能力没有按用途选择、字体整套打包。
2. **只加一个链接选项就减 31%**：同一批目标文件加 `--gc-sections` 重新链接，26.7 MB → 18.5 MB，程序照常运行（§1.2 的实验）。这是第一步，今天就能做。
3. **体积的主方案是“由应用自己推出它需要什么”**（D-212）：组件、字体字形、语言数据、图像解码器的集合从应用的声明里算出来，不靠开发者手工列 feature；feature 机制只做底下那一层开关。运行时生成界面的应用按 `omui.config.ts` 的开放程度保留完整目录。
4. **每一项都有一个最强者和一条并排基准**（§2）：体积与内存对 Slint，帧时间与列表对 Flutter，Web 首屏对 Flutter Web 与 React，上手对 Flutter 与 Tauri。对手的同一个应用放进 `tests/bench/competitors/apps/`，和我们的在同一台机器、同一个任务里测。
5. **上手的主方案是“TS 应用不需要编译就有第一个窗口”**（D-215）：发布的 `omui` 自带预编译的播放器；`omui new` 加 `omui dev` 不下载编译器。C++ 编译只在 C++ 模板和发布构建时发生。
6. **发布通道缺的只是“发布”这一步**（§5.1）：工具、清单、演练都已就绪，剩下四个对外动作需要维护者确认。
7. **目标先写成上限，由实测收紧**（§2）：最小应用的可执行文件 ≤ 8 MB、分发目录 ≤ 10 MB；数字在并排基准跑出来之后改成“不大于最强者”。

## 1. 事实底稿（2026-11-18 实测，Linux x64，GCC 16.1，`dist` 配置：`-O3 -ffunction-sections -fdata-sections`）

### 1.1 四个应用

| 应用 | 可执行文件 | gzip | 分发目录 | 无窗口 60 帧的内存峰值 |
|---|---|---|---|---|
| `examples/01-hello-im`（C++） | 26.7 MB | 11.5 MB | 36.5 MB | 22 MB |
| `examples/03-counter` | 29.3 MB | 12.7 MB | 39.2 MB | 22 MB |
| `examples/12-notes` | 30.1 MB | 13.1 MB | 39.9 MB | 未取得（程序提前结束） |
| `showcase/markdown-wall` | 30.9 MB | 13.5 MB | 42.5 MB | 26 MB |

- 分发目录另有：五个字体 7.5 MB（NotoSansSC 4.15、TwemojiMozilla 1.47、Inter 0.88、NotoSansArabic 0.84、JetBrainsMono 0.19），X11 的共享库 2.0 MB。
- 带窗口（SDL 的离屏视频驱动）：首帧冷 170 ms、热 60 ms；内存峰值约 160 MB，其中图形驱动占多少没有拆分。

- `--release` 配置在本机失败（mcpp 2026.11.17.2：“previous compiler unit is occupied or unknown”），待报上游；本文的数字来自 `dist`。

### 1.2 体积去了哪里

hello 的链接输入是 1408 个目标文件，全部进了可执行文件，链接行没有 `--gc-sections`，也没有 LTO。

| 做法 | 可执行文件 | gzip | zstd -19 |
|---|---|---|---|
| 现状 | 26,694,368 B | 11.49 MB | 9.03 MB |
| 同一批目标文件加 `-Wl,--gc-sections` | 18,476,224 B | 8.16 MB | 6.54 MB |

加了之后的程序无窗口与带窗口都正常运行（首帧 69.5 ms）。去掉无用代码之后剩下的 18.5 MB，按链接图归到包：

| 包 | 大小 | 为什么在 |
|---|---|---|
| SDL3 | 3.08 MB | 全部子系统（音频、手柄、相机、传感器、各 GPU 后端）都编了进来 |
| `omui.ui.base` | 1.84 MB | 组件经注册表被引用，用不用都留下（去掉无用代码之前是 11.8 MB） |
| AccessKit | 1.72 MB | 系统无障碍桥 |
| `omui.view` | 1.27 MB | |
| `xrender.vector` | 1.17 MB | |
| HarfBuzz、FreeType | 0.99、0.73 MB | 文字 |
| openkal、libstdc++ | 0.83、0.80 MB | 运行时 |
| `openmui.spec`、`omui.agent`、`omui.core`、`mlibs.i18n`、`omui.sdk`、`omui.viewdoc` | 0.54–0.32 MB | |
| 其余约 40 个包 | 约 4 MB | |

另有两处：`.eh_frame` 等展开表约 2.3 MB（核心代码不用异常）；hello 的链接输入里有 `xengine.dynamics`、libwebp（123 个文件）、libjpeg-turbo（121 个文件），一个只显示文字和按钮的应用用不到它们。

### 1.3 框架级的对照现在是空的

领先度台账里 omui 的 12 个指标（冷启动、万行列表、万行内存、输入延迟、热重载、Web 首屏的时间与字节、Agent 任务等）全部是“计划中”。已有的自测（1012 个节点的仪表盘改一个标签 0.77 ms、全部标签 1.98 ms、挂载 4.4 ms）没有对手的数。

## 3. 体积

### 3.1 按三级次序（D-185）

- **① 原始性创新：由应用推出闭包（D-212）。** 本体系里界面是声明出来的：组件有契约，TS 源码是唯一事实来源，视图文档、主题、语言都是数据。别的框架靠开发者手工配置或链接器猜；我们可以在构建时从这些声明算出应用实际用到的组件、字形、语言与解码器，生成只含它们的注册表与数据。这是主方案。
- **② 前沿加组合：** 链接期优化（`--gc-sections`、相同代码折叠、LTO）与字体子集化都是成熟技术，和 ① 组合：① 决定“哪些可达”，② 把不可达的去掉。
- **③ 业界做法：** Flutter 的 tree shaking（图标字体按用到的字形裁）、Slint 的编译期界面、Qt 的模块选择。这是低线：我们至少做到这一级。

### 3.2 OP1：链接期（D-211）

1. 发布类配置（`release`、`dist`）的链接加 `--gc-sections`；Windows 与 macOS 用各自等价的选项（`/OPT:REF,ICF`、`-dead_strip`）。先写在工作区的配置里，同时向 mcpp 提议作为发布配置的默认。
2. 相同代码折叠（LLVM 行用 lld 的 `--icf=safe`）。
3. LTO 作为 `dist` 的选项：先量构建时间与体积，只在收益超过 10% 时默认打开。
4. 不用异常的包不生成展开表（核心代码已经不用异常与 RTTI）：约 2 MB。先核对第三方库与崩溃报告对它的依赖。
5. 浮点规则不变：动画、布局、光栅仍禁用 fast-math 与浮点收缩；LTO 不得改变 CPU 参考的字节（像素哈希的用例就是检查）。

预期：26.7 → 约 15 MB。已实测的部分是第 1 步的 18.5 MB，其余是估计，以实测为准。

### 3.3 OP2：能力按用途选择（D-212、D-213）

**底层：feature。** 按 D-99，在所属包里用 feature 选择，不新建包。

| 能力 | 现在 | 改为 |
|---|---|---|
| SDL3 的子系统 | 全部 | `compat.sdl3` 的 feature：视频与事件必选；音频、手柄、触感、相机、传感器、各 GPU 后端可选；SDK 只开应用声明要用的 |
| 图像解码器（PNG、JPEG、WebP） | 全部 | `mlibs.image` 的 feature；由应用的资源与 `image` 的用法推出 |
| 系统无障碍桥（AccessKit） | 必带 | 默认带（语义树是本体系的身份）；feature `a11y` 可关，面向游戏与嵌入式 |
| Agent 总线、MCP、视图文档、表达式 | 必带 | 默认带；`omui.config.ts` 的开放程度为 `none` 时不链接总线（规范 §14 已允许构建时去掉） |
| `xengine.dynamics` 等经间接依赖进来的 | 带 | 查清是谁引入的，改成用到才依赖 |
| GPU 路径 | 必带 | 默认带；`renderer = "cpu"` 的应用不链接设备后端与着色器 |

**上层：推导，不手写。** `omui build` 的构建插件做三件事：

1. **组件**：注册表由“全部登记”改为“按用到的生成”。C++ 的构造函数直接引用组件，去掉无用代码后自然只留用到的；TS 与视图文档的应用，由构建插件扫出用到的组件种类，生成只登记它们的表。
2. **运行时生成**（D-144）：应用在 `omui.config.ts` 里开放了运行时生成界面，就保留完整目录（或开发者列出的那一部分）。开发模式永远是完整目录。
3. **报告**：`omui build --release` 结束时打印体积的构成（每项能力多少、为什么在），并给出“关掉哪项省多少”。体积的预算进应用自己的测试（`omui test` 可以断言上限）。

三个预设给不想细调的人：`full`（开发模式，全部）、`app`（发布的默认：推导出的闭包，带 Agent 与无障碍）、`lean`（推导出的闭包，不带总线与无障碍桥）。预设只是 feature 的组合，走同一条路径。

预期：`app` 预设的最小应用约 8–10 MB，`lean` 约 5–6 MB。都是估计，门按 §2。

### 3.4 OP3：字体与随带的库（D-214）

1. **字形子集**：静态文字（源码、视图文档、语言包里的串）用到的字形在构建时子集化进默认字体；Inter 的常用拉丁子集常驻。
2. **按语言带字体**：应用声明的语言决定带哪些字体。不声明中文的应用不带 NotoSansSC（4.15 MB），不声明阿拉伯语的不带 NotoSansArabic；表情字体按需。
3. **动态文字的回退**：用户输入或网络来的文字超出子集时，`fonts = "bundled"`（默认，逐字节一致的像素）带全量字体；`fonts = "system"` 回退到系统字体（体积最小，像素不再跨平台一致，声明里写明）。Web 已经是“全量字体按需下载”（RC2.9），桌面与它用同一套声明。
4. **X11 的库不随带**：SDL 在运行时按需加载系统的库；查清现在为什么把 2 MB 的 X11 库复制进分发目录，去掉。

预期：最小的英文应用的字体从 7.5 MB 到 0.3 MB 以内。

## 4. 内存（OP4）

先量，再定目标；量法走 mtest 的监测，不另写脚本。

1. **拆分**：同一个应用分别在 CPU 渲染的窗口、lavapipe、真实显卡上测常驻内存，把驱动与我们自己的分开；再按字体、字形缓存、显示列表、纹理、脚本堆、线程栈归类。
2. **已经看得见的几处**：字体整份读进内存（改成映射，回退字体用到才开）；设备创建时预留的缓冲；线程池的栈；万行列表是否只为可见行建节点。
3. **门**：最小应用与万行列表两项，对 Slint 与 Flutter 并排；每帧零分配已有预算（AGENTS §4），这里加的是常驻量的预算，进 `tests/bench/budgets.bench.xdef.json`。

## 5. 上手与安装

### 5.1 “卡在发布通道上”具体指什么

方案 §6.1 的门是：一条命令装上 `omui`，十分钟内出第一个窗口。现在的上手文档第一步还是“克隆仓库、自己编译 `omui`”，因为下面四个对外动作还没做：

| 动作 | 已就绪的 | 还缺的 |
|---|---|---|
| 四个平台的 `omui` 可执行文件 | `omui.yml`：打 `omui-v*` 的 tag 就构建单文件程序与校验和并建 release | 打第一个候选 tag |
| `xlings install omui` | — | 向 xlings 的包索引提一条 `omui`，指向上面的 release |
| 库进 mcpp-index | `omui-devtools release index`：模板的闭包 65 个包，外部依赖 21 个都已在索引里；`mcpp publish --dry-run` 通过 | 真正发布 65 个包（一次索引 PR）与国内镜像的地址 |
| 模板从发布物解析依赖 | `omui new` 已能从发布物取模板 | 上面三项之后，CI 加“干净机器上一条命令装上并新建项目”这一行 |

这些动作会把名字和版本公开出去，发出去的版本不好收回，所以一直写的是“由维护者发布”。规范已经在 2026-11-18 发布（openmui 0.4.1、openas 0.2.1），这一步的前置都齐了。

### 5.2 OP6：发布候选通道（D-216）

以 `0.1.0-rc.N` 的预发布版本走完上表四步：库的版本带预发布后缀，索引里与正式版分开；候选可以反复发，不占用 `0.1.0`。每个候选自动跑“干净机器”这一行。这样十分钟上手（N3）不必等到最后才第一次验证。

### 5.3 OP7：第一个窗口不需要编译（D-215）

- **① 原始性创新：** 本体系的开发模式本来就是“宿主进程持有窗口，应用是 TS”（D-154）。发布的 `omui` 自带预编译的播放器与开发宿主，TS 模板的 `omui new` 加 `omui dev` 不下载编译器、不编译任何 C++：第一个窗口的时间只剩下载 `omui` 本身。C++ 只在两处出现：C++ 模板，以及发布时把应用原生化（D-146）。
- **② 组合：** C++ 路径上，SDK 随发布提供预编译的模块产物，首次构建只编应用自己的代码。这依赖 mcpp 对预编译产物的支持范围，先核对；不支持的部分写明并报上游。
- **③ 业界做法：** Flutter 预编译引擎、Tauri 用系统 WebView，都是“第一个窗口不编框架”。这是低线。

门：TS 路径从空机器到第一个窗口 ≤ 2 分钟（宽带），C++ 路径 ≤ 10 分钟，三个桌面平台实测（即 RC3.2 的四个数之一）。

## 6. 性能的并排基准（OP5）

1. `tests/bench/competitors/apps/` 下放 Flutter 与 Slint 的三个对照应用（最小应用、万行列表、1012 节点仪表盘），版本钉住；Web 的对照是 Flutter Web 与一个 React 应用。
2. 度量：可执行文件与分发目录的字节、冷启动到首帧、常驻内存、滚动与更新的帧时间分布、Web 首帧前的字节与时间。同一台机器、同一个任务、轮流跑，结论取比值的 95% 区间（领先度台账的既有规则）。
3. 进 Bench 工作流；结果写入领先度台账与声明台账。落后的项留在台账里并转成任务，不删、不改口径。
4. 需要显示器、采集设备或移动设备的项（输入延迟、移动端首屏）标“未验证”。

## 7. 任务与次序

| 任务 | 内容 | 依赖 | 验收 | 进 0.1 |
|---|---|---|---|---|
| **OP1** | 链接期：去掉无用代码、相同代码折叠、LTO 的取舍、展开表 | — | hello ≤ 15 MB；像素哈希的用例不变；三个桌面平台 | 是 |
| **OP5a** | 并排基准的骨架：最小应用的体积、启动、内存，对 Slint 与 Flutter | — | 台账里 4 个指标有数 | 是（收口清单第 8 项） |
| **OP3** | 字体按语言与字形；X11 的库不随带 | — | 最小英文应用的分发目录里字体 ≤ 0.3 MB | 是 |
| **OP6** | 发布候选通道：`0.1.0-rc.1` 走完四步；CI 的“干净机器”行 | 维护者确认 | 一条命令装上并新建项目 | 是（RC3.1） |
| **OP7** | 发布的 `omui` 自带播放器；TS 模板不编译 | OP6 | TS 路径 ≤ 2 分钟，三平台实测 | 是（RC3.2） |
| **OP2** | feature 与推导：SDL3、解码器、无障碍桥、总线、GPU；注册表按用到的生成；体积报告与三个预设 | OP1 | `app` ≤ 8 MB，`lean` ≤ 6 MB（由实测收紧） | 底层 feature 是；推导若赶不上，标预览 |
| **OP4** | 内存：拆分、归类、常驻量预算 | OP5a | 两项并排不落后，或差距与原因写明 | 测量是；优化按结果 |
| **OP5b** | 万行列表、仪表盘、Web 首屏、热重载的并排 | OP5a | 台账里其余指标有数 | 是 |

次序：OP1 → OP5a → OP3 → OP6 → OP7 → OP2 → OP4 → OP5b。OP1 与 OP3 不改接口，可以立刻做；OP6 等确认。估计 12–16 个检查点。

## 8. 提议的决策

| 编号 | 内容 |
|---|---|
| D-211 | 发布类配置的链接默认去掉无用代码并折叠相同代码；LTO 按实测的收益决定；CPU 参考的字节不因此改变 |
| D-212 | 应用的闭包由它的声明推出（组件、字形、语言、解码器）；feature 是底层开关，预设是 feature 的组合；运行时生成的应用按开放程度保留目录 |
| D-213 | 语义树、Agent 总线与无障碍桥在默认预设里保留；`lean` 预设可以去掉总线与无障碍桥，并在应用的清单里写明 |
| D-214 | 字体按声明的语言与用到的字形随带；`fonts = "bundled"｜"system"`，默认 `bundled`，选 `system` 即放弃跨平台逐字节一致 |
| D-215 | 发布的 `omui` 自带预编译的播放器与开发宿主；TS 应用的开发不需要编译器 |
| D-216 | 发布通道先以预发布版本（`0.1.0-rc.N`）走通，每个候选在干净机器上验证 |
| D-217 | 体积、内存、启动、帧时间各有并排基准与预算；上限由实测收紧，落后的项留在台账并转成任务 |

## 9. 风险与未定

- **按用到的生成注册表会不会破坏 Live Design**：开发模式始终是完整目录；只有发布构建裁剪。运行时生成的发布应用按 D-212 保留目录，体积相应变大，报告里写明。
- **LTO 与确定性**：逐位一致是硬约束；LTO 若改变任何像素哈希就不默认打开。
- **对手应用进 CI 的成本**：Flutter 与 Rust 的工具链让 Bench 任务变慢；只在 Bench 工作流里跑，不进每次推送的行。
- **预编译模块产物**：取决于 mcpp；不支持时 C++ 路径的首次构建仍然慢，数字如实写。
- **需要 review 时定的**：`a11y` 是否允许在 `app` 预设里关（本文建议不允许，只在 `lean` 里）；`0.1` 是否等 OP2 的推导（本文建议不等，底层 feature 与 OP1、OP3 足以到 §2 的上限附近，以实测为准）。
