# 闭包推导：应用带什么，由它写了什么推出（B7a，一页设计）

2026-11-19 起草，**已定**（2026-11-19 review）。任务 B7a（[实施方案](2026-11-18-omui-meng-implementation-plan.md)），即 [compose 子方案](2026-11-18-compose-slots-worlds-design.md)的 K8，挡着 B7b；决策 D-251。背景：D-212、D-213（应用的闭包由它的声明推出；feature 是底层开关；默认保留 Agent 与无障碍）。

## 1. 要定的

发布构建里，一个应用该带哪些组件、哪些能力、哪些语言与字体，怎样不靠人手写就得出来，并且不破坏开发模式与运行时生成。

## 2. 事实（2026-11-19，`d8894152`）

- 能力的开关已经有了：`omui.sdk` 的世界 `lean` ⊂ `app` ⊂ `full`（默认）与 `minimal`，每项能力是一个加法的 feature，削减是 `no-*`（compose K0–K6）。例子 01 装入的字节：`full` 18,088 KiB、`app` 17,307、`lean` 13,154、`minimal` 12,676。现在选哪个世界要人写在依赖那一行。
- 组件的登记是全量的：`register_base_components()` 把基础组件逐个 `register_type`（约 65 处），`omui::run` 与播放器都调用它。只要这个函数在，链接器就回收不掉任何一个组件。
- C++ 的界面由构造函数直接引用组件；TS 的界面按名字经登记表创建。TS 应用的组件都从 `openmui` 导入，是 ES 模块的具名导入（例子 02：`import { signal, fmt, column, row, text, textBox, button, mount } from "openmui"`）。
- 声明式数据（主题、契约、时间线、`omui.config.ts`）在构建时由内嵌引擎确定地求值成 JSON 快照（D-139）。
- 图像解码器不需要推导：没有调用就被链接器回收（compose §10 已验证）。

## 3. 按三级次序（D-185）

**① 原始性创新：用到什么，是源码与快照里已经写明的事实；推导是读，不是猜。**

三个来源，都在构建时已经有了：

| 来源 | 给出什么 | 为什么是可靠的 |
|---|---|---|
| TS 模块的具名导入 | 用到的组件种类的上界 | ES 的导入是静态的：没被导入的名字不可能被用到。组件只从 `openmui` 与声明了契约的组件包导入（D-157），所以名字到组件种类的对应是契约里的数据 |
| `omui.config.ts` 的快照 | 能力：Agent 的开放程度、运行时生成（`generation`）、无障碍、渲染方式、语言 | 配置本来就是这些开关的唯一事实来源 |
| 清单与资源 | 字体包与语言（依赖里声明的）、脚本、视图文档 | 已在 `[package.metadata.openmui]` |

由此算出两样东西：**世界与能力的那一行 feature**，以及**只登记用到的组件的登记表**。

- 不可靠的写法（把 `openmui` 整个当对象用、按运行时算出的名字创建组件）在读的时候就认得出来；遇到就退回完整目录，并指出是哪一行、怎么改。
- 运行时生成开着的应用保留它开放的那部分目录（`generation` 里列出的，或全部）；这是声明，不是推导失败。
- 开发模式永远是完整目录（`omui dev` 加 `full`），所以 Live Design 里 Agent 随手用一个新组件不会失败；推导只作用于发布构建。
- 推导的结果是一个值（一份小的 JSON：世界、能力、组件、每一项的依据），构建报告把它与 `composition.json` 并排写出；`omui build --release` 打印“为什么带着它”与“关掉省多少”。

**与只靠链接器回收相比**多出的：按名字创建的东西（TS、视图文档、Agent 的 `ui` 操作）链接器看不见用没用，必须有登记表；登记表由事实生成，就把“看不见”变成了“写明了”。

**② 前沿加组合：用运行作旁证。** 应用的测试与招牌镜头在无头宿主上本来就跑；跑的时候记下实际创建过的组件种类。它不参与决定（没跑到的分支不等于用不到），只用来报告“导入了但从没出现过”的组件，提示可以删导入。0.1 做报告，不做自动删除。

**③ 业界做法（低线）**：摇树（按导入回收）、Flutter 的图标与字体子集、Android 的资源收缩。做到“没导入的不带”就是这一级。

## 4. 设计

| 部分 | 归属 | 说明 |
|---|---|---|
| 读导入 | `mlibs.ts`（已有的去类型器旁边） | 只取模块的导入表；不求值 |
| 组件名 → 种类、种类 → 提供它的包 | 组件契约里的数据 | 已由生成器产出；加一列“脚本里的名字” |
| 推导 | `mlibs.build.compose`（`unit` 与 `report` 所在处） | 输入：导入表、配置的快照、清单；输出：`closure.json` 与生成的登记单元 |
| 登记单元 | 应用的构建目录里生成 | 取代对 `register_base_components()` 的调用；C++ 应用没有按名字创建的入口时，登记表为空 |
| 入口 | `omui build`（代写 feature 那一行）；直接用 mcpp 时由构建程序核对并报出不一致 | 两条入口结果一致（AGENTS §5） |
| 播放器运行的 TS 应用 | 共用运行时里是完整目录；`omui package` 打成自带运行时的时候才推导 | 与[共用运行时](2026-11-19-shared-runtime-design.md)的 `needs` 是同一份结果 |

漏掉时的行为（发布构建里用到了没登记的组件）：第一次创建时报出组件的名字、推导的依据里为什么没有它、改法（加导入，或在配置里列出）。每个失败带出路（D-186）。

## 5. 最小验证（B7a 的另一半）

例子 02（TS，9 个导入里 5 个是组件）：手写一份只登记这 5 种组件的登记单元，替换全量登记，量三个数——可执行文件、装入的字节、第一帧的像素哈希。预期像素不变；体积的差就是“全量登记”的代价，也是 B7b 值不值得做的依据。结果写进本页与 STATUS。

## 6. 任务与验收

| 任务 | 内容 | 验收（本机） |
|---|---|---|
| B7a | 本页的 review；§5 的最小验证 | 三个数与像素哈希；差距小于 200 KiB 时，B7b 降为“只推导世界与能力，登记表保持全量”并写明 |
| B7b（K8） | 读导入、推导、生成登记单元、`omui build` 代写、mcpp 路径核对、报告 | 例子 02、03、13 与两个模板经它构建，像素不变；开发模式仍是完整目录；故意用一个没导入的名字时得到带出路的错误；`closure.json` 进体积检查 |

验证状态：推导是构建时的纯函数，在本机 Linux x64 上真实验证即对所有平台成立；各平台链接器的回收效果不同，体积的数在另三个平台上靠节点的矩阵，之前标“待确认”。

## 7. 风险与降级

| 风险 | 应对 |
|---|---|
| 推导漏掉动态用到的组件 | 认得出的动态写法退回完整目录并指出位置；认不出的在第一次使用时报出带出路的错误；开发模式不受影响 |
| 收益小（登记表只占几百 KiB） | §5 先量；小就只做世界与能力的推导 |
| 视图文档与 Agent 的 `ui` 操作按名字创建任意组件 | 开着 Agent 的创建类操作或运行时生成时，目录按配置里开放的范围保留；这是 D-144 已有的开关 |
| 做不完 | 降级写法（五项）；推导标预览，世界仍可手写，`app` 是默认 |

## 8. 已定的（2026-11-19 review：下列各条同意）

1. 以具名导入为组件的上界、配置的快照为能力的来源。
2. 运行的记录只作报告、不参与决定。
3. §5 的差距小于 200 KiB 就不生成登记表。
