# 0.1 发布的顶层收敛方案（part 2）：分两波，第一波是高品质的 omui

2026-11-18 起草，**第一版，草案，待 review**（D-222–D-228 为提议）。基线：`fa99971f`（PR #1）。

本文接在[收敛与发布方案](2026-11-15-convergence-first-release-design.md)（下称 part 1）之后，回答一个问题：part 1 做到 N0 之后，剩下的工作怎样收成一次高品质的发布。它做三件事：把发布分成两波（第一波是 omui 框架和它依赖的一切，第二波是游戏引擎）；把[体积、内存、性能与上手方案](2026-11-18-size-memory-performance-install-lead-design.md)（下称优化方案）的 OP1–OP10 全部并进第一波；把 part 1 里没做完的功能与能力按波重新排进一张任务表。part 1 的规则（标注、验证状态、开发策略、记录规则、发布门的写法）全部沿用，本文只改范围的划分、任务的次序与节点。

## 0. 核心点（review 入口）

1. **发布分两波**（D-222）。第一波 **omui 0.1**：openmui 与 openas 规范（已发布）、mlibs、xrender、hanim、omui（组件、语言、SDK、模板、命令行与工具）、它们依赖的引擎内核包，加上应用与 Agent 两个切片的作品。第二波 **xengine 0.1**：游戏层、其余的引擎内核、gongfu、xtools 的总入口、2D 与 3D 世界两个切片的作品。
2. **第一波的目标是品质，不是日期**：每项对外的指标对最强者并排实测，持平是低线（AGENTS §2 第 10 条）；现在实测落后的两项（描边、Lottie 播放）与没有数据的十二项（omui 的框架级指标）都在第一波里补上。
3. **优化方案的 OP1–OP10 全部在第一波**（D-224）：链接期、分级与可选、字体、内存、并排基准、通道与免编译上手、共用运行时、系统字体回退、终端宿主。进 0.1 不等于标“稳定”：每项在发布门上按实测取标注。
4. **第二波的工作不停、不删、不挡第一波**（D-223）：仓库与 CI 仍是一个，全量照跑；第二波成员的红照样记入清单并修，但不计入第一波的发布门。引擎内核里被 omui 与 hanim 依赖的包随第一波发布，标注照它们自己的。
5. **状态按三类写**（D-219）：已做；确定可做、未做（写明等什么）；需要设计或有风险。§2 的清单逐项标了。
6. **第一波八个阶段、三个节点**（§4）：对账 → 体积与分级 → 并排与性能 → 平台与基本功 → 通道与上手 → 终端宿主 → 作品与官网 → 候选与发布。估计 75–95 个检查点。
7. **第一波的发布物里有四个预览级的引擎内核包**（§8 第 2 点）：它们被 hanim 与 `omui` 命令行依赖，以预览级随第一波走，名字仍是 `xengine.*`。
8. **需要实机的项如实处理**（D-201）：输入法、系统无障碍桥、睡眠与恢复、输入延迟、Direct3D 12 需要带显示器的机器；有机器就测，没有就标“未验证”，不算通过也不挡发布。
9. **需要 review 时定的**（§8）：两波的版本号怎么叫；随第一波走的引擎内核包是否照现状；第一波的作品清单；实机从哪里来。

## 1. 为什么分两波

- **依赖的方向本来就是这样**：mlibs ← xrender、hanim、引擎内核 ← omui ← 游戏层 ← 类型框架与作品（AGENTS §2 第 8 条）。omui 这一层和它下面的可以独立成立；游戏层在它上面。
- **收口的进度不同**：收口清单 55/64 里，mlibs、xrender、hanim 已过；omui 欠并排对照一格与发布物探针；xengine 欠并排对照，它的度量还没有基准的骨架。四个切片里，应用与 Agent 两个切片离发布门近，2D 与 3D 世界还有需要显示器与真机的门（Quay 在 Web 上的帧时间、D-187 的实测）。
- **一次发布承诺的东西越少，越容易做到每一项都好**：part 1 的规则是“调整范围只有一种方式：改标注”；分波是同一个思路用在发布的批次上——目标与门不变，变的是哪一批先兑现。

### 2.2 第二波：xengine 0.1

`xengine/game`（world、runtime、input、nav、ui、playtest）；其余的引擎内核（cellular、matter、field、particles 等）；gongfu；xtools 的总入口与各引擎的适配器；xrender 的 3D 部分的门（与 model-viewer 的保真度对照 37/53、红 87 与 102）；作品 Kiln、Quay、打砖块、格斗、Glade、Swarm；2D 与 3D 世界两个切片的门（D-187 的真机帧时间、Quay 在 Web 上的 p99、KTX2 带透明的块）。

第二波的现状不因分波而倒退：这些成员已经做到的（无头可玩、分叉与因果、确定性回滚、Agent 以人的档位试玩）继续由 CI 守着。它的方案在第一波发布之后另写一份，不在本文展开。

### 2.3 分波的规则（D-223）

1. **一个仓库、一个 CI**：全量照跑；第二波成员的失败记入红灯清单并按根因修，不计入第一波的门。
2. **第一波的发布物不含第二波的包**：`omui-devtools release index` 的闭包以第一波的模板与作品为根；第一波的包不依赖第二波的包（lint `project-dag` 已经保证方向，加一条按波的检查）。
3. **两波各有自己的节点记录与计数器**，STATUS 里分两节；第一波的行排在前面。
4. **第一波冲刺期间，第二波只做三类事**：修它在 CI 上的红；第一波改动共享接口时跟着改；不需要主会话时间的后台验证。不开第二波的新功能。
5. **发布之后**：第一波的补丁版本只修不增；第二波在 omui 0.1 的发布物之上做，同时是对它的第一次外部式使用。

## 4. 第一波的阶段、次序与节点

次序的理由：先让 CI 回到全绿并把本地的提交推上去（之后每个阶段都要靠它对账）；体积与分级改的是构建与依赖的形状，越早越好，后面的并排基准量的才是改完之后的东西；并排与性能给出数字，决定哪些要再做；平台与基本功和通道可以并行（一个要实机，一个要发布）；终端宿主依赖 OP2 把视图层的像素部分做成可选；作品与官网用的是前面全部的结果；最后是候选。

| 阶段 | 内容 | 出口 | 约（检查点） |
|---|---|---|---|
| **W1-A 对账** | 这一轮的红修掉并推送；`--gpu` 崩溃的根因；mcpp 的 `--release` 报上游；STATUS 按两波分节；lint 加“按波”的检查 | 一轮 CI 在第一波成员上全绿 | 4–6 |
| **W1-B 体积与分级** | OP1、OP3、OP2（先断越级依赖与底层开关，再做推导与报告） | hello 的可执行文件 ≤ 8 MB、分发目录 ≤ 10 MB；像素哈希不变；三个桌面平台 | 12–16 |
| **W1-C 并排与性能** | OP5a、OP5b、OP4；描边与 Lottie 的定位与修；RC2.10b 的 token | 台账里 omui 的指标都有数；没有“落后”，或落后的项写明原因并改标注 | 14–18 |
| **节点 M1** | 体积、内存、性能的数字齐了；收口清单里 omui 的并排一格通过 | | |
| **W1-D 平台与基本功** | 输入法、无障碍桥、睡眠与恢复、Direct3D 12（有实机则测）；OP9；开关的盲比；`task()` | 平台表的第一波各格是实机、软件或写明的未验证 | 8–10 |
| **W1-E 通道与上手** | OP6、OP7、OP10；RC3.2 的四个数；RC3.5 的安装一节；RC3.11；发布物探针 | CI 上从干净机器装上、新建、出窗口；TS 路径 ≤ 1 分钟 | 10–14 |

| **W1-G 作品与官网** | 三个作品闭合；README 与首页按声明重写；官网更新 | 每个作品有安装后启动的用例；每句对外的话有 `claim` | 10–12 |
| **W1-H 候选与发布** | `0.1.0-rc.1` 公开发布；声明重跑；冷启动任务；修到连续两轮全绿；`0.1.0` | part 1 §8 的门，按 §5 的口径 | 8–10 |

合计约 75–95 个检查点。W1-D 与 W1-E 可以交错；W1-F 可以在 W1-B 的 OP2 完成后任何时候开始。每个阶段结束做一次 CI 对账，每 20 个检查点或每个节点做一次整体自我 review（AGENTS §6）。

## 5. 发布门：第一波的口径（D-225）

part 1 §8 的十条门照用，按波取范围：

| 门 | 第一波的口径 |
|---|---|
| 1 一级平台连续两轮全绿 | 第一波的成员；第二波成员的红逐条有编号并进发布说明 |
| 2 lint 0 | 全仓库（不分波） |
| 3 收口清单 | 规范、mlibs、xrender、hanim、omui 与它们的工具；随第一波走的引擎内核包按它们的标注（实验级 4 项） |
| 4 D-187 | 第一波的作品与招牌场景（文档墙、风格画廊、宣传片、官网）：RTX 4080 一档 p99 ≤ 8.3 ms，真实浏览器里 ≤ 16.7 ms；Quay 的两条移到第二波 |
| 5 四个开发者体验数 | 不变；TS 路径的上限收紧到 1 分钟 |
| 6 三个冷启动任务 | 第一波里的任务（应用与 Live Design）；游戏的任务移到第二波 |
| 7 声明重跑 | 第一波的声明 |
| 8 模板与例子从发布物构建 | 不变 |
| 9 发布物 | 四个平台的 `omui`；第一波的库在 mcpp-index；运行时在 xlings 的索引 |
| 10 规范的 tag | 已满足（openmui 0.4.1、openas 0.2.1），增补后重新打 |

另加三条，来自优化方案：

11. **体积与内存的预算**：最小应用、文档墙、Web 首帧前的字节、最小终端应用，各不超过 §2（优化方案）的上限，或不落后于并排实测的最强者。
12. **并排基准没有“落后”**：台账里第一波的指标，要么持平或领先，要么该项能力的标注降一级并写进发布说明。
13. **默认集合之外的组合各有一条冒烟**：`lean`、终端、共用运行时、`fonts = "bundled"`，能构建、出第一帧、体积在预算内。

## 8. 需要 review 时定的

1. **两波怎么叫**。本文的写法：第一波是 `omui 0.1.0`，第二波是 `xengine 0.1.0`，各自的版本号独立。另一种：整个仓库一个版本号，第一波 0.1、第二波 0.2。建议前者：omui 已经可以独立成项目，版本各走各的更干净。
2. **随第一波走的引擎内核包**。`xengine.dynamics`（hanim 的 `engine` feature 下）、`xengine.video` 与它的工具（`omui` 命令行）、`xengine.audio` 都是预览级；稳定级的包用它们，靠的是清单里的 `lower` 声明与 README 里的标记，lint `maturity` 已经这样检查。第一波照此发布：这几个包以预览级随发布物走，名字仍是 `xengine.*`。要定的是这是否可以接受，还是把被用到的那一小部分下沉到 mlibs 或 hanim（那样第一波的发布物里就没有 `xengine.*` 的包）。建议接受现状：归属是对的，下沉会制造第二份实现。
3. **第一波的作品**。本文列的是文档墙、风格画廊、宣传片。打砖块是 omui 组件的展示，但它依赖游戏层（`xengine.ui`、`xengine.input`），所以放在第二波；要它进第一波就得先把它用到的那部分定为第一波的依赖。
4. **实机**。输入法、无障碍桥、睡眠与恢复、输入延迟、Direct3D 12 需要带显示器的 Windows、macOS、Linux 机器各一台。有的话 W1-D 能把这些格子从“未验证”变成“实机”。
5. **终端宿主的并排对象**。本文写的是 ratatui 与 FTXUI；要不要加一个带脚本的对手（例如基于 Node 的 Ink），与 TS 的终端应用比。
