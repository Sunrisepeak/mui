## 0. 核心点（review 入口）

1. **项目是五层体系，omui 是其中一层；项目之间也必须无环**（D-161，已确认现在就拆）。Agent 内核与通用库在最下，引擎内核其上，再上是 omui，再上是 xengine 游戏层。xengine 目录现在拆成 `kernel/`（UI 之下）与 `game/`（UI 之上）；时间线模型下沉到 hanim；`xrender.vector` 去掉对 `hanim.core` 的依赖；新增 lint `project-dag`。
2. **游戏归引擎，渲染归 xrender，窗口输入与 UI 归 omui**（D-162）。
   - 世界、tick、规则、玩法、场景以及世界的 Agent 面归 xengine，**不依赖 omui 就能无头运行**（服务器、批量试玩、CI）。
   - 2D 与 3D 的全部渲染、图层合成、呈现、离屏出图与截图归 xrender，引擎和 omui 都只描述内容、都不自己画；所以无头的游戏不链接 omui 也能出图给 Agent 审查。
   - 窗口、输入设备、输入法、无障碍桥和 UI 归 omui。有窗口的游戏由唯一认识两边的桥 `xengine.ui` 接起来。帧的节奏归宿主，tick 归引擎。
3. **Agent 原生是底层架构，不是 UI 层的功能**（D-173、D-174）。它的本质是每个引擎原生提供状态、观察、控制、时间、因果、身份与授权六个原语；训练、评测、试玩、自动测试只是这些原语的应用场景。今天的事实是：端点、会话、协议都在 `omui.agent` 里，内核半的包没有一个自带操作目录。本版把它翻过来：
   - **Agent 内核 `mlibs.agent`**（base 层）：会话与端点、操作目录运行时、观察、预演与事务、因果记录、在场与认领、后台任务。任何引擎不链接 UI 也能被 Agent 发现、观察、控制。
   - **Agent 契约**：八个原生性质落成每个模块必须提供的东西，并由一套契约 CTS 在每个引擎上跑，结果分通过、失败、不支持。
   - **设计门**：新引擎和新模块在写代码之前，README 先写“Agent 面”；lint `agent-surface` 把守。
4. **omui 承担引擎 UI 的八项要求**（D-163，R1–R8）：三级嵌入、帧内预算、世界与 UI 两个主体的联动、空间焦点导航、指针锁定、tick 边界的状态发布、编辑器级组件、编辑器即 Live Design 的领域适配器。
5. **2D 和 3D 是同一个渲染器的不同特性**（D-164）。缺 3D 数学、场景抽取和 mesh 特性；材质是“数据＋Slang 接口实现”，管线是数据。3D 的金图钉在固定版本的软件 GPU 上；ID 缓冲把“像素是谁画的”延伸到 3D。
6. **物理管运动，化学管状态**（D-165，已确认）。新增 `xengine.matter`：材料是一组性质，状态是一组通道，规律只引用性质，不点名材料（lint）。“变成什么”也是性质，所以不需要成对的反应表。作者的工作量是 O(材料＋规律)。
7. **一套规则，四种载体**（D-166）：格点（Noita）、物体（塞尔达）、粒子、环境场。一步四段：收集、反应、提交、发出；读不可变输入，可交换累加，统一提交，所以并行且确定。
8. **元胞内核 v2**（D-167）：聚合、反应、传输、交换、提交五个阶段；交换用 2×2 块划分，守恒、可并行、CPU 与 GPU 逐位；按块的活动域与休眠。
9. **表现由配方决定**（D-168）：物体只声明材料与状态，外观、粒子、声音由“状态 → 表现”的配方驱动；世界风格包可换。
10. **世界可解释、可分叉**（D-169）：`world.explain` 给出因果链，`world.branch` 分叉快进看后果。它们不是世界专有的功能，而是 Agent 契约里“可解释、可预演”两条在世界主体上的实现。
11. **顶尖的独立中间件优先复用**（D-176；D-170 按它改写）：经 mwrap 引入，放在唯一的 owner 包之下、我们的契约之下。3D 刚体接 Jolt，寻路接 Recast／Detour，空间音频接 Steam Audio，网格处理接 meshoptimizer，骨骼压缩接 ACL；2D 刚体先评估 Box2D v3。Agent 契约与确定性是硬约束：中间件过不了就自研，自研则以它的基准为低线。**资产以代码和数据为一等**（D-171）。
12. **推进纪律**（D-172）：CI 修绿并对账、P0 验收关闭是硬门；M6.0 是一次行为不变的结构调整（规模接近 M1）；同时最多两条工作流；每个阶段的验收在 CI 上关闭后才开下一阶段。
13. **水平目标与 UI 框架同一个策略**（D-175，§14）：每个引擎一张特性表，每一项的低线是与该项最强者持平，交叉特性要超过或远超；没有“永远不做”的项，只有暂缓：暂缓项写明当前的替代、架构预留和重启条件。交叉特性有四组：全栈的 Agent 原生、全栈确定、UI 与世界同一套渲染与语义、不写死的涌现规则。
14. **暂缓不等于不做**（D-177，§9.4）：虚拟几何、全动态全局光照与硬件光追、主机平台、动作匹配、工程级仿真目前先不做，但架构要支撑以后做。预留只留三样：接口上的扩展点与能力查询、数据格式里带版本的位置、管线里可插的阶段；不预先实现，而且每个预留都要有一个现在就在用的消费者。设计评审增加“不堵路”检查。

## 2. 项目体系：五层与项目级依赖

### 2.1 目标项目图

```
第 4 层  类型框架与作品   gongfu、showcase、examples、site
第 3 层  游戏层           xengine/game：runtime（无头游戏运行时）、world、scene、input、net、ui（桥）、tool
第 2 层  UI 框架          omui：宿主（窗口、输入设备、输入法、无障碍桥）＋ UI（语义树、组件、lang、sdk、designer）
第 1 层  引擎内核         xrender（全部渲染：2D、3D、图层合成、呈现、截图）  hanim（动画，含时间线）  xengine/kernel：matter、dynamics、cellular、audio、video
第 0 层  通用库与 Agent 内核  mlibs（base、gfx、content，含 mlibs.control、mlibs.agent、mlibs.simulation、mlibs.pipeline）、mpal
规范                      openmui（UI 语义）、openas（Agent 交互的模型）
```

- 每一层只依赖更低的层。第 1 层的内核之间只通过第 0 层的接口和数据组合。
- “xengine”有两个含义：**xengine 体系**是第 1 层到第 3 层的总称（AGENTS.md 的一句话定义说的是它）；**xengine 游戏层**是第 3 层的包。
- 第 3 层里只有桥 `xengine.ui` 依赖 omui；`runtime`、`world`、`scene`、`input`、`net` 不依赖 omui（§2.4）。
- Agent 内核在第 0 层，所以每一层都从同一处得到会话、授权、目录、观察、预演和记录（§3）。

### 2.2 让 omui 可以独立的修正（去向已定）

| 现状 | 修正 | 规模 |
|---|---|---|
| `xrender.vector` → `hanim.core`（只为 `dm` 别名） | 直接用 `mlibs.math` 的 det，删掉依赖 | 很小，像素不变 |
| `omui.ui.timeline` → `xengine.timeline` | **时间线模型下沉到 hanim，成为 `hanim.timeline`**；编辑器组件 `omui.ui.timeline` 留在 omui，只依赖 hanim。音频增益自动化（`timeline/audio`）归 `xengine.audio`；xengine 工具里的时间线操作移到 hanim 的工具与目录 | 中，行为逐位不变 |
| hanim → `xengine.dynamics`（XPBD） | 不复制求解器。模拟内核认定为第 1 层，放进 `xengine/kernel/`，只依赖 mlibs | 随目录拆分完成 |
| 后端包开发依赖消费者的套件 | 翻转方向：CTS 归契约 owner，由 owner 的测试拿后端当被测对象来跑 | 小 |

时间线下沉到 hanim 的理由：

- hanim 是“编排、播放”的唯一归属（AGENTS §2.3），时间线就是按精确时间排布的片段加带关键帧的属性，属于编排；它现在的依赖本来也只有 `hanim.core`。
- 顶层方案 §6.5 已经决定把时间线的动画轨道和音频自动化收敛到 hanim 的通道。
- Live Design 的“内容时间线”（D-152）是 omui 设计器的一等概念，omui 需要这个模型，而 omui 不能依赖游戏层。
- 音频、视频、字幕片段的种类由各自的 owner 作为片段类型注册；hanim 不认识它们的内容。

### 2.3 目录现在就拆（D-161，已确认）


规则与 lint：

- `kernel/` 的包只依赖 mlibs 和同在 `kernel/` 的包；不得依赖 `game/`、omui。
- `game/` 里只有 `ui` 可以依赖 omui。
- lint `project-dag`（新）：一张“项目 → 允许依赖的项目”表。omui 的闭包里不得出现 `xengine/game/` 的包；xrender 不得依赖 hanim；hanim 只能依赖 mlibs、xrender（`hanim.visual`）和 `xengine/kernel/dynamics`。
- lint `layering` 的“路径 → 层”映射表随之更新；`kernel/` 的 CPU 部分仍是 base，`rhi` 子包是 gfx，audio、video 是 media。
- 拆仓顺序（以后）：mlibs → xrender → hanim 与 `xengine/kernel` → omui → `xengine/game` → gongfu。目录现在就按这个顺序可切。

### 2.4 游戏归引擎，渲染归 xrender，窗口输入与 UI 归 omui（D-162）

**职责划分**

| 职责 | 归属 | 说明 |
|---|---|---|
| 世界状态、固定步长 tick、规则与玩法、场景 | xengine 游戏层（`xengine.runtime`、`world`、`scene`） | 不依赖 omui；可以无头运行 |
| 世界的 Agent 面（操作目录、语义投影、解释、分叉、实时会话） | xengine 游戏层，建在 `mlibs.agent` 上 | 没有 UI 也完整 |
| **渲染**：2D 与 3D 的全部特性、图层合成、呈现到表面、离屏出图与截图、像素溯源 | **xrender** | 同时服务引擎和 omui。两边都只描述内容（omui 交显示列表，引擎交场景抽取的结果），都不自己画 |
| 窗口、输入设备、输入法、无障碍桥、平台服务、帧的节奏 | omui 的宿主 | 只有一套；宿主把表面和设备交给 xrender（后端由宿主注入，现状如此） |
| HUD、菜单、编辑器等界面 | omui 的 UI | UI 是交给 xrender 的一个图层 |
| 把两边接起来 | 桥 `xengine.ui` | 唯一同时认识引擎和 omui 的包 |

**为什么渲染归 xrender**（维护者意见，采用）

- 这本来就是“渲染器只写一次”（AGENTS §3）的意思；`xrender.graph` 已经把一帧建模成若干 pass，图层与合成是它现成的概念。缺的只是一个正式的、多个生产者共用的帧入口（§5.6）。
- 无头的游戏不链接 omui，直接经 xrender 离屏出图。Agent 审查游戏画面不需要 UI 框架。
- 截图、ID 缓冲、SVG、像素溯源成为同一个 Agent 面（“帧”这个主体），UI 和世界共用，不各做一套。
- 只要画面不要 UI 的游戏，闭包只剩宿主和 xrender，体积问题比第二版小得多。

**桥做四件事**：告诉 xrender 世界图层放在哪（UI 树里是一个视口节点，布局、命中、语义都知道世界在哪）；把 omui 的输入事件路由成游戏动作（含指针锁定）；在 tick 边界把世界的快照发布成 signal 给 UI 读；把世界主体和 UI 主体挂到同一个 Agent 端点上。

**帧的节奏、渲染、tick 各有其主**

```
有窗口：omui 的宿主决定帧的节奏
  输入采样 → [世界阶段：0..n 个 tick，由引擎注册] → 动画（hanim）→ 布局 → UI 显示列表
          → xrender 的一帧 { 世界图层的 pass … → 后处理 → UI 图层 → 合成 } → 呈现到宿主给的表面
无窗口：引擎自己驱动 tick
  输入（Agent 的动作或回放）→ tick → tick → …    没有 omui；需要画面时直接经 xrender 离屏出图
```

- 同一个游戏有两种运行方式，世界的每一位都相同：有窗口时录下的输入，无头回放必须逐位一致（验收）。
- 现有 `xengine.ui` 的 pacer（在组件里步进）保留给嵌在页面里的小游戏；它和世界阶段步进的是同一个 `mlibs.simulation` 时间线。

**三种做法的比较**

| 做法 | 问题 |
|---|---|
| 引擎拥有窗口、帧和渲染，UI 是插件（Unreal、Unity、Godot） | 宿主、输入法、无障碍、开发宿主都要再做一遍，和 omui 重复 |
| 游戏是 omui 应用（第一版的建议，已撤回） | 游戏离开 omui 就跑不起来：服务器、上千局的批量试玩、CI 都要链接 UI；游戏的生命周期寄生在一个组件里；世界的 Agent 面只能借 UI 协议暴露 |
| **游戏归引擎，渲染归 xrender，窗口输入与 UI 归 omui**（采用） | 需要 Agent 内核、帧管线、渲染的帧入口都在引擎和 omui 之下（前两个已在 base 层或本版下沉，第三个见 §5.6） |

这和开发宿主（D-154）是同一个模式：应用是渲染输出目标，宿主持有窗口。游戏也是渲染输出目标。

**UI 与 3D 的三种组合**（D-81 §4.3）都是 xrender 一帧里的图层合成：UI 叠在世界上；世界嵌在 UI 里（视口节点）；UI 进世界（UI 图层渲染到纹理，由引擎贴到世界里）。

### 2.5 omui 作为引擎 UI 的八项要求（R1–R8，D-163）

## 3. Agent 原生是底层架构（D-173、D-174）

### 3.0 本质：六个原语

Agent 原生的本质不是某个场景。训练、评测、自动试玩、自动测试、运行时生成、人机协作都只是场景；本质是**每个引擎从数据模型起，原生地向 Agent 提供六样东西**：

| 原语 | 含义 | 没有它时只能怎样 |
|---|---|---|
| 状态 | 显式、可寻址、可整体快照 | 靠截图和日志猜 |
| 观察 | 设计出来的投影：紧凑、分档、带预算、可订阅增量 | 把内部结构整个倒出来，或只给像素 |
| 控制 | 操作是唯一的改变途径，声明效果类别、可否撤销、成本 | 把内部函数直接暴露出去 |
| 时间 | 单步、跳转、回放、分叉 | 只能实时跑一遍 |
| 因果 | 在提交点记录，能回答“为什么” | 只知道结果 |
| 身份与授权 | 谁做的、受谁委派、在哪个授权下，每个请求经判定 | 外面套一层弹窗 |

有了这六样，上面那些场景都是它们的组合，不需要逐个场景去做适配。§3.3 的八个原生性质是这六样的可检查形式。

### 3.1 现状的问题

设计准则早就写了“预演、事务、确定性、像素溯源从架构上内建，不靠事后适配”（AGENTS §2.4），第二部分方案也列了八个原生性质并要求每个项目满足。但落到代码上，§1 的事实是：

- 授权在 base 层（`mlibs.control`），但端点、会话的传输、信封、后台任务、记录都在 UI 层的 `omui.agent` 里，每个分区都 import `omui.view`。
- 内核半的包没有自带的操作目录；它们的操作长在工具和应用上（Inspector、xengine 工具、打砖块）。
- 因果记录（D-148）只有 UI 的；预演只有 UI 的分支执行；Live Design 的历史与认领在 `omui.designer` 里。

结果是：一个不带 UI 的模拟、渲染或游戏进程，要么链接 omui，要么自己再写一个端点。这正是“最后做一个适配”的结构性原因。

### 3.2 Agent 内核 `mlibs.agent`（base 层，新）

Agent 内核是 openas 的模型在进程内的实现，面向任何“主体”。它不认识 UI，也不认识游戏。

| 模块 | 内容 | 现在在哪 |
|---|---|---|
| 授权 | 策略、会话、委派、`decide` | `mlibs.control`（保留为它的 owner，内核依赖它） |
| 端点与传输 | 本地 IPC、发现描述、在安全点（帧或 tick 的边界）处理请求；传输可由宿主替换（Web 上是 postMessage） | `omui.agent:endpoint` |
| 信封与分帧 | openas 的信封、按行的记录、全双工 | `omui.agent:protocol` 的通用部分 |
| 主体登记 | 一个进程里的多个主体（UI、世界、动画舞台、渲染器……）各有名字、地址空间和能力声明 | 没有 |
| 目录运行时 | 从 `*.ops.omui.ts` 的快照注册动词；每次调用先 `decide`；**分级披露**：先给主体与命名空间，再按需展开操作 | 生成器有；运行时注册在 player 与 `omui.agent` |
| 观察 | 带预算的投影、增量订阅、按 token 成本设计 | UI 的 `changes` |
| 事务与预演 | 开始、预演（在分支里执行并返回差异）、提交、撤销；对外部效果只记录不执行 | UI 的分支执行 |
| 因果记录 | 分级的环形缓冲、因果 ID、`timeline` 与 `explain` 的通用形状 | `omui.view` 的交互记录器 |
| 实时会话 | 按 tick 订阅观察、带 tick 编号提交动作、截止时间、公平档位 | 打砖块里的实现与 openas 草案 |
| 在场与认领 | 参与者、意图、接管；细粒度认领与租约（D-160） | `agent_presence` 组件、`omui.designer` |
| 历史 | 内容寻址的提交、分支、合并（D-151 的 `DesignHistory`） | `omui.designer` |
| 后台任务 | 提交即得句柄、可取消、由所属方在边界提交 | `omui.agent:broker` |
| 适配层 | MCP、WebMCP、A2UI：把内核的目录与会话投影成各协议 | `omui-mcp`、`omui.agent:a2ui` |

- **主体接口是最小的**：名字与地址空间、状态哈希、一组可选能力（观察、操作、预演、解释、时间控制、历史）。没有的能力如实回答不支持（能力查询），不伪装。
- **拆出之后 `omui.agent` 只留 UI 主体**：`openmui.tree` 的操作（find、act、inspect、capture、drew）、API 导出。`generation` 是产品能力，成为 `omui.generate`；`present` 是显示传输，归开发宿主。这同时解开红灯 44 那类依赖环。
- **对外契约不变**：协议字段、信封、`openmui.tree@0.1`、MCP 工具名都不改；验收是 Agent 端到端测试的收发记录逐字节相同。
- **为什么单独成包而不并进 `mlibs.control`**：control 的定位是“只依赖 openas、日志和追踪，没有传输”；端点需要 `mcpplibs.os` 的 IPC 和 `mlibs.json`，属于依赖隔离（D-99）。
- **抽取分两步**（至少两个消费者才提取）：M6.0 抽端点、信封、主体登记、目录运行时、记录、后台任务（第二个消费者是无头的游戏运行时）；历史与认领在第一个非 UI 的设计适配器出现时抽（M6.1 的材料实验台）。

### 3.3 Agent 契约：八个原生性质落到每个模块

八个性质来自第二部分方案 §1.4（不另立一套）。本版给出每条对模块的架构要求，以及契约 CTS 检查什么。

| # | 性质 | 模块从设计起就要做到的 | 契约 CTS 的检查 |
|---|---|---|---|
| 1 | 单一来源 | 能力就是目录：每个公开能力要么有操作（状态、效果类别、可否撤销、成本），要么声明为不对外；一切可被提及的东西有稳定地址（实体、格的区域、材料、规律、pass、绘制、通道、片段、声音） | 目录完整；同一输入两次运行，地址相同 |
| 2 | 事务化 | 状态是显式的纯数据，可整体快照；改变状态只有操作这一条路，没有后门的 setter | 预演之后状态哈希不变；撤销之后回到原哈希 |
| 3 | 确定性 | 时间是显式的（tick、seek、单步），内部不读墙钟和全局随机数 | 录制的会话回放后状态哈希相同；分叉不影响原状态 |
| 4 | 同源的离屏输出与溯源 | 输出能追回来源：像素 → 绘制 → 实体或节点 → 源文件位置；声音 → 事件 → 原因；状态 → 规律 → 数据文件的 JSON 指针 | 给定一个输出位置，能得到非空的来源链 |
| 5 | 执行者在模型里 | 每次改变都记下谁做的、受谁委派、在哪个授权下；意图可显示 | 记录里的执行者与会话一致 |
| 6 | 授权在核心 | 每个请求经 `decide`，包括读、截图、导出；嵌套调用按当前操作重新判定 | 策略拒绝时操作确实没有执行（没有绕过的路径） |
| 7 | 为 Agent 设计的观察 | 观察是设计出来的投影：紧凑、分精度档、带预算、可订阅增量；不是把内部状态整个倒出来 | 回答不超过给定预算；增量与全量一致 |
| 8 | 为 Agent 设计的工程细节 | 操作幂等；诊断结构化并带位置；每个工具有 CLI 与 JSON 输出；无头下远快于实时；在提交点记录因果（可解释） | 诊断带位置；对一次记录在案的变化，`explain` 给出因果链 |

- 契约 CTS 是 `mlibs.agent` 的套件（`src/cts/`，D-65 与顶层方案 §5.5 的做法），**每个主体注册自己来跑**：omui 的 UI 主体、hanim 的舞台、matter 与 cellular 的场、dynamics 的世界、xengine 的游戏、xrender 的帧。结果分通过、失败、不支持；不支持必须来自能力查询。
- 热路径的约束不变：控制请求只在帧或 tick 的边界进入；记录写在提交点的环形缓冲里，关闭时零开销；不在逐格、逐像素、逐采样的循环里判定授权。

### 3.4 各引擎的 Agent 面

每个引擎在自己的数据模型里回答同样的六个问题。标“缺”的是今天核对到没有的。

| 引擎 | 主体与地址 | 观察 | 操作 | 解释与溯源 | 预演与时间 | 现状 |
|---|---|---|---|---|---|---|
| omui | 语义树，节点 ID 路径 | 语义、任意区域截图、SVG | act、invoke、design.*、generate.* | `ui.explain`、`ui.drew` | 分支预演、撤销、时钟控制 | 齐全，是其他引擎的样板 |
| hanim | 舞台：对象、部件、通道、播放、时间线片段 | 计划查询、任意时刻采样 | 播放、跳转、暂停、编辑动画文档 | 某个值来自哪些动画层与混合：缺 | 纯动画是时间的函数 | 有目录；解释缺 |
| xrender | 帧：图层、pass、绘制、资源、像素（UI 与世界共用这一个主体） | 任意图层与区域的像素、SVG、pass 计时；3D 的 ID 缓冲缺 | 截图、离屏出图、检查渲染图 | 2D 像素到节点已有；3D 像素到实体、材质、光源贡献：缺 | 帧是输入的函数 | 2D 有，3D 缺 |
| matter、cellular | 场：区域、格、材料、规律（JSON 指针） | 区域统计、通道直方图、变化块、事件流 | 放置、施加某个量、改规律数据（事务） | `world.explain`（§6.10） | 单步、跳转、分叉 | 自带目录缺（操作在 Inspector 里） |
| dynamics | 世界：刚体、形状、约束、接触 | 接触、能量、休眠岛 | 施力、设置、单步 | 接触为什么发生（`inspect` 有雏形） | 单步、跳转、分叉 | 自带目录缺 |
| 游戏运行时、world、scene | 游戏：实体 ID、组件、区域、场景文件位置 | 语义投影（按区域、种类、预算；增量） | 场景事务；玩法动作 | 实体来自场景文件哪一处；状态的因果链 | `world.branch`；回放 | 缺（打砖块是手写的一例） |
| input（Agent 玩家） | 动作词汇，与人相同 | 按公平档位：人类同等、特权 | 按 tick 对齐提交动作 | 意图叠加 | 实时会话 | 打砖块已有 |
| audio | 声音、总线、发声体 | 正在响什么、各总线响度、频谱摘要（Agent 听不见，要给结构化的“听”） | 播放、参数 | 声音 ← 事件 ← 原因 | 离线渲染逐位 | 声音是数据已有；观察缺 |
| net | 对局、帧、输入 | 回滚统计 | — | 失步定位到 tick 与通道 | 回滚就是分叉 | 缺 |
| 工具与编辑器 | Live Design 的主体（D-160） | — | 领域的结构化编辑 | 设计历史 | 预演、分支、认领 | UI 的有；其他领域随适配器 |

### 3.5 设计门、README 与 lint

- **设计门**：新的引擎、内核包或领域适配器，设计文档和 README 必须先有“Agent 面”一节，按 §3.4 的六栏写清楚，再写实现。评审先看这一节。
- **README 模板**：`modules/projects/` 下每个有状态的包的 README 增加“Agent 面”：主体与地址、观察投影、操作与效果、解释、预演与时间、预算与档位、不支持的能力及原因。
- **lint `agent-surface`**（新）：`projects/` 下的包要么登记了契约 CTS 的主体并有自己的操作目录，要么在清单的 `[package.metadata.openmui]` 里声明 `agent = "library"` 并写明理由（纯函数库：`mlibs.math` 一类，只需满足确定性和结构化诊断）。已有的 lint `ops`、`skills` 继续检查目录与 skill 的一致。
- **补齐的顺序**：按 M6 的阶段，谁先成为主线谁先补（matter、cellular、dynamics 在 M6.1–M6.2，xrender 的 3D 在 M6.3，游戏运行时在 M6.0 以打砖块起步）。M6.0 先让契约 CTS 在 omui、hanim 上通过，在 cellular、dynamics 上如实报出不支持的项。

### 3.6 与 Live Design 通用底座、openas 的关系

- **Live Design（D-160）是“创作”，Agent 内核是“运行与控制”，两者共用同一组概念**：主体、参与者、在场、认领、历史。所以历史与认领属于内核，不属于 UI；`omui.designer` 留下的是它们的可视化和 UI 领域的适配器。
- **openas 是规范，`mlibs.agent` 是它的进程内实现。** 实时会话、存在与接管、事务等扩展先在这里用真实消费者验证，再写回 openas（顶层方案 §8.3 的流程）。内核稳定后是否上游成 openas 的 SDK，留作开放问题（§12）。
- **适配层保持薄**：MCP、WebMCP、A2UI 只做投影，不持有状态（D-137）。目录分级披露之后，MCP 的工具清单只列主体和少量入口工具，操作按需展开，解决 W4 发现的固定开销。

## 4. omui 与各类框架：对照与决策

逐项特性的对照表在 [Agent 时代收敛方案 §3](2026-11-09-agent-era-ts-first-convergence-design.md)（61 项）；指标在[第二部分方案 §4.1](2026-11-08-part2-industry-leading-design.md)。这里只按架构取舍归纳，并补上此前没有对照过的“游戏与编辑器 UI”。

| 取舍 | 主流做法 | omui 的选择 | 判断 |
|---|---|---|---|
| 画面由谁画 | 原生控件（SwiftUI、RN）；自绘（Flutter、Slint、GPUI）；DOM（React、Tauri、Electron） | 全平台自绘（D-140），webview 只作外部表面（D-141） | 对。确定性、像素溯源、强动画都以它为前提。代价是输入法、无障碍桥、平台手感要自己补，这些现在还在 P2 |
| 界面的模型 | 组件树加 diff（React、Flutter、Compose、SwiftUI）；属性绑定（Slint、QML）；立即模式（Dear ImGui） | 语义树是唯一来源，像素、无障碍、Agent、测试都是它的视图 | 对，而且是别人事后补不出来的。无障碍树在别处是派生物，在这里是本体 |
| 上层语言 | Dart、Kotlin、Swift、TSX、Rust、专用 DSL | C++ 内核加最薄的 TS，TS 即数据（D-138、D-139） | 方向对。风险是模型对 omui 的 API 不熟，“一次写对率不低于 Next + shadcn”的实验还没做 |
| 动画 | 组件各写各的隐式动画；共享元素过渡；CSS | 组件不写动画，hanim 统一求值（D-93） | 对，已有扫测证据 |
| Agent | 事后适配：无障碍树、截图、手写 MCP 工具 | 原生：预演、事务、授权、因果记录（openas） | 最强的一项。本版把它从 UI 层下沉为整个体系的内核（§3） |
| 开发回路 | 热重载（Flutter）、预览（SwiftUI）、DevTools | 应用即设计器，Live Design（D-149） | 独有。标志性镜头要先在 CI 上重新通过 |
| 确定性 | 都不保证 | CPU 像素跨平台逐位 | 独有，已有证据 |
| 游戏内 UI | Unreal UMG、Unity UI Toolkit、Godot Control、RmlUi、NoesisGUI、Gameface | 没有专门设计过 | 本文 R1–R6。Godot 用自己的 Control 写出了整个编辑器，证明“引擎的 UI 同时做编辑器”可行 |
| 谁拥有窗口、帧和渲染 | 游戏引擎自己全部拥有，UI 是引擎的一个子系统 | 游戏归引擎，渲染归 xrender，窗口输入与 UI 归 omui（§2.4） | 与主流不同：三者各有一个 owner，互不重复；引擎和 UI 框架都可以单独使用 |
| 调试与工具 UI | Dear ImGui（几行代码一个面板） | Inspector、TS 热重载、Agent | 缺一个“一句话加一个调试面板”的 L0 入口；用 TS 热重载补，不引入立即模式 |
| 生态与生产验证 | 都远强于 omui | 只有官网和作品 | 短期追不上；用 xengine 作为第一个重度内部消费者来磨 API |

三条结论：

1. **omui 有两个市场，要求不同。** 做应用框架，短板是平台行为、组件深度、首包体积和生态；做引擎的显示与 UI，短板是 R1–R8。两边共用同一个内核，不分叉。
2. **xengine 是 omui 最好的第一个重度消费者。** 编辑器要用到大表格、大树、停靠、节点图，正是应用框架一侧也缺的专业组件（收敛方案的 D1、E1）。
3. **对外的说法要跟着证据走。** omui 自己的 12 项对照指标一项都没测；在测出来之前，“领先”只用在已有证据的三处：Agent 原生的能力对照、确定性、hanim 的交互动效。

## 5. 渲染：2D 与 3D 同构（D-164）

承接[统一渲染架构（D-81）](2026-10-28-openmui-structure-render-web-game-design.md)：2D 和 3D 只是不同的渲染特性。这里补上 D-81 没有展开的部分。

### 5.1 分层与归属

| 层 | 内容 | 归属 | 现状 |
|---|---|---|---|
| 数学 | 二到四维向量、3×3 与 4×4 矩阵、四元数、变换、视锥；确定性分档 | `mlibs.math` | 缺 |
| 几何 | 3D 形状、包围盒、射线、BVH；网格数据（顶点属性、索引、子网格）；过程化建模（方、柱、挤出、旋转体、简单布尔） | `mlibs.geom` | 只有 2D |
| 设备 | 深度、MSAA、实例、计算、时间戳 | `mlibs.rhi`，每项进 CTS | 大部分已有 |
| 着色 | Slang 模块、接口与泛型；按后端输出；反射出绑定 | `mlibs.shader` | 已有 |
| 场景抽取 | 视图与相机、可见性与剔除、灯光、绘制包排序与合批 | `xrender.scene`（新） | 缺 |
| 特性 | `vector`、`effect`（已有）；`mesh`（静态、蒙皮、实例）、`sprite`（批处理、图集、2D 蒙皮）、`particle`（新） | xrender | gongfu 私有的 2D 蒙皮回到 `sprite` |
| 管线 | 一帧有哪些 pass，是数据（`*.pipeline.omui.ts`），特性注册自己的 pass | `xrender.graph` | 渲染图已有 |

### 5.2 材质不写死

- 一个材质 ＝ 数据（参数、贴图）＋ 一个实现 `IMaterial` 接口的 Slang 模块（表面函数）。
- 着色程序由四个正交的部分在构建期组合：顶点来源（静态、蒙皮、实例、粒子）× 材质 × 光照模型（PBR、卡通、无光照）× pass（阴影、深度、前向、ID）。组合由 `mlibs.shader` 生成并缓存，运行时不拼字符串。
- 人或 Agent 新增一种外观，只写一个 `.slang` 模块和一份 `*.material.omui.ts`，不改渲染器。
- 渲染材质与物质（§6）用表面类型 ID 关联（D-133 已定）；“状态 → 外观”的映射见 §6.8。

### 5.3 管线与分档

- 默认管线是前向加分簇光照（Forward+）：对 Web 和移动端最稳，透明与 MSAA 简单。延迟管线以后作为另一份管线数据加入，不改特性。
- 分档沿用[性能分档](2026-11-01-openmui-performance-tiers-design.md)：WebGPU 与桌面走分簇；WebGL2 降为有限光源数的简单前向；每档的降级写在能力查询里，不静默降级。
- 只画 2D 的应用不链接 scene 和 mesh（feature），体积不变。
- 前置 pass 从一开始就输出深度、法线、速度、ID；着色里的间接光是一个可换的接口；渲染图要有跨帧保留的历史资源。这三处是为暂缓的高端特性留的路，各自现在就有消费者（§9.4）。
- 2D 也要光：像素世界的自发光、辉光、遮挡阴影、战争迷雾，都是 `effect` 的 pass，输入是格点的通道（§6.8）。

### 5.4 确定性与 Agent 面

- 2D 矢量保留 CPU 参考，逐位一致不变。
- 3D 没有 CPU 参考（D-81 已定）。金图钉在固定版本的软件 GPU（CI 已用的 lavapipe；浏览器里是 SwiftShader），真实 GPU 按容差比较，结果分通过、失败、不支持。
- **ID 缓冲**（Agent 契约第 4 条在 3D 的实现）：每个像素写出实体（实例）、簇、三角形和材质的 ID；这个级别同时是以后做可见性缓冲的基础（§9.4）。Agent 问“这个像素是谁画的”在 3D 里同样能答；语义截图给出每个实体的屏幕包围框和遮挡比例。
- **渲染的解释**：对一个像素，回答它来自哪条绘制、哪个材质、哪些光源在照它（在软件 GPU 的调试 pass 上算，不进正常帧）。
- 探索项（不排期）：Slang 的 CPU 目标能把材质着色编成 C++，理论上可以给 3D 也做一个慢而确定的参考光栅；先看软件 GPU 钉版本是否够用。

### 5.5 资产（D-171）

- 导入：glTF 2.0（免版税；解析经 mwrap 接现成的库，D-56、D-83）；贴图 KTX2。
- 过程化：建模、贴图（`mlibs.math` 的确定性噪声，CPU 与着色器同一个函数）、声音（`xengine.audio` 已有）都可以用代码和数据生成，确定可重现，Agent 可读可改。
- 骨骼动画归 hanim（唯一的通用动画归属）：姿态是通道，混合、叠加、约束用已有的层与约束；布娃娃是动力学写回姿态通道（D-133 的 L4 桥接）。

### 5.6 帧的合成、呈现与截图归 xrender

渲染的全部出口都在 xrender，引擎和 omui 是两个平等的内容生产者：

| 概念 | 内容 |
|---|---|
| 目标 | 宿主给的表面，或一张离屏纹理 |
| 图层 | 一帧里按顺序排列的内容来源：UI 的显示列表、世界的场景抽取结果、视频帧、外部纹理；每个图层登记自己的 pass |
| 合成 | 图层的顺序、位置、混合与整帧的后处理；是管线数据的一部分 |
| 出口 | 呈现到表面；离屏出图；任意图层与区域的截图；ID 缓冲；2D 图层的 SVG |

- xrender 不创建窗口，不认识 UI 和游戏；表面和设备由宿主经 `mlibs.rhi` 交进来（现状如此）。
- omui 的宿主现在直接驱动 UI 的绘制；改为经这个帧入口提交 UI 图层，像素不变。
- 没有 omui 的程序（无头的游戏、材料实验台的批处理、动画导出）直接用同一个入口离屏出图。
- Agent 面：`帧`是一个主体，截图、溯源、渲染的解释都在它上面，UI 的 `ui.capture`、`ui.drew` 成为它在 UI 图层上的投影，对外的操作名不变。

## 6. 世界模拟：物理管运动，化学管状态

承接[仿真与动力学方案（D-133、D-134）](2026-11-08-simulation-dynamics-architecture-design.md)的分层与八条契约；本节补上它没有展开的“化学”一侧，并对其中两点提出修订（§13）。

### 6.1 两个参照给出的原理

| | 旷野之息（GDC 2017 的公开分享） | Noita（GDC 2019 的公开分享） |
|---|---|---|
| 分工 | 物理引擎算运动，“化学引擎”算状态 | 每个像素都被模拟；刚体交给 Box2D |
| 基本量 | 材料（木、金属、石、草）和元素（火、水、冰、电、风） | 材料分粉末、液体、气体、固体，各带密度、可燃等性质 |
| 规律 | 三条：元素改变材料的状态；元素改变元素的状态；材料不直接改变材料 | 相邻像素按性质移动和反应 |
| 尺度 | 物体级，粗粒度的场（风、温度、雨） | 像素级，分块、脏矩形、棋盘式多线程 |
| 耦合 | 火产生上升气流，带起滑翔伞 | 刚体由像素构成，像素被毁则重算形状 |

两者的共同点才是架构要抓住的：**相互作用通过少数几个被传输的量发生，规律写在性质上，不写在“谁对谁”上。** 火不认识木头；火只是让温度升高，而任何燃点低于这个温度、还有燃料、周围有氧的东西都会烧起来。

### 6.2 七条设计原则

1. **量与规律分开。** 状态是纯数据（通道），规律是数据（规则表），内核里没有“火”“水”这样的词。
2. **规律只引用性质。** 新材料只填性质就参与全部作用；规则里出现材料名由 lint 报出，只有标明为“配方”的特例可以点名。
3. **变成什么也是性质。** 水的“气态”是蒸汽、“固态”是冰，写在水自己的性质里；规律只说“高于沸点的液体变成它的气态”。成对的反应表因此不需要。
4. **作用经由被传输的量。** 热、湿、电荷、压力与速度（风）、燃料与氧。物体不两两交互，而是与场和邻居交换这些量。
5. **读不可变输入，累加，再提交。** 一步之内所有判定读同一份输入；增量是可交换的累加；最后统一提交。并行顺序不影响结果。
6. **守恒与稳定由构造保证。** 移动是交换；传输是成对对称的整数定点流量；写入饱和。不会凭空多出质量或能量，也不会数值爆炸。
7. **事件向外，脚本不向内。** 玩法、声音、特效订阅事件（点燃、熄灭、冻结、碎裂）；脚本只写规则数据和处理事件，不进逐格、逐帧的循环（AGENTS §2.6）。

第 1、5 条同时就是 Agent 契约的第 2、3 条：状态是显式的纯数据，所以能快照、预演、分叉；提交点是唯一改变状态的地方，所以因果记录写在那里就够了。

### 6.3 物质模型：`xengine.matter`（新，`kernel/`，base 层，只依赖 mlibs）

| 构件 | 内容 |
|---|---|
| 性质列 | 带类型和单位的列，可注册：力学（密度、摩擦、恢复、柔度）、热学（比热、导热、燃点、熔点、沸点）、化学（燃料、燃速、氧需求）、电学（电导）、相态与“变成什么”（固态、液态、气态、燃尽后） |
| 材料 | 一行性质加标签；数据文件 `*.matter.omui.ts`，求值成 JSON 快照（D-139） |
| 状态通道 | 每个物质实例携带：材料、温度、湿度、电荷、燃烧进度、完整度、相态；应用可以加通道 |
| 规律 | 三类：**传输律**（某个量按什么系数流动）、**反应律**（性质与状态满足条件时发生什么）、**转换律**（越过阈值时相变或变成别的材料） |
| 程序 | 规律编译成的不可变计划（准备与执行约定）：预算、诊断带 JSON 指针、可查询 |
| 载体接口 | 一组物质实例，加一个带权的相邻关系 |
| Agent 面 | 自带操作目录：查询区域与材料、放置、施加某个量、单步、跳转、解释；规律数据的编辑是事务 |

数据的样子（示意，字段名在实现时定）：

```ts
export default defineMatter({
  materials: {
    wood:  { phase: 'solid',  density: 600,  ignition: 570, fuel: 15, burnt: 'ash' },
    water: { phase: 'liquid', density: 1000, melting: 273, boiling: 373, gas: 'steam', solid: 'ice', conduct: 0.05 },
    lava:  { phase: 'liquid', density: 2600, melting: 1300, solid: 'stone', emits: { heat: 40 } },
    iron:  { phase: 'solid',  density: 7800, melting: 1800, liquid: 'molten_iron', thermal: 80, conduct: 1.0 },
  },
  laws: [
    { transfer: 'heat',   by: 'thermal' },                                   // 热从高温流向低温
    { transfer: 'charge', by: 'conduct' },                                   // 电沿导体流动
    { when: 'temperature >= ignition && fuel > 0 && near.oxygen > 0', burn: 'burn_rate' },
    { when: 'phase == liquid && temperature >= boiling', become: 'gas' },    // 变成“它的”气态
    { when: 'phase == liquid && temperature <  melting', become: 'solid' },
    { when: 'wetness > 0', raise: { ignition: 'wetness * 40' } },            // 湿的东西更难点燃
  ],
})
```

- 物质表从 `xengine.dynamics.material` 移到 matter；dynamics 读其中的力学列（修订 D-133 的“物理材质表归 dynamics”，已确认）。理由：表是物理、化学、元胞三者共用的，放在最下面才不成环；化学性质不该由动力学包拥有。
- 载体的适配放在载体一侧，以 feature 选择：`xengine.cellular` 的 `matter` 特性把程序降到格点程序；`xengine.dynamics` 把接触与重叠对交给 matter。matter 不依赖它们，元胞内核本身仍然不含任何材料规则（D-132 不变）。

### 6.4 四种载体（D-166）

| 载体 | 实例是什么 | 相邻关系 | 权重 | 典型用途 |
|---|---|---|---|---|
| 格点 | 一格 | 邻域 | 1 | Noita 式像素世界、局部的高精度区域 |
| 物体 | 一个刚体、软体或其上的一块表面 | 动力学宽相的接触与重叠对 | 接触面积或重叠体积 | 塞尔达式的箱子、草丛、武器、角色 |
| 粒子 | 一个粒子 | 空间哈希的近邻 | 距离核 | 火星、水花、飞散的像素 |
| 环境场 | 稀疏粗网格上的一个采样点，或一个解析场 | 实例所在位置的采样 | 1 | 风、气温、雨、日照 |

同一份规律在四种载体上求值。远处用物体和粗场，近处或需要时用格点：这是规则不变的表示切换，和 hanim 的多表示选择是同一种思路。

### 6.5 一步的四个阶段

```
每个 tick（在动力学的积分之后）：
  1 收集   对每个相邻对和每个场采样，按传输律算通量（热、湿、电荷……），累加到两端（成对对称）
  2 反应   对每个实例，按反应律判定，产生状态增量、产物、放出的量
  3 提交   积分状态，按转换律做相变与材料变换，饱和，记录变化与因果
  4 发出   事件（点燃、熄灭、冻结、融化、导电、碎裂）；场源（火向温度场和风场放热与上升气流）；
           对动力学的力（浮力、风压、爆炸冲量）在下一个 tick 生效
```

- 每个阶段是一次批量调用（D-65、D-66），有 trace 与预算。
- 随机性用按（种子、tick、实例）取值的计数器式随机数，和遍历顺序无关。

### 6.6 元胞内核 v2：分阶段的格点程序（D-167）

现在的内核能表达“按邻域计数改写本格”，这做得出生命游戏和简单的蔓延，做不出落沙、液体找平、热扩散。升级为分阶段程序，每个阶段都是同一份 Slang 源码的 CPU 参考与 GPU 实现，逐位一致：

| 阶段 | 新增的表达能力 | 用来做什么 |
|---|---|---|
| 聚合 | 邻域上对某通道求和、最小、最大（现在只有计数） | 邻居的平均温度、周围有没有氧 |
| 反应 | 写入可以是聚合值的线性式；查材料性质表 | 燃烧、放热、相变 |
| 传输 | 成对对称的定点流量 | 热扩散、湿度渗透、电荷传导 |
| 交换 | 2×2 块内的置换，块的偏移按 tick 在四种位置间轮换；置换由密度、相态、速度决定 | 落沙、液体流动与找平、气体上升、油浮于水 |
| 提交 | 饱和、阈值转换、变化块掩码 | 稳定性、脏块 |

- **为什么用块划分交换**：每格在一个 tick 里只属于一个块，所以不存在两格抢同一个位置的仲裁问题；交换天然守恒；块与块之间无依赖，可以任意并行，也可以整个放到 GPU。Noita 自己用的是块内顺序扫描加棋盘式分块，手感好但依赖顺序；我们先用块划分，手感由一 tick 多个子步和速度通道补，并与 Noita 并排对照（D-135）后再决定要不要加顺序扫描的 CPU 调度。
- **稀疏活动域**：世界按固定大小的块组织，块记录“上一 tick 有没有变化”；不变的块休眠，被邻块的变化唤醒。大世界只为活动的部分付费。块的大小、休眠与唤醒是全局约定，物理的休眠岛和实体的流式加载用同一套词汇（§7）。
  - 落地时的判据（T1.6，2026-11-13）：光看“上一 tick 没变”对交换阶段不够——切分每 tick 换位，横向扩散还取决于一次随机选择。块要在四种切分下都被看到“没有任何一个 2×2 块可能移动（不论随机结果）”才休眠；规则与传输阶段与时间无关，一个不变的 tick 就够。变化唤醒的范围是程序的读取半径（`reach`：halo，有交换时至少 1 格），绕回边界照样算。这样稀疏执行与全量执行逐位一致（测试并排比较每一步）。活动状态是调用方持有的每块一字节，随检查点、分叉一起保存。
- 元胞内核仍然只认整数通道和规则，不认识材料；材料语义全部来自 matter 的降级。

### 6.7 耦合（D-133 契约 3 的具体化）

| 耦合 | 做法 |
|---|---|
| 刚体 ↔ 格点 | 刚体的占位印进格点作为边界；格点的压力、浮力、阻力积分成作用在刚体上的力；属于刚体的格被毁后，由轮廓提取、简化、凸分解重算形状，脱落的格变成粒子 |
| 物体 ↔ 环境场 | 物体在所在位置采样场（风压、气温、雨量），并作为场源写回（火的热与上升气流） |
| 格点 ↔ 粒子 | 被撞飞或喷出的格变成粒子，落定后变回格（质量守恒） |
| 化学 → 物理 | 相变改变力学性质（冰面的摩擦、烧断的绳的约束）；爆炸是极高的燃速加气体膨胀，以冲量进入动力学 |
| 物理 → 化学 | 接触与重叠对是物体载体的相邻关系；速度影响传输（风助火势） |

### 6.8 表现配方：状态 → 外观、粒子、声音（D-168）

物体和格点只带材料与状态。看到和听到的东西由配方决定：

| 状态 | 外观（xrender） | 粒子与运动（hanim、xrender.particle） | 声音（xengine.audio） |
|---|---|---|---|
| 燃烧中 | 自发光随燃烧进度，表面炭化 | 火焰、烟、火星；热浪扭曲 | 噼啪声，强度随燃速 |
| 湿 | 变暗、粗糙度降低 | 滴水 | — |
| 冻结 | 偏色、霜 | 冷雾 | 碎裂声（事件） |
| 带电 | 边缘电弧 | 电火花 | 嗡鸣 |
| 相变 | — | 蒸汽、凝结 | 嘶声 |

- 配方是数据，属于“世界风格包”，与 omui 的风格包同一种机制：换包改变观感，规则与状态不变。
- 配方由游戏层的一个小适配读取并分别调用 xrender、hanim、audio；三者互不依赖。
- 2D 像素世界的上屏沿用 `xengine.cellular.present`（一张图、一条命令、只传变化的块），通道到颜色、自发光的映射进配方。
- 这一条保证“自动得到好的效果”不止在逻辑上成立：新材料填了性质，就有默认的着火、淋湿、结冰的样子和声音。

> 实现记录（2026-11-13，T1.10）：配方的“外观”一栏已落地，粒子与声音两栏留给 M6.5。归属分三处：格点内核定义“算出来的颜色”是什么（`cellular::Shade`：按键通道查底色、颗粒感、沿通道量程的着色、发光；整数算术写进内核契约，CPU 与设备同一条规则）；`xengine.matter` 的 `appearance` 特性是配方数据（`*.appearance.omui.ts`、`defineAppearance`），对着程序准备成一份只有数字的 `Look`，不认识渲染器；`xengine.cellular.present` 的 `matter` 特性把 `Look` 降成 `Shade`，发光单独成一张图，`draw_glow` 用模糊加叠加画出辉光。配方与规律同一条纪律：状态只读通道与性质，不点名材料（`by: "material"` 被拒绝），所以岩浆发光是因为它 1600 K，新加的一行材料按相态得到底色，并和别的东西一样被烧焦、淋湿、结霜、烧红。配方包可以服务多个世界：包里上了色而世界没有的材料只记入 `unused`，不算错误。标准包为“火焰看得见”补了一条“热空气”状态（气体 420–900 K）：燃烧只发生在可燃格里，火焰的形状是它上方的热空气。

### 6.9 确定性分档

| 部分 | 档位 | 依据 |
|---|---|---|
| matter、cellular | 跨平台逐位（整数与定点） | 元胞内核已是整数通道，CPU 与 GPU 逐位一致已有 |
| 2D 刚体、XPBD | 跨平台逐位为目标（确定性数学、禁用 fast-math 与浮点收缩） | AGENTS §4；Box2D v3、Rapier 也做到了，不算差异点 |
| 3D 刚体 | 同二进制确定为底线，跨平台逐位看适配的引擎 | §6.11 |
| 装饰性的粒子与效果 | 不要求 | 不进权威状态 |

权威状态只走确定性路径（D-133 契约 5），因此整个世界可以快照、回放、回滚、分叉。

### 6.10 解释与分叉（D-169）：Agent 契约在世界主体上的实现

- **因果记录**：提交阶段记下“哪个实例的哪个通道越过了哪个阈值，量来自哪些邻居或场”。用内核的分级环形缓冲（§3.2），开发模式全开。
- **`world.explain`**：给一个实体或一格，回答它当前状态的因果链，例如“箱子在第 812 tick 点燃：温度 570，热量来自相邻的草（已燃烧）和风场向东 3”。
- **`world.branch`**：从当前快照分出一个世界，注入假设的输入，快进 N 个 tick，返回状态差异与事件；原世界不受影响。Agent 用它试玩、找卡关、做平衡，也用它在行动前预演（与 UI 的“先预演，再授权”是内核里同一个预演能力）。
- **语义投影**：Agent 观察世界先读语义（实体、材料、状态、关系），需要看才截图，需要精确才读 ID 缓冲。

### 6.11 求解器族与中间件（D-170，按 D-176 改写）

- **3D 刚体、角色控制器、布娃娃**：经 mwrap 接 Jolt（MIT；公开资料称支持跨平台确定模式与状态存取）。这一项按构造与最强者持平。
- **2D 刚体**：M6.2 的第一个检查点先评估 Box2D v3（MIT）的适配。它是 2D 领域最强的求解器，Noita 当年也是用 Box2D 做像素刚体的。评估只看硬约束：世界状态能否快照与恢复（回滚与 `world.branch` 要用）、跨平台确定、Web 体积。通过就适配；不通过就自研，并以 Box2D v3 的官方基准场景为低线。
- **软体**：2D 的 XPBD 已有，继续自研；3D 先用 Jolt 的软体。
- **契约、阶段管线、操作目录、CTS 是我们的**，适配器只是求解器族的一种实现，要通过的验收就是 Agent 契约 CTS：快照与回放、分叉、接触解释、稳定地址。达不到的项如实报不支持。
- 超过的部分放在交叉特性上：与格点和化学的耦合、可解释、可分叉（§14.2 的 P6、P7）。

### 9.3 涌现测试集（验收的核心）

每一条都是一个无头场景加状态断言，全部只靠通用规律成立，规则数据里不出现成对的材料名：

| 3 | 水浇灭火并变成蒸汽；蒸汽上升，遇冷凝回水 | 传热、沸点、气体上升、熔沸点转换 |
| 4 | 熔岩遇水凝成岩石并冒蒸汽 | 传热、熔点、沸点 |
| 5 | 冰靠近火融化；水在低温下结冰 | 传热、熔点 |

> 实现记录（2026-11-13，T1.7、T1.9）：1–8 与 12 在 CPU 格点上通过（`modules/projects/xengine/kernel/matter/cts/tests/emergence_test.cpp`，同一份标准定义：17 种材料、19 条规律、0 条点名材料；lint `matter`）。场景暴露并已补上的模型缺口，全部以数据或通用能力补，没有为场景写专门规则：燃烧加热以火焰温度为上限（`flame` 列；此前封闭空间里木火能把石头烧成熔岩）；沸腾吸收、凝结放出潜热（`latent` 列、`phase_heat` 通道；此前浮油下的水在燃烧的前十分之一就烧干）；格点的常量边界可以是一个“浴”（每通道一个值，`open_to(空气)`：世界向外散热；此前封闭世界留住全部热量，蒸汽永不凝结）；火药是一行性质（燃速、火焰温度、自带氧、`blast`），压力是一个会扩散与消退的量，`cellular::push_on` 把它对一块区域的净推力读出来交给物体。尚存：`thermal` 的量程（空气 1 到铁 8）压缩了真实的导热差距，所以第 7 条放在封闭房间里；压力按扩散传播而不是波，只推物体、不推散落的格；每格热容相同；每条的 Agent 侧断言（`world.explain`）随 T1.11。测试集之外自己出现的一条：往盛满水的池子里丢沙，水漫过池壁流到木条下，木头受潮后 700 K 点不着。

### 9.4 暂缓的事与架构预留（D-177）

维护者（2026-11-12）：目前先不做，不代表以后不做；基础设施和架构设计要能支撑以后去做。

**原则**

1. 暂缓项和低线项一样进特性表，状态是“暂缓”，写明四样：现在的替代、以后做需要什么、现在就要留好什么、重启条件。
2. 预留只留三样东西：**接口上的扩展点与能力查询**、**数据格式里带版本的位置**、**管线里可插的阶段**。不预先实现。
3. 每个预留都要有一个**现在就在用的消费者**，或者不占任何成本；两样都不满足就不留，避免为想象中的需求做设计。
4. 设计评审增加“**不堵路**”检查：渲染、动画、设备、平台、模拟的设计，逐条对照下面“现在就要留好的”。
5. 以后启动时照样走中间件规则（D-176）和 Agent 契约（§3.3）。

**虚拟几何（Nanite 一类；最强者 Unreal 5）**

- 现在的替代：meshoptimizer 的细节层次与分簇剔除（RN5）。
- 以后做需要：带误差的簇层次、GPU 驱动的剔除与间接绘制、可见性缓冲加延后的材质着色、几何按页流式加载。
- 现在就要留好的：
  - 网格资产从第一天起按“簇”存储，格式带版本，留出簇层次与误差的位置。现在的消费者：RN5 的分簇剔除。
  - ID 缓冲写到实例、簇、三角形这一级。现在的消费者：Agent 的像素溯源（RN9）。**它正是可见性缓冲的基础**，所以为 Agent 做的这件事同时铺好了这条路。
  - 材质按 pass 组合（§5.2 已是如此），可以新增“可见性着色”这种 pass。
  - 设备的能力查询：`mlibs.rhi::Caps` 已有，缓冲已有间接绘制的用途；网格着色器等以后作为可选能力加入，不改接口的形状。
  - 资源的身份、版本、租约契约要容得下按页加载。
- 重启条件：有作品的三角形量超出分簇剔除的预算；或 Web 的设备能力跟上。
- 届时可复用：meshoptimizer 自带的簇层次构建。

**全动态全局光照（Lumen 一类）与硬件光线追踪（最强者 Unreal 5）**

- 现在的替代：烘焙光照图与探针（RN6）。
- 以后做需要：光栅之外的场景表示（距离场、加速结构、表面缓存、辐射探针）、时间累积与降噪、设备的光追能力。
- 现在就要留好的：
  - 着色里的间接光是一个接口，实现可换：常量环境光 → 烘焙与探针 → 以后的动态方案。现在的消费者：环境光，随后是 RN6。
  - 前置 pass 输出深度、法线、速度、ID。现在的消费者：抗锯齿与放大要速度，Agent 要 ID。
  - 渲染图支持跨帧保留的历史资源。今天的纹理池只有“若干帧不用就销毁”，没有显式的历史资源；时间性抗锯齿是它现在的消费者。
  - 场景抽取给出稳定的实例 ID 和每帧的变更列表，别的场景表示可以由同一份抽取结果增量构建。现在的消费者：剔除、Agent 的语义投影。
  - 光追是 `Caps` 里的可选能力，接口放在 `mlibs.rhi`。现在的 SDL_GPU 后端按公开资料不提供光追，届时要加一个后端；后端由宿主注入，渲染器不用改。
  - `mlibs.geom` 的距离场与 BVH。现在的消费者：物理与空间查询。
- 重启条件：有需要动态光照变化的作品；或有许可合适的开源实现可以复用。

**主机平台（最强者 Unity、Unreal）**

- 现在的替代：桌面、Web、移动。
- 以后做需要：各主机的图形后端、宿主、平台服务与认证要求；厂商的工具链；保密协议下不能开源的代码。
- 现在就要留好的：
  - 后端、宿主、平台服务都做到“接口在开源仓，实现可以在仓外”：`mlibs.rhi` 的后端、omui 宿主的接缝（R1）、mpal 按用途划分的服务。现在的消费者：三个后端、四个宿主、仓外消费者探针。
  - 着色器统一由 Slang 产出，可以输出 HLSL 交给厂商的编译器。
  - 脚本是解释执行的 QuickJS，运行时不生成机器码（主机通常禁止）；可选的原生化（D-146）可以完全不带脚本引擎。
  - 每帧零分配、内存有预算（AGENTS §4 已是规范）。
  - 手柄优先的焦点导航（R4）。
  - 发布构建可以关掉 Agent 端点与开发设施（配置已有）。
- 架构解决不了的风险：厂商工具链对 C++23 模块的支持可能滞后。能做的只是内核包不依赖最新编译器才有的特性（C++26 反射已经限制在 omui 的 reflect 包）。
- 重启条件：有要上主机的作品和相应的开发资质。

**动作匹配（最强者 Unreal）**

- 现在的替代：动画状态机加混合（§14.2 动画表的 M4）。
- 以后做需要：带特征的姿态数据库、最近邻搜索、惯性化过渡、轨迹预测。
- 现在就要留好的：
  - “选择下一个姿态”是一个可插的阶段；状态机是它的第一个实现，动作匹配和学习型的控制器是以后的实现。
  - 任何片段都能按（片段、时刻）随机取姿态。现在的消费者：跳转与预览。
  - 根运动与速度是通道。现在的消费者：角色移动。
  - 过渡是混合算子，可以新增惯性化。现在的消费者：交叉淡化。
  - 片段带标签与标记；离线提取特征走“准备与执行”的约定。
  - `mlibs.compute` 以张量为一等公民（D-134 已定），学习型的控制器以后可以建在上面。
- 重启条件：有需要高质量移动动画的 3D 角色作品。

**工程与科学计算级的仿真（最强者是各专用软件）**

- 现在的替代：图形级的实时模拟。
- 以后做需要：双精度与误差控制、经过验证的求解器、单位、稀疏线性代数、自适应网格、高性能计算的后端。
- 现在就要留好的：
  - 档位声明里已经有“精确”这一档（`mlibs.simulation` 的 `Fidelity::accurate`，代码里已有）。
  - 求解器族是插件，可以是外部求解器的适配器（D-176）。
  - 性质列带类型和单位（§6.3）。
  - 数据模型不把标量类型写死成单精度。
  - 可微分的位置已经预留（D-133 的契约 7）。
- 重启条件：有明确的工程用例和可用来验证的数据。

## 14. 水平目标、中间件复用与应用场景

### 14.1 策略：与 UI 框架同一个标准（D-175）

沿用[Agent 时代收敛方案 §3](2026-11-09-agent-era-ts-first-convergence-design.md) 给 omui 定的办法，推广到每个引擎：

- **低线**：每一项特性至少与该项最强者持平（＝）。“最强者”按项来定，不是一个对手比到底。
- **亮点**：交叉特性要超过（↑）或远超（★，对方没有，或差距在数量级上）。
- **暂缓**（⏸）：目前先不做，不代表以后不做。必须列出当前的替代、架构预留和重启条件（§9.4）。没有“永远不做”这一类。
- **等级**：✗ 未达低线　＝ 持平　↑ 超过　★ 远超　⏸ 暂缓　？ 没有数据。带 * 的有实测或已通过的验收，其余是现状判断或目标。
- **期**：这一项在哪个阶段达到目标。低线是目标状态，不是一次交付；每个阶段只关当期的项，并按并排对照（D-135）更新这张表。
- **怎么达到**：自研，或复用中间件（§14.3），或两者。

**四组交叉特性**（各表里标 ★ 的行都属于它们）：

| 组 | 内容 | 为什么别人难追 |
|---|---|---|
| X1 全栈的 Agent 原生 | 六个原语在每个引擎里都有，同一套契约与 CTS | 别人的状态、能力、授权、时间是分开的，只能外加适配 |
| X2 全栈确定 | 处处可回放、预演、分叉 | 要求从数学、时间到求解器都不读墙钟和全局随机数 |
| X3 同一套渲染、动画与语义 | UI 与世界共用渲染器、动画引擎、截图与溯源 | 别的引擎里 UI 是另一个子系统 |
| X4 不写死的涌现规则 | 规律只写性质；状态到表现由配方决定 | 通用引擎没有这一层，专用游戏的实现不可复用 |

### 14.3 中间件复用规则与候选（D-176）

**规则**

1. **默认复用**：一个领域里有顶尖的、独立的（不绑定某个引擎）、许可合适的中间件，就经 mwrap 复用，不自研。这是 D-56 在引擎上的延伸；仓库已经这样做了（SDL3、QuickJS、HarfBuzz、SheenBidi、Opus、miniaudio、libvpx、libwebp、libpng、md4c、AccessKit）。
2. **四个硬约束**，过不了就不用：
   - Agent 契约：适配后能通过契约 CTS（至少快照与回放；缺的项如实报不支持并有补齐计划）；
   - 确定性档位：权威状态用到它时，要满足该档位；
   - 许可：按 D-83（不用 GPL、AGPL；LGPL 只作可选的动态插件；MPL 不修改即可）；
   - Web 可构建，体积进预算。
3. **在契约之下**：中间件只在一个 owner 包里出现，按 feature 链接；对外是我们的数据模型、操作目录和 CTS。上层不得直接使用它（lint `thirdparty`）。
4. **不整体复用的三类**：会丢掉交叉特性的（整个渲染器、整个 UI 框架、整个游戏引擎）；本来就是差异化核心的（matter、cellular、Agent 内核、hanim 的内核）；已有对照证据不落后的（2D 光栅）。
5. **自研要有证据**：过不了硬约束才自研；自研以该中间件的基准为低线，持平之前不得对外宣称。
6. **缺的能力先向上游贡献**，其次在适配层补，最后才分叉或自研。

**候选**（许可与能力是记忆中的公开信息，引入时按 D-83 逐个核实）

| 领域 | 中间件 | 许可 | 归到哪个 owner 之下 | 要先核实的 |
|---|---|---|---|---|
| 3D 物理 | Jolt Physics | MIT | `xengine.dynamics` 的 3D 刚体族 | 确定模式、状态存取、wasm 体积 |
| 2D 物理 | Box2D v3 | MIT | `xengine.dynamics` 的 2D 刚体族 | **有没有世界快照与恢复**；跨平台确定 |
| 寻路 | Recast／Detour | zlib | 游戏层的导航 | 确定性（寻路结果进权威状态时） |

### 14.4 整体

- **每个引擎的每一项都以该项最强者为低线**；达到低线的主要办法是复用顶尖的中间件，其次是有对照证据的自研。
- **超过的部分在四组交叉特性上**（X1–X4）。它们没有直接对手，但目前只有 UI 一侧和 2D 渲染、动效有证据，其余是本方案要去证明的。
- **定位**：一套从 UI 到世界都 Agent 原生、全栈确定的引擎与框架体系；每个部分不输该领域最好的，合在一起做到别人做不到的。
- **现在离这个目标的距离**（如实）：特性表里标 ✗ 和 ？ 的占多数；已有 * 的集中在 2D 渲染、UI 动效、确定性、Agent 的能力对照。
- **决定成败的三个条件**：
  1. 节奏：硬门和并行上限守得住；
  2. 证据：每一项都测出来并入台账，没有数据的不算持平；
  3. 真机与真实使用者：GPU 在真实硬件上验证，有第一个外部的真实应用或游戏。

场景是六个原语和上面这些能力的应用，不是定位本身。

| 场景 | 用到的系统 | 何时具备 | 注意 |
|---|---|---|---|

| 互动教学与科普（物理、化学沙盒） | matter、cellular、dynamics、omui | M6.1–M6.2 | 是图形级的模拟，不是科学精度 |

### 14.6 不确定性

- 最不确定的三项：像素世界的手感（C1）；3D 在 Web 上的体积与真机性能（RN2、RN8）；模型对新 API 的一次写对率。
- 中间件的许可与能力没有在本次核实；Box2D v3 的世界快照是 P1 选型的关键。
- 标 ★ 的每一项都对应一个要做的对照实验，做出来之前只算目标。
