# 核心工具与应用：人和 Agent 共用的创作、控制与验收

2026-11-04。状态：**产品／实施讨论稿**，不是下列工具均已实现。配套[顶层架构](2026-11-04-multi-engine-product-architecture-design.md)、[引擎细案](2026-11-04-omui-engine-framework-architecture-design.md)和[官网方案](2026-11-03-openmui-site-redesign-implementation-design.md)。要求：工具基于公共基础设施开发，后续作为真实应用及框架／引擎场景验证；人使用可视化界面观察／审查／控制，Agent 直接通过 openas 语义完成开发、设计、编曲等操作。

## 1. 选择六类核心工具，复用一套工作台基础

建议把已有 Inspector 逐步发展为轻量工作台：承载项目／资源浏览、选中对象、命令入口、任务结果、变更历史、诊断与 profile。它是可选工具基础，不是引擎必须链接的运行时。不同编辑器复用这些功能，领域模型仍在各自引擎或领域库。

| 工具／应用 | 用户能完成的真实任务 | 消费的公共能力 | 主要验收对象 |
|---|---|---|---|
| **1. Inspector／调试与性能工作台** | 连接运行中的应用或引擎，定位对象和源码，查看状态／资源／执行阶段；暂停、单步、回放、比较 profile，导出问题复现包 | provider、openas、trace／log／session、引擎控制；omui 构建界面 | 无 UI 的引擎也可连接；人与 Agent 查询同一状态；请求到帧／资源／阶段可关联，观测有有界成本 |
| **2. UI／交互／风格设计器** | 从组件库构建可使用的面板，编辑约束、状态、部件、主题与默认动效；预览多种视口及交互，导出可构建工程 | omui、组件契约、布局、hanim adapter、通用风格、绑定生成器 | 默认组件动画组合公共库；呈现／命中／焦点／语义一致；更换风格无组件分叉；源码和设计模型往返保持公开语义 |
| **3. 动画／场景／时间线编辑器** | 用公开 HObject 和库完成形状、字形、像素、骨骼等所选域的动画；组合材质／效果；拖动时间线、打断、预览与离线输出 | hanim core／object／library／effect／engine、共享 renderer、内容与编解码库 | 三角→圆等真实几何插值、效果叠加、资源持有、确定性 seek；只用 hanim 的工程可独立运行，不依赖编辑器或 UI |
| **4. 音频／MIDI／编曲工具** | 编辑轨道、音符、速度图、自动化及效果总线；按能力录入／路由 MIDI，试听、保存和离线输出 | 音频／DSP／音序、MIDI 库、sample／beat 时间映射、设备后端 | 人编辑的片段可由 Agent 查询和改编；事件、tempo、自动化与渲染结果一致；音频回调不等待 GUI／Agent，设备与离线结果分别验证 |
| **5. 模拟／材料／元胞实验室** | 用区域画刷和规则配置材料／场；注入输入、固定步长运行、单步与检查点回放，观察反应和计算成本 | 模拟 core、物理／化学／元胞模型、spatial／field、计算算子、renderer | 大 field 批量更新，不逐像素建 UI／HObject；跨 chunk 边界一致；输入重放与检查点正确；Noita 类负载按引擎细案验收 |
| **6. 材料／Shader／算子工作台** | 编辑材料或算子，编译变体并查看诊断／参数，比较 CPU 参考和设备结果，检查资源读写、执行计划及成本 | 公共材料／shader／计算库、构建插件、RHI／设备、trace／bench | 材料供 UI／动画／场景共同使用；设备差异有能力结果；编译、热重载、误差及 GPU 时间可审查，不把提交时间当执行时间 |

这是六类领域工具的产品边界，不要求同时开发六个独立大型程序。可先共用一个工作台宿主和选定面板，也能各自提供独立 CLI／无界面任务；领域库不能依赖这个工具宿主。通用编辑功能有一个 owner，工具按需组合，不把全套编辑器放入默认 SDK。

后续要求覆盖成熟独立游戏与素材编辑，完整补充见[游戏工具／素材工作流](2026-11-04-indie-game-tools-assets-design.md)：在这六类基础上增加素材资源工作台、场景／关卡设计器、玩法／数据／叙事工作台，形成九类可组合工具；角色／VFX／游戏音频／测试和发布维护扩展原有工具及公共底座。六类基础不等于游戏制作链完整。

## 2. 编译器与构建工具链是公共基础

复用现有 omui-gen、shader 编译工具及 mcpp 构建插件，逐步形成可被以上工具直接调用的版本化编译／诊断接口：

| 编译／处理能力 | 输入与产物 | 归属与边界 |
|---|---|---|
| 规范／契约／绑定生成 | 规范、组件／native 契约 → schema、ABI、模块与多语言 façade | 既有生成器及对应标准／契约 owner；一个生成源，不在每个设计器复制解析和生成 |
| 动画／场景准备 | 公开对象／资源／时间编排 → 校验结果、准备计划和资源要求 | hanim／内容库；编辑器调用公共 prepare／compile，CLI 可运行相同输入 |
| 材料／shader／kernel 编译 | 公共参数与源码 → IR／目标变体、反射／绑定、诊断与能力元数据 | shader／计算子系统及 mcpp 构建插件；编译依赖和运行时依赖分开 |
| 内容与资源处理 | 字体、图像、声音及场景资源 → 目标所需资产与引用清单 | 既有内容／媒体／资源包；共享处理器、缓存键及租约 |
| 模型／执行计划准备 | 规则、算子和管线 → 类型／资源校验、执行计划、变体与成本解释 | 对应模拟／计算／渲染产品；共用真正相同的机制，保留不同领域 IR |
| 构建、运行、测试与打包 | mcpp.toml、源码、选定目标 → 构件、报告与输出包 | mcpp 及插件；工具消费其 JSON／退出码／构件信息，不另造项目构建系统 |

不开发第二套 C++／GPU 编译器替代成熟工具链。这里的编译能力是项目自己的契约／领域准备、资源处理及后端集成。后续确有 DSL 时，先证明业务需求与公开契约，再增加前端；不为可视化编辑器发明只能由它读取的语言。

缓存键至少关联输入内容、资源与契约版本、编译器／插件版本、目标能力与选项。错误保留文件／对象／参数位置；重编译失败继续保留上一份有效资源，成功后在明确提交边界交换。GUI、Agent、CLI 和 CI 读同一份诊断，不各自解析不同的自由文本。

UI 仍遵守原生 builder／视图代码优先。设计器的往返验收限定于公开可编辑的视图／资源子集，明确源码映射、生成区和手写逻辑边界，输出可审查的源码变更；超出可解析范围时保留源码与诊断。动画、音频、模拟内容分别使用所属公开模型，工作台面板状态另存。不能用一个编辑器私有大文件取代这些公开入口。

## 3. 从底层自然形成双视角

**所有工具完整支持仅CLI／API运行，GUI是可选前端。** 工程创建、导入／编辑、编译、运行、测试、调试、保存、输出及其实际支持的任务均能在不开GUI时完成；不能将核心操作只放在菜单或要求屏幕点击。CLI／API提供类型化参数、结构化结果、进度与退出码，GUI调用同一操作。已有工具是否已完全达到此要求需逐项验收，本文不把当前入口存在记为全任务完成。

~~~mermaid
flowchart TD
    Human[人：GUI／适用的 TUI] --> Control[openas actor／verb／effect／grant／decide]
    Agent[Agent：CLI／local API／所选桥接] --> Control[openas actor／verb／effect／grant／decide]
    Control --> Commands[类型化公开操作与查询]
    Commands --> Model[公共项目／领域模型及事务]
    Model --> Engines[公开引擎／资源／计划接口]
    Engines --> Records[状态版本／结果／trace／日志／产物]
    Records --> Human
    Records --> Agent
~~~

图示表示共同操作边界，不要求人点击先转成 JSON，也不要求每次采样／每个 DSP 算子经过 openas。GUI 输入和 Agent 请求在控制面进入同一操作实现；引擎内部热路径仍用 native 数据和按批调用。

需要从底层提供的契约包括：

1. **稳定寻址与模型**：项目资源、对象、部件、轨道、规则或算子有稳定标识和版本；UI 面板、屏幕坐标和显示文本不是唯一操作地址。运行时句柄与可保存的项目资源 ID 分开。
2. **可发现操作**：provider 描述实际支持的查询、参数、能力、约束、效果类别和结果。工具加载已选模块的 provider，独立引擎不为了接入 Agent 导入 omui Runtime。
3. **同一事务实现**：鼠标拖动、快捷键、TUI、Agent 命令和 CLI 修改同一模型；包含前置版本、验证、批量编辑、提交和记录。高频拖动或参数自动化可合并／批处理，不逐像素发送 JSON。
4. **公共操作状态**：长任务区分 accepted／applied／settled，关联 request／transaction／object revision／artifact，允许观察进度、取消和最终结果。取消后的有效状态和已产生成果明确。
5. **可观测结果**：参数差异、结构差异、预览图／帧、波形／事件、模拟状态摘要、诊断和 trace 关联同一操作；人和 Agent 可查询同一证据，记录哪些执行了、哪些未完成。
6. **时间与历史**：业务 undo、动画 seek、模拟检查点恢复、音频 transport 分别定义；可逆编辑共用事务历史。已播放的声音或已发生的外部设备动作不能靠撤销项目编辑“抹掉”。

**openas 负责共同的身份、动作效果、授权决定与报告语义；领域模型和操作参数契约由各产品负责。** 不能把一个 openas verb 清单当作完整编辑器数据协议。这里引用现有 openas 0.2 的 actor／Verb／Effect／Grant／decide 和报告种类；新增 provider 操作、事务与诊断字段属于实现契约提案，不擅自变更 OpenLifa 标准。

默认开发配置预授权已注册的开发能力，方便 Agent 建模、构建、调试与验证；最终作品默认保留人和 Agent 双视角，由开发者、宿主／用户和会话限制范围。请求关联可信 actor 和资源作用域，调用同一 decide 流程；独立工具不各自实现另一套授权。所选 transport、MCP 或网络桥接是适配，不是每个基础库必须启动的服务。

## 4. 人的可视化也是过程与效果的审查界面

人类工具既能主动编辑，也能观察 Agent 正在做什么。共用工作台应呈现：

- 正在执行的任务、目标对象／资源和所属 actor，操作处于准备、应用还是完成。
- 输入参数、基于哪个版本、准备后的差异、校验结果和实际效果；按任务展示合适的结构／图像／音频／数值证据。
- 可支持的暂停／单步／取消／恢复／撤销，及实际可逆范围；控件调用同一公开操作。
- 当前能力、资源成本、设备与后端、错误位置和关联 trace；不只给“成功”或一张最终截图。

Agent 可以查询相同信息，拿到结构化摘要、错误与可定位资源，并按需要读取具体预览／trace。大图、场数据和音频使用有界读回与资源引用，避免无条件把全部数据放进每次响应。

界面自身用 omui 的组件、默认动画、风格和 Agent 接口；工作台因此同时验证框架的真实工具负载。可视化构图须简洁、渐进披露；动作和状态不应藏在只有 Agent 知道的私有入口里。

### 4.1 无GUI的视觉审查是所有工具的公共能力

Agent可通过CLI／openas控制入口请求离屏输出，既能渲染素材／场景／动画当前帧，也能按需渲染共享模型生成的工具面板或诊断视图；无需打开窗口。无界面运行需要所选渲染／内容后端，能力不足明确失败。保持最小CLI依赖可通过可选离屏renderer／worker交付实现，不能为了截图让所有纯计算库导入UI。

请求至少包含：目标资源／对象／视图和版本，时间或tick，视口／相机、逻辑区域或目标像素区域、DPI／缩放、主题／语言／档位及所选后端。UI／场景区域要明确坐标系与裁切、映射和效果外扩；可先查询可渲染目标、bounds和能力，再请求具体区域。

输出包含PNG／WebP或明确格式的像素产物引用，以及实际对象／资源版本、采样时间、输出区域／尺寸、后端／档位、就绪状态、诊断和关联请求。像素通过有界binary／文件／资源通道交付，不把大RGBA塞进每条JSON响应。等待字体／资源、GPU fence、读回或异步任务时提供可等待状态；失败不伪造成功图像。

捕获必须使用真实引擎／renderer、相同状态、资源与呈现规则；截图不反向修改业务状态。运行中捕获在确定版本／采样边界执行；离线可显式seek／重放。只渲染一个资源与捕获某个真实GUI后端的最终呈现分别记录，前者不能证明浏览器／设备合成等未运行路径。

验收至少覆盖：无显示环境下CLI完整任务；GUI未启动而指定目标／区域可得真实像素；全图裁切与同状态区域输出对应；任意时间重复输出一致；人与Agent读到同一版本；错误目标／区域／资源未就绪／能力不足明确报告。图像编辑、编曲波形／钢琴卷帘、场景、Shader、Inspector和编译诊断面板均可使用这套能力，不每个工具另写截图器。

## 5. 每类工具的第一条完整验收任务

| 工具 | 第一条真实工作流 | 要保留的证据 |
|---|---|---|
| Inspector | 连接运行时 → 定位一次 Agent 编辑 → 找到资源／阶段 → 暂停单步 → 导出复现包 → 无界面重放 | 请求与 actor、模型版本、trace／log、重放命令及一致性结果 |
| UI 设计器 | 组合一个可使用的设置面板 → 配约束和默认动效 → 换风格／视口 → 人与 Agent 分别操作 → 导出并独立构建 | 工程、公开契约引用、输入／焦点／语义与呈现证据；导出程序不依赖设计器 |
| 动画编辑器 | 创建对象 → 从公开库编排真实形变×材质／效果 → seek／打断 → 输出帧与独立程序 | 资源／计划版本、端点与中间态、确定性回放、能力降档与 CPU／设备结果 |
| 编曲工具 | 人建立片段 → Agent 修改和声／节奏／自动化 → 人审查差异并试听 → 保存后离线输出 | 音符／tempo／路由事件、命令历史、离线音频与指标；实时设备时延单独测 |
| 模拟实验室 | 编辑材料和区域 → 注入确定输入 → 单步观察反应 → 保存检查点 → 恢复重放 → 观察跨区计算成本 | 种子／更新次序／输入、状态摘要／哈希、边界一致性、活动域、资源与设备时间 |
| Shader／算子工作台 | 编辑一个真实材料或算子 → 构建 → CPU 参考对照 → 切换可用后端 → 热重载与失败恢复 → 输出可消费包 | 诊断／反射、目标与版本、数值误差、资源读写、有效旧版保留与重新提交结果 |

这些是各工具首批纵切，不替代 Manim 全范围、Noita 负载、40 项公共动画与20项创意组合、完整音频／MIDI及全部平台要求。创意组合优先取这些可用工具中的工作流，避免官网另写一套展示逻辑；官网内容本身仍按完整方案验收。

## 6. 分期与多后端

1. **基础设施阶段**：优先引擎独立性、公共模型／操作／provider、日志／trace、最小 CLI／Inspector 和可重现测试。利用现有工具，不先建设六套完整编辑器。
2. **引擎纵切阶段**：每项能力先选一个参考平台／后端，建立公共消费者和关键工作流。Web 是首批重点，性能／交付限制从底层考虑；现有 native／Web 回归继续保留。
3. **工具验证阶段**：优先扩展已有 Inspector；随 hanim／omui 公共链路可用，做动画编辑器及 UI 设计器纵切；音频／MIDI、模拟、材料／算子工具跟随对应能力。完整创作工具放在相关底层能力之后。
4. **多目标阶段**：扩展 Web SDK 子后端（如 bilibili Toy）、其它原生／移动后端、TUI 及输出包。共用项目和操作，呈现按能力适配；图像／3D密集工具的 TUI 可以提供结构／参数／诊断／控制视图，不宣称相同视觉效果。

每个工具至少具有 CLI JSON／退出码和 omui GUI；适用时增加 TUI。工程构建配置继续使用 mcpp.toml，领域内容使用公开、版本化数据契约；面板布局可以是工具自己的偏好，不能成为唯一工程事实。导出的作品不链接编辑器，关闭工具后 Agent 仍能操作所选引擎或应用。

## 7. 当前事实与实施缺口

已存在 omui CLI、MCP、Inspector、生成器、shader 构建工具及 UI 的 Agent／trace／log 基础，详见 tools README 和对应包。Inspector 已通过应用 endpoint 显示语义、属性、帧／管线／时钟并控制运行中的 UI。它是可复用起点，不等于全引擎工作台。

仍需实现中立 provider／策略和资源范围、公共事务／诊断契约，以及无 UI 引擎的连接／控制。完整 UI／动画／音频MIDI／模拟／材料算子编辑器、项目往返、跨引擎时钟、TUI 和全部多后端工作流尚未交付。本稿规定真实任务和证据，后续按单一模块归属逐项落地；不以界面或操作名存在替代能力验收。
