# 局部能力中心 × 全局契约协作：统一架构准则

2026-11-05。维护者明确的设计原则，纳入[AGENTS.md](../../AGENTS.md)；具体API、模块拆分和后端仍按各设计review与真实验收推进。与[多引擎产品架构](2026-11-04-multi-engine-product-architecture-design.md)、[hanim可组合／反应IR](2026-11-05-hanim-composable-operators-reactions-ir-design.md)配套。

## 1. 核心准则

**局部围绕本域核心能力建模，以通用底层能力、可控数据、可组合算子／管线和自定义扩展覆盖场景；全局通过公开、类型化的契约与适配组合各系统，共享同职责的基础实现，保留领域语义、时间和实时约束，按需承担依赖与成本。**

这是一套交叉视角：单独看每个系统，它应是完整、通用、可独立使用的产品；放到全局，它又是可与其它系统协作的能力模块。场景越复杂，越需要显式契约和良好的组合能力，不把场景分支堆进内核。

“统一”首先统一设计语言、契约表达、组合／扩展模式、能力与错误、生命周期、观测及人／Agent控制方式。各系统的数据表示、算法、状态和调度仍遵守本域要求。

## 2. 每个模块有自己的核心视角

| 系统 | 局部核心视角 | 可组合能力举例 | 对外输出／协作边界 |
|---|---|---|---|
| hanim | 公开适配的属性／对象／相机／运动／参数都可动画 | 对应、插值、路径、变换、修饰、反应与编排 | 已采样属性／姿态／场、执行计划及控制；业务状态和render资源由其所有者维护 |
| audio | 适用的声音、数据与事件均可作为音源、信号或控制／调制源 | 声源、采样、路由／总线、混合、DSP、包络、自动化与音序 | 音频块、设备／离线输出、分析、时钟与控制；不由GUI帧率驱动采样 |
| renderer | 适配的内容和数据可进入视觉表达／合成 | 2D／3D／文字／粒子／场、材料、相机、效果与pass | 图像／视图／读回和资源能力；不接管业务／玩法状态 |
| simulation／reaction | 选定域的属性／状态按规则与输入演化 | 约束、邻域、连续影响、条件／触发、状态迁移与检查点 | 版本化状态、事件／统计及可重建输入；求解模型为可选模块 |
| UI | 应用的交互／状态以同一语义契约呈现给人、无障碍、Agent和测试 | 组件、布局、输入、焦点、动作、motion和style | 业务／交互事实与公开adapter；作为动画／渲染等能力的普通消费者 |
| compute／HPC | 合适的类型化数据可由批量算子计算 | 数值、几何、信号／场算子、CPU／SIMD／GPU执行 | 数据视图、kernel／执行能力及同步；不拥有UI或某个上层引擎的生命周期 |
| AI／Agent（可选） | 合法观察、约束与任务可生成可校验意图 | 规则／策略、模型调用、工具编排、外部Agent委派 | 带revision／期限的Intent；通过同一领域操作提交，不接管引擎状态或绕过授权 |

“万物可动画／可audio”指开放可适配的数据与处理能力。例如相机pose可供动画控制并作为audio listener输入，温度可映射为色彩或音高；数据映射、单位、采样率和权限仍需明确。身份、资源代次和内部不变量不因此变成任意可写的动画属性。

模块可互相提供能力，但C++包依赖仍保持单向。运行时双向信息交换由中立数据契约、adapter、宿主组合及显式时间边连接，不能形成UI↔hanim↔renderer的静态依赖环。

## 3. 从少量能力组合场景，场景保持在上层

统一模式是：**基础数据／数值 → 本域算子与模型 → 组合／可编排计划 → 可复用配方 → 应用／工具。**

- 先识别目标、属性／端口、输入输出、状态和执行频率；
- 可跨系统复用的算法／存储／调度机制给一个明确owner；
- 本域算法和策略通过稳定契约扩展，用户可提供满足能力要求的自定义算子；
- 常见场景包装为配方，配方仍可展开、观察和重组；
- 从简单入口到高级图／数据描述，都进入同一实现与执行计划。

例如“玻璃按钮进入重力区域并触发声音”应由UI部件／状态、动画、反应profile、材料／renderer及audio触发组合；不在hanim写特定按钮行为，也不在audio重新实现一个按钮系统。组合扩大场景覆盖面，数量清单不能代替通用性、质量和性能证据。

图／端口／版本／存储等公共机制可以复用；hanim的动画IR、audio的DSP图、renderer的资源图仍保留各自语义，通过adapter和宿主连接。统一设计模式不要求audio或renderer依赖hanim播放器，也不要求所有领域使用同一种IR。

## 4. 可控属性与统一算子，保留类型与领域

每个公开目标都有schema、选择器、单位、空间、范围、默认值、版本／所有权和可控制性。位置、焦距、路径点、效果幅度、滤波截止频率、总线增益、材料温度等可以使用一致的描述／控制模式；具体插值、约束和有效范围由域定义。

通用算子／函数可用于不同上下文。例如noise可影响路径、力、材质或声音调制，但需要明确输出尺度／频带／单位及域adapter。算法共享不意味着无类型连接；颜色通道、空间坐标、声道和模拟属性的含义分别保留。

自定义是正式扩展能力：算子声明typed端口、读写集、阶段、状态／时间、后端、数值等级、预算与观测。脚本只构造／控制，热路径执行已准备的原生批次或编译后的kernel。缺少某个后端实现时通过能力／降档契约处理，不假装任意回调都可GPU执行。

## 5. 公共基础按职责收敛，不过度统一

| 候选公共能力 | 复用边界 |
|---|---|
| math／数值／插值／随机 | 已有公共实现及其确定性规则；域算法消费，不各写同名函数 |
| buffer／内存／格式与通道布局 | typed view、stride、位宽／格式描述、所有权与生命周期；声道／颜色／场通道的解释由域提供 |
| time／时间映射 | 单位、时间基与转换／同步契约；保留audio sample clock、animation time、simulation tick及render submission边界 |
| signal／采样／重采样 | 确有共享语义时提取通用算法；音频抗混叠、图像过滤、场重建和精度预算分别声明 |
| task／pipeline／compute／RHI | 阶段／批次与资源依赖、设备能力和同步；domain scheduler仍满足本域deadline |
| trace／log／session／CLI／Agent | 共同事件／查询／版本与结果模式；实时线程使用有界轻量通道，不格式化大日志或执行网络请求 |

位宽、采样、通道等是值得评估的公共基础，不因概念同名就提前造一个巨型通用库。优先复用现有模块和mcpp生态；在明确多个消费者／独立用途、共同语义和收益后提取一个实现。可选库／算法／后端按需引入，不把全部audio／GPU／模拟拖入轻量UI或动画。

mcpp是构建工具，借GPU／HPC构建插件交付运行时库和算子；运行时执行、数据驻留和调度由相应独立模块承担。

核心契约与可选实现按包／feature分离，构建闭包和资产决定体积，运行开关决定已编入能力的使用。可选内置AI不改变默认双用户控制；决策来源可为规则、内置Agent或openas外部Agent。风格包通过token／部件选择／公共effect／motion组合，允许局部scope和混合风格，组件不写按风格名分支。具体边界与反例见[feature／AI／style补充](2026-11-05-features-ai-agent-scoped-style-design.md)。

## 6. audio体现相同思想，同时有独立实时约束

从audio视角，源、信号、参数、路由与效果都可组合、调制和控制：文件／振荡器／流可作为音源，事件触发voice，运动／状态可以经映射控制音高、增益或空间位置。外部环境可提供混响区域或其它控制输入。

自动化曲线可复用公共时间／数值能力，audio按自己的采样时间／block求值，不依赖每个sample调用一个GUI／hanim对象。区分control-rate、audio-rate、跨线程参数更新及sample-accurate事件；从渲染帧输入参数时声明时间映射、插值／平滑及延迟。

音频callback必须遵守无分配、无阻塞／GUI锁／网络／GPU同步等待等本域实时要求。GUI／CLI／Agent经有界命令通道控制，结构更新在合法边界准备／发布。离线输出和实际设备共用领域算法，设备生命周期与调度仍有自己的契约。

本仓库已有独立[openmui.audio](../../modules/media/audio/README.md)及音源／总线／效果、音乐和离线工具原料；本稿不把这些记作完整通用调制图或跨引擎自动化已经落地。

## 7. 属性＋状态＋条件／触发的反应是通用模式

环境场只是影响来源之一。通用反应可来自事件、属性变化／阈值、区域进入离开、接触、邻域、材料组合、时间等。反应契约描述输入／读写集、条件与触发方式、状态迁移／输出、时间／顺序和成本。

| 场景例示 | 同一设计模式中的角色 |
|---|---|
| 动画对象经过区域 | 当前姿态＋响应属性＋场／区域条件→路径／属性／状态变化 |
| 相机遭遇事件 | 相机状态＋触发事件→shake／跟随／镜头参数配方 |
| audio包络／门限／区域响应 | 信号或状态＋条件／控制输入→增益、调制、路由或效果变化 |
| Noita类像素反应 | 材料／温度等属性与状态＋邻域／阈值规则→迁移、扩散或反应；只是通用求解能力的一个场景 |

共同的是契约模式，反应算法和执行由对应域承担。纯插值不必变成事件系统；大规模格点也不必逐像素发事件或调用虚函数。需要的条件／状态可编译成批量mask、数值／邻域kernel与有界状态边。

## 8. 全局协作示例与验收

场景可由模拟产生状态／反应，hanim编排对象与相机，renderer呈现，audio消费映射后的状态／事件，UI与工具负责交互和审查。各系统交换带时间／版本的数据，不共享一团可变世界状态。

宿主明确时钟映射、状态／资源所有权、写入仲裁和发布边界。音频事件映射到sample时间；视觉采样不重复推进模拟或重复发声；相机／运动快照可供renderer和audio各自按合法时间消费。纯函数、可重建状态和外部副作用分别处理。

Agent和人通过相同公开操作／数据控制与观察；工具提供完整CLI／API、可选GUI、结构化报告及实际离屏像素。支持范围与权限按现有多级策略执行，纯库不为Agent控制强制依赖UI或网络。

新增功能的review至少回答：本域核心语义是什么；通用基础／领域插件／上层配方归谁；能否由已有能力组合；是否引入重复实现或依赖环；未使用时付出什么成本；时间／状态／实时语义是否成立；怎样做CTS、性能／资源预算、观测与独立消费者验证。

上述原则指导实现，不替代具体功能验收。当前完整通用IR、反应／调制图、各域adapter及跨引擎工具仍需逐项落地。
