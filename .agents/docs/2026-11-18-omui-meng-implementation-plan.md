# omui 与 meng 的实施方案与任务依赖：做到“达到发布标准、随时可以拆”

2026-11-18 起草，**第一版，草案，待 review**。基线：`0adef252`（PR #1）。它实施[顶层设计](2026-11-18-omui-meng-top-level-design.md)（D-211–D-237）；范围与清单的来历见 [part 2](2026-11-18-release-0.1-convergence-part2-design.md)，指标与 OP 任务的细则见[优化方案](2026-11-18-size-memory-performance-install-lead-design.md)。

**终点**：第一波（基础层与 omui）在内部仓库里通过全部发布门，三层各自的导出物能独立构建并通过测试。**不包含**：对外发布（打 tag、公开候选、进公共索引）与物理的拆仓——这两步在终点之后另行决定。

## 0. 核心点（review 入口）

1. **八个阶段、五个节点、60 个任务**，每个任务有编号、依赖、验收与状态的类别（已做一部分／确定可做／需要设计）。
2. **关键路径有两条**：规范线（对账 → 三层 lint 与切边 → 拆分演练三行 → 干净机器行 → 免编译上手 → 共用运行时）与体积线（链接期 → 断越级依赖 → 能力开关 → 视图层的像素部分可选 → 终端宿主）。其余任务挂在这两条线上或与它们并行。
3. **三项风险最大的先做最小验证**（G0、B7a、G3），结果决定后面怎么排：Web 上用浏览器的引擎跑一个 TS 例子；闭包推导在一个例子上；设计历史导出十秒。
4. **需要设计的任务各自先写一页设计并 review**（闭包推导、终端宿主、共用运行时、官网），不在实现里边做边定。
5. **并行的方式不变**：实现侧工作树做代码与小范围测试，验证侧工作树做长构建；子 Agent 最多一个，只接与主线不相交的一条线（建议：并排基准的对手应用，或静态 HTML 投影）。
6. **每个阶段结束对一次 CI；每个节点做一次整体自我 review**；本地领先远端不超过约 10 个检查点。
7. **终点的判定是机械的**（§5）：十三条门在内部通过、三层导出物各自全绿、跨层接口连续两个节点没有破坏性改动。
8. **估计 95–125 个检查点**。它比 part 1 剩下的大；次序保证每个节点结束时都有可以单独拿出来看的结果。

## 1. 规则

- 任务一行、一个提交一个检查点、STATUS 一行（≤ 600 字符，带证据指针），沿用 part 1 §3.3、§3.4。
- 检查点只跑它触及的范围；全量以 CI 为主；构建经 `omui-devtools govern`，不超过本机 90%。
- 状态的类别：**做**＝确定可做；**设**＝需要设计，先写一页；**验**＝先做最小验证再决定；**等**＝等一个外部条件（写明是什么）。
- 标准不降：门上达不到的，降该项能力的标注并写明，不改期望值。
- 第二波（引擎层）在这期间只修失败、跟随接口、做后台验证。

## 4. 节点与次序

| 节点 | 到这里为止完成的 | 拿得出来看的结果 | 约（累计检查点） |
|---|---|---|---|
| **M0 规范立住** | A 全部；G0、G3、B7a 三个最小验证 | CI 全绿；三层由 lint 与三行拆分演练守住；引擎叫 meng；三项风险有了初步答案 | 12–16 |
| **M1 体积与数字** | B 全部；C 全部 | 最小应用 ≤ 8 MB；omui 的指标在台账里都有对手的数，没有“落后”或写明 | 50–65 |
| **M2 上手与平台** | D 全部；E 全部 | 干净机器上一条命令到第一个窗口；TS 路径 ≤ 1 分钟；平台表的格子都有实测或写明的状态 | 75–95 |
| **M3 终端与官网** | F 全部；G 全部 | 同一个例子出窗口与终端；官网由 Live Design 重做、可被检索、不卡；设计过程的视频 | 95–120 |
| **M4 达标与可拆** | H 全部 | 十三条门的结果；三层的导出物各自全绿；综合汇报 | 100–125 |

**次序的安排：**

1. 先做 A1（已在进行），随即并行开三件最小验证（G0、G3 现在就能做，B7a 等 B6）与 C1 的骨架。
2. M0 之前不开 B6 之后的任务：规范没立住时改依赖与 feature，容易造出新的向上依赖。
3. B 与 C 交错：B1、B4 完成后重跑 C1 的数，之后每完成一个 B 任务，体积的并排自动更新。
4. D0 一旦接通，D1–D3 与 C4 立刻做；它不在关键路径上，但越早接通，“未验证”的格子越早变少。
5. E 线与 F 线可以分给主会话与一个子 Agent，两条线只在 B6 上相交。
6. G5（官网）排在 B8 与 G1 之后：它要用体积的预设与 Web 上的脚本，早做会做两遍。

**一个子 Agent 的用法**：M0 之前接 C1（对手应用，与主线的代码不相交）；M1 之后接 G2（静态 HTML 投影）或 F 线。它的简报里写明主会话正在改的共享包，避免同一项能力做两次。

## 5. 终点的判定

全部满足即“达到发布标准、随时可以拆”：

1. part 1 §8 的十条门按第一波的口径在内部仓库里通过；其中“发布物在公共索引里”一条以本地索引代替，并写明。
2. 三条附加的门：体积与内存的预算、并排基准没有“落后”、默认集合之外的组合各有一条冒烟。
3. 三层的导出物各自从零构建并通过全部测试；导出物里没有内部资料。
4. 跨层接口连续两个节点没有破坏性改动。
5. 平台表的每一格是实机、软件、未验证（带毕业条件）或未测（输入延迟）之一；没有空格。
6. 一轮多视角自我 review 完成，偏离与例外写明。

到这里停下并汇报。对外发布与拆仓是之后的两个独立决定。
