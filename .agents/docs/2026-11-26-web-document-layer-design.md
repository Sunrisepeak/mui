# Web 宿主的文档层（UI3，一页设计）

状态：草案，待 review（2026-11-26）。决策：D-286（提议）。上级：[0.1.0 顶层方案](2026-11-26-release-0.1.0-top-level-design.md) 的 D-258–D-260；上游：FE1、UI1；下游：UI4（深浅色、打印、减少动态效果）、UI5（带样子的投影、加载策略）、ST2。

## 1. 事实（2026-11-26）

- 有界面的 Chromium 156 与 Firefox 159 里，画布接管之后：页内查找找不到，文字选不中，没有可见的 `<a href>`；打印是空白页（顶层方案 §1.4）。
- Web 宿主已经有一份 DOM 镜像（`omui.host.web:mirror`）：语义树的每个节点是画布上方一个绝对定位的元素，按差异增量同步（一帧里改了一个标签就只发一个属性），焦点、朗读区、跳到主要内容的链接都在它上面。
- 它为什么没解决上面三件事：整层是“视觉上隐藏”的；每个节点都是 `div` 加 ARIA 角色，链接不是 `<a href>`；一段文字只有一个盒子，没有逐行的位置；画布里的滚动不是浏览器的滚动，查找没法把匹配处滚进来。
- 构建时的静态投影（`static_html`）与这份镜像是两套代码：投影现在按属性与标记写出完整的元素（UI1），镜像还是 `div`。程序到达时投影被换掉，不是被接手。

## 2. 三级次序（D-185）

**① 从本体系出发。** 一棵语义树、多种渲染，HTML 是其中一种——那么它应当只有一份：构建时写出的投影、程序到达前读者看到的页面、程序到达后的镜像，是**同一份 DOM 的三个时刻**。程序到达时按 id 接手已有的元素，之后按差异更新；元素的标签、属性、行内结构由同一个映射给出。文字的位置、每一行的盒子、滚动的范围，引擎本来就有（布局是它做的），不必猜。**结论：取这一级。**

**② 前沿与组合。** 查过的做法（2026-11-26 检索）与取什么：

| 做法 | 现状 | 取什么 |
|---|---|---|
| 画布上叠一层透明文字（PDF.js 的文字层；typst.ts 的语义层） | 通行多年。PDF.js 的查找用的是它自己的查找条，不是浏览器的；typst.ts 的讨论里把选中不准归因于拿不到排版信息 | 形状：真实的文字放在画布画它的位置。我们有排版信息，所以逐行对齐可以做准 |
| HTML-in-Canvas（把 DOM 元素画进画布，浏览器负责命中与读屏的同步） | Chrome 148 起试用，155 改过接口（`layoutsubtree` 改为 `drawable` 等），试用期延到 160；有二手消息称 157 默认开启，未经一手来源核实。Firefox 与 Safari 没有实现 | 不作为基础：只有一个引擎、接口还在变。预留：文档层是真实的 DOM，将来可以交给它画 |
| 画布应用另挂一棵语义 DOM（只给读屏） | 我们现在的镜像就是这样 | 不够：查找、选中、链接、打印都不靠 ARIA |
| CSS 自定义高亮（不改 DOM 给一段范围上色） | 各引擎已有 | 留给引擎自己的选中与搜索结果在文档层上的显示（需要时） |

组合：**镜像升格为文档层**——真实的元素（来自 UI1 的映射）、透明而可查找可选中的文字（按引擎的行盒放置）、真实的滚动容器（与引擎的滚动双向同步）。

**③ 业界通行的做法**（画布应用不支持查找与选中，或自己做一套查找条）不取。

## 3. 设计（D-286）

### 3.1 一份映射，三个时刻

- `omui.semantic` 的 HTML 映射（角色与属性 → 标签与特性，标记 → 行内元素）是唯一的一份；`static_html` 与镜像都用它。镜像的每个批次带上节点的标签与由属性来的特性（`href`、`id`、`start`、`align`），文字带行内的结构。
- 程序到达时，页面里已有的投影元素按 `data-omui-target` 被接手：同一个元素换上位置与事件，不重建。之后的更新照旧是差异。
- 页面没有投影时（应用页、`eager` 策略），第一批照旧新建全部元素。

### 3.2 文字：透明、在原位、逐行

- 文档层不再隐藏。文字是透明的（画布画看得见的字），但参与查找、选中与复制；选中的底色与查找的高亮由浏览器画，落在画布画字的位置上。
- 位置：每个节点的盒子（已有）；多行的文字再给出每一行的盒子与这一行的字节范围（引擎的行布局，无障碍那边已经在用），页面把每行放进一个不换行的行内块，宽度不合时按比例缩放到行盒的宽度。
- 字体：页面用引擎自己的字体数据登记同名的字体（`FontFace`），两边的字宽先天接近，缩放只是修正。
- 判据是量出来的：查找的高亮矩形与画布上那段文字的矩形，偏差不超过钉住的像素数（先在 Chromium 与 Firefox 上各量一遍再定这个数）。

### 3.3 链接、滚动、指针

- **链接**是真实的 `<a href>`，盖在画布里链接的位置上：悬停看得到地址、能在新标签页打开、能复制地址。点击先交给引擎（应用内的路由、需要回答的外部链接照 S-1、S-2 走）；引擎不处理的才由浏览器走默认。
- **滚动**：语义树里的滚动视图在文档层里是真实的滚动容器（不显示滚动条），内容的大小取引擎给的范围。两边双向同步：引擎滚了，设它的 `scrollTop`；浏览器滚了它（查找跳到匹配处、锚点、读屏），把偏移发给引擎。于是“查找的下一个”能把屏幕外的匹配滚进来，嵌套的滚动也一样。
- **指针**：文档内容的文字（段落、标题、单元格、代码）接受指针，原生的拖选可用；其余元素不接指针，事件照旧落到画布。落在文字上而不是拖选的点击转给画布。可操作的节点（按钮等）照旧由画布处理，镜像上的激活只给辅助技术。

### 3.4 不变的

- 焦点、朗读区、跳到主要内容、粘贴板、隐藏的输入框：不动。
- 文档层不决定任何像素：画布画什么与它无关（接管后的样子不变）。接管前后的样子一致是 UI5 的事。
- 没有脚本时页面就是投影本身（UI1），不依赖本文。

## 4. 实施的三步

| 步 | 内容 | 验收（有界面的 Chromium 与 Firefox，屏幕 2） |
|---|---|---|
| 1 | 镜像用同一份映射：真实的标签与特性、行内结构；不再隐藏，文字透明；接手已有的投影 | 页面里的 `<a href>` 数与树里的链接数相同，位置在画布的链接上；`window.find` 找到正文里的词；全选后复制得到正文 |
| 2 | 逐行的盒子与字体；偏差的测量 | 查找的高亮与画布文字的偏差不超过钉住的值；跨行的选中连续 |
| 3 | 滚动容器的双向同步；指针的分工 | 查找屏幕外的词，页面滚到它并且画布同步；锚点链接滚到标题；拖选一段跨两行的文字，复制的内容与树的文字相同 |

并排（UI3 的验收里加的一条，顶层方案 §16 第 9 项）：同一篇文档在 Flutter Web 与一个 PDF.js 页面上做同样的三件事（浏览器自己的查找、原生选中、`<a href>`），结果并排记入台账。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 行内的字宽与画布对不齐（字体回退、字距、连字） | 同一份字体数据；逐行缩放；偏差进检查。对不齐超过界限的文字（例如回退到系统字体的文字）只保证“找得到、选得中”，高亮的位置按行盒 |
| 透明文字层接了指针，挡住画布的悬停与点击 | 只有文档内容的文字接指针；非拖选的点击转发；可操作节点不接 |
| 元素多了（每行一个）拖慢同步 | 行盒只对视口附近的节点展开；虚拟化的列表照旧只镜像物化的项 |
| 文档层与引擎的滚动互相触发 | 每次同步带来源标记，自己引起的回声丢弃 |
