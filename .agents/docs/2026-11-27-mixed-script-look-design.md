## 1. 中文行里的拉丁词（`/zh/` 的 3 px）

### 1.1 事实（改前）

- `/zh/` 在 1280 宽：动得远的都是横向、都在写在程序之前的页面一侧——文档层的词按引擎画它的位置摆（词盒的左边就是那个位置），页面上的词却偏了：`HTML，给` +0.73 px，`Agent` +3.39，下一行的 `先取` +2.47、`llms.txt` +2.59；纵向的差都在行内。
- **原因一：块的字体。** 样子给一个画了文字的节点写“它大多数字形的字体”：中文段落写的是 `'omui-notosanssc'`。段落里的拉丁词是没有元素的纯文字，只能取块的字体，浏览器于是用 Noto Sans SC 自带的拉丁字母排它们（CDP：这一段 Noto Sans SC 61 个字形，Inter 只有链接里的 4 个）。宽度：`Agent` 在页面上 40.44 px、画布上 41.95 px；`HTML` 短 2.25 px。后面的词跟着差。
- **原因二：空格。** 引擎（`mlibs.text.harfbuzz` 的 `shape.cpp`）让空格取它前一个字素的字体，使一段不被空格切开：中文后的空格是 Noto Sans SC 的（15 px 时 3.375 px），拉丁词后的是 Inter 的（4.219 px）。浏览器按字体列表逐字取第一个有这个字的字体：只把块的字体改成 Inter 在前时，中文后的每个空格在页面上宽 0.84 px，一行往后累计（`/zh/` 首段一行有四个这样的空格，最多 3.4 px）。在 Chromium 159 与 Firefox 159 里实测（字体列表 Inter、Noto Sans SC）：中文后的空格与拉丁词后的一样宽（Chromium 4.234，Firefox 4.0；Noto Sans SC 单独 3.367）——两个浏览器都不看前邻。
- **字间的空隙。** 引擎默认在汉字与拉丁字母、数字之间加 1/8 em（`TextStyle::autospace`，CSS Text 4 的 `text-autospace: normal`），没有哪个组件关掉它；Chromium 159 与 Firefox 159 的默认值是 `no-autospace`（计算值实测），只在页面要求时才加（`由oweb构建` 在 15 px 下宽 3.75 px = 2 × 15/8，Firefox 3.77）。文档模板里中文与拉丁之间都写了空格，这一项在本语料上没有位移，换一种写法的文档就有。
- **标点挤压**（未改，见 1.5）：引擎挤“闭＋闭／中”与“开前是开／中”以及非首行行首的开标点；Chromium 的 `text-spacing-trim: normal` 还挤“闭＋开”（`写成（甲）。（乙）` 在 Chromium 里 120 px，不挤是 135）；Firefox 159 不支持这个属性，一个也不挤。本语料没有相邻的全角标点。

### 1.2 三级次序（D-185）

**① 原始性：次序也从那一帧量出来。** 样子本来就是引擎第一帧的投影。字体的次序同样是那一帧的事实：一个字体画了另一个字体也有的字，它就排在那个字体前面（否则那个字会由另一个画）。按这个偏序排出的列表交给浏览器逐字回退，每个非空白的字由画它的同一个字体画——由构造一致，样子不需要知道段落样式写了哪些字体，也对任何字体组合成立（中文、阿拉伯文、emoji）。空白不按字体次序取（引擎按前邻），所以只有“浏览器按列表会给另一个字体”的那几段空白单独写成带字体的行内元素：元素里只有空白，不切开任何词，查找、选中与读回都不变。

**② 前沿与组合。** 查过的：

| 做法 | 与这里 |
|---|---|
| CSS Fonts 4 的逐字匹配（§5.3）：按 `font-family` 列表，每个字取第一个有它的字体 | 就是浏览器这一侧；列表的次序由上面的偏序给出 |
| `@font-face` 的 `unicode-range`（Google Fonts 按区段切子集的做法） | 能把中文字体限在中日韩区段，但空白仍按列表取，前邻规则写不出来；不取 |
| 两个浏览器对空白的取法（实测，上面） | 都按列表；所以把空白写明，不依赖哪个浏览器的启发式 |

组合：站点的字体子集（CF3）与样子用同一份字体文件，覆盖相同，偏序在两边成立。

**③ 低线。** 服务端渲染加水合的站点前后是同一个渲染器，天然一致。这里是两个渲染器，靠“同一份字体、同一个回退次序、写明的空白”一致。

**另一条路（未取，作为提议）：** 让引擎的空格也按字体列表取（CSS 的规则），页面就不需要写空白。代价：中文里的空格变宽 0.84 px（15 px），而且行上多出 Inter 的下降，按行取字体的段落里含空格的中文行高一点（21.75 → 22.83 px）——画布上所有中日韩夹空格的文字都动，钉住的画面随之重钉。它与[表格方案](2026-11-27-markdown-table-narrowing-design.md) §2.5 第 3 条（把 CSS 的行盒规则作为框架的默认，25 个钉）是同一类有意的改动，应一起决定。

### 1.3 设计（已实现）

- **块的字体是一个列表**（`omui.semantic` 的 `look.cpp`）：同一设置（字号、字重、倾斜）的各段字形用到的字体，按“画了对方也有的字的在前”排；排不进同一次序的（彼此都有对方画的字：与正文同字号的代码）不在列表里，它的段照旧是有自己样式的部分。空白不参与排序。字号、字重、颜色仍取字形最多的那一段。
- **部分（`Look::spans`）**：写在行内元素上的字体也是它那一组的列表；与块的列表相同就不写。`line-height:0` 只给首个字体（页面的支柱）或字号不同的部分。
- **写明的空白（`Look::apart`，新）**：一段字形里的空白，若页面按它所在元素的字体列表会取另一个字体，就记下它的字节范围与它的字体（`font-family:<画它的字体>;line-height:0`）；`static_html` 把纯文字在这些范围切开，包成只含空白的 `span`。
- **文档层读回页面时**（`omui_web.js` 的 `projection`）：一个元素“只有文字”的判断把这种 `span`（只有 `style`，不是节点也不是标记）当作文字——否则只有一个标签的链接（`开始 →`）读不出文字，阅读程序画不出它。
- **字间的空隙**：样子的基础规则写 `text-autospace:normal`（引擎的行为）。
- 引擎、文档层的位置、检查与界都没有改。

### 1.4 实测（2026-11-27，Linux x64，`--profile ci`，无头 Chromium 159）

### 1.5 欠项

- 标点挤压在三处各不相同（上面）。Chromium 与引擎只差“闭＋开”一类；要一致，先定引擎的规则以 CSS Text 4 的哪一条为准，再决定页面写 `text-spacing-trim` 的哪个值（Firefox 不支持，只能不挤或接受差）。到有这样的文档时做。
- 检查的词数下限（50）对短的中文页不够，归检查自己定（主线）。
