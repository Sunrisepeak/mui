# openmui.render

The rendering abstraction (module `openmui.render`, D-57): the display list of contract ⑤ (paths, paints, gradients, strokes, clips, transforms, layers with blend modes and effect parameters, glyph runs, images, external textures, node markers), resources by reference (an image store; glyphs from the text engine through `GlyphSource`), and backends. The CPU backend renders through openmui.raster, byte-for-byte the same on every platform, records pixel provenance, and reports what a CPU cannot draw (effects, external textures — spec R-3). Knows nothing of nodes or views.

**Incremental frames** (`:damage`, D-62). A `DamageTracker` compares a display list with the previous one, segment by segment (the node markers; a segment's hash covers its own commands and its children's order, its bounds are in device space) and returns the bands of rows that can differ. The CPU backend draws only those rows over the previous frame (`CpuOptions::rows`), skipping commands that cannot reach them, and the result is the full render byte-for-byte — `tests/damage_test.cpp` holds it to that for every kind of change (colours, moves with shadows, rotations under rounded clips, clips, layer opacity, z-order, nodes appearing and going, strokes), and the headless host's tests for real frames. On the 1000-node dashboard of M1 ⑤ at 1080p a one-label frame goes from 28 ms to under 2 ms (`tests/bench`). With a `Parallel` (`CpuOptions::parallel`, the host's task pool) the bands are cut into tasks drawn at the same time — each by its own pooled canvas, glyph masks resolved first on the calling thread — and the bytes are still the serial render's: every band is exact. `CpuOptions::measure` fills `RenderReport::kinds`: count and time per kind of command (`command_kind_name`), which is where a frame's raster time goes (the `ui/raster/full-1080p` benchmark reports it).


**GPU backend** (`:gpu`, D-33). `GpuRenderer::create(device)` builds its pipelines on an `omui.rhi` device (any backend that takes one of `gpu_shader_formats()`); `render(list, target, resources, options)` draws the list into an `rgba8_unorm` colour target and returns the same `RenderReport`. Slang shaders (`shaders/`, `effects/`), compiled at build time by `openmui.slang.rules` into every format the target's backends take, draw every primitive as an instanced quad, cut into batches only where a texture changes.

The GPU works in the CPU's bytes: coverage as raster makes it (rectangles in 1/256 pixel, the rasteriser's masks for paths, strokes, glyphs, box shadows and clips, placed in an atlas), colours premultiplied to 8 bits, gradients read from raster's own 256-entry tables at the same index, images sampled with the same integer weights, every product a rounded `mul255`; source-over is left to the blending unit, which on an exact one gives the CPU's bytes — `tests/gpu_test.cpp` measures 0 levels of difference on lavapipe for rectangles, gradients, strokes, shadows, clips, layers, images, glyphs and every effect, and holds each scene to a stated tolerance. Rounded rectangles are the exception, and the GPU is the exact one there: it covers a pixel by the true circle's area, where the CPU's chords (1/32 pixel) are within 8 levels. A layer under a blend mode is composited by `shaders/blend.slang` over a copy of the target beneath it, with the CPU's arithmetic. On Metal the MSL asks for IEEE arithmetic without contraction (`openmui.slang`), as SPIR-V has it.

**Effects on the GPU** (D-68). An effect layer is drawn offscreen in a surface of its own — the layer plus the effect's reach, as the CPU prepares it — the effect runs on it, and the result is composited where the layer is. Each built-in has a GPU path held to its CPU reference: per-pixel effects are fragment shaders written against the effect template (`effects/lib/openmui_effect.slang`: the source, an auxiliary row texture, the parameters and values the CPU derives — trigonometry, sizes — so the arithmetic is the reference's; the 64-bit hash in pairs of 32-bit words), blur is box passes in integers, pixelate a compute pass with one invocation a block, particles one instance a cell. `EffectInfo::gpu` says how; an effect without a GPU path is drawn without it and counted in `effects_skipped`, as the CPU counts one without a CPU path. A program's own effects — a `*.effect.omui.toml` and a Slang shader against the same template, no C++ — are [openmui.effect](../effect)'s, loaded and reloaded while the program runs; the template's text is carried in the program (`:effect_template`, generated by `omui-gen embed`). **External textures** (`OMUI_EXT_external_texture`): `GpuOptions::external` maps an `external_texture()` id to a texture the program made on the same device — a video frame it decoded, an engine's view, premultiplied — drawn over its rectangle as `draw_image` would draw the same pixels (bilinear, within a level of the CPU's image of them); an id it does not know is skipped and counted, as the CPU renderer counts every one.

**Backdrop effects and liquid glass** (`OMUI_EXT_backdrop_effect`, D-64). An effect that declares `EffectInfo::backdrop` reads what lies under its layer: the renderer captures it where the layer begins — the CPU renderer copies the target when its draw reaches the layer, the GPU renderer copies the parent target into the effect's aux texture — frosted by `backdrop_blur` with the same integer box blur on both (`box_blur`). A layer carries shapes (`EffectShape`, rounded rectangles in its space; a glass group's members), which the effect reads as signed distances (`shape_distance`, `smooth_min`; the template's `shapes_distance`). A frame with a backdrop effect is drawn by the CPU in one band, and a band that reaches such an effect takes all of its rows; the damage tracker marks a backdrop effect damaged whenever damage reaches it. The built-in `liquid_glass` is one: the backdrop bent at the bevel from the distance's gradient, split by colour, frosted, tinted darker over bright backdrops and lighter over dark ones, lit at the rim facing the light and along a fine inner edge, with the layer's content over it — its CPU reference and GPU path give the same bytes on lavapipe (`tests/gpu_test.cpp`), and its CPU pixels are pinned for every platform (`tests/effects_test.cpp`).
