# Integer cellular rules, v0.2

- Input and output have exactly `width * height * channels` values and are disjoint. Invalid shape, boundary, alias or tile returns a typed `Failure` before any output write. A valid partial tile leaves all other output values untouched. Storage and publication belong to the caller.
- Rules match in author order. Every condition reads the old field, including same-cell channels. All writes of the first match also read old values, not prior writes. No duplicate channel writes. Empty condition lists match unconditionally; empty writes stop later rules. With no rules, output equals input.
- Inclusive unsigned ranges and integer counts; exact saturating arithmetic. Boundaries are constant (one value for every outside channel — or `Boundary::values`, one a channel and as many as the channels, else `shape`: the outside is then a cell of its own that flows reach and conditions read, the same at every edge and never changed; the device's kernel takes it for up to 32 channels), clamp or wrap. Offsets are distinct, but on tiny clamped/wrapped fields several offsets may address the same cell; each offset contributes once. Tile borders are not world borders.
- Default limits: 16 channels, 128 rules, 65,536 descriptor words, 64 Mi values per field. Configurable maximum values/words must not exceed `UINT32_MAX / 4`. Offsets are within ±32, at most 128 per condition. Dimensions plus halo fit signed 32-bit coordinates. These are logical bounds, not a guarantee a device can allocate that much.
- `prepare` is cold and owns a snapshot of rules. Copies own their descriptors; moved-from plans are unprepared. No allocations during `step/step_tile` after caller storage is prepared. Parallel callers require immutable rules/input and disjoint output rectangles; aggregate statistics outside the kernel. Or give the step the host's parallel-for (`Execution::parallel`, a `ForEach`): the step hands it pieces — each tile; then each row of the exchange's blocks; then each tile's recount — that read only the input and write cells, `changed_tiles` bytes and activity bytes no other piece of the same call writes (the exchange's marks on a tile's activity are atomic, set once), the statistics added atomically. Output, activity, `changed_tiles` and statistics are the same bits whatever order and threads run the pieces; the kernel itself starts no thread and allocates nothing for it.
- Sparse execution (`Execution::activity`, one byte a tile, the caller's between steps): a tile whose byte says asleep (`asleep(byte)`: its low four bits set) is not run and its output is its input — copied, or left where `alternate` says the output buffer held this field's input one step ago. A step sets a tile's bits when nothing in it changed and no block of an exchange touching it could move (one bit for the tick's cut where cells move, all four otherwise), and clears the bits of every tile within `reach()` cells of a tile that changed (round a wrapped edge). The output, `changed` and `changed_tiles` are those of a step with every tile run; `cells`, `matched` count the tiles run, `asleep` the tiles not. The upper four bits are a step's own and zero when it returns. Cells written outside a step: `Program::wake` over them, or the bytes zeroed. A byte count other than the tiles' is refused (`tile`) before any write.
- Where a cell came from (`Program::origins`): for a step of `input` at `Execution::tick`, `from[index]` is the cell of the input that is at `index` in the output — itself where it did not move, and everywhere for a program without an exchange. It is the exchange's own decision, made from the input alone (the blocks, their cut at the tick, weights and mobilities, the seed), so every carried channel of the output's cell is what the step's rules, transfers and reactions made of the input's cell at `from[index]`; it reads no `Execution::activity` and writes none; given the activity bytes as they were before that step (`asleep_before`), it does not look at the tiles that slept — a tile asleep is one where no block could move at any cut — so it costs what was awake; and it allocates nothing. What compares a cell with itself a step ago — a record of causes — compares through it.
- `words()` exposes a read-only, versioned execution descriptor for optional backends. There is no public unchecked bytecode constructor. Do not persist it as an application authoring format; retain typed/versioned rule definitions instead.

Encoding v1 uses uint32 words: header `[1, channels, rule_count, halo]`, rule-offset table, then variable rule records. A rule starts `[end_offset, condition_count, write_count, writes_offset]`. A condition is `[kind, channel, low, high, min_count, max_count, offset_count]` then offset pairs encoded as `dx+32, dy+32`. A write is `[channel, kind, value]`. Kinds follow the public enums. CPU and GPU execute this one prepared representation; no backend-specific rule authoring/compiler is duplicated.

Encoding v2 (a program whose rules aggregate or whose writes have terms; `Program::encoding()`): the same header with `2` first, the same rule and condition records — condition kinds `2, 3, 4` are a neighbourhood's sum, least and greatest of the values within `[low, high]`, tested against `[min_count, max_count]` — and a write is `[channel, kind, value, term_count]` followed by its terms, each `[source, channel, low, high, multiply, shift, negative, offset_count]` then offset pairs. Sources: `0` the cell's own value, `1` a count, `2` a sum, `3` the least, `4` the greatest. The amount is `plus = value + Σ positive terms`, `minus = Σ negative terms`, a term being `saturating(source × multiply) >> shift`; `set` gives `plus − minus` not below 0, `add_saturating` `old + plus` then `− minus`, `subtract_saturating` `old − plus` then `+ minus`, each step saturating in 32 bits. A sum saturates; of no value the least is `0xffffffff` and the greatest `0`. In v2 the rule-offset table has one entry more, the offset of the stages after the rules: `[transfer_count]`, then each transfer as `[channel, by, by_limit, multiply, shift, offset_count]` and its offset pairs (`by` = `0xffffffff`: none, the conductance is 1). For a cell and each neighbour the flow is `saturating(saturating(|difference| × min(by here, by there, by_limit)) × multiply) >> shift`, gained where the neighbour has more and lost where it has less; the channel's output is the rules' value, less what is lost, plus what is gained (saturating; neither bites while no rule writes the channel, by the bound preparation holds). A cell counts as changed when any channel's output differs from its input. After the transfers: `[exchange_count]` (0 or 1), then `[weight, mobility, seed, carried_count]` and the carried channels. The cut is at `(tick & 1, (tick >> 1) & 1)`; a block whose second column or row is over the edge goes round a wrapped edge of an even size and otherwise sits the tick out. With the block's cells above-left, above-right, below-left, below-right and weights and mobilities read from the input: (1) in each column the upper and lower change places when both have `falls` (1) and the upper is heavier; (2) for the upper-left then the upper-right, when it, the cell beside it and the cell diagonally below have not moved, it has `slides` (2), the diagonal has `falls` and is lighter, and the one beside has `falls` and is lighter, they change places (at most one); (3) in each row, when neither has moved and their weights differ, the heavier has `spreads` (4), the lighter `falls`, and `mix32(mix32(seed ^ mix32(fold32(tick))) ^ (left × 0x9e3779b1) ^ mix32(top × 2 + row)) & 1` is 1, they change places. The carried channels' outputs are permuted accordingly. A program that needs none of it is prepared as v1, unchanged.

`push_on(shape, values, region)`: with the region clipped to the field, `x` is the sum of `values` over the cells of the column just left of it less those of the column just right of it, `y` those of the row just above less those just below, each within the region's rows or columns; a side beyond the field is 0; a region outside the field, or `values` not of `width × height`, gives 0. It reads one channel and writes nothing.

Encoding v3 (a program with a table and reactions): the v2 words with `3` first, and after the exchanges the table and the reactions: `[key, rows, columns]`, the table's `rows × columns` values; the near neighbourhood (`offset_count`, pairs); the near slots, `[count]` then `[kind, index]` each (`0` a channel's sum, `1` a column's); the derived values, `[count]` then each one's column; the adjustments, `[count]` then each `[end_offset, derived, raise, conditions, amount]`; the reactions, `[count]` then each `[end_offset, flag, become, conditions, change_count]` and its changes `[channel, kind, amount]` (`0` add, `1` take, `2` set); the flagged channels, `[count]` then each; the resets, `[count]` then `[channel, initial, from]` each. Conditions are `[count]` then `[compare, amount, amount]` each (`0 ≥`, `1 ≤`, `2 >`, `3 <`, `4 =`, `5 ≠`); an amount is `[term_count]` then `[read, index, multiply, shift, negative]` each — reads `0` a number (the index), `1` a channel of the cell, `2` a column of its row, `3` a derived value, `4` and `5` a near slot. "None" is `0xffffffff`. A transfer's conductance word and an exchange's weight and mobility words have bit 31 set when they are columns of the table.

What a v3 step computes for a cell whose key is a row, every read from the input: (1) the rules, as before, onto a copy of the cell; (2) the derived values — each its column's value, then each adjustment in order whose conditions hold (on the row as written) adds its amount (saturating) or takes it (stopping at 0); (3) every reaction in order whose conditions hold: `plus[channel]` or `minus[channel]` gains its amount (saturating), the first set of a channel gives its `base`, its flag's `base` is 1 (a flagged channel's `base` is 0 when none holds), and the first with `become` whose column holds another row's index makes the cell that row; (4) per channel a reaction touched: `v = base` when set, else what the rules left; `v = sat_add(v, plus)`; `v = v − min(v, minus)`; (5) the transfers, of the input's values: `v = sat_add(v − min(v, lost), gained)`, a pair's conductance the lesser of the two ends' and 0 where either is no row; (6) for a cell that became another row, each reset: the new row's `from` column where that is not 0, else `initial`; (7) the exchange, decided from the input (a cell of no row weighs nothing and does not move), carrying what (1)–(6) made. An amount is `plus − min(plus, minus)` of its terms, each `sat_mul(value, multiply) >> shift`; a near sum is the saturating sum over the neighbourhood of the neighbours that are rows. A cell whose key is no row is copied. This is `xengine.matter`'s reference step on a lattice (its CONTRACT.md), which `xengine.matter.cts` checks bit for bit.

A shade (`Shade`, `shade_of`; D-168) is what a presenter computes for a cell, from the cell alone and its index. Colours are straight RGBA8 packed `0xAABBGGRR`; every division truncates. (1) The row is the key channel's value; the colour is `base[row]`, or `fallback` beyond the table. (2) Grain, where `grain[row]` is not 0: `roll = (mix32(index) & 255) − 128` (`mlibs.math`'s `mix32`, the cell's index in the field), `shift = roll · grain[row] / 128` (toward zero), added to red, green and blue, each kept in 0 … 255; alpha as it was. (3) Each tint in order: its end is `to`, or `to_by_row[row]` where the tint has ends by row (`from` beyond them); a tint whose end is its `from` is skipped. `share` is 0 at or before `from`, 256 at or past the end, else `|value − from| · 256 / |end − from|`; `amount = share · alpha(tint) / 255`; where it is not 0 each of red, green, blue becomes `(component · (256 − amount) + tint's · amount + 128) >> 8`, alpha the same toward 255; a tint that emits adds `(tint's · amount + 128) >> 8` to the light's red, green and blue, each stopping at 255. (4) The pixel is premultiplied — `x · alpha / 255` to the nearest, as `t = x · alpha + 128; (t + (t >> 8)) >> 8` — and packed with its alpha; the light is its three sums with the greatest of them as its alpha, or 0 where they are all 0. `check` refuses a key or a tint's channel the field has not, a table of no rows, and grain or ends by row that are not one a row. The same numbers on a device are the painter's to keep (the GPU kernel's task).

Numerical level is exact integer equality on verified backends. Ordered updates, stochastic rules, float integration and scientific chemistry are not supported by these operator sets (v2 adds aggregates, linear writes, conserving transfers and movement; v3 a table and reactions that all act). Unsupported behavior needs a new declared operator/solver and CTS, not an application-name branch in this kernel.
